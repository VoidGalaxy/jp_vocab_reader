작성: 2026-10-08. 기준 제품 코드: `c4dd25c`. 준비 브랜치: `codex/reading-storage-boundary`.

상태: **권장 계약·작업 준비만 완료. 구현과 브라우저 재현은 아직 하지 않았다.** 제품 코드·저장 키·실제 사용자 자료를 변경하지 않았고, 기존 localStorage 값도 열람하지 않았다.

> 갱신(2026-10-08): Gate A 재현은 [gate-a/REPORT.md](gate-a/REPORT.md)에 있다. 사용자가 승인한 계약과 Gate B 결과(순수 저장 모듈·테스트)는 [gate-b/CONTRACT.md](gate-b/CONTRACT.md)에 있다. 아래 권장안과 다른 점은 둘이다. Web Locks 미지원은 **A안**(읽기·메모리 편집·다운로드만, 자동 저장·복사 중지)으로 정했고, 복구 기본값은 **원문만 복사**다. page 연결은 Gate C에서 한다.

## 목표와 권장 결정

읽기 원문·토큰 상태·선택·위치를 계정별로 복원하되, 소유자를 알 수 없는 과거 자료를 자동 귀속하거나 삭제하지 않는다.

| 결정 | 권장안 |
| --- | --- |
| 저장 범위 | 백엔드 환경 + 로그인 user ID. 방문자는 별도 기기 영역 |
| 서버 보관 | 추가하지 않음. 원문·읽기 세션은 브라우저에만 보관 |
| 과거 공통 자료 | 자동 복원·자동 계정 귀속 중단, 원값 보존, 사용자 선택으로 복사/다운로드 |
| 계정 전환 | 기존 계정의 쓰기를 종료하고 화면·비동기 작업을 격리한 뒤 새 영역만 복원 |
| 저장 실패 | 기존 저장을 보존하고 미저장 복구본을 별도 메모리에 유지. 영구 보존으로 오인시키지 않음 |
| 다른 창 | 인증 변경을 계정 경계로 처리. 같은 계정의 충돌도 조용히 덮지 않음 |
| 디자인 | 현재 지면 유지. 필요한 저장 안내·복구 확인만 작게 추가 |

이 권장안을 Gate A에서 확정한다. 작업 준비 요청을 제품 구현·새 저장 계약의 최종 승인으로 간주하지 않는다.

## 저장 포맷 제안

- 새 키: `jp-vocab-reader:reading-session-v3:<api-scope>:user:<id>` 또는 `...:<api-scope>:guest`.
- API 범위는 [learningPlanStorageScope](../../../frontend/components/learningPlanStorage.ts)의 정규화 규칙을 그대로 재사용한다. 새 공용 추상화는 실제 중복 제거가 필요할 때만 추가한다.
- 새 payload `version: 3`에는 범위·owner 종류/ID·revision·updatedAt과 기존 읽기 데이터를 둔다. 이메일·토큰·비밀번호는 저장하지 않는다.
- 새 키의 owner와 payload가 불일치하면 복원하지 않고 원값을 보존한다. 알려지지 않은 버전·깨진 JSON·잘못된 필드는 `corrupt`로 구분한다.
- 읽기 결과는 `empty / ok / corrupt / unavailable`, 쓰기 결과는 `ok / conflict / tooLarge / unavailable / error`를 구분한다. 접근 거부를 빈 자료로 취급하지 않는다.
- 기존 200,000자 제한을 유지하되 초과 쓰기는 거절하고 **직전 저장본을 지우지 않는다**. UI의 새 원문은 메모리에 남고 저장되지 않았음을 알린다.
- 빈 초기값을 이유로 기존 자료를 삭제하지 않는다. 사용자 확인을 받은 현재 영역 초기화만 삭제할 수 있다. 다른 영역·옛 키·분류 초안은 건드리지 않는다.

백엔드 URL 범위는 같은 URL 뒤의 DB 교체까지 식별하지 않는다. QA는 별도 브라우저 컨텍스트와 포트/환경을 사용한다. user ID 재사용, 원문 암호화, 기기 간 동기화는 별도 설계다. 이 작업은 앱 표시·저장 문맥의 격리이며 같은 브라우저 프로필의 개발자 도구 접근까지 막는 보안 경계가 아니다.

## 소유 영역과 계정 경계

1. owner는 `pending → user 또는 guest → hydrating → ready`로 진행한다. 토큰이 있는 pending 상태에서 JWT 문자열이나 직전 user ID로 자료를 추정 복원하지 않는다.
2. 로그인 응답 또는 현재 epoch의 `/me` 결과로 user를 확정한다. `auth_provider=dev`는 등록 계정으로 보지 않는다. 토큰이 없는 방문자는 별도 guest 영역이며, 등록 계정의 저장을 가져오지 않는다. 사용자 조회 실패를 다른 계정으로 임의 전환하지 않는다.
3. hydration이 끝나기 전에는 자동 저장, 덱 갱신, 상태 변경·일괄 저장을 막는다. 덱 목록은 같은 epoch에서 확인한 것만 사용한다.
4. 계정 전환 직전 최신 스냅샷을 **기존 owner**에 저장한다. 마지막 타이핑이 React effect보다 먼저 일어난 경우도 포함한다. 새 토큰·새 user ID를 기존 스냅샷의 저장 대상으로 쓰지 않는다.
5. 이미 발급한 debounce·분석·refresh를 취소하고 읽기 세대를 증가시킨다. 원문·분석 원문·토큰·덱 항목·결과 안내·최근 저장 IDs·선택·스크롤·복원 알림·로딩을 초기화한다.
6. ReadingTab/ReaderMode는 owner 또는 읽기 세대로 key를 달리하여 바구니·검색·옵션·단어창 등 자식 상태를 이전 계정에서 이어받지 않는다. 읽기에서 연 뜻 수정/신고도 닫고 옛 응답을 가드한다. 다른 탭 동작을 불필요하게 바꾸지 않는다.
7. 새 owner를 확정한 뒤 그 키만 복원한다. 이후 예전 owner의 타이머·응답·finally는 새 화면과 저장 키를 변경하지 않는다.
8. 로그아웃·만료·다른 창 토큰 변경도 같은 경계를 지난다. 같은 user의 토큰 재발급은 쓰기 경계는 갱신하되 동일 계정의 자료를 지우지 않는다.

브라우저 저장 실패와 인증 만료가 겹쳐도 옛 내용을 새 화면에 남기지 않는다. 기존 저장본은 유지하고 실패한 최신 스냅샷은 기존 owner 전용 메모리 복구함에 둔다. 해당 owner를 다시 확인했을 때만 복구/다운로드할 수 있다. 새로고침·창 종료에는 이 미저장 메모리가 사라질 수 있음을 알린다. 수동 전환에서는 저장 실패 시 머무르기·본인 자료 다운로드·계속하기를 명시적으로 선택하게 한다. 자동 만료는 보안 경계를 먼저 닫는다.

## 과거 자료 이전: 이동이 아닌 복사

- 기존 `reading-session-v1` 원값은 byte-equivalent 문자열로 보존한다. v1/v2 payload의 읽기 호환을 검증하되 새 영역에 자동 적용하지 않는다.
- 복구 안내에는 자료 존재와 호환 여부만 표시한다. 원문·단어·상태·예문·옛 덱 이름을 기본 화면에 노출하지 않는다.
- 사용자에게 현재 목적지 계정 또는 방문자 영역을 표시하고, 본인 자료임을 확인한 명시적 동작으로만 복사한다. 로그인/만료/새로고침이 복사 동작이 되어서는 안 된다.
- 두 복사 경로를 제안한다: 원문만 입력칸에 복사, 또는 호환되는 전체 읽기 로컬 사본(분석·분류·선택·위치) 복구. 후자는 온라인 저장·자동 재분석 없이 수행한다.
- 전체 사본에서는 옛 deck ID, savedVocabItemId, 최근 저장 IDs, 저장 완료 문구 등 서버 연결을 끊는다. 저장된 뜻/예문 보조 필드도 현 계정의 서버 항목으로 신뢰하지 않는다. 원래 필드는 옛 원값/다운로드에 남겨 보존한다.
- 현재 계정의 덱을 다시 명시적으로 고르게 한다. 계정 확인과 덱 소유 확인이 끝나기 전에는 서버 저장이 없다. 현재 덱 재조회 후 상태를 대조할 때 로컬 분류와 서버 사실을 구분한다.
- 목적지에 기존 세션이 있으면 덮지 않는다. 권장 동작은 기존 자료 유지 + 옛 자료 다운로드다. 교체 기능은 이번 범위에서 제외한다.
- 목적지가 비어 있고 보호된 쓰기·읽기 검증까지 성공해야 복사 완료다. 쓰기 실패·계정 변경·다른 창 충돌에는 원본과 목적지 기존값을 보존한다.
- 원문 다운로드는 사용자 클릭 때만 메모리 Blob으로 생성한다. 파일 자동 생성·원문 로그·원문 커밋·서버 업로드는 하지 않는다.
- 원본은 복사 성공 후에도 자동 삭제하지 않는다. 삭제는 별도 명령·키를 표시한 재확인으로만 가능하다. 깨진/미지원 자료도 원자료 다운로드·명시 삭제는 가능하다.
- `classification-draft`는 기존 안내를 유지한다. 읽기에서 열기를 누르면 현재 owner를 다시 확인하고 원문만 연다. 분석·삭제·계정 귀속을 자동 수행하지 않는다.

## 비동기·여러 창 규칙

- 읽기 작업마다 `{ownerKey, accountEpoch, readingGeneration, requestId}`를 캡처한다. 분석 진행·응답·catch·finally·단일 상태 저장·일괄 저장·뜻 수정·복원 refresh가 적용 전에 전부 검사한다.
- 각 분석 조각을 보내기 **전에도** 같은 문맥과 인증 토큰임을 확인한다. 계정이 바뀌면 후속 조각을 보내지 않는다. 이미 서버에 도착한 저장 요청은 취소로 되돌릴 수 없으며, 옛 계정에 수행된 것과 새 계정 오염을 구분한다.
- API/SRS 의미는 바꾸지 않는다. 요청 문맥 보호가 필요한 경우 선택적 가드를 추가하되 기존 현재 토큰 401 처리와 비읽기 호출을 보존한다.
- 다른 창의 access-token 변경은 해당 창의 경계 초기화/인증 재확인으로 연결한다. 읽기 키의 변경은 자동으로 현재 편집을 덮지 않고 충돌 안내를 표시한다.
- localStorage의 `읽기 → revision 비교 → 쓰기`만으로 원자적 충돌 방지를 주장하지 않는다. Gate A에서 실제 브라우저의 Web Locks 지원·보안 컨텍스트를 확인하고 키별 직렬화 + revision 검사를 채택한다. 미지원에서는 해당 쓰기/복사 기능을 읽기 전용·다운로드 경로로 제한하는 권장안을 확인한다.
- 잠금 대기 후에도 owner와 revision을 다시 확인한다. 계정 변경·취소 뒤 대기 중 복사/쓰기가 실행되지 않아야 한다. 광범위한 storage clear나 다른 계정 key 순회·내용 수집은 하지 않는다.
