# Gate A 보고: 읽기 저장 계정 경계

작성: 2026-10-08. 브랜치 `codex/reading-storage-boundary`, HEAD `c4dd25c`. 제품 코드·저장 키·백엔드·스키마·SRS는 **변경하지 않았다**. 이 문서의 계약은 **제안**이며 승인 전이다.

## 1. 검증 환경

- 백엔드: 스크래치 폴더의 세션 전용 SQLite(`APP_ENV=development`), 포트 8010. 프론트: `next dev` 포트 3010 (`NEXT_PUBLIC_API_BASE_URL`을 8010으로 지정).
- 계정: 합성 계정 A(ALPHA)·B(BETA). 비로그인 상태는 로컬 개발 환경에서 dev 사용자(덱 1)로 대체된다.
- 원문: `〔ALPHA-n〕`, `〔BETA-n〕` 표지를 붙인 합성 일본어 문장만 사용했다. 보고에는 표지·길이·덱 ID·요청 순서만 남긴다.
- 브라우저: 앱 내장 Chromium 152, origin `http://localhost:3010`. QA 전용 origin이라 사용자 앱(3000)의 localStorage와 분리된다. 시작과 끝에 이 origin의 읽기 키·토큰 키만 지웠고, 다른 키는 읽지 않았다.
- 지연·실패 주입: 페이지 안에서 `fetch`를 감싸 특정 요청만 늦췄다(6초). 저장 실패는 읽기 키에 대한 `Storage.setItem` 예외로 흉내 냈다. 제품 코드는 바꾸지 않았다.
- 정리: 서버 2개 종료, 임시 DB·로그 삭제, QA origin의 읽기·토큰 키 삭제.

## 3. 정책 제안 (승인 필요)

### 3-1. 방문자 정책
- 토큰이 없거나 `/me`가 등록 계정을 확인하지 못한 상태는 방문자다. 로컬 개발의 `auth_provider=dev`도 방문자로 본다. 방문자는 `…:<api-scope>:guest` 키를 쓴다.
- 토큰은 있지만 `/me`가 아직 끝나지 않은 상태(pending)에서는 아무 영역도 복원·저장하지 않는다. 화면은 빈 읽기 지면과 "계정 확인 중"만 보여 준다.
- `/me`가 401이면 방문자로 확정한다(R1 차단). 401이 아닌 오류(네트워크 등)에서는 pending을 유지하고, 읽기 저장을 하지 않으며, 다시 시도하게 한다. 방문자로 임의 전환하지 않는다.
- 방문자 자료는 로그인해도 계정으로 자동 이동하지 않는다. 로그인한 계정 영역이 비어 있을 때만 "방문자 때 읽던 글을 이 계정으로 복사"를 제안하고, 사용자가 확인해야 실행한다. 방문자 원본은 남긴다.
- 방문자 영역은 기기 공용이다. 공용 PC에서 다른 사람이 볼 수 있다는 점을 방문자 상태 안내에 짧게 적을지 결정이 필요하다(권장: 적지 않음. 기존 동작과 같고 범위 밖).

### 3-2. 원문만 복사와 전체 로컬 사본 복구의 차이
| | 원문만 | 전체 로컬 사본 |
| --- | --- | --- |
| 가져오는 것 | 원문 입력값 | 원문, 분석 원문, 토큰과 로컬 분류, 선택, 두 스크롤 분율, 접힘 |
| 끊는 것 | 없음 | `deckId`, `savedVocabItemId`, `savedExampleSentence`, `recentlySavedVocabItemIds`, 저장 완료 `message` (원본 키와 다운로드에는 그대로 남김) |
| 이후 흐름 | 사용자가 덱을 고르고 직접 "분석" | 덱을 다시 고를 때까지 상태 변경·저장 버튼을 막음. 덱을 고르면 그 계정의 서버 항목으로 상태를 다시 계산 |
| 서버 요청 | 복사 중 0. 분석은 사용자가 누를 때만 | 복사 중 0, 자동 재분석 0 |
| 위험 | 분류·위치를 잃음 | 다른 사람의 분류가 자기 것처럼 보일 수 있음. "이전 기기 기록에서 가져온 분류"라는 표시가 필요 |

권장: 기본 동작은 **원문만** 복사로 둔다. 전체 사본은 호환되는 v1/v2일 때만 보조 선택지로 제공한다. 두 경로 모두 목적지가 비어 있을 때만 가능하고, 원본은 자동 삭제하지 않는다.

### 3-3. 저장 실패 후 계정 전환
- 저장소에는 계속 마지막 성공본을 남긴다. 초과 길이도 삭제하지 않고 쓰기만 거절한다(R7 수정). 안내 문구는 "이 기기에 저장되지 않았어요. 이전 저장본은 그대로예요"처럼 실제 동작에 맞춘다.
- 실패한 최신 편집은 **기존 owner 키에 묶인 메모리 복구본**으로 둔다. 같은 owner가 이 페이지에서 다시 확인될 때만 "저장 못 한 편집 복구/다운로드"를 보여 준다. 새로고침하거나 창을 닫으면 사라진다는 점을 안내에 쓴다.
- 직접 로그아웃하거나 계정을 바꿀 때 미저장 편집이 있으면 "머무르기 / 내 글 다운로드 / 그래도 계속" 확인을 띄운다.
- 만료나 다른 창의 로그아웃처럼 자동으로 일어나는 전환은 묻지 않고 먼저 경계를 닫는다. 화면에서 읽기 내용을 즉시 지우고, 복구본은 메모리에만 남긴다(R9 차단).

### 3-4. 두 창 동시 저장
- 키마다 `navigator.locks.request(<읽기 키>)` 안에서 "읽기 → 저장된 revision과 기준 revision 비교 → 쓰기 → 다시 읽어 확인" 순서로 처리한다. 잠금을 기다린 뒤 owner·세대가 바뀌었으면 쓰지 않는다.
- revision이 다르면 쓰지 않고 충돌로 표시한다. 선택지는 "다른 창 내용 불러오기 / 내 편집 다운로드"이고, 조용히 덮어쓰지 않는다(R11 차단).
- `storage` 이벤트 처리:
  - 토큰 키가 바뀌면 이 창도 계정 경계를 지나고 `/me`를 다시 확인한다(R12 차단).
  - 현재 owner의 읽기 키가 바뀌면 편집 중인 내용을 덮지 않고 충돌 안내만 보여 준다.

### 3-5. 직렬화 기능 미지원 브라우저
- 대상: `navigator.locks`가 없는 환경. 비보안 컨텍스트(LAN IP의 http 등)이거나 오래된 브라우저다. Chromium 69+, Firefox 96+, Safari 15.4+는 보안 컨텍스트에서 지원한다(공개 호환표 기준이며 직접 검증하지 않음).
- 선택지 A (PLAN 권장안): 자동 저장·복사를 끄고 읽기 전용과 다운로드만 허용한다. 안전하지만 단일 창 사용자의 이어 읽기까지 사라진다.
- 선택지 B (**Gate A 권장**): 자동 저장은 revision 검사와 `storage` 이벤트 충돌 감지를 최선 노력으로 유지한다. 이때 "동시 편집 보호 미지원"을 표시하고 원자성은 주장하지 않는다. 복사·이전처럼 빈 목적지 확인이 필요한 쓰기는 끄고 다운로드만 둔다.
- 운영은 HTTPS라 대부분 지원 환경이다. 미지원은 주로 LAN 개발 환경에서 생긴다.

## 4. 저장 계약 세부 (PLAN과 같은 점·다른 점)

- 키: `jp-vocab-reader:reading-session-v3:<api-scope>:user:<id>` / `…:guest`. `api-scope`는 `learningPlanStorageScope`의 정규화를 재사용한다. payload `version: 3`에는 `scope`, `owner`, `revision`, `updatedAt`과 기존 필드를 담는다. 이메일·토큰은 넣지 않는다. PLAN과 같다.
- 옛 `reading-session-v1` 키는 읽기 전용이다. 자동 복원·삭제·재저장을 하지 않는다(R10 차단). 깨진 자료와 미지원 버전은 `corrupt`로 표시하고 원자료 다운로드·명시 삭제만 허용한다.
- 빈 상태 저장이 키를 지우는 현재 동작(`!originalText && tokens.length === 0` → `removeItem`)은 없앤다. 삭제는 사용자가 확인한 "초기화"에서만 한다. PLAN과 같다.
- 계정 경계에서 읽기 상태를 전부 비운다: 원문, 분석 원문, 토큰, 덱 항목, 안내, 최근 저장 IDs, 선택, 두 스크롤 분율, 복원 알림, 분석 진행, 저장 중 표시. ReadingTab에는 `key={readingOwnerKey + 세대}`를 줘서 바구니·검색·옵션·단어창 상태를 새로 만든다.
- 분석: 시작할 때 `{ownerKey, epoch, generation, token}`을 잡는다. 각 조각을 보내기 직전에 현재 값과 비교하고, 다르면 abort해서 후속 조각 0건으로 만든다(R4 차단). 조각 요청은 잡아 둔 토큰으로만 보내고, 현재 토큰을 다시 읽지 않는다.
- 단어 상태·일괄 저장·뜻 수정·복원 refresh: 응답·catch·finally에서 같은 문맥 검사를 한다(R5 차단). 경계 직후 화면이 비어 있으므로 R6의 재료도 없어진다.
- 서버 측 변경은 하지 않는다. 경계 직전에 이미 출발한 옛 계정 요청은 옛 계정에 정상 귀속된다(R5에서 서버 귀속이 맞았음을 확인).

- 확인 필요: 분류 초안 "읽기에서 열기"가 page의 콜백을 거치는지 Gate C에서 확인한다. 거친다면 owner 재확인을 page에서 한다.

## 6. 승인 요청 사항

1. 위 키·payload v3 계약과, 옛 v1 키를 읽기 전용으로 남기는 방침(자동 복원·삭제 중단).
2. 방문자 정책: dev 사용자를 방문자로 취급, `/me` 비401 오류에서는 pending 유지, 방문자 → 계정 자동 이동 금지.
3. 복구 기본값: "원문만"을 기본으로 하고 전체 사본은 보조로 둘지.
4. 직렬화 미지원 동작: 선택지 B(자동 저장은 최선 노력, 복사는 끔)를 채택할지, PLAN의 선택지 A(읽기 전용)를 유지할지.
5. 수동 전환 확인창("머무르기 / 다운로드 / 계속")을 추가할지. 이는 새 UI 동작이다.
6. 저장 실패 안내 문구를 실제 동작에 맞게 바꾸는 것(R7). 문구 변경이다.

## 7. 미검증·남은 위험

- 비보안 컨텍스트(LAN IP), Firefox·Safari에서 Web Locks와 `storage` 이벤트 동작은 확인하지 않았다. 내장 Chromium·localhost만 확인했다.
- 실제 저장소 할당량 초과는 `setItem` 예외 주입으로만 흉내 냈다.
- 운영 환경의 비로그인 동작(dev 사용자 대체가 없을 때)은 확인하지 않았다. 로컬에서는 비로그인이 dev 덱 1로 대체된다.
- 같은 API URL 뒤의 DB 교체나 user ID 재사용은 키로 구분할 수 없다(PLAN과 같은 한계).
- R6처럼 이미 서버에 들어간 교차 계정 단어는 이번 작업으로 정리되지 않는다. 운영 데이터에 같은 일이 있었는지는 조사하지 않았다(운영 DB 접근 금지).
