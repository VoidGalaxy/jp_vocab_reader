# 운영 도구 안전 계약 (설계안 보정 3차, 2026-10-21, 재검토 대기)

상태: **설계안. 승인되지 않았다.** 문서만 썼다. 제품 코드·스키마·의존성 변경, 앱 import, DB 접속, PG·서버 실행은 없었다.
기준: 브랜치 `codex/fsrs-srs-replacement`, HEAD `e2c07f8`, 미커밋 169개(보존). 스테이징·커밋·푸시·병합 없음.
근거(정적 대조): `OPERATIONS_READINESS_PLAN.md`, `P_RB_TOOL_CONTRACT.md` 2·12~15절, `P_RB_BLOCK_CONTRACT.md`, `backend/scripts/prb_recover.py`·`_local_test_postgres.py`·`delete_account.py`·`d2_*.py`·`srs_invariant_audit.py`, `app/database.py`(`get_connection`·`assert_safe_database_url`), `app/account_blocks.py`·`app/account_write.py`(토큰 해시), `app/recovery.py`(`prepare`·`resume_status`), `app/srs/migration.py`(`apply_plan`·`_run_id`·창 판정).
"사용자 방향"은 2026-10-21 검토 지시에서 사용자가 제시한 정책 방향을 계약에 반영했다는 뜻이며, 운영 실행이나 역할 생성의 승인이 아니다. "권장"은 제안이다.

보정 1차 요지(2026-10-21 검토 3건):
- 대상 지문을 **DB 식별 지문·연결·권한 지문·계획 지문** 셋으로 나눴다. 역할은 DB 식별에서 빠지고 단계별로 승인 기록에 고정된다(3절).
- A 결과를 **미커밋 확인·커밋 확인·결과 미확정**으로 나누고, 토큰 수명을 승인 유효 기간과 분리했다(9절).
- 승인 기록은 사용자 보유 키의 **전자서명**으로만 유효하고, 실행 코드는 **서명된 파일 manifest**로 고정한다. HEAD 비교는 쓰지 않는다(4·5절).

보정 2차 요지(2026-10-21 검토 3건):
- 계획 지문을 **작업 계획 지문**으로 바꾸고 하위 명령을 뺐다. 실행 명령·단계별 역할은 승인 기록의 허용 목록으로 따로 검사한다(3-1·3-3·3-5).
- manifest의 공통 루트를 **배포 루트**(운영) / 저장소 루트(합성)로 정하고, 코드·계약·의존 자료의 허용 경로를 그 루트 기준으로 정의했다(5-2·5-3).
- 실제 PG 검증을 개별 질의·거부 검사 [P]와 정상 종단 연결 [P*]로 나누고, 현재 단위의 완료 기준을 그에 맞췄다(13절).

보정 3차 요지(2026-10-21, 최초 preview 승인 순환):
- 승인을 **조회 승인**(작업 계획 지문 없이 읽기 명령만, 결과로 제품 지문·작업 계획 지문 출력)과 **적용 승인**(조회 결과의 작업 계획 지문을 고정하고 쓰기 명령 허용)으로 나눴다. 결과 미확정·승인 만료 뒤의 `status`도 기존 작업 키에 묶인 조회 승인으로 한다(4-6).

## 0. 이 계약이 다루는 것과 다루지 않는 것

- 다룬다: 운영 DB를 대상으로 하는 **모든** 운영자 도구(감사·전환·모드 설정·P-RB 복구·정리 3종·계정 삭제)가 공통으로 지킬 승인·실행 코드 고정·대상 확인·연결·권한·dry-run·재확인·재개·결과 확정·기록·토큰 규칙.
- 다루지 않는다: 도구별 업무 판정(전환 후보, 복구 관문, 삭제 차단 사유). 기존 도구 계약 그대로다.
- 바꾸지 않는다: 기존 로컬 보호 장치(`assert_safe_database_url`, `_local_test_postgres`, `tests/_local_postgres_guard.py`, E-1 장치). 운영 경로는 이것을 완화하거나 재사용해 열지 않고 **별도 경로**로 만든다.
- **계약 정렬 전 운영 실행 금지.** 현재 운영 DB를 가리킬 수 있는 `prb_recover.py`(앱 `DATABASE_URL`, `APP_ENV=production`이면 Neon 허용)를 포함해, 이 계약을 구현·검증·승인하기 전에는 어떤 도구도 운영 DB에 실행하지 않는다.

## 2. 용어

- **운영 대상 별칭**: 승인 기록이 가리키는 대상 이름(예: `prod-primary`). 비밀이 아니다.
- **비밀값**: 비밀번호를 포함한 연결 문자열, 복구 토큰, 서명 개인 키. 출력·기록·명령줄·저장소에 나오지 않는다.
- **승인 기록**: 한 번의 운영 작업을 허가하는 문서 1건과 그 서명(4절).
- **실행 manifest**: 실행할 코드·계약·의존성 파일의 해시 목록과 그 서명(5절).
- **작업**: 승인 기록 1건이 허가하는 일. P-RB에서는 복구 키 1개의 A~해제 전체.

## 3. 지문 세 가지

### 3-1. 정의

| 지문 | 담는 것 | 담지 않는 것 | 언제 계산 | 다르면 |
| --- | --- | --- | --- | --- |
| **DB 식별 지문** | 별칭, 호스트(엔드포인트) 이름, 포트, `current_database()`, 서버 주 버전, 운영 식별 행의 값(3-2) | 역할, 권한, TLS 설정, 세션 설정 | 모든 연결 직후 | 연결 종료·실행 중단, 재승인(3-4) |
| **연결·권한 지문** | 그 단계의 `current_user`·`session_user`, 역할 속성(슈퍼유저·CREATEROLE·CREATEDB·REPLICATION·BYPASSRLS), 역할 소속, 표·열별 실효 권한, `transaction_read_only`, `search_path`, TLS 사용·인증서 검증 방식(`verify-full`) | DB 자료, 계정 범위 | 모든 연결 직후 | 연결 종료. 그 단계에 승인된 프로필과 다르면 실행하지 않음 |
| **작업 계획 지문** | DB 식별 지문, 실행 manifest 지문, 도구, 계정 id, 작업 키(복구 키·`run_key` 등), 업무 범위·입력, 제품 계획 지문(있는 도구) | 하위 명령·실행 단계, 역할, 연결·권한 지문, 배치 커서 | 조회(dry-run)에서 계산해 출력, 적용 승인에 고정, 적용 승인 아래 단계마다 측정값·입력으로 다시 계산해 대조 | 그 명령을 실행하지 않음(쓰기 0), 조회부터 다시·재승인 |

- 작업 계획 지문에 역할과 하위 명령이 없으므로 **dry-run(읽기 역할)에서 만든 계획이 preview → prepare → recover → verify → release 내내 같은 값으로 유지되고, 승인된 쓰기 역할로 적용할 수 있다.**
- 명령과 역할은 지문이 아니라 **허용 목록**으로 검사한다(3-5). 승인 기록의 `steps`가 단계별 명령·역할·연결·권한 프로필을 고정하고(4-1), 각 연결의 연결·권한 지문이 그 단계의 프로필과 같아야 한다. 승인 기록에 없는 명령·역할, 다른 단계의 역할, 프로필보다 넓거나 좁은 권한은 모두 거부한다.

### 3-2. 운영 식별 행과 그 한계
- 권장안: 운영 역할 생성 단계(별도 승인)에서 운영 관리자가 만드는 **읽기 전용 식별 행**(별칭·무작위 값·생성 UTC). 도구 역할은 SELECT만 갖는다. 로컬 표식 표와 달리 도구 역할이 소유하지 않는다.
- 한계: 백업 복원·시점 복구·Neon 분기 재설정은 식별 행도 복사한다. **같은 엔드포인트에 복원된 DB는 호스트·DB 이름·식별 행이 모두 같아 DB 식별 지문으로 원본과 구별할 수 없다.** 이 지문은 "다른 DB에 잘못 붙은 것"을 막을 뿐, "같은 자리의 DB가 다른 시점 자료로 바뀐 것"은 막지 못한다.
- 대응(별도 운영 작업): 복원·시점 복구·분기 재설정·장애 조치는 **식별 갱신 작업**을 반드시 따른다. 운영 관리자가 식별 행의 무작위 값을 새로 쓰고(별도 승인), 그 전에 발급된 승인 기록은 DB 식별 지문이 달라져 모두 무효가 된다. 진행 중이던 P-RB 작업은 새 승인 아래 `status`로 상태를 다시 읽는다(9절). 이 작업 자체는 도구가 하지 않는다.
- PG의 `system_identifier`(`pg_control_system()`)는 기본 권한으로 읽을 수 없고 물리 복원 뒤에도 같을 수 있어 근거로 쓰지 않는다.

### 3-3. 제품 지문과의 결합 (제품 지문·API 변경 없음)
- 제품 지문은 그대로 제품에 넘긴다: P-RB `--plan`(`recovery.preview`의 64 hex, prepare·recover·release에 같은 값), 계정 삭제 `--expect-plan`. 제품은 지금처럼 잠금 아래 스스로 다시 확인한다.
- 작업 계획 지문 = H(DB 식별 지문, manifest 지문, 도구, 계정 id, 작업 키, 업무 범위·입력, 제품 지문). 정리 3종처럼 제품 지문이 없는 도구는 업무 범위·입력(계정, 정리 종류, `--purge-expired` 여부, 배치 크기)만 넣고 커서는 넣지 않는다(재개 때 바뀌므로).
- 단계마다 다시 계산하는 값은 **측정값**(그 연결의 DB 식별 지문, 시작 때 검증한 manifest 지문)과 **입력값**(계정·작업 키·업무 입력·제품 지문 인자)이다. A 뒤 자료가 바뀌어 제품이 새로 계산할 지문이 달라지는지는 공통 모듈이 판정하지 않고, 기존처럼 제품이 잠금 아래 거부한다.

### 3-3-1. 계획 산출물 지문 `artifact_sha256` (2026-10-25 고정, 합성 구현 범위)
- 목적: 조회가 만든 계획 산출물(예: 명시 전환의 계획 파일, `OPS_MIGRATION_CLI_PLAN.md` 2절)의 바이트를 서명된 적용 승인 `plan`에 묶는다. 제품 지문은 바꾸지 않는다.
- 입력 형식: `None` 또는 `str`이면서 ASCII 소문자 16진수 정확히 64자. 그 밖의 값(대문자, 길이 다름, 비ASCII, `bytes`, 불리언, 숫자, 배열, 객체, 앞뒤 공백 등)은 변환하지 않고 고정 코드 `artifact_sha256_invalid`로 거부한다. 거부 결과에 입력 원값을 담지 않는다.
- 지문 계산: `job_plan_fingerprint`의 다이제스트 입력에 값이 `None`이면 `artifact` 키 자체를 넣지 않는다(기존 도구의 작업 계획 지문은 바이트 단위로 그대로). 값이 있으면 `"artifact": <값>`을 넣는다. 같은 제품 지문이라도 산출물 지문이 다르면 작업 계획 지문이 다르다.
- 결속: 조회 승인 결과로 출력된 작업 계획 지문(산출물 지문 포함)을 사람이 적용 승인 `plan`에 적고 서명한다. 적용 때는 제시된 값으로 다시 계산한 지문이 서명된 `plan`과 같아야 한다(`job_plan_mismatch`). 조회 승인의 `job.inputs`에는 넣지 않는다(조회 때는 산출물이 아직 없음, 4-6-2의 `job` 동일 규칙 유지).
- 전달 경로: `PreflightInput.artifact_sha256`(기본 `None`) → 사전 검사의 `authorize_command` → 공급자의 연결 후 `authorize_command` 재판정(같은 입력 객체의 같은 값). 어댑터는 입력을 그대로 넘긴다. 연결·재연결마다 다시 판정한다.
- 금지: 로컬 실행 기록·파일의 해시가 같다는 사실로 서명된 `plan` 대조를 대신하지 않는다. 산출물 읽기·직렬화, 전환 도구 등록, 승인 형식·`supersedes`·이전 승인 사슬은 이 단위 범위 밖이며 기존대로다.

### 3-4. 재승인 조건
하나라도 해당하면 기존 승인으로 실행하지 않는다.
- 승인 유효 기간 밖(최대 24시간, 4-1)
- DB 식별 지문이 승인과 다름(식별 갱신 작업 포함)
- 실행 manifest 지문이 승인과 다름(5절)
- 계정 목록 밖의 계정, 또는 목록보다 많은 계정
- 단계마다 다시 계산한 작업 계획 지문이 승인과 다름, 또는 제품이 잠금 아래 계획 변경으로 거부
- 실행하려는 명령이 승인의 `steps`에 없음, 또는 그 단계의 역할·연결·권한 프로필이 승인과 다름
- 배치형 도구가 일부 커밋 뒤 실패: 같은 승인 유효 기간 안의 재개만 허용, 지나면 재승인

### 3-5. 실행 단계 허용 목록과 예시
- 적용 승인 아래 각 명령은 실행 전에 (1) 작업 계획 지문 대조, (2) 명령이 `steps`에 있는지, (3) 그 단계의 역할·연결·권한 프로필 대조를 따로 한다. 하나라도 실패하면 연결 전 또는 첫 문장 전에 거부한다.
- 조회 승인 아래에서는 (1) 대신 고정 필드(DB 식별·manifest·도구·계정·작업 키·업무 범위) 대조를 하고, 작업 계획 지문은 계산해 출력만 한다(4-6). (2)·(3)은 같다.
- 단계 순서와 재호출 의미는 제품이 DB 상태로 판정한다(10절). 공통 모듈은 순서를 따로 강제하지 않고, 승인되지 않은 명령만 막는다.

P-RB 작업 예시(조회 승인 `steps`: preview·status = 읽기 프로필. 적용 승인 `steps`: status = 읽기 프로필, prepare·recover·verify·release(`completed`) = P-RB 쓰기 프로필):

| 사례 | 작업 계획 지문 | 명령·역할 검사 | 결과 |
| --- | --- | --- | --- |
| 조회 승인으로 preview → 출력된 작업 계획 지문으로 적용 승인 → prepare → recover → verify → release(`completed`), 입력 동일 | preview가 계산한 값과 적용 단계마다 같음 | 각 승인의 허용 목록·프로필 일치 | 진행 |
| 단계 사이 `status`(읽기) | 같음 | 허용 | 진행(읽기만) |
| 결과 미확정 뒤 같은 명령 재호출 | 같음 | 허용 | 제품이 재호출 의미대로 처리(10절) |
| release `precheck_unrecoverable`(승인에는 `completed`만) | 같음 | 명령 거부 | 실행 안 함 |
| 승인에 없는 도구 명령(예: 같은 계정의 `delete_account`) | 다른 도구라 다름 | 명령 거부 | 실행 안 함 |
| prepare를 읽기 역할로, recover를 정리 쓰기 역할로 | 같음 | 역할·프로필 거부 | 실행 안 함 |
| 다른 계정 id·다른 복구 키 | 다름 | - | 거부, 새 dry-run·재승인 |
| `--plan`에 다른 제품 지문 | 다름 | - | 거부 |
| A 뒤 자료 변경으로 제품 지문이 낡음 | 같음(입력이 같음) | 허용 | 제품이 잠금 아래 `plan_changed` 등으로 거부, 새 dry-run·재승인 |
| manifest 파일 변경 | 다름 | - | 시작 거부, 재승인 |

### 4-2. 신뢰 근거 후보 비교
임의 JSON 파일의 `approved_by`와 도구가 계산한 해시는 누구나 만들 수 있어 사용자 승인을 증명하지 못한다.

| 후보 | 증명하는 것 | 약점 | 판단 |
| --- | --- | --- | --- |
| A. JSON + 자체 해시 | 파일이 깨지지 않았음 | 아무나 작성·재계산 가능 | 불가 |
| B. 보호된 경로(OS 계정 권한으로 승인자만 쓰기) | 그 경로에 쓸 수 있는 계정이 썼음 | 운영자·승인자가 같은 OS 계정이면 무의미. Windows ACL·백업 복사로 쉽게 깨짐 | 단독으로는 부족 |
| C. 접근 통제된 외부 저장소(예: 보호 브랜치·필수 검토) | 그 서비스의 계정이 승인했음 | 실행 때 네트워크·외부 API 필요, 도구가 서비스 인증 정보를 가져야 함 | 보조 기록으로 가능 |
| D. 전자서명(사용자 보유 개인 키의 분리 서명, 고정된 공개 키로 검증) | 개인 키 보유자가 이 바이트에 서명했음 | 개인 키 관리가 필요. 사용자 본인의 잘못된 서명은 막지 못함 | **권장** |

권장 방식: **D. 분리 서명.**
- 승인 기록 파일과 실행 manifest를 각각 서명한다. 서명 용도(namespace)를 `ops`와 `synthetic`으로 나눈다.
- 검증용 공개 키 목록(신뢰 루트)은 저장소 밖의 고정 위치에 두고, 운영 도구 실행 계정이 쓰지 못하게 한다. 위치와 보호 방법은 사용자 결정.
- 개인 키는 사용자만 보유한다. Claude·Codex 세션, 운영 도구, 저장소, 실행 계정에서 접근할 수 없어야 한다.
- 서명 도구 선택(예: 이미 설치된 OpenSSH의 서명 기능, 또는 새 의존성)은 사용자 결정이다. 새 의존성은 이 계약으로 추가하지 않는다.
- 한계: 1인 운영에서는 서명이 "도구·에이전트의 자기 승인과 파일 변조"를 막을 뿐, 사용자 본인의 잘못된 승인을 막지 못한다.
- 서명 도구·신뢰 루트 설계안(4-0단위, 승인 대기): `OPS_SIGNATURE_DESIGN.md`. 권장은 OS 기본 OpenSSH `ssh-keygen -Y verify`(이 기기 9.5p2 확인), 대안은 Git의 `gpgv`. 서명 용도는 운영/합성 × 승인 기록/manifest의 네 이름 공간으로 나눈다. 에이전트의 운영 개인 키 비접근과 같은 계정에서의 신뢰 루트 보호는 코드로 보장할 수 없어 보류 항목으로 남겼다.

### 4-2-1. 합성 서명 검증 구현 경계 (4단위, 2026-10-21)
사용자 승인 범위: OS 기본 OpenSSH 사용과 검증 제한 시간 10초를 **합성 구현 기준**으로 한다. 운영 키 관리·신뢰 루트 설치·운영 실행 승인은 아니다.
- 실행 파일은 고정 경로 `C:\WINDOWS\System32\OpenSSH\ssh-keygen.exe`. PATH 검색·셸 실행 없음, 인자 배열로 호출. 실행 전 그 경로가 링크·재분석 지점이 아닌 일반 파일인지 확인한다(소유자·ACL·Authenticode 확인은 미구현).
- 자식 환경은 고정 두 값(`SystemRoot`, `PROGRAMDATA`)만 준다. 이 기기의 OpenSSH는 `PROGRAMDATA`가 없으면 아무 출력 없이 255로 끝나는 것을 확인했다. 사용자 프로필·`SSH_AUTH_SOCK` 등은 넘기지 않는다.
- 이름 공간: `jp-vocab-ops/v1/{ops|synthetic}/{approval|manifest}` 네 값만. 1단위 `signature_namespace`는 이 값을 만들도록 바꾸고(승인 판정 규칙은 그대로), manifest 서명은 같은 인터페이스로 `manifest` 대상 이름 공간을 쓴다.
- 입력: 메시지는 시작 때 고정한 원본 바이트를 표준 입력으로, 서명·허용 서명자·폐기 목록은 고정한 바이트를 실행마다 새로 만든 전용 임시 폴더에 써서 넘긴다. 검증 시각은 인자로 받아 `YYYYMMDDHHMMSSZ`(UTC)로 넘긴다. 서명자 이름은 인자로 받는다.
- 판정: 종료 코드 0만 성공. 0이 아닌 종료는 `signature_invalid`, 시작 실패는 `signature_verifier_unavailable`, 10초 초과는 자식을 종료·회수한 뒤 `signature_verifier_timeout`, 임시 파일 정리 실패는 `signature_tempfile_cleanup_failed`. 도구의 표준 출력·오류와 원문 예외는 담지 않는다(출력은 버린다).
- 자식 정리(2026-10-21 검토 보정): 검증 대기 10초가 지나거나 통신이 실패하면, 검증기가 직접 만든 자식 핸들 하나만 종료 요청(`kill`)하고 회수(`wait`)한다. 두 단계는 **최대 5초의 정리 예산 하나**를 함께 쓰고, 각 단계는 한 번만 시도한다(무제한 재시도 없음). 종료 요청이 실패해도 남은 예산으로 회수를 한 번 시도하고, 회수가 끝나면 종료가 확인된 것으로 본다. 회수 실패·예산 초과는 `signature_verifier_child_unconfirmed`. 이름·PID 검색이나 다른 프로세스 종료는 하지 않는다.
- 오류 우선순위: ① `signature_verifier_child_unconfirmed`(자식이 남았을 수 있음) ② 원래 검증 결과(`signature_verifier_timeout`·`signature_verifier_unavailable`·`signature_invalid` 등) ③ `signature_tempfile_cleanup_failed`. 자식 종료를 확인하지 못하면 "종료·회수·정리 완료"로 보고하지 않는다.
- 임시 자료: 자식 종료 확인과 임시 폴더 삭제는 따로 판정한다. 종료를 확인하지 못한 경로에서도 삭제를 한 번 시도하지만, 남은 자식이 그 파일을 쥐고 있으면 삭제가 실패하거나 일부만 지워질 수 있다. 이 경우 코드는 ①이고, 폴더(합성 서명·허용 서명자·폐기 목록 사본, 비밀값 없음)가 남을 수 있음을 뜻한다. 운영자는 그 자식이 끝난 것을 확인한 뒤 폴더를 지운다.
- 운영 경계: 신뢰 집합은 합성뿐이다. 1단위 인터페이스에 연결하는 검증기는 합성 이름 공간만 받고, 운영 이름 공간 요청은 실행 없이 거부한다. 운영 이름 공간의 암호학적 분리는 낮은 수준 검증 함수를 시험 키로 직접 불러 확인할 뿐이며 운영 모드를 열지 않는다. `production_verifier()`는 계속 거부하고, 운영용 우회 플래그·임의 신뢰 루트 경로 인자는 없다.
- 시험 키 생성·서명은 테스트 코드에만 있다. 제품 모듈은 서명하지 않고 승인 파일을 만들지 않는다.
- 한계: 같은 OS 계정의 다른 프로세스는 임시 사본·실행 파일을 바꿀 수 있다. 실제 운영 키·ACL·실행 계정 검증은 미구현이다.

### 4-3. 금지
- 도구가 승인 기록이나 서명을 만들거나 고치는 코드 경로를 두지 않는다. 승인 기록 작성 도우미가 필요하면 **서명 없는 초안**만 출력하고, 서명은 사용자가 도구 밖에서 한다.
- 서명 검증 실패·공개 키 미등록·용도 불일치·`purpose` 불일치는 고정 코드로 거부한다. "승인 없이 dry-run만 허용" 같은 완화도 운영 대상에는 두지 않는다(운영 dry-run도 운영 접속이다).

### 4-4. 실행 중 승인 파일 변경
- 실행 시작 때 승인 기록·서명·manifest를 **한 번 읽어 바이트를 메모리에 고정**하고, 그 바이트로 서명을 검증한다. 실행 중 파일을 다시 읽지 않는다. 시작 뒤 파일이 바뀌어도 이번 실행은 고정한 바이트로만 판정하고, 실행 기록에 시작 시 승인 바이트의 해시를 남긴다.
- 여러 번의 명령으로 이어지는 작업(P-RB A → B → verify → release): 매 명령이 처음부터 다시 검증한다. 같은 작업에 승인이 여러 건일 때의 연결 규칙은 4-6-4에 따른다. 그 밖의 승인은 거부한다.

### 4-5. 합성 시험 승인과 운영 승인의 경계
- 합성 시험은 시험마다 임시 폴더에서 만든 **시험 전용 키**와 `synthetic` 용도로 서명한다. 시험 공개 키는 시험 임시 폴더에만 있고 운영 신뢰 루트에 넣지 않는다.
- 운영 모드는 `ops` 용도와 운영 신뢰 루트만 받는다. `synthetic` 승인·시험 키 서명은 운영 모드에서 거부한다. 반대로 시험 모드는 로컬 합성 대상(기존 장치가 확인한 대상)만 받는다.
- 합성 시험 통과는 사용자의 실제 키 관리·신뢰 루트 보호를 검증하지 않는다.

### 4-6. 조회 승인과 적용 승인
최초 preview 전에는 작업 계획 지문이 없으므로, 계획 지문을 요구하는 승인 하나로는 preview를 허가할 수 없다. 그래서 승인을 두 종류로 나눈다. 두 종류 모두 서명·대상 확인·연결마다 검사·권한 검사(4-2·6·7절)를 생략하지 않는다.

#### 4-6-1. 조회 승인 (`kind: inquiry`)
- 고정: `db_identity`, `manifest`, `tool`, `accounts`·`max_accounts`, `job`(작업 키·업무 범위·입력), 읽기 역할과 읽기 프로필, `valid_from`·`valid_until`(최대 24시간).
- `plan`은 요구하지 않고 두지도 않는다.
- 허용 명령: `steps`에 명시된 읽기 전용 명령만(P-RB `preview`·`status`, 감사, 정리 3종과 계정 삭제의 dry-run). 쓰기 명령, 쓰기 역할, 쓰기 프로필은 조회 승인에 넣을 수 없다(넣으면 승인 형식 오류로 거부).
- 결과: 제품 지문(있는 도구)과 작업 계획 지문을 출력하고 실행 기록에 남긴다. 작업 계획 지문은 그 연결에서 측정한 DB 식별 지문과 시작 때 검증한 manifest 지문으로 계산한다.
- 조회 승인은 적용 승인을 만들지 않고, 토큰 폐기 판단(9-3)도 내리지 않는다. 출력은 사람이 다음 승인과 판단에 쓰는 근거일 뿐이다.

#### 4-6-2. 적용 승인 (`kind: apply`)
- 조회 승인의 고정 항목에 더해 `plan`(조회 결과의 작업 계획 지문, 계정별)을 고정한다.
- `based_on`: 근거 조회 승인의 id와 서명된 바이트 해시. 실행 때 그 조회 승인 파일도 함께 받아 서명을 검증하고 해시를 대조한다. 근거 조회 승인의 유효 기간은 적용 시점에 지나 있어도 된다(근거로만 쓰고 실행 허가로 쓰지 않는다).
- 근거 조회 승인과 **같아야 하는 필드**: `purpose`, `alias`·`db_identity`, `manifest`, `tool`, `job`(작업 키·업무 범위·입력). `accounts`는 근거 조회 승인 목록의 부분집합이고, 계정마다 `plan`이 있어야 한다.
- 허용 명령: 쓰기 명령과 그 단계별 쓰기 역할·프로필, 필요한 읽기 명령(`status` 등)과 읽기 역할을 `steps`에 명시한다.
- 적용 승인 아래 각 명령은 3-5의 (1)~(3)을 모두 거친다. 제품의 잠금 아래 재판정과 기존 API(`--plan`, `--expect-plan`)는 그대로다.

#### 4-6-3. 결과 미확정·승인 만료 뒤의 `status`
- 새 조회 승인으로 한다. `job`은 **기존 작업 키**와 같아야 하고, 계정도 그 작업의 계정이어야 한다. 쓰기 명령·쓰기 역할은 허용하지 않는다.
- `status`는 읽기만 하며, 결과 확정 규칙(9-2)과 토큰 보존 규칙(9-3)을 바꾸지 않는다. 미커밋 확인은 여전히 거부 결과와 `status` 두 근거가 모두 있어야 하고, 토큰 폐기 여부는 9-3 표대로 운영자가 판단한다.
- 식별 갱신(3-2) 뒤라면 새 조회 승인의 `db_identity`는 갱신된 값이다. 이때 이전 적용 승인은 DB 식별 지문이 달라 쓸 수 없고, 쓰기를 이어가려면 새 조회 결과에 근거한 새 적용 승인이 필요하다.

#### 4-6-4. 같은 작업의 승인 연결 규칙
- 한 작업(같은 `job` 작업 키)의 승인은 종류별로 사슬을 이룬다.
  - 조회 → 적용 전환은 `supersedes`가 아니라 `based_on`으로 연결한다. 적용 승인이 나와도 조회 승인은 무효가 되지 않지만, 조회 승인으로는 읽기 명령만 계속 가능하다.
  - `supersedes`는 **같은 종류끼리만** 쓴다. 적용 승인을 다시 받을 때(만료·계정 축소 등) 새 적용 승인은 이전 적용 승인을 `supersedes`로 가리키고, 자기 `based_on` 조회 승인을 따로 가진다.
  - 결과 미확정·만료 뒤의 조회 승인(4-6-3)은 이전 조회 승인을 `supersedes`로 가리킬 수 있고, 적용 승인을 대체하지 않는다.
- 각 명령은 지금 제시된 승인 1건(적용 승인이면 그 `based_on` 조회 승인 포함)으로만 판정한다. 여러 승인의 권한을 합치지 않는다.
- 거부: 다른 작업 키의 승인, 다른 종류를 `supersedes`로 가리킨 승인, `based_on`이 없거나 근거 조회 승인과 필드가 다른 적용 승인.
- `supersedes` 사슬의 변경 범위(2026-10-21 검토 보정, 합성 판정 기준):
  - 사슬은 **같은 종류·도구·용도·작업 키**의 승인끼리만 이어진다. 넷 중 하나라도 다르면 `approval_job_mismatch` 또는 `approval_supersedes_kind_mismatch`로 거부한다.
  - DB 식별·manifest 변경은 일률적으로 금지하지 않는다(식별 갱신, 새 배포). 새 서명 승인이 바뀐 값을 그대로 적어야 하고, 각 명령의 관측값은 **새 승인**의 값과 같아야 한다. 이전 승인의 값은 새 승인에 적용되지 않고, 이전 승인도 새 값으로는 통과하지 않는다.
  - 적용 승인은 사슬 안에서도 자기 `based_on`(근거 조회 승인 id·서명 바이트 해시·필드 대조), 자기 작업 계획 지문, 자기 계정 범위를 다시 검증한다. 이전 적용 승인이 유효했다는 사실은 근거가 되지 않는다.
  - 계정은 이전 승인에서 상속하지 않는다. 새 적용 승인의 계정은 그 승인의 근거 조회 승인 목록 안에서만 넓힐 수 있다.
  - 이전 승인과 새 승인의 명령·역할·계정 권한을 합치지 않는다. 새 승인에 없는 명령·계정은 이전 승인에 있었어도 거부한다.
  - 구현: `scripts/_ops_approval.py` `check_succession`(종류·도구·용도·작업 키)과 `authorize_command`(제시된 승인 자체의 값으로 판정). 실제 서명 검증은 미구현이다.

#### 4-6-5. 승인 형식 버전 2: `supersedes` 바이트 결속 (2026-10-25 고정, 합성 구현 범위)
- 지원 버전: `format_version` 1과 2. 그 밖의 값(0, 3, 문자열, 불리언 등)은 `approval_format_version`으로 거부한다.
- 버전 2의 `supersedes`: `null` 또는 키가 정확히 `approval_id`·`sha256` 둘인 객체. `approval_id`는 승인 id 형식, `sha256`은 소문자 16진수 64자. `sha256`은 **이전 승인 파일의 서명 대상 바이트 전체**(서명이 덮는 승인 JSON 바이트 그대로)의 SHA-256이며, 서명 파일의 해시가 아니다. 키 집합·타입·형식 오류와 자기 참조(`approval_id`가 자기 id)는 `approval_supersedes_invalid`로 거부한다. 거부 결과에 원값을 담지 않는다.
- 버전 1: `supersedes`가 `null`인 승인(최초 승인)은 기존대로 해석하고, 기존 도구의 작업 계획 지문도 그대로다. `supersedes`가 있는 버전 1 승인은 `approval_supersedes_resign_required`로 거부하며, 사람이 버전 2 형식으로 **다시 서명**해야 한다. 버전 1 문자열을 버전 2 객체로 바꾸거나 해시를 채워 넣는 자동 변환은 하지 않는다.
- 연결 검사(`check_succession`): 종류·도구·용도·작업 키가 같아야 하고(기존 코드 그대로), 이전 승인은 **서명 검증을 거친 승인**이어야 하며(`approval_prior_unverified`), 지금 승인의 `supersedes.approval_id`가 이전 승인 id와 같고 `supersedes.sha256`이 이전 승인 바이트의 SHA-256과 같아야 한다(어느 하나라도 다르면 `approval_supersedes_mismatch`). 같은 id라도 바이트가 다른 이전 승인은 해시가 달라 거부된다.
- 버전 2 승인이 버전 1 최초 승인(`supersedes: null`)을 가리키는 것은, 그 이전 승인의 서명이 검증되고 id·원문 바이트 해시가 맞을 때만 허용한다.
- 권한은 합치지 않는다: 각 명령은 지금 승인 1건(적용이면 그 `based_on` 포함)으로만 판정하고, 이전 승인은 연결 근거로만 쓴다(4-6-4).
- 범위 밖(기존대로): `PreflightInput`에는 이전 승인 사슬 필드가 없으므로 사전 검사·공급자는 `supersedes`가 있는 승인을 계속 `approval_supersedes_unknown`으로 거부한다. `based_on`·`artifact_sha256`의 의미, 운영 모드 폐쇄는 바뀌지 않는다.

#### 4-6-6. 이전 적용 승인 사슬의 전달·검증 (2026-10-26 고정, 합성 구현 범위)
- 대상: **적용 승인**의 대체 사슬만. 지금 승인이 조회 승인인데 사슬이 주어지면 `approval_chain_kind_unsupported`로 거부한다(조회 승인 대체 사슬은 별도 범위).
- 입력: `PreflightInput.prior_chain` = `ChainLink` 튜플. 각 항목은 바이트 네 개(`approval`, `approval_signature`, `inquiry`, `inquiry_signature`)뿐이며 순서는 이 작업의 **첫 적용 승인부터 지금 승인 바로 앞 적용 승인까지**다. `inquiry`는 그 적용 승인의 `based_on` 조회 승인이다. 호출자가 만든 `Approval` 객체, `verified` 표시, 사전 검사 결과는 입력으로 받지 않는다(필드가 없다). 기본값은 빈 튜플이며 기존 경로는 그대로다.
- 상한(서명 검증 전, 연결 전): 항목 수 최대 8(`approval_chain_too_long`), 사슬 바이트 합계 최대 1 MiB(`approval_chain_too_large`). 튜플이 아니거나 항목이 `ChainLink`가 아니거나 필드가 `bytes`가 아니면 `approval_chain_invalid`. 개별 승인은 기존 64 KiB, 서명은 기존 서명 검사 상한을 그대로 따른다.
- 검증 순서(사전 검사 승인 단계, 하나라도 실패하면 그 뒤는 하지 않음): ① 상한·형식 ② 지금 승인과 그 `based_on` 조회 승인의 서명(기존) ③ 사슬 항목마다 적용 승인과 조회 승인의 형식·서명·용도(`verify_signed`, 지금 시각의 신뢰 목록·폐기 목록으로 검사; **유효 기간은 요구하지 않음**) ④ 항목마다 적용 승인과 자기 `based_on`의 id·해시·필드·계정 범위(`check_based_on`) ⑤ 지금 승인 포함 id·바이트 해시 중복(`approval_chain_duplicate`; 해시 연결이라 순환은 중복으로만 생길 수 있음) ⑥ 첫 적용 승인의 `supersedes`가 `null`(`approval_chain_first_linked`) ⑦ 둘째부터 각 항목은 바로 앞 항목을, 지금 승인은 마지막 항목을 `check_succession`(종류·도구·용도·작업 키, 서명 검증된 이전 승인, id·원문 바이트 해시)으로 확인 ⑧ 지금 승인은 기존대로 유효 기간·명령·역할·계정·계획 지문(`artifact_sha256` 포함)을 `authorize_command`(`prior` = 마지막 항목)로 판정.
- 사슬 없이 `supersedes`가 있는 승인은 기존대로 `approval_supersedes_unknown`, 사슬이 있는데 지금 승인의 `supersedes`가 없거나 마지막 항목과 다르면 `approval_supersedes_mismatch`.
- 권한은 합치거나 상속하지 않는다. 과거 승인은 연결 근거일 뿐이며 명령·역할·계정·계획은 지금 승인 1건으로만 판정한다.
- 한계: 검증은 **제시된 사슬이 서로 맞물린다**는 것만 보인다. 그 사슬이 실제 최신 사슬이라는 것(더 나중 승인이 없음)은 증명하지 않는다.
- 연결 후 재판정: 사전 검사는 직접 서명 검증한 지금 승인·근거 조회 승인·직전 승인을 결과 객체의 내부 필드(표시·비교 대상 아님)로 돌려준다. 공급자는 그 객체의 바이트 해시가 같은 입력 바이트(`approval`, `inquiry`, 사슬 마지막 `approval`)와 맞는지 확인하고(`preflight_result_mismatch`), 연결 후 실제 관측값으로 `authorize_command`를 `prior`·`artifact_sha256`과 함께 다시 부른다. 연결·재연결마다 사전 검사 전체를 다시 한다. 운영 모드와 기본 실제 연결 진입점은 닫힌 채다.

## 5. 실행 코드 고정: 서명된 파일 manifest

### 5-1. 왜 HEAD가 아닌가
지금처럼 미커밋 변경 169개가 있으면 HEAD가 같아도 실제 실행 코드는 다르다. 실행 버전은 **실제로 읽히는 파일의 바이트 해시**로만 판정한다.

### 5-2. 공통 루트와 manifest 내용
- **공통 루트**: manifest의 모든 경로는 루트 하나를 기준으로 한다.
  - 운영: 승인된 커밋에서 만든 **별도 배포 폴더**의 최상위(저장소와 같은 배치). 루트 경로는 명시 인자로만 받고 현재 폴더·환경 기본값으로 정하지 않는다.
  - 합성 시험: 저장소 루트 또는 시험이 만든 임시 배포 폴더. 운영 승인은 작업 폴더를 루트로 받지 않는다(5-1의 미커밋 혼입 때문).
- **허용 경로**(루트 기준, 이 밖은 manifest에 넣을 수 없다):

| 종류 | 허용 경로 | 내용 |
| --- | --- | --- |
| 코드 | `backend/scripts/`의 해당 운영 도구와 공통 모듈, `backend/app/` 아래 그 도구가 import하는 모듈 | 파이썬 원본 |
| 계약 | `docs/plans/srs-improvement/gate-e/`의 이 계약과 해당 도구 계약 문서 | 문서 바이트 |
| 의존 자료 | `ops/` 아래 비밀이 아닌 자료(예: TLS 루트 인증서, 권한 프로필 정의) | 배포 폴더에만 둠. 위치 이름은 구현 때 확정 |

- 넣지 않는 것: `backend/tests/`, `frontend/`, `.env`류, DB 파일, 비밀값, 서명 검증용 신뢰 루트(manifest를 검증하는 쪽이므로 manifest 밖, 4-2).
- 각 항목: 루트 기준 상대 경로(`/` 구분자), 바이트 크기, SHA-256(줄바꿈 변환 없이 바이트 그대로).
- 외부 패키지(예: `psycopg`, `fsrs`)는 루트 밖의 설치 위치에 있으므로 경로가 아니라 배포 이름·버전과 설치 기록(RECORD)의 파일 해시로 고정한다. 파이썬 버전도 적는다.
- manifest 지문 = manifest 바이트의 SHA-256. 승인 기록이 이 값을 담고, manifest 자체도 분리 서명한다(4-2).

### 5-3. 검증 규칙
- 경로 형식: 루트 기준 상대 경로만. `..` 구성 요소, 절대 경로, 드라이브 문자, UNC·장치 경로, 대체 데이터 스트림(`:`), 끝의 점·공백, 대소문자만 다른 중복 항목은 거부. 정규화한 실제 경로가 루트 안이고 5-2의 허용 경로 안이어야 한다.
- 시작 때: manifest의 모든 파일이 존재, 일반 파일, 크기·해시 일치. 누락 1개라도 거부.
- 심볼릭 링크·Windows 접합점(junction)·재분석 지점·하드 링크 수 2 이상은 거부(루트 밖을 가리킬 수 있음). 루트 자체와 상위 폴더도 같다.
- 동적 import: 파이썬을 격리 모드로 실행하고, 맨 앞에 import 확인기를 둔다. 루트의 `backend/` 아래 모듈은 import되는 순간 manifest에 있는지·해시가 같은지 확인하고, **검증한 원본 바이트를 직접 컴파일**해 쓴다(.pyc 캐시를 읽지 않음, 바이트코드 쓰기 끔). manifest에 없는 `backend/` 모듈은 import 거부. 함수 안의 늦은 import(`from app import recovery` 등)도 같은 확인기를 지난다.
- 외부 패키지: 시작 때 배포 버전과 RECORD 해시를 확인한다. 루트 밖에서 manifest 의존성이 아닌 프로젝트 모듈이 잡히면 거부.
- 실행 중 파일 변경: 이미 검증해 로드한 모듈은 메모리 바이트를 쓴다. 늦게 import되는 모듈은 그 순간 다시 확인하므로, 시작 뒤 바뀐 파일은 해시 불일치로 거부된다.
- 거부는 고정 코드와 상대 경로만 출력한다.

### 5-4. manifest 형식과 파일 검사 (3단위, 2026-10-21 고정)
- 형식: UTF-8 JSON 객체 하나(BOM 없음). 중복 키·실수·NaN 거부, 알 수 없는 필드 거부. 필드는 `format_version`(정수 1), `kind`(`"ops_manifest"`), `files`(항목 배열) 셋뿐이다. 항목은 `path`(문자열)·`size`(0 이상 정수)·`sha256`(소문자 16진수 64자리) 셋뿐이다.
- 외부 패키지·파이썬 버전 필드는 다음 단위(RECORD·런타임 검증)에서 추가한다. 이번 형식은 루트 안 파일만 다룬다.
- 한도: manifest 1 MiB, 항목 1~2,000개, 파일 하나 64 MiB, 경로 240자, 구성 요소 100자.
- 경로: `/` 구분 상대 경로. 첫 구성 요소부터 `backend/scripts/`, `backend/app/`, `docs/plans/srs-improvement/gate-e/`, `ops/` 중 하나로 시작해야 한다. 구성 요소는 영문·숫자·`_`·`-`·`.`만 쓰고, `.`로 시작하거나 끝나지 않으며(`.`·`..`·숨김 파일·끝의 점 포함), Windows 예약 장치 이름(`CON`·`PRN`·`AUX`·`NUL`·`COM1`~`9`·`LPT1`~`9`, 확장자 포함)이 아니다. `__pycache__` 구성 요소와 `.pyc`·`.pyo`는 거부한다. 경로 중복과 대소문자만 다른 중복은 거부한다. 이 형식 규칙으로 `..`, 절대·드라이브·UNC·장치 경로, 역슬래시, 대체 데이터 스트림(`:`), 끝의 공백이 모두 막힌다.
- 루트: 호출자가 명시한 절대 경로. UNC·장치 경로는 거부한다. 루트 자신과 그 모든 상위 폴더가 실제 디렉터리이고 심볼릭 링크·접합점·재분석 지점이 아니어야 한다.
- 파일: 루트부터 각 구성 요소를 링크를 따르지 않고 확인한다. 중간은 디렉터리, 마지막은 일반 파일이어야 하고, 어느 것도 링크·접합점·재분석 지점이 아니며 마지막 파일의 하드 링크 수는 1이어야 한다. 디스크의 이름 대소문자도 manifest와 정확히 같아야 한다. 디렉터리·특수 파일은 열지 않는다.
- 내용: 바이트 그대로 크기와 SHA-256을 대조한다. 줄바꿈·대소문자·내용을 보정하지 않는다. 파일은 import·컴파일·실행하지 않는다.
- 교체 경합: 열기 전 확인한 파일 정체(장치·파일 번호·크기)를 연 핸들의 정체와 비교하고, 다 읽은 뒤 경로를 다시 확인해 같은 파일인지 본다. 이것으로 검사~열기·읽기 사이의 **다른 파일로의 교체**는 거부한다. 남는 한계: 같은 파일을 읽은 뒤 제자리에서 고치는 것, 중간 폴더를 잠깐 바꿨다가 되돌리는 것은 막지 못한다.
- 결과 의미: 통과는 "검사한 순간 읽은 바이트가 manifest와 같다"는 뜻뿐이다. 그 뒤 실행 시점까지 파일이 바뀌지 않음, 모든 import 의존성 포함, 서명된 승인 실행물임은 뜻하지 않는다. 서명 검증은 미구현이고, 이 결과로 실행하는 경로는 두지 않는다.
- 거부는 고정 코드와 (형식 검사를 통과한 경우) 항목 번호·상대 경로만 담는다. 파일 본문·해시 기대값·절대 경로는 담지 않는다.
- 영역별 파일 규칙(2026-10-21 검토 보정): 접두사만으로는 받지 않는다. 마지막 구성 요소의 확장자는 소문자 그대로 대조한다.
  - 코드(`backend/scripts/`, `backend/app/`): 파이썬 원본 `.py`만. `.pyw`·`.pyd`·`.so`·`.dll`·실행 파일·DB 파일·설정 파일 등은 거부.
  - 계약(`docs/plans/srs-improvement/gate-e/`): 이 폴더 바로 아래의 Markdown `.md`만.
  - 의존 자료(`ops/`): TLS 루트 인증서 `ops/tls/<이름>.pem`만(6-1의 `sslrootcert`). 하위 폴더·다른 확장자·`ops/` 바로 아래 파일은 거부. 권한 프로필 정의 등 다른 의존 자료는 형식이 정해지지 않아 **결정 항목**으로 남기고, 정해질 때까지 거부한다.
  - 한계: 이름 규칙은 내용의 종류나 안전성을 증명하지 않는다. `.py` 이름의 DB 바이트, 비밀이 든 `.pem`도 이름 규칙은 통과한다. DB 파일·실행 바이너리·비밀 파일을 이름으로 완전히 탐지한다고 주장하지 않는다.
- 연 파일의 I/O 오류(2026-10-21 검토 보정): `fstat`·읽기 실패는 `manifest_file_unreadable`, 닫기 실패는 `manifest_file_close_failed`로 거부한다. OS 오류 원문·경로는 담지 않는다. 핸들 닫기는 성공·실패 모든 경로에서 한 번 시도한다.
  - 우선순위: 먼저 생긴 거부(정체 변경·읽기 실패·크기·해시 등)가 이기고, 닫기 실패는 그 앞에 아무 거부가 없을 때만 보고한다.
  - 닫기 실패 뒤에는 재시도하지 않고 정리 성공을 가정하지 않는다. 그 핸들의 실제 상태는 OS에 달려 있다(보장 범위 밖).

## 6. 비밀 연결 정보 전달과 연결 전 확인

- 공개값: 승인 기록 파일과 `--target <alias>`·`--approval <파일>` 인자.
- 비밀 연결 문자열: 실행 셸에만 있는 **운영 전용 변수 1개**(앱의 `DATABASE_URL`이 아님). 명령줄 인자·`.env`·파일·저장소·출력·예외 메시지·실행 기록에 넣지 않는다. 실행 뒤 셸에서 지운다. 예시 문서에도 쓰지 않는다.
- 도구는 `DATABASE_URL`·`.env`·기본값으로 운영 대상을 고르지 않는다.
- 연결 전 확인: 연결 문자열의 호스트·포트·DB를 승인의 `db_identity` 공개 부분과, 역할을 그 명령의 `steps` 역할과 비교. 다르면 연결하지 않는다.
- 호스트 1개만(다중 호스트·`target_session_attrs` 거부), `service`·`passfile`·`options` 등 대상·세션을 바꾸는 매개변수 거부, 대상을 바꿀 수 있는 libpq 환경 변수(`PGHOST`·`PGHOSTADDR`·`PGPORT`·`PGDATABASE`·`PGUSER`·`PGSERVICE`·`PGSERVICEFILE`·`PGOPTIONS`·`PGTARGETSESSIONATTRS`·`PGSSLMODE`·`PGSSLROOTCERT` 등)가 있으면 거부.
- **직접 엔드포인트 + `sslmode=verify-full`**(사용자 방향). 풀러 엔드포인트, `verify-full`이 아닌 값, 루트 인증서 지정 누락은 거부. 루트 인증서 파일의 위치·고정 방식은 구현 때 정하고 manifest 의존 자료로 다룬다.

### 6-1. 연결 전 판정의 입력·지원 형식·거부 기준 (2단위, 2026-10-21 고정)
- 입력(모두 인자): 비밀 연결 문자열, 승인 대상(호스트·포트·DB·그 단계 역할), 승인된 TLS 설정(`sslmode`·`sslrootcert` 지정값), 호출자가 넘긴 환경 변수 스냅숏. 실제 환경 변수·파일·DNS·네트워크는 읽지 않고 연결 함수를 부르지 않는다.
- 판정하는 것: 입력끼리의 일치뿐이다. 승인 대상이 서명 승인에 묶였는지, 인증서 파일이 맞는지, 서버가 누구인지, 직접 엔드포인트가 실재하는지는 증명하지 않는다(연결 공급자·서명 단위).
- 지원 형식: `postgresql://<역할>:<비밀번호>@<호스트>:<포트>/<DB>?sslmode=verify-full&sslrootcert=<지정값>` URI 하나. `postgres://`, `key=value` 형식, 프래그먼트는 거부한다.
- 허용 매개변수: `user`·`password`·`host`·`port`·`dbname`(URI 자리), `sslmode`·`sslrootcert`(질의). 그 밖은 모두 거부. 질의에서 URI 자리 값을 다시 지정하거나 같은 키를 두 번 쓰면 거부(libpq는 뒤 값으로 조용히 덮어쓴다).
- 명시 필수: 역할·비밀번호·호스트·포트·DB·`sslmode`·`sslrootcert`. 빠지면 거부한다. 환경 변수·드라이버 기본값(기본 포트, 기본 pgpass 등)으로 보충하지 않는다.
- 호스트: 단일 DNS 이름 또는 점 표기 IPv4 하나. 쉼표(다중 호스트), 소켓 경로(`/`·`@` 시작), 대괄호 IPv6, 퍼센트 인코딩, 대문자는 거부. 승인 호스트와 정확히 같아야 한다. 직접 엔드포인트 여부는 이름 추측이 아니라 승인 호스트와의 일치로만 판정한다.
- 포트는 앞자리 0 없는 1~65535, 역할·DB에는 퍼센트 인코딩 금지. 비밀번호와 `sslrootcert`만 퍼센트 인코딩을 허용하고, 구조 해석과 libpq 해석 결과가 같아야 한다.
- TLS: `sslmode=verify-full`과 승인된 `sslrootcert` 지정값이 정확히 같아야 한다. 파일은 열지 않는다. `sslrootcert=system`(시스템 인증서 저장소)은 고정된 파일이 아니므로 거부한다.
- 환경 변수 스냅숏: 이름이 `PG`로 시작하는 변수(대소문자 무시)가 하나라도 있으면 거부한다. libpq 환경 변수는 대상·인증·TLS·세션을 바꿀 수 있고, Windows 환경 변수 이름은 대소문자를 구별하지 않기 때문이다.
- 거부는 고정 코드만 낸다. 드라이버 원문·연결 문자열·비밀번호는 반환값·예외·로그에 없다. 반환값에는 공개 판정 결과만 있고 비밀값은 담지 않는다.
- 퍼센트 인코딩은 엄격한 UTF-8로만 해석한다. 잘못된·잘린·과잉 길이 바이트와 서로게이트는 대체 문자로 바꾸지 않고 `conninfo_unparseable`로 거부한다(구조 해석과 libpq 해석 양쪽, 2026-10-21 보정).
- 현재 지원 범위(이번 합성 구현의 제한, 운영 접속·인증 방식의 승인이 아님):
  - 명시적 비밀번호가 있는 연결 문자열만 지원한다. 기본 pgpass·클라이언트 인증서·그 밖의 인증 방식은 지원하지 않는다.
  - `sslrootcert=system`은 거부한다.
  - 위 허용 목록 밖의 매개변수는 모두 거부한다.
  - 이름이 `PG`로 시작하는 환경 변수는 대소문자와 관계없이 거부한다. 한계: libpq와 무관한 변수(예: 다른 도구의 `PG` 접두 변수)도 막을 수 있다. 실행 셸에서 지워야 한다.
- 다음 단위(실제 연결 공급자)의 결정 사항으로 남긴다: 연결·명령 제한 시간, `connect_timeout`·`application_name`·`channel_binding` 등 추가 매개변수의 허용 여부.

## 7. 연결마다 확인 (재연결·별도 연결 포함)

- 모든 운영 연결은 공통 연결 공급자 **하나**에서만 연다. 앱 함수 안에서 연결을 여는 도구(P-RB)는 공급자 주입 지점이 필요하다(제품 변경, 12절 의존성, 별도 단위).
- 공급자는 실행 시작 때 공개값을 고정하고, **새 연결마다** 연결 직후·첫 문장 전에 DB 식별 지문과 그 단계의 연결·권한 지문을 계산해 승인과 대조한다. 다르면 그 연결을 닫고 실행을 중단한다.
- 단계 전환(dry-run → apply)은 새 연결로 하고, 새 연결의 연결·권한 지문이 apply 단계 프로필과 같아야 한다. DB 식별 지문은 앞 단계와 같아야 한다.
- dry-run 연결은 서버에서 읽기 전용이어야 한다(`transaction_read_only = on`). 확인 못 하면 중단.
- 확인과 사용 사이: 확인한 연결을 그대로 쓴다. 재연결은 새 연결로 보고 다시 확인한다. 실행 도중 운영 변수가 바뀌어도 공급자는 시작 때 고정한 값만 쓴다.
- 출력은 고정 거부 코드만. 연결 문자열·SQL·드라이버 원문 없음.

- 연결 공급자·연결 후 재확인 계약안(6-0단위, 승인 대기): `OPS_CONNECTION_PROVIDER_CONTRACT.md`. 공급자 고정 매개변수, 같은 연결에서의 관측(드라이버·SQL 출처 구분), 관측 트랜잭션 롤백 뒤 인계, 오류 우선순위, 제한 시간, 인증서 검증 사본, 실제 PG 준비 별도 승인 항목을 담는다.

### 7-1. 합성 통합 사전 검사 (5단위, 2026-10-21)
- 입력(시작 때 한 번 고정): 승인 기록·서명, 적용 승인이면 근거 조회 승인·서명, manifest·서명, 합성 배포 루트, 명령·인자·계정·작업 키·업무 입력·제품 지문, 합성 대상 관측값(호스트·포트·DB·서버 주 버전·식별 행 값), 연결·권한 관측값(프로필 지문·읽기 전용 여부), 비밀 연결 문자열, 환경 변수 스냅숏, 합성 신뢰 집합(허용 서명자·폐기 목록·서명자 이름), 시각.
- 모드: 합성만. 운영 모드는 어떤 검사도 하기 전에 거부한다. 결과는 "합성 사전 검사 일치"일 뿐 DB 연결·업무 실행 허가가 아니다.
- 순서(앞 단계가 거부하면 뒤 단계는 부르지 않는다): ① 모드 ② 승인 기록 서명(적용이면 근거 조회 승인 서명) ③ 승인의 `manifest` 지문 = manifest 바이트 지문 ④ manifest 서명·용도·형식 ⑤ 대상 관측값으로 계산한 DB 식별 지문 = 승인의 `db_identity` ⑥ 명령이 승인 `steps`에 있는지와 그 단계 역할 ⑦ 연결 문자열의 대상·역할·TLS·환경 변수(파싱만) ⑧ 명령·계정·작업·입력·제품 지문·단계 역할·프로필 판정(1단위) ⑨ TLS 루트 지정값과 manifest 항목의 결합 ⑩ manifest 파일 무결성(여기서 처음 파일을 읽는다).
- 결합:
  - DB 식별: 승인은 지문만 담으므로, 호출자가 준 대상 관측값으로 지문을 다시 계산해 같을 때만 그 호스트·포트·DB를 연결 문자열 대조 기준으로 쓴다. 서버 주 버전·식별 행 값은 **호출자 제공값**이며 실제 서버에서 확인한 것이 아니다.
  - 역할: 연결 문자열의 역할은 그 명령 단계의 승인 역할과 같아야 하고, 1단위 판정의 관측 역할로 그 값을 쓴다. 프로필 지문·읽기 전용 여부는 호출자 제공값이다.
  - TLS 루트: 승인 기록에는 TLS 루트 필드가 없다. 그래서 서명된 manifest에 `ops/tls/*.pem` 항목이 **정확히 하나**일 때만, 그 파일의 배포 루트 기준 절대 경로를 승인된 `sslrootcert` 지정값으로 삼고 ⑩에서 그 파일 바이트를 확인한다. 0개 또는 여러 개면 거부한다(어느 것이 승인됐는지 증명할 수 없음).
  - 이전 승인(`prior`) 사슬은 실행 기록이 없어 연결하지 않는다. 따라서 `supersedes`가 있는 승인은 1단위 규칙대로 거부된다.
- 실제 연결 뒤 DB·TLS·권한 재확인, import 의존성 완전성, 실행 기록은 다음 단위다.

## 8. 최소 권한 프로필 (사용자 방향: 읽기·쓰기 분리, 도구군별 쓰기 역할)

| 프로필 | 쓰는 단계 | 권한 | 금지 |
| --- | --- | --- | --- |
| 읽기 | 감사, 모든 dry-run, `status`, 사후 확인, 복원 확인 | 필요한 표의 SELECT, 기본 읽기 전용 트랜잭션 | INSERT·UPDATE·DELETE·DDL |
| 쓰기: 전환·모드 | 명시 전환, 모드 설정 apply | 해당 도구 계약의 표·열만 | 다른 도구군 표 쓰기 |
| 쓰기: P-RB | A·B·verify 저장·release | 차단·기록·롤백 대상 표·열만, 계정 잠금용 권한 | 위와 같음 |
| 쓰기: 정리 | 영수증·snapshot 정리 apply | 영수증·snapshot·실행 표의 해당 열·행 삭제만 | 위와 같음 |
| 쓰기: 삭제 | 계정 삭제 apply | E5B 소유 표의 DELETE와 필요한 읽기 | 위와 같음 |
| 공통 금지 | - | - | 슈퍼유저, CREATEROLE·CREATEDB·REPLICATION·BYPASSRLS, 표 소유, DDL, `init_db`, TRUNCATE, 앱 소유 역할 소속 |

- 각 쓰기 프로필의 정확한 표·열 목록은 도구 정렬 단위마다 그 도구 계약에서 정한다. 계정 잠금(`SELECT … FOR UPDATE`)은 PG에서 UPDATE 권한이 필요하므로 쓰기 프로필에만 둔다. P-RB `status`는 잠금을 쓰지 않는 읽기 스냅숏이라 읽기 프로필로 가능(구현 단위에서 실제 PG로 확인 필요).
- 스키마 변경(`init_db` 업그레이드)은 운영 도구가 하지 않는다. 앱 배포·운영 창 절차(별도 승인)다.
- 실제 역할 생성·권한 부여는 별도 승인 단계다.

## 9. 결과 확정과 복구 토큰

### 9-1. 토큰 단위·생성 (사용자 방향: 작업 단위 토큰)
- 토큰 1개 = 복구 작업 1개 = `recovery_key` 1개 = 차단 1개. A부터 B·verify·release와 그 재호출까지 같은 토큰을 쓴다.
- 생성: A 직전에 운영자가 비밀 보관소에서 암호학적 난수로 만든다. 권장 43자 이상(32바이트 난수의 URL 안전 표기). 사람이 정한 짧은 값 금지(DB에 소금 없는 해시가 남음).
- 보관소에 저장하고 다시 읽어 확인한 뒤에 A를 실행한다.
- 매 단계 `getpass` 숨김 입력으로만 넣는다. 명령줄·환경 변수·파일·셸 기록·실행 기록·저장소·DB 원문·출력에 남기지 않는다.
- 비밀 보관소의 실제 제품은 **미정**이다.

### 9-2. 결과 확정 규칙
- 실패 종료 코드, 시간 초과, 연결 끊김, 예외 출력만으로 **미커밋이라고 추정하지 않는다.** 커밋 경계 직후의 응답 유실은 "커밋됐는데 응답만 못 받은" 상태일 수 있다.
- "미커밋 확인"은 두 근거가 모두 있을 때만이다: (1) 도구가 커밋 전 단계에서 낸 고정 거부 결과(`RecoveryRefused`·`AccountWriteError`의 JSON 출력) 그리고 (2) 유효한 조회 승인(또는 적용 승인의 읽기 단계) 아래 **같은 대상·같은 계정·같은 복구 키**의 읽기 전용 `status` 결과가 커밋이 없음을 보임(`next: preview`, 그 키의 닫힌 기록 없음, 활성 차단 없음).
- 결과 미확정이면 토큰을 보존하고, 다음 행동은 읽기 전용 `status` 확인뿐이다. 승인이 만료됐으면 기존 작업 키에 묶인 새 조회 승인을 받는다(4-6-3). 조회 승인은 쓰기를 허가하지 않는다.
- 토큰 수명은 **작업** 기준이고, 승인 유효 기간은 **실행 허가** 기준이다. 승인 만료는 실행 중단을 뜻할 뿐, 토큰 폐기나 차단 해제를 뜻하지 않는다. 승인이 만료돼도 차단은 그대로 남고 토큰은 보존한다.

### 9-3. 상황별 표

| 상황 | 판정 근거 | 다음 행동 | 허용 쓰기 | 토큰 폐기 |
| --- | --- | --- | --- | --- |
| A 전(토큰만 생성) | 실행 기록에 A 시도 없음 | 그대로 A, 또는 중단 | - | 중단 시 가능 |
| A 거부·롤백 확인 | 거부 JSON + `status`가 `preview`, 그 키의 닫힌 기록 없음 | 원인 확인 뒤 새 키·새 토큰으로 preview부터 | 없음 | **가능** |
| A 결과 미확정(응답 유실·연결 끊김·처리되지 않은 예외·시간 초과·종료 코드만 있음) | 위 두 근거 중 하나라도 없음 | 유효한 조회 승인 아래 같은 대상·키로 `status`(읽기) | 없음 | **불가** |
| A 커밋 확인 | A 결과 `prepared` 또는 `status`가 B 재시도 안내 | B, 또는 무변경 해제 | 승인된 B·무변경 해제 | 불가 |
| B 결과 미확정 | B 결과 없음 | `status`(읽기): `prepared`면 B 재시도, `applied`면 verify | 없음(확인 전) | 불가 |
| B 거부·실패 | 거부 JSON + `status`가 B 재시도 안내(`prepared`) | 원인 확인, 같은 키·토큰으로 B 재시도 또는 무변경 해제 | 승인된 B·무변경 해제 | 불가 |
| verify 결과 미확정·`not_verified` | `status` | verify 재호출(증명 갱신 쓰기 가능) 또는 보고 | 승인된 verify | 불가 |
| release 결과 미확정 | 해제 응답 없음 | 같은 키·토큰·지문으로 completed 해제 재호출(끝났으면 쓰기 0으로 결과 반환) 또는 `status`가 `closed` | 승인된 release | 불가 |
| completed 해제 확인 | 해제 결과 + 재호출 `created: false` 기록 | 작업 종료 기록 | 없음 | **가능**(재호출 기록 뒤) |
| 무변경 해제 확인 | 해제 결과 + `status`가 `closed` | 작업 종료 기록 | 없음 | **가능** |
| 승인 만료(작업 진행 중) | 승인 `valid_until` 지남 | 실행 중단. 상태 확인은 새 조회 승인, 쓰기 재개는 새 적용 승인 | 없음 | 불가 |
| 대상 식별 갱신(복원 등) | DB 식별 지문 변경 | 새 조회 승인 아래 `status`(읽기)로 상태 재확인 | 없음(확인 전) | 불가 |
| 토큰 분실(A 커밋 확인 또는 미확정 뒤) | 보관소에서 읽을 수 없음 | 작업 중단, 보고. 처리 방법은 결정 항목 | 없음 | 해당 없음 |
| 토큰 유출 의심 | 운영자 판단 | 작업 중단, 보고. 처리 방법은 결정 항목 | 없음 | 결정 전에는 보존 |

- 분실·유출 의심 시 자동 교체·재발급·강제 해제·범용 우회는 두지 않는다. 현재 도구에는 토큰 교체 경로가 없고, 차단은 그대로 남는다.
- DB의 토큰 해시는 차단 이력과 함께 남는다(계정 삭제 때 함께 삭제).

## 10. dry-run·재확인, 트랜잭션·재개·재호출 (도구별, 일반화하지 않음)

- 기본은 dry-run이다. 쓰기는 apply 단계 승인, 계정 id 재입력이 모두 있어야 한다.
- dry-run 출력: 건수·고정 사유 코드·작업 계획 지문·제품 지문(있는 도구)·DB 식별 지문. 이메일·단어·뜻·JSON 본문·토큰·연결 문자열 없음.
- 적용 때는 공통 모듈이 작업 계획 지문을 대조하고(3-3), 제품이 계정 잠금 아래 자기 계획을 다시 계산해 다르면 쓰기 0으로 거부한다(기존 동작).

| 도구 | 트랜잭션·배치 | 완료된 같은 요청 재호출 | 미완료 재개 | 실패 뒤 재시도 | 만료·확인 불가 |
| --- | --- | --- | --- | --- | --- |
| 명시 전환 `apply_plan`(CLI 없음) | 카드 1개마다 snapshot·커서 함께 커밋 | 같은 `run_key`·같은 범위: 저장 결과 반환, 쓰기 없음(`already_applied`) | 같은 `run_key`로 커서부터. 범위·설정이 다르면 `migration_run_conflict`, `aborted`면 `migration_run_closed` | 실패 카드 앞까지 커밋 유지, 같은 키 재개 | 쓰기가 필요한 재개는 최초 `started_at`부터 30일 창 안에서만(`migration_resume_window_closed`·`_unverifiable`) |
| P-RB A `prepare` | 한 트랜잭션(차단+기록 함께) | 같은 키·토큰·지문: 기존 기록 반환(`created: false`), 새 행 없음 | - | 거부 시 이번 차단·기록 롤백 | 기간·snapshot 판정 실패는 preview에서 차단 |
| P-RB B `recover` | 한 트랜잭션(원자적) | `applied`·`verified`: 쓰기 문장 0 | `prepared`·`changes_started=0`이면 B 재시도 | 전체 롤백, `prepared` 유지 | 창 만료·확인 불가면 거부. 무변경 해제 외 처리는 결정 대기 |
| P-RB verify | 읽기 R + 잠금 아래 저장 | **무쓰기가 아닐 수 있다**: 자료가 바뀌었고 필수 검사 pass면 증명 갱신(1행) | `applied`면 `verified`로 | `not_verified`·`verification_stale`은 쓰기 없음 | - |
| P-RB release `completed` | 한 트랜잭션 | 같은 키·토큰·지문: 끝난 결과 반환, 쓰기 0 | - | 거부 시 차단 유지 | - |
| P-RB release `precheck_unrecoverable` | 한 트랜잭션 | **결과 반환 없음**: 해제 뒤 재호출은 `recovery_grant_invalid` | - | 거부 시 차단 유지 | - |
| 영수증 정리 | 배치마다 계정 잠금·커밋(전체는 한 트랜잭션 아님) | 키 없음. 재실행은 이미 최소인 행을 건너뜀 | `--after-id <cursor>` 또는 재실행 | 앞 배치 커밋 유지, 실패 배치 롤백 | 7일 판정은 실행 시각 기준, 읽을 수 없는·미래 시각은 보고만 |
| snapshot 최소화 | 같음 | 같음(형식 2는 건너뜀) | 같음 | 같음. 충돌 행은 보고하고 둠 | - |
| 만료 정리 | 같음 | 같음(정리된 값 건너뜀) | 같음 | 같음 | 창 안 실행은 건너뜀, 확인 불가는 그대로 두고 보고 |
| 계정 삭제 | 한 트랜잭션 | **결과 반환 없음**: 삭제 뒤 재실행은 `account_not_found`(종료 4) | - | 롤백(종료 1), preview부터 | 지문 변경 `plan_changed`(종료 5) |
| 감사 | 읽기 전용 | 매번 새 관측 | - | - | 단독 실행 I6/I7 `not_evaluated` |
| 모드 설정 | 제품·CLI 경로 없음 | - | - | - | - |

배치형 도구와 삭제의 결과 미확정도 9-2와 같은 원칙이다. 종료 코드만으로 미커밋을 추정하지 않고, 같은 승인 아래 읽기 전용 dry-run·감사로 현재 상태를 다시 본 뒤에 다음 행동을 정한다.

## 11. 실행 기록

## 13. 다음 구현 단위 제안: 공통 승인·대상 확인·연결 모듈 (합성 환경까지)

범위: 모듈과 그 테스트만. 기존 도구에 연결하지 않고, 제품 코드(`app/`)·의존성은 바꾸지 않는다. 운영 DB 연결·역할 생성·서명 키 생성(운영용)은 없다. **이번 보정에서는 구현을 시작하지 않았다.**

- 산출물(가칭): `backend/scripts/_ops_target.py`(승인 기록·서명 검증, manifest 검증·import 확인기, 연결 전 확인, 연결 공급자, DB 식별·연결·권한·계획 지문, 결과 확정 상태 기록, 실행 기록 작성기), `backend/tests/test_ops_target.py`(판정 함수 단위), `test_ops_target_real.py`(로컬 합성 PG).
- 서명 검증 시험: 시험 전용 키·`synthetic` 용도만. 서명 도구가 결정되기 전에는 검증 함수의 인터페이스와 거부 판정만 만들고, 실제 서명 검증 경로는 **미구현·미검증**으로 둔다.
- 나중에 이 모듈을 쓸 도구(각각 별도 단위): `srs_invariant_audit.py`(첫 적용 권장, 읽기 전용), 명시 전환 CLI(새로 만듦), 모드 설정 CLI(새로 만듦), `prb_recover.py`(앱 연결 공급자 주입 필요), 정리 3종, `delete_account.py`.
- 로컬 장치는 그대로 두고, 합성 시험이 로컬 장치 거부를 우회하지 않는다.

### 13-1. 검증 종류
- [U] 판정 함수 단위: 가짜 연결 값·모킹. **[U] 통과는 실제 PG·TLS·서명 검증이 아니다.**
- [P] 기존 장치의 로컬 합성 PG에서 하는 **개별 질의·거부 검사**: 연결 뒤 읽는 질의(DB 이름, 역할 속성, 표 권한, 소유, `transaction_read_only`, 식별 행 질의)가 실제 PG에서 기대한 값을 읽는지, 그리고 조건이 안 맞을 때 거부하는지. 기존 제한 역할은 표를 소유하고 루프백·비 TLS이므로, 운영 프로필 판정에서는 **거부되는 것이 기대 결과**다.
- [P*] **정상 종단 연결**: 실제 서명 검증 + 비소유 운영형 역할 + TLS `verify-full`이 모두 맞는 대상에 연결해 끝까지 통과. 서명 구현과 로컬 PG 관리자 준비(비소유 역할, 두 번째 DB, TLS 서버 구성) 전에는 **미구현·미검증**으로 표시한다.
- 시험을 통과시키려고 TLS·권한·서명 조건을 완화하지 않는다. 운영 경로에 시험용 생략 플래그를 두지 않고, `synthetic` 승인으로 운영 경로를 열 수 없다.
