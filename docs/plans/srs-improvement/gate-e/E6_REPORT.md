## 2. 생성 규칙과 정확성 확인

**자료 구성** (`tests/e6_read_benchmark.py`, 시드 20261020+N):
- 계정 T(FSRS 모드, 하루 목표 20)에 N장을 둔다.
  - 개인 N/2장: 덱 2개
  - 구독 N/2장: 계정 O가 소유한 공유 덱 2개
- 종류별 상태: 신규 30, 학습 5, 재학습 5, 오늘 복습 15, 연체 15, 나중 예정 25, legacy 미전환 5 (%)

**생성 경로:** 사용자·덱·카드 생성, 발행, 구독, 상태 변경, legacy·FSRS 평가는 모두 앱 함수로 했다. FSRS 평가에는 request_id·세션·버전을 넣었다.
- 평가 일정은 앱 엔진으로 계획했다. 그 결과 기준 시각에 각 카드가 목표 상태에 있다.
- 버전·로그 사슬·영수증은 앱이 쓴 그대로다. 임의 복제는 하지 않았다.

**생성 속도를 위해 바꾼 것(생성에만 적용):**
- 공유 연결 1개를 썼다. 호출마다 commit한다. SQLite는 `synchronous=OFF`로 두었다.
- 시계를 고정했다.
- 평가 응답의 "오늘 새 단어 수"는 실제 계산 함수에 첫 평가 표를 누적해 넘겼다.
- 위 지름길로 만든 DB는 지름길 없는 앱 경로로 만든 DB와 모든 표 내용이 같다. 이것은 집중 검사로 확인했다. 첫 구현의 소개 수 오차(1 작음)는 이 검사가 잡아 고쳤다.

**바꾼 것과 남은 차이:**
- 일시중지 카드는 앱 경로가 없어 만들지 않았다. 5%는 모두 legacy 미전환이다.
- 구독 신규는 모두 progress 행 없음이다. FSRS 진도 행을 평가 없이 만드는 앱 경로가 없다.
- 모드 전환은 E-5 fixture처럼 설정 행에 직접 썼다(API 없음).

**측정 전 확인(모든 크기·DB 통과):**
- 생성 규칙의 기대값과 API 결과가 같다: 큐 범주별 수·범위 합계, 지금 복습 id 집합, 통계 카드 수, 오늘 평가·신규 수.

**측정 중:**

## 4. 병목 후보 (판정 아님, 근거와 추정 구분)

1. **한 요청 안에서 계정 전체 로그를 두 번 읽는다(측정, 호출 관계는 정정).**
   - 큐 1회가 반환 행 10만 줄을 읽는다(1만 기준).
   - 정정 전 설명: 로그 4.9만 행 전체를 첫 평가일·읽기 불가 기록·오늘 신규 수가 각각 다시 읽는다고 썼다. 이것은 틀렸다.
   - 실제 큐 호출 관계(`queue.py` `build_queue`):
     - `first_review_dates`가 두 로그 표를 UNION ALL로 한 번 읽는다.
     - 그 결과 `dates`를 읽기 불가 판정과 `count_introduced`(계정·범위) 모두에 재사용한다.
     - `readability.unreadable_history_keys`가 두 표의 시간·평가를 표별로 다시 읽고, 증거 창 기록을 따로 읽는다.
     - 따라서 전체 로그 읽기는 두 번이다. 오늘 신규 수는 다시 읽지 않는다.
   - 3절의 `introduction_count` 내부 시간은 첫 평가일 읽기를 포함한 별도 호출이다. 큐 요청 안에서 그만큼 다시 드는 것이 아니다.
   - 통계는 오늘 평가 집계(UNION ALL)와 `goals.introduction_count`(안에서 `first_review_dates`)가 같은 로그를 두 번 읽는다.
   - 지금 복습은 `first_review_dates`와 `unreadable_history_keys`를 쓴다. 개인 카드만 필요한데 구독 로그까지 읽는다. 내부 계산만 267 ms다.
2. **PG 실행 계획(1만).**
   - 로그 전체 읽기는 `review_logs`·`lexeme_review_logs`의 Seq Scan이다(각 약 8 ms, 실행 약 18.6 ms).
   - 1천에서는 같은 질의가 `idx_*_user_*_time` Index Only Scan이었다.
   - 구독 카드 읽기는 Hash Join + Sort 5,000행(15.3 ms)이다.
   - SQLite는 커버링 인덱스를 쓰지만, 읽기 불가 검사 질의(`SELECT … FROM review_logs WHERE user_id = ?`)는 SCAN이다.
3. **SQL 밖의 시간(추정, 범위 정정).**
   - 진단 회차의 SQL 시간은 요청 시간의 약 30~45%다(PG 1만 큐 전체: SQL 174 ms / 요청 507 ms).
   - **정정:** PG 요청 시간에는 테스트 보호 장치 시간이 포함된다.
     - 앱 연결마다 연결 전 환경 확인이 있다.
     - 연결 뒤 같은 연결에서 대상·표식 확인 질의 3개와 롤백이 실행된다(`_srs_e2_adapter._GuardedPsycopg.connect` → `verify_app_connection`).
     - 1차 SQL 계측(`Diagnostics`)은 앱의 `execute`만 감싼다. 이 보호 장치 질의와 롤백은 SQL 문 수·행 수·SQL 시간에 들어가 있지 않다.
     - 1차 PG 수치는 보호 장치를 포함한 값이다. 앱 처리 시간과 보호 장치 시간은 1차에서 분리해 재지 않았다.
   - 나머지는 Python 분류·정렬, 응답 직렬화, PG 연결 생성으로 추정한다.
   - 로컬 PG 연결 1회(보호 장치 밖에서 연결+`SELECT 1`)는 중앙값 26.2 ms, p95 134.2 ms였다.
   - 1천에서 PG가 SQLite보다 느리고 p95가 넓은 이유를 1차에서는 연결 생성으로 추정했다. 연결 수와 시간은 4-1절에서 따로 쟀다.
4. **응답 크기(측정).** 지금 복습 전체는 1만에서 1.08 MB다. 페이지 나눔 없이 1,750항목을 전부 보낸다.

## 4-1. 대표 요청 연결 진단 (2026-10-20, 1차 수치와 별도)

**조건:**
- 로컬 PG, 합성 1천 카드(1차와 같은 생성 규칙·시드), `/study-queue` 전체 범위만 측정했다.
- 예열 3회를 버리고 진단 10회를 돌렸다.
- 보호 장치는 그대로 실행했다. 계측(`ConnectionDiagnostics`)은 같은 요청 안의 연결 단계에 시간 측정만 감쌌다.
- SQL 계측은 이 회차에 걸지 않았다.

**정확성:**
- 진단 전 불변식 I1~I5가 pass이고, 큐 범주별 수가 생성 규칙과 같았다.
- 매 회 응답 본문이 기준과 같았다. 진단 뒤 전 표 해시와 응답도 같았다.
- 읽기 전용(`default_transaction_read_only=on`)으로 돌렸다.

시간의 포함 관계:
- `연결 열기`는 보호 장치 연결 전 확인 + 드라이버 연결 + 연결 위 검증을 **포함**한다.
- `드라이버 연결`은 libpq 연결(SSPI)만이다.
- `검증`은 대상·표식 질의 3개와 롤백이다.
- `닫기`는 앱의 commit/rollback과 close다.
- 열을 서로 더하지 않는다. 비율은 같은 요청 안의 값으로 계산했다.

| 항목 (10회) | 중앙값 | 최소–최대 | 같은 요청 대비 비율 중앙값 (최소–최대) |
| --- | --- | --- | --- |
| 전체 요청 | 124.2 ms | 121.6–231.7 ms | - |
| 요청당 연결 수 | 2 | 2–2 | - |
| 연결 열기(두 연결 합) | 60.3 ms | 58.0–165.9 ms | 48.8% (46.7–71.6%) |

| └ 보호 장치 검증 | 9.4 ms | 9.2–10.2 ms | 7.6% (4.1–8.1%) |
| 닫기 | 0.7 ms | 0.7–0.9 ms | 0.6% (0.3–0.7%) |

**근거:**
- 이 요청은 연결 2개를 연다(인증 1개, 큐 조회 1개로 보인다).
- 요청 시간의 약 절반이 연결 열기다. 그중 대부분이 드라이버 연결이고, 보호 장치 검증은 약 8%다.
- 10회 중 1회(231.7 ms)는 드라이버 연결이 156 ms로 길었다. 1차의 넓은 p95와 같은 양상이다.

**미확인:**
- 연결 2개가 각각 무엇을 위한 것인지는 호출 위치를 기록하지 않아 추정이다.
- 운영 환경의 연결 비용은 모른다. 운영은 SSPI가 아니고 네트워크·TLS가 있으며, 보호 장치 검증이 없다.
- 1만 카드와 다른 요청에는 이 진단을 하지 않았다.
- 연결 밖 시간(SQL·Python·직렬화)은 이 회차에서 나눠 재지 않았다.
- Seq Scan(1만 PG)만으로 결함이나 인덱스 필요성을 판단하지 않는다.
