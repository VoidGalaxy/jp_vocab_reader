## 1. 코드 확인 사실

### 1-1. 전환(`apply_plan`, 최초·재개 공통) 카드 한 장의 트랜잭션 [코드]

`backend/app/srs/migration.py` `apply_plan`의 카드 반복은 카드마다 새 연결(제품 연결 컨텍스트) 하나를 열고, 정상 종료 시 한 번 커밋한다. 순서는 다음과 같다.

1. `begin_card_write(connection, user_id)` → `begin_account_write` → `SELECT id FROM users WHERE id = ? FOR UPDATE`(`app/account_write.py:53`). 요청 계정의 `users` 행 하나만 잠근다.
2. 실행 행 읽기와 cursor·`aborted`·30일 창 확인
3. snapshot 존재 확인
4. `inspect_card(connection, key, for_update=True)`
   - `load_card(..., for_update=True)`: PostgreSQL에서 `user_word_progress` 행 `FOR UPDATE`(`app/srs/storage.py:63-67`)
   - `load_logs`
   - `_authorized(connection, key)`(`migration.py:65-74`): 구독 카드의 접근 판정은 다음 문장 하나다.
     `SELECT words.lexeme_id FROM shared_deck_words AS words JOIN user_deck_subscriptions AS subscriptions ON … WHERE subscriptions.user_id = ? AND subscriptions.is_active = TRUE AND words.lexeme_id = ? LIMIT 1`
     **잠금 절이 없다.** 덱을 특정하지 않고, 활성 구독 중 하나라도 그 단어를 포함하면 참이다.
   - 접근이 없으면 후보 품질은 `unavailable`이고, 계획 후보와 달라 결과는 `conflict`(쓰기 없음)다.
5. 후보가 계획과 같으면 `update_card`, snapshot INSERT, `record_intro`, 실행 요약(cursor + 1) UPDATE
6. 컨텍스트 정상 종료 시 커밋

최초 연결(`_run_id`)과 마무리 연결도 계정 잠금만 잡는다. 카드 사이에는 아무 잠금도 유지하지 않는다.

### 1-2. 리뷰 경로 [코드]

- `require_subscription`(`storage.py:133-148`)은 덱을 특정해(`shared_deck_id = ?`) 같은 조인을 `FOR SHARE OF subscriptions, words`로 읽는다. 주석의 목적은 "판정과 커밋 사이에 해제·제거가 끼어들지 못하게"다.
- 호출: `record_fsrs_review`(`reviews.py:122`), `record_first_lexeme_review`(`reviews.py:523`), 기존 진행 행 경로(`lexeme_repository.py:567`, 카드 `FOR UPDATE` 뒤). 모두 계정 쓰기 잠금 아래에서 실행된다.
- 따라서 리뷰는 판정한 구독·덱 단어 행을 커밋까지 잠그고, 전환은 잠그지 않는다. 이것이 LQ1의 차이다.

### 1-3. 구독·덱 단어를 바꾸는 주체 [코드]

| 대상 | 변경 경로 | 잠금 |
| --- | --- | --- |

정리: 계정 잠금은 **같은 계정**의 카드 쓰기·리뷰·가져오기·계정 삭제끼리만 직렬화한다. 구독 비활성화나 덱 단어 제거를 막는다고 가정할 수 없다. 오늘의 제품에는 접근을 잃게 하는 사용자 흐름이 없고, 접근 상실은 관리자 직접 변경이나 행 삭제로만 생긴다.

### 1-4. 권한과 트랜잭션 성질 [코드]

- 쓰기 프로필(`srs_migrate.WRITE_PRIVILEGES`)은 `user_deck_subscriptions`·`shared_deck_words`에 `SELECT`만 있다. PostgreSQL의 `SELECT … FOR SHARE`는 그 테이블의 적어도 한 열에 대한 `UPDATE` 권한도 요구한다(D12에서 `users.updated_at`에 대해 확인한 것과 같은 규칙). 지금 프로필로는 전환 경로에 `FOR SHARE`를 넣을 수 없다.
- 제품 연결의 격리 수준은 기본값(READ COMMITTED)이다. 문장마다 새 스냅숏을 보므로, `_authorized`는 그 문장 시작 전에 커밋된 변경만 본다.
- 롤백 판정(`judge_rollback_card`, `migration.py:987-1001`)도 `_authorized`가 거짓이면 `access_lost`로 거부한다. 접근이 없어진 뒤 전환된 카드는 접근이 돌아오기 전까지 롤백할 수 없다.

## 2. 시점별 경합 (구독 비활성화 또는 덱 단어 제거가 경쟁 트랜잭션에서 커밋되는 시점)

카드 트랜잭션의 시점: ① 접근 판정(`_authorized`) 전, ② 판정 뒤·카드 쓰기 전, ③ 카드 쓰기 뒤·커밋 전, ④ 커밋 뒤.

| 시점 | 현재 코드가 보장하는 것 [코드] | 보장하지 못하는 것 |
| --- | --- | --- |
| 계획 작성(dry-run)과 실행 사이 | 다음 카드 연결의 `_authorized`가 변경을 보고 `unavailable` → `conflict`, 카드 쓰기 0(L6·L7이 실제 PG에서 확인한 범위) | 없음(이 경우는 경합이 아니다) |
| ① 판정 전 커밋 | 판정 문장이 변경을 본다 → `conflict`, 카드·snapshot 쓰기 0, cursor는 진행한다 | 없음. 단 변경 트랜잭션이 **판정 시점에 아직 커밋 전**이면 판정은 옛 상태(접근 있음)를 읽고 ②와 같아진다 |
| ② 판정 뒤·쓰기 전 커밋 | 계정·카드 행 잠금, cursor·snapshot·CAS 판정은 그대로 성립한다 | 판정은 다시 이뤄지지 않는다. 접근을 잃은 카드가 전환되고 커밋된다(`applied`). 변경 주체는 기다리지 않는다(전환이 그 행을 잠그지 않으므로) |
| ③ 쓰기 뒤·커밋 전 커밋 | ②와 같다 | ②와 같다. 커밋 시점에 접근이 없는 카드가 전환된 상태로 남는다 |
| ④ 커밋 뒤 | 전환은 그 시점에 유효했던 접근으로 끝났다. 이후 리뷰는 `require_subscription`으로 막힌다. 다음 카드는 ①처럼 판정한다 | 전환된 카드는 남는다(이 경로에 되돌리는 동작은 없다). 롤백은 `access_lost`로 거부된다 |

행이 이미 없거나 접근 경로가 여럿인 경우 [코드]:

- 진행 행(`user_word_progress`)이 없으면 `load_card`가 `None` → `unavailable` → `conflict`다. 진행 행을 지우는 경쟁 트랜잭션은 카드 `FOR UPDATE`와 충돌하므로, 판정 뒤에는 커밋까지 기다린다.
- 구독 행이나 덱 단어 행이 삭제되는 경우도 ①~④의 비활성화와 같은 결과다(행 잠금 없음).
- 여러 활성 구독이 같은 단어를 포함하면 `_authorized`는 그중 하나만 있어도 참이다(`LIMIT 1`, 덱 무관). 한 덱의 비활성화는 다른 덱이 남아 있으면 접근 상실이 아니다. 리뷰 경로는 요청이 지정한 한 덱만 판정하므로 판정 의미가 다르다.

## 4. 대안과 보장 범위

### A. 현행 유지 [제안]

- 보장: 1-1과 2절 표 그대로. ①과 계획-실행 사이 변경은 `conflict`다.
- 보장하지 않음: ②·③의 접근 상실 전환.
- 대가: 없음(코드·권한 변경 0). 위험은 문서와 운영 보고에 남긴다.

### B. 커밋 직전 재확인 [제안]

- 방법: 카드 쓰기 뒤, 커밋 전에 `_authorized`를 다시 실행하고, 거짓이면 예외로 그 카드 트랜잭션을 롤백한다(결과 코드는 별도 결정).
- 보장: 재확인 문장 전에 커밋된 변경을 잡는다. ②와 ③의 대부분이 줄어든다.
- 보장하지 않음: **재확인과 커밋 사이에 커밋된 변경은 여전히 놓친다.** 창을 줄일 뿐 경합을 없애지 않는다.
- 대가: 카드당 문장 1개, 실패 시 결과·cursor·`failed` 표시 규약을 새로 정해야 한다. 권한 변경은 없다.

### C. 판정 행 잠금(`FOR SHARE`)으로 리뷰 경로와 맞춤 [제안, 권장 후보]

- 공통 방법: 전환의 쓰기 경로(`inspect_card(..., for_update=True)`에서 부르는 `_authorized`)에서만 `FOR SHARE OF subscriptions, words`를 붙인다. dry-run 같은 읽기 전용 트랜잭션에서는 잠금 절을 쓰지 않는다(읽기 전용 트랜잭션의 행 잠금 거부는 이 프로젝트 PG에서 확인하지 않았다, 7절).
- 잠금 범위는 두 안으로 나뉜다(LQ1-f). 아래 PostgreSQL 18 문서 근거(`SELECT`의 Locking Clause, 13.2.1 Read Committed)는 두 안에 공통이다.
  - 최상위 잠금 절은 질의가 **반환한** 행을 잠근다. 조인이면 반환 조인 행에 기여한 행이다. 스냅숏에서는 조건에 맞았지만 경쟁 갱신 뒤 재평가에서 빠져 반환되지 않은 행도 잠길 수 있으므로, 반환 행 수가 전체 잠금 수의 상한은 아니다. `LIMIT`이 있으면 반환 행 수가 채워질 때 잠금을 멈춘다.
  - 경쟁 트랜잭션이 이미 바꾸고 있는 행을 만나면 그 트랜잭션이 끝날 때까지 기다린다. 커밋됐으면 갱신된 행에 `WHERE`를 다시 평가하고, 삭제됐거나 더 이상 맞지 않으면 그 행은 반환하지 않는다(스냅숏 시점에 맞았던 행은 잠기지만 반환되지 않을 수 있다).
  - 따라서 정정: 이전 판의 "`LIMIT 1`이면 경쟁 변경 뒤 행이 빠질 수 있으므로 전부 잠금이 필수"는 근거가 틀렸다. `LIMIT 1`에서 첫 행이 재평가로 빠지면 반환되지 않으므로, 실행기는 질의 스냅숏 안의 다음 일치 행으로 넘어간다. 스냅숏 안에 다른 유효 경로가 있으면 그 경로가 반환·잠금된다. 없으면 0행이고 결과는 `unavailable` → `conflict`(보수적 판정)다. 스냅숏 뒤에 새로 생긴 경로(새 구독 등)는 보지 못하지만, 이는 접근을 좁게 판정하는 쪽이다.
  - `ORDER BY`와 잠금 절을 함께 쓰면 Read Committed에서 반환 순서가 원래 값 기준이 될 수 있다(문서 경고). 잠글 행을 고르는 정렬 기준은 바뀌지 않는 `id`로 둔다.

| 비교 | C-1 유효한 접근 경로 하나 | C-2 일치하는 접근 경로 전부 |
| --- | --- | --- |
| 문장 | 현행 조인 + `ORDER BY subscriptions.id, words.id LIMIT 1 FOR SHARE OF subscriptions, words` | 같은 조인, `LIMIT` 없음, 같은 `ORDER BY`·잠금 절 |
| 보장 조건 | 반환된 한 경로(구독 행 1·단어 행 1)는 커밋까지 비활성화·삭제·갱신될 수 없다. 그 경로 하나로 커밋 시점 접근이 성립한다(LQ1-a (나)) | 판정 시점의 모든 유효 경로가 커밋까지 바뀌지 않는다. 커밋 시점 접근 성립은 C-1과 같다 |
| 경쟁 변경 후 재평가 | 첫 행이 경쟁 변경 뒤 맞지 않으면 다음 일치 행을 잠근다. 0행이면 `conflict` | 각 행이 같은 규칙으로 재평가된다. 남은 행만 잠긴다. 0행이면 `conflict` |
| 잠금 수 | 경쟁 없는 정상 반환은 구독·단어 2행. 재평가 과정의 추가 잠금이 가능하므로 2행을 상한으로 보장하지 않는다 | 경쟁 없는 정상 반환은 (그 단어를 포함한 활성 구독 덱 수) × 2행. 재평가로 반환되지 않는 행의 잠금도 가능하다 |
| 대기 비용 | 잠긴 경로의 변경만 기다린다. 다른 덱의 비활성화·단어 제거는 기다리지 않는다(접근은 잠긴 경로로 유지된다) | 그 단어를 포함한 모든 덱의 해당 변경이 기다린다. 전환이 진행 중인 변경을 만날 때도 경로마다 기다릴 수 있다 |
| 교착 노출 | 잠금 대상이 적다 | 잠금 대상이 많아 역순 관리자 변경과 만날 가능성이 커진다 |
| 향후 검사 | 경로 둘 중 잠긴 경로의 변경은 대기, 잠기지 않은 경로의 변경은 즉시 커밋하고 카드는 `applied`. 잠긴 경로가 경쟁 변경으로 빠지면 다른 경로로 넘어가는지 확인한다 | 경로 둘 모두의 변경이 대기. 일부 경로만 남는 재평가를 확인한다 |

- 권장: **C-1을 기본 후보**로 둔다. LQ1-a (나)의 "커밋 시점 접근 유지"에는 유효 경로 하나의 고정으로 충분하고, 잠금 수·대기·교착 노출이 작다. C-2는 "판정에 쓰인 모든 경로가 커밋까지 바뀌지 않음"을 감사나 설명 목적으로 따로 요구할 때의 정책·설계 선택이다. 그 요구는 현재 계약에 없다. 어느 안도 승인되지 않았다.
- 대상 행: 요청 계정의 활성 구독 행 중 그 lexeme를 포함하는 덱의 것과, 그 덱의 해당 `shared_deck_words` 행. C-1은 그중 한 쌍, C-2는 전부다.
- 잠금 순서(제안 공통 규약): `users`(계정, `FOR UPDATE`) → 카드 행(`FOR UPDATE`) → 구독·덱 단어(`FOR SHARE`, `id` 순). 진행 행 리뷰 경로(`lexeme_repository.py`: 계정 → 카드 `FOR UPDATE` → `require_subscription`)와 같은 순서다. 첫 리뷰 경로(`record_first_lexeme_review`)는 구독을 카드보다 먼저 잠그지만, 같은 계정 잠금을 먼저 잡으므로 같은 계정의 전환과는 직렬화된다.
- 유지 기간: 그 카드 트랜잭션의 커밋 또는 롤백까지(카드 한 장). 카드 사이에는 유지하지 않는다.
- 보장: 잠근 경로의 비활성화·삭제·덱 단어 갱신(`UPDATE`/`DELETE`/upsert의 갱신)은 전환 카드가 커밋할 때까지 기다린다. 판정 전에 이미 진행 중인 변경이 있으면 전환이 기다린 뒤 재평가한다. 커밋 시점에 판정이 유효하다.
- 보장하지 않음: 잠그지 않은 경로의 변경(C-1에서 다른 덱), 접근을 넓히는 변경(새 구독)은 막지 않는다. 둘 다 커밋 시점 접근을 해치지 않는다. `TRUNCATE`·스키마 변경, 다른 DB 사본 같은 경로는 범위 밖이다.
- 교착(정정): 공통 순서는 `users` → 카드 → 구독·덱 단어다. 순환은 이 순서를 **거꾸로** 잡는 관리자 트랜잭션과 만날 때 생긴다. 두 연결로 쓰면 다음과 같다.
  1. 전환: 계정 `users` 행·카드 행을 보유하고, 구독·단어 행 `FOR SHARE`를 기다린다(관리자가 그 행을 바꾸는 중).
  2. 관리자: 같은 구독·단어 행을 이미 바꿔(보유) 커밋 전이고, 같은 트랜잭션에서 그 계정의 `users` 행이나 카드 행을 잡으려고 기다린다(전환이 보유).
  - PostgreSQL은 교착을 감지해 한쪽을 오류로 끝낸다(`deadlock_timeout` 뒤). 어느 쪽이 끝날지는 정하지 않는다.
  - 순환하지 않는 경우: 관리자 트랜잭션이 구독·단어만 바꾸고 `users`·카드 행을 잡지 않으면, 한쪽 대기만 생긴다(전환이 기다리거나 관리자가 기다린다). 같은 계정 잠금을 먼저 잡는 제품 경로(가져오기·계정 삭제·리뷰)는 그 계정의 전환과 계정 잠금에서 직렬화되므로 이 순환에 들지 않는다. 다만 다른 계정의 잠금만 잡는 경로(덱 소유자의 단어 upsert 등)는 직렬화되지 않는다. 이 경로는 구독자의 `users`·카드 행을 잡지 않으므로 대기만 생긴다.
  - 규약 [제안]: 구독·덱 단어를 바꾸는 관리자 직접 변경은 같은 트랜잭션에서 구독자의 `users`·카드 행을 잡지 않는다. 잡아야 한다면 공통 순서(`users` → 카드 → 구독·단어)를 따른다. 규약은 관리자 직접 SQL을 강제하지 못하므로, 규약 밖 변경의 교착 가능성은 남는다. 이 제안은 모든 교착을 없애지 않는다.
  - `lock_timeout` 상한과 교착 오류·대기 초과 시 결과 코드(카드 롤백, cursor 미진행, 실행 `failed` 표시 여부)는 별도로 정한다.
- 대가:
  - 제품 변경: `_authorized`(또는 쓰기 전용 판정 함수) 하나. 리뷰 동작은 바꾸지 않는다.
  - 권한 변경(LQ1-e): PostgreSQL 18 `SELECT` 문서상 `FOR SHARE`는 잠그는 각 테이블의 적어도 한 열에 `UPDATE` 권한을 요구한다. 쓰기 역할에 `user_deck_subscriptions`·`shared_deck_words` 각 한 열의 열 단위 `UPDATE`가 필요하다(정확한 열은 후속 계약에서 실제 스키마로 고른다. `shared_deck_words`에는 `updated_at`이 없다). 열 단위 `UPDATE`는 잠금 전용 권한이 아니다. 그 역할이 해당 열을 실제로 수정할 수 있다. 권한 프로필·지문·옛 승인은 새 버전으로 다시 만들어야 하며, 옛 승인을 자동 변환하지 않는다. C-1·C-2 모두 같다.
  - 운영: 전환 카드가 커밋할 때까지 잠긴 경로의 관리자 변경이 기다린다(카드 한 장 단위).

### D. 변경 주체가 구독자 계정 잠금을 잡게 하는 규약 [제안, 비권장]

- 덱 단어 제거는 그 덱의 모든 구독자 계정을 잠가야 하므로 비용이 크다. 관리자 직접 SQL은 규약을 강제할 수 없다. 보장 범위가 C보다 넓지 않다.

### E. 운영 절차: 전환 창 동안 구독·덱 단어 직접 변경 동결 [제안]

- 보장: 없다(절차 위반을 막지 못한다). A와 함께 쓰는 위험 완화일 뿐이다.

## 5. 향후 검증 설계 (이번에는 실행하지 않는다)

### 5-1. 합성 제품 검사 (SQLite, 별도 승인 단위)

- 한계: SQLite에서 `FOR SHARE`는 붙지 않고 쓰기는 DB 단위로 직렬화된다. 따라서 잠금 대기나 경합 자체는 재현하지 않고, **제품 분기의 결과**만 확인한다.
- 방법: `_authorized` 뒤(②), 카드 쓰기 뒤(③), 커밋 뒤(④) 정지점에서 같은 연결로 변경을 주입하는 훅을 시험 코드에만 둔다. 실패 주입은 실제 경합 증거로 쓰지 않는다.
- 판정: 결과 코드뿐 아니라 카드 버전·엔진, snapshot 키, 실행 요약 결과·cursor, 다른 계정(b·c)과 범위 밖 자료 불변을 각각 대조한다.
- 대상: A(현행)와 선택된 대안(B 또는 C)의 분기, 활성 구독이 둘인 경우(한 덱만 비활성화하면 접근 유지), 진행 행 없음.

### 5-2. 실제 PG 검증 (별도 승인 단위, 새 프리셋·DB, L-2 자료와 합산 안 함)

- 두 연결: 전환 실행(공급자 경로) 1개와 관리자 변경 연결 1개. 정지점과 순서를 고정한다.
  - R1 판정 전 변경 커밋 → 전환 카드 `conflict`, 쓰기 0
  - R2 판정 뒤 변경 시도: 현행(A)이면 변경이 기다리지 않고 커밋되며 카드가 `applied`로 남는 것을 **현행 위험의 관측**으로 기록한다. C면 변경 연결이 대기하는 것을 아래 대기 근거로 확인한 뒤, 전환 커밋과 변경 진행 순서를 확인한다. C-1이면 잠기지 않은 다른 경로의 변경은 대기 없이 커밋되는지도 확인한다.
  - R3 쓰기 뒤·커밋 전 변경: R2와 같은 방식
  - R4 변경 연결이 먼저 행을 잡고 커밋 전 대기: C면 전환이 기다린 뒤 재평가해 `conflict`가 되는지 서버 잠금으로 확인
  - R5 커밋 뒤 변경 → 카드 유지, 다음 카드 `conflict`, 롤백 판정 `access_lost`(읽기만)
  - R6 활성 구독 둘 중 하나만 비활성화 → 접근 유지
- 대기 판정은 반환 코드·시간 지연·sleep으로 추정하지 않고, 서버 잠금 근거로만 한다. 근거 수집(관리 연결, 정지점에서 고정 SQL):
  - 대기 연결의 PID(그 연결이 직접 `pg_backend_pid()`로 기록), `pg_stat_activity`의 `wait_event_type = 'Lock'`·`wait_event`·`state`
  - `pg_blocking_pids(대기 PID)`에 차단 연결의 PID가 정확히 들어 있음
  - 대기 PID의 `pg_locks` 중 `granted = false`인 행의 `locktype`·`mode`·`transactionid`(또는 `relation`·`tuple` 정보)
  - 차단 연결의 트랜잭션 ID(그 연결이 `pg_current_xact_id_if_assigned()`로 기록)
- 행 잠금 대기는 대상 행이 아니라 보유 트랜잭션 ID를 기다리는 형태로 보이는 것이 보통이다(PostgreSQL 18 `pg_locks` 문서: 행 잠금은 디스크에 저장되어 이 뷰에 대개 나타나지 않고, 대기자는 보유자의 트랜잭션 ID를 기다리는 행으로 나타난다). 이때 `locktype = 'transactionid'`이고 `relation`은 NULL일 수 있다. 따라서 대기 행에 대상 relation이 있어야 한다는 조건은 두지 않는다. 대신 대기 행의 `transactionid` = 차단 연결이 기록한 트랜잭션 ID를 확인한다. `tuple` 잠금 행이 함께 보이면 기록하되 필수 조건으로 쓰지 않는다.
- 대상 행과의 관계는 서버 뷰가 아니라 기록으로 연결한다. 정지점 이벤트에 각 연결이 실행한 고정 SQL 이름, 바인딩한 행 키(계정·덱·lexeme), 그 문장이 반환·변경한 행 수를 남긴다. 대기 근거 + 정지점 순서 + 행 키를 함께 맞춰야 "그 행 때문에 기다렸다"로 판정한다. 하나라도 빠지면 판정하지 않고 시험 장치 결함으로 멈춘다.
- 변경 귀속: 관리자 변경은 관리자 연결 이벤트(대상 행 키·변경 전후)로, 전환의 쓰기는 공급자 계수(생성·인계·문장·쓰기·커밋)로 따로 기록한다. DB 대조는 관리 조회로 하고 기대값은 기준선·계획·계약에서 계산한다.
- 중단: 첫 준비 실패·시험 장치 결함·기대값 불일치·기록 실패에서 멈추고 미실행을 기록한다. 기록은 저장 뒤 다시 읽어 확인한다.
- 원복·정리: 관리자 변경과 권한 변형(C 채택 시 새 열 권한 포함)은 검사마다 원복하고 공급자 경로로 재관측한다(1·1·0·0·0). 사후에 업무 세션·idle in transaction 0과 대기 잠금 0을 확인한다. R2 정리는 기존 규약(기록 대조, CASCADE 금지, 소유 불명 잔존물 보고)을 따른다.

2. C 채택 시 **제품·권한 계약 단위**(문서만): 잠금 범위에 맞는 잠금 문장, 대상 열 권한 한 쌍, 프로필 버전·옛 승인 처리, 결과 코드
3. **합성 구현·검사**(제품 한 함수 + SQLite 분기 검사, 5-1)

## 7. 미검증

- 2절의 모든 시점 결과는 코드 읽기에서 나온 것이다. 실제 PG와 SQLite 어느 쪽에서도 확인하지 않았다.
- `FOR SHARE`의 권한 요구, 잠금 절과 `LIMIT`·재평가 동작, 행 잠금 대기의 `pg_locks` 표현은 PostgreSQL 18 공식 문서(`SELECT` Locking Clause, 13.2.1 Read Committed, `pg_locks`)에 근거했다. 이 프로젝트의 PG 18.6에서는 확인하지 않았다. 읽기 전용 트랜잭션의 행 잠금 거부는 문서로도 이번에 확인하지 않았다.

## 8. 검토 보정 기록 (2026-10-29, 문서만)

- 4절 C 교착: 순환 조건을 공통 순서(`users` → 카드 → 구독·덱 단어)의 역순 관리자 트랜잭션으로 정정하고, 두 연결의 보유·대기를 적었다. 같은 계정 잠금으로 직렬화되는 제품 경로와 규약 밖 관리자 변경을 구분했고, 규약이 모든 교착을 없앤다고 하지 않는다.
- 5-2 대기 근거: 대기 행의 대상 relation 필수 조건을 없앴다. 행 잠금 대기는 보유 트랜잭션 ID 대기(`transactionid`, relation NULL 가능)로 확인하고, 대상 행과의 관계는 고정 SQL·행 키·정지점 기록으로 연결한다.
- 4절 C `LIMIT`: "`LIMIT 1`이면 행이 빠질 수 있어 전부 잠금이 필수"라는 근거를 철회했다. 경로 하나 잠금(C-1)과 전부 잠금(C-2)을 비교하고 LQ1-f로 분리했다. 권장 후보는 C-1이며, C-2는 별도 정책 선택이다. 어느 안도 승인되지 않았다.
- 독립 정적 재검토: 세 지적 사항의 보정과 정책 미결 상태를 확인했다. 반환 행 수와 전체 잠금 수를 구분하도록 표를 보강했다. 문서 검토만 마감하며 LQ1-a~f 정책 결정·제품 구현·검사·실제 PG는 승인하지 않는다. REPORT 101-1절을 참조한다.

## 10. 제품·권한 계약안 (정적 검토 완료, 세부 결정·구현·GRANT 미승인)

표기는 1절과 같다. **[코드]**는 코드로 확인한 사실, **[제안]**은 계약안이다.

### 10-1. 쓰기 경로 전용 접근 판정 문장 [제안]

- 적용 위치: `apply_plan` 카드 반복에서 `inspect_card(connection, key, for_update=True)`가 부르는 접근 판정이다. PostgreSQL 연결일 때만 적용한다. `is_postgres_connection`이 거짓(SQLite)이면 지금 문장을 그대로 쓴다. `load_card`가 `FOR UPDATE`를 붙이는 방식과 같다(`storage.py:65`).
- 함수 계약: `_authorized(connection, key, *, lock: bool = False)`. `inspect_card`는 `for_update`를 그대로 `lock`에 넘긴다. 기본값 `False`에서는 현행 문장을 유지한다. 개인 카드(`personal`) 판정은 바꾸지 않는다.
- 문장(PostgreSQL, `lock=True`):

```sql
SELECT subscriptions.id AS subscription_id, words.id AS word_id
FROM user_deck_subscriptions AS subscriptions
JOIN shared_deck_words AS words ON words.shared_deck_id = subscriptions.shared_deck_id
WHERE subscriptions.user_id = ? AND subscriptions.is_active = TRUE AND words.lexeme_id = ?
ORDER BY subscriptions.id, words.id
LIMIT 1
FOR SHARE OF subscriptions, words
```

- 정렬 기준은 바뀌지 않는 `id`로 고정한다. 판정은 행이 있는지만 본다. 반환한 `id`를 기록에 남길지는 구현 단위에서 정한다. 읽는 열은 모두 이미 있는 테이블 `SELECT` 권한 안에 있다.
- 반환 경로가 없으면 [코드 동작 유지] 지금과 같다. 0행이면 `quality = "unavailable"`이 되고, 계획과 달라 `conflict`로 끝난다. 카드·snapshot 쓰기는 0이고 cursor는 진행한다.
- 경쟁 변경으로 재평가되는 경우(PostgreSQL 18 문서, 4절 C):
  - 진행 중이던 변경이 롤백되면 원래 행을 잠근다.
  - 변경이 커밋되어 그 행이 더 이상 맞지 않으면(비활성화·삭제·덱 변경), 그 행은 반환되지 않는다. 대신 스냅숏 안의 다음 일치 행을 잠근다. 다음 경로도 없으면 0행이 되어 `conflict`다.
  - 스냅숏 뒤에 새로 생긴 구독은 보지 않는다. 접근을 좁게 판정하는 쪽이므로 보수적이다.
- 기존 호출 경로 영향 [코드]:
  - `dry_run`(`migration.py:641`)은 `inspect_card(connection, key)`(기본 `for_update=False`)를 부르므로 잠그지 않는다. 읽기 프로필과 읽기 전용 트랜잭션도 그대로다.
  - 롤백 판정 `judge_rollback_card`(`migration.py:999`)는 `_authorized(connection, key)`를 기본값으로 부르므로 바뀌지 않는다. 롤백 경로에도 같은 종류의 경합이 있지만 이번 범위 밖이다. 그 역할에는 두 테이블의 `UPDATE`가 없어 잠금을 붙일 수도 없다.
  - 리뷰 경로 `require_subscription`은 바꾸지 않는다. 리뷰의 `FOR SHARE`와 전환의 `FOR SHARE`는 서로 충돌하지 않는다.

### 10-2. 잠금 순서와 유지 기간 [제안]

- 카드 트랜잭션 안의 순서는 다음과 같다. `users` 행 `FOR UPDATE`(`begin_card_write`) → 카드 행 `FOR UPDATE`(`load_card`) → 판정 경로 한 쌍 `FOR SHARE`(10-1). [코드] 앞의 두 단계는 지금 순서 그대로다.
- 유지 기간은 그 카드 트랜잭션의 커밋 또는 롤백까지다. 실행 시작 연결, 마무리 연결, 실패 표시 연결에서는 잠그지 않는다. 이 연결들은 `_authorized`를 부르지 않는다.
- 관리자 규약(LQ1-d와 함께 두며, 강제되지 않는다): 구독·덱 단어를 바꾸는 직접 변경 트랜잭션은 구독자의 `users`·카드 행을 잡지 않는다. 잡아야 한다면 같은 순서를 따른다(4절 C 교착).

### 10-3. 추가 `UPDATE` 열 후보와 근거 [제안]

PostgreSQL 18 문서에 따르면 `FOR SHARE`는 잠그는 각 테이블의 적어도 한 열에 `UPDATE` 권한을 요구한다. 그래서 두 테이블에 한 열씩만 추가한다. 테이블 전체 `UPDATE`, `DELETE`, 소유 권한은 제안하지 않는다.

| 테이블 | 후보 열 | 선정 근거 | 제외한 열과 이유 |
| --- | --- | --- | --- |
| `user_deck_subscriptions` | `updated_at` | [코드] 앱은 재활성화할 때 이 열을 쓰고, `get_or_create_subscription`이 돌려주는 dict에만 담는다. 접근 판정, 정렬, 새 카드 시각에는 쓰지 않는다 | `is_active`(접근 판정). `user_id`·`shared_deck_id`·`id`(소유·식별·조인). `imported_at`(학습 큐의 새 카드 시각 `queue.py:290`, 공유 덱 목록 표시 `shared_deck_repository.py:240`). `created_at`(생성 사실) |
| `shared_deck_words` | `created_at` | [코드] 덱 단어 목록 조회(`lexeme_repository.py:406`)가 값으로 돌려줄 뿐이다. 접근 판정, 정렬, 큐, 식별에는 쓰지 않는다 | `lexeme_id`·`shared_deck_id`·`id`(접근 판정·식별). `sort_order`(목록 정렬, 학습 큐 순서 `queue.py:291`, 큐 커서). 표시 내용 열 `display_meaning_ko`·`example_sentence`·`context_explanation_ko`·`tags_json`·`published_note`(모든 구독자에게 보이는 내용) |

- 제안 GRANT. 문장 형태만 적으며 실행하지 않는다.
  - `GRANT UPDATE (updated_at) ON public.user_deck_subscriptions TO <쓰기 역할>`
  - `GRANT UPDATE (created_at) ON public.shared_deck_words TO <쓰기 역할>`
- 그 열을 실제로 수정했을 때의 영향(대가):
  - 쓰기 역할은 어느 계정의 구독 행이든 `updated_at`을, 어느 덱의 단어 행이든 `created_at`을 바꿀 수 있다. 행 범위 제한은 없다(RLS 없음).
  - `shared_deck_words`는 전역 행이다. `created_at`을 바꾸면 그 덱의 모든 구독자에게 반환되는 값이 바뀐다.
  - 복구 도구의 지문(`recovery.py:395-400`)은 `SELECT w.*`·`SELECT *`로 두 테이블의 행 전체를 해시한다. 두 열을 바꾸면 해당 계정·단어의 `lexeme_access`·`subscriptions` 지문이 바뀌고, 복구 사전 검사는 이를 변경으로 판단한다.
  - 위 근거로 보면 접근 판정, 학습 큐 순서, 소유는 바뀌지 않는다. 이는 정적 코드 확인일 뿐이며 검사로 확인하지 않았다.
  - 전환 제품 코드는 이 열을 쓰지 않는다. 업무 쓰기 계수에서 두 테이블의 `UPDATE`가 0인지를 향후 검사로 확인한다(10-9).

### 10-4. 잠금 대기 초과·교착 처리 [코드 동작 + 결정 필요]

- [코드] 지금 전환 카드 연결에는 `lock_timeout`이 없다. 공급자는 관측 중에만 `SET LOCAL`로 설정하고, 인계 전 롤백으로 풀린다. 따라서 잠금 대기가 끝없이 이어질 수 있다. 대기하는 동안 그 계정의 `users`·카드 행을 쥐고 있어서, 같은 계정의 리뷰도 함께 기다린다.
- [코드] 교착이 감지되거나 대기 초과 오류가 나면, 그 오류는 `apply_plan` 카드 반복 밖으로 전파된다.
  - 제품 연결 컨텍스트가 그 카드 트랜잭션을 롤백한다. 카드, snapshot, cursor는 변하지 않는다.
  - `apply_plan`의 예외 처리가 새 연결을 열어, 실행이 `started`이고 cursor가 그 카드를 가리키면 `failed`로 표시한다.
  - 앞 카드의 커밋은 보존된다.
- [코드] CLI(`run_apply`·`run_resume`)는 시작 뒤의 비-`SrsWriteError` 예외를 이렇게 보고한다: `failed`, `apply_failed`/`resume_failed`, `phase: after_start`, `uncertain: true`, `next: status_required`, 종료 1. 이 보고의 뜻은 "커밋 여부 미확정"이며, 실제 상태는 `status`로 확인한다. 첫 카드 이전(시작 연결)의 실패는 기존 규칙(`first_connection`)을 따른다.
- 결정 필요(미결):
  - D-L1: `lock_timeout`을 도입할지와 그 값. 제안은 카드 트랜잭션 안에서 판정 문장 직전에 `SET LOCAL lock_timeout`을 두는 것이다(권한 추가 없음). 초과 시 별도 고정 코드(예: `migration_access_lock_timeout`)의 `SrsWriteError`를 낼지도 정한다.
  - D-L2: 교착(`40P01`)과 대기 초과를 고정 코드로 CLI 출력에 남길지. 남기더라도 `after_start`·`uncertain`·종료 1 분류는 유지한다. 커밋 응답 유실과 구분하지 않는다.
  - D-L3: 대기 초과로 `failed`가 된 실행을 재개 대상으로 둘지. [코드] 현행 재개는 `failed`를 재개 가능 상태로 다룬다. 이를 바꾸지 않을 것을 제안한다.

### 10-5. 프로필·manifest·승인 재생성 영향 [제안·코드 확인]

- 권한표: `srs_migrate.WRITE_PRIVILEGES`에 두 튜플 `("table","public","user_deck_subscriptions","updated_at","UPDATE")`와 `("table","public","shared_deck_words","created_at","UPDATE")`를 더한다. `READ_PRIVILEGES`는 바뀌지 않는다.
- 프로필 지문: 쓰기 기대 프로필 지문의 값이 바뀐다. 알고리즘(`PROFILE_VERSION` `jp-vocab-ops/profile/v2`)과 형식은 바꾸지 않는다. 권한 값이 바뀐다는 이유만으로 버전을 올리지 않는다. 읽기 프로필 지문은 그대로다.
- 승인: 적용·재개 승인 단계의 쓰기 `profile`은 새 지문이어야 한다. 옛 지문의 승인은 기존 판정대로 거부된다(프로필 불일치 또는 관측 초과 권한). 승인 형식 버전(현행 3)은 바꾸지 않는다. 옛 승인을 고치거나 자동 변환하지 않는다.
- manifest(정정):
  - [코드] `_ops_manifest.ALLOWED_PREFIXES`는 manifest에 **등록할 수 있는** 경로 접두사다(`_check_path`). 그 아래 파일을 모두 넣으라고 강제하지 않는다. `check_manifest_files`는 manifest에 적힌 파일만 바이트로 대조한다. 실행 중 import되는 파일이 모두 등록됐는지(import 완전성)는 후속 단위로 남아 있으며 확인하지 않는다(모듈 설명).
  - 따라서 `migration.py`나 `srs_migrate.py`를 바꿨을 때 manifest 지문이 바뀌는 것은, **그 파일이 실제 배포 manifest에 등록돼 있을 때만**이다. 등록돼 있지 않으면 지문은 그대로이고, 변경은 manifest 대조로 드러나지 않는다. 이것은 무결성 공백이다. 옛 승인을 이어 쓰는 근거로 쓰지 않는다.
  - 지문이 바뀌면 새 배포에서는 새 manifest로 서명한 조회 승인 I₀, 새 계획 결속(`job_plan_fingerprint`에 manifest 포함), 새 적용 승인 A₀가 필요하다.
  - 별도 계약 제안 [제안, 현행 보장 아님]: 이 변경의 배포 manifest에는 바뀐 제품·도구 파일(`backend/app/srs/migration.py`, `backend/scripts/srs_migrate.py`)을 반드시 등록한다. 배포 절차에서 등록 여부를 확인한다. 등록을 강제하는 코드(필수 목록·import 완전성 검사)는 지금 없으며, 만들지 여부는 별도 결정이다.
- 제품 지문·계획 파일: 후보 내용(`_plan_json`)은 바뀌지 않으므로, 같은 DB 상태라면 제품 지문도 그대로다. 다만 계획 결속은 manifest를 포함하므로 새 배포의 승인에서는 다시 계산된다.
- 환경: 실제 DB에 두 열 권한을 부여하는 일은 별도 승인 단위다. 권한이 없는 DB에서 새 코드는 관측 단계에서 `observed_privileges_missing`으로 거부된다(연결 인계 전).

### 10-6. 기존 미완료 실행의 재개 영향 [코드 확인 + 제안]

두 원인을 나눠 적는다.

- (1) 실제 manifest가 바뀐 경우(10-5 조건: 바뀐 파일이 manifest에 등록돼 있을 때):
  - 재개는 **현재 manifest = Aₙ의 manifest = I₀의 manifest**를 요구한다(`OPS_MIGRATION_RESUME_PLAN.md` 4·9절 사전 검사). I₀는 그 실행의 최초 배포 때 서명됐으므로, manifest가 바뀐 새 배포에서는 그 실행의 재개 사전 검사가 거부된다. 이 계획은 기존 규칙("배포가 바뀐 뒤의 재개는 별도 절차가 마련될 때까지 거부")을 바꾸지 않는다.
  - A₀의 `plan`은 A₀에 서명된 manifest 문자열로 다시 계산해 대조한다(과거 manifest 바이트를 쓰지 않음). 이 결속 자체는 새 배포와 충돌하지 않는다. 충돌은 현재 manifest와 I₀의 일치 규칙에서 생긴다.
- (2) 쓰기 프로필이 바뀐 경우(manifest와 별개):
  - 쓰기 기대 프로필은 코드의 계약 권한표로 만든다. 권한표에 두 튜플이 더해지면 기대 지문이 바뀐다. 이미 서명된 옛 Aₙ은 단계 `profile` 불일치로 거부되고, 두 열 권한이 아직 없는 DB에서는 관측 단계에서 `observed_privileges_missing`으로 거부된다.
  - 재개 권한은 Aₙ만 준다. A₀의 단계·역할·프로필은 재개 권한에 합치지 않는다(`OPS_MIGRATION_RESUME_PLAN.md` 3-1절). 따라서 manifest가 같다면, 프로필 변경 자체는 새 프로필로 서명한 새 Aₙ과 DB 권한 부여로 해결된다. manifest도 바뀌었다면 (1)에 먼저 막힌다.
- 금지: 과거 승인·기록 수정, 자동 호환, I₀ 규칙 완화, manifest 등록 누락을 이용해 옛 승인을 이어 쓰는 방식은 제안하지 않는다. 필요하면 "배포 변경 뒤 재개" 절차를 별도 계약으로 다룬다(이번 범위 밖).

#### 10-6-1. 배포 전 미완료 실행 확인 절차안 [제안, 일부 미구현]

- [코드] `status`(`read_status`·`judge_status`)는 지정한 **작업 키 하나**의 실행 행과 snapshot을 읽어 판정한다. 전체 실행 목록을 내지 않는다.
- [코드] 그 키가 없거나, 다른 계정의 실행이거나, 소유를 확정할 수 없으면 "실행 없음"과 같은 답을 낸다(`read_status`가 `None`). 이 비노출 정책은 유지한다. 따라서 `status`의 "없음"은 "미완료 실행 없음"의 증거가 아니며, `status`만으로 전체 미완료 실행이 없다고 선언하지 않는다.
- 절차는 두 단계로 나눈다.
  1. **전체 목록 확보와 완전성 확인** [미구현·운영 결정]: 대상 DB의 `srs_migration_runs` 전체 목록을 확보하고, 종료가 검증된 실행과 미해결 실행을 나눠야 한다. 원시 `status`가 `completed`·`aborted`라는 이유만으로 사전에 제외하지 않는다. 특히 `completed`라도 요약·cursor·snapshot·finished_at 불일치로 기존 상태 판정에서 `inconsistent`가 될 수 있다. 현재 도구에는 전체 목록 조회가 없다. 관리자 직접 조회로 할지, 승인된 읽기 도구를 새로 만들지, 그 목록이 완전한지(같은 DB 식별, 조회 시점, 조회 뒤 새 실행 시작 차단) 어떻게 보증할지는 운영 결정이다. 이번에 조회 도구나 관리자 SQL 실행 장치를 만들지 않는다.
  2. **개별 상태 확인** [현행 도구]: 목록의 각 실행에 대해 그 계정·작업 키·카드 범위로 `status`를 실행해 상태를 확인한다. 소유를 확정할 수 없어 `status`가 "없음"으로 답하는 실행은 해소된 것으로 보지 않고, 1단계 목록에 남은 미해결 항목으로 보고한다.
- 배포 판단: 1단계 목록이 완전하고 2단계에서 모두 종료 상태(또는 옛 배포에서 끝냄)로 확인될 때만 "배포 전 미완료 실행 없음"이라고 말할 수 있다. 1단계가 없는 지금은 이 선언을 할 수 없다.

### 10-7. 카드 롤백·cursor·snapshot·CLI 종료 코드의 관계 [코드 + 제안]

| 상황 | 카드·snapshot | cursor·실행 상태 | 앞 카드 | CLI |
| --- | --- | --- | --- | --- |
| 경로를 잠그고 판정 성공 → 쓰기·커밋 | 변환, snapshot 1 | cursor + 1 | 보존 | 진행(최종 `completed`는 종료 0, 부분은 3) |
| 0행(경로 없음, 재평가로 빠진 경우 포함) | 쓰기 0 | `conflict` 결과, cursor + 1 | 보존 | 완료 시 종료 5(`conflict` 있음), 부분은 3 |
| 잠금 대기 중 경쟁 변경이 커밋되어 행이 맞지 않게 됨 | 다음 경로가 있으면 그 경로로 성공, 없으면 0행과 같음 | 위와 같음 | 보존 | 위와 같음 |
| 교착·대기 초과(현행) | 그 카드 롤백, 쓰기 0 | cursor 그대로, `failed` 표시(실패 표시 연결이 성공했을 때) | 보존 | `failed`·`after_start`·`uncertain`·`status_required`, 종료 1 |
| 커밋 뒤 접근 상실(LQ1-b) | 변환 유지 | 그대로 | 보존 | 영향 없음. 다음 카드는 다시 판정한다. 보고는 운영 절차(10-8) |

### 10-8. 보고(LQ1-b) [미구현]

- 확정 정책은 유지한다. 커밋 뒤 접근을 잃은 카드는 그대로 두고 보고한다. 자동 롤백·상태 보정은 하지 않는다.
- [코드] 전환은 커밋 뒤의 접근 상실을 알 수 없다. 기존 `status`(`read_status`·`judge_status`)는 실행 행·요약·snapshot만 판정하고, 구독·덱 단어의 현재 접근을 확인하지 않는다. 따라서 기존 `status`는 접근 상실을 보고하지 못한다.
- 접근 상실 보고는 **별도 점검 기능 또는 절차가 필요한 미구현 범위**다. 예: 전환된 구독 카드 중 현재 활성 구독 경로가 없는 카드를 찾는 읽기 점검. 기능의 형태(도구·관리 조회), 권한, 출력의 비노출 규칙, 실행 시점은 별도 결정이다. 이번에 만들지 않는다.

## 11. 세부 결정 확정과 최소 합성 구현 계약 (2026-10-29 사용자 승인, 기준 `8dcf35b`, 구현 전 기록)

이번 승인은 아래 결정을 계약에 반영하고, PG 없이 최소 구현과 합성 검사를 하는 데까지다. 실제 PG 실행·접속, GRANT, 운영 배포는 승인되지 않았다.

### 11-1. 확정 결정

- 추가 권한 열(10-3 확정): `user_deck_subscriptions.updated_at`, `shared_deck_words.created_at`. 쓰기 역할은 계정·덱 구분 없이 이 두 열을 실제로 수정할 수 있다(10-3의 대가 유지). 제품 전환 코드는 두 테이블을 `UPDATE`하지 않는다.
- D-L1: 새 접근 판정 잠금의 대기 상한은 5초다.
  - 적용 범위: PostgreSQL 연결에서 구독 카드의 쓰기 판정(`_authorized(..., lock=True)`)만이다.
  - 완화 금지: 판정 직전의 유효 `lock_timeout`이 0(무제한)이거나 5초보다 길 때만 그 트랜잭션에 5초를 둔다. 이미 5초 이하로 더 짧으면 바꾸지 않는다.
  - 복원: 판정 문장이 정상 반환되면, 바꿨던 경우에만 원래 값을 같은 트랜잭션 범위로 되돌린다(`set_config(..., true)`).
  - SQL 실패: 판정 문장이 실패하면 트랜잭션이 실패 상태이므로, 복원 SQL을 더 실행하지 않고 기존 롤백 경로에 맡긴다. 트랜잭션 범위 설정이므로 롤백과 함께 사라진다.
  - 의미: `lock_timeout`은 잠금 하나를 얻으려고 기다리는 시간의 상한이다. 카드 처리 전체가 5초 안에 끝난다는 보장이 아니다. `users`·카드 잠금을 얻은 **뒤**에 설정하므로, 그 앞 단계의 대기는 제한하지 않는다.
  - 5초는 이번 계약에서 고른 값이다. 성능 검증 결과나 운영 안전성 보장이 아니다.
- D-L2: 새 접근 판정 문장에서 난 오류만, SQLSTATE로 좁게 판정해 고정 코드로 바꾼다.
  - `55P03`(lock_not_available) → `migration_access_lock_timeout`
  - `40P01`(deadlock_detected) → `migration_access_deadlock`
  - 그 밖의 오류는 그대로 다시 던진다. 드라이버 원문은 코드·출력에 싣지 않는다(`SrsWriteError(code)`, 원인 연결 없음).
  - `KeyboardInterrupt`·`SystemExit` 같은 중단은 잡지 않는다.
  - 실행 시작 뒤에는 CLI의 기존 분류를 유지한다: `failed`, 고정 코드, `phase: after_start`, `uncertain: true`, `next: status_required`, 종료 1.
- D-L3: 실패한 실행은 기존처럼 명시적 `resume`으로만 이어간다. 자동 재시도·자동 재개는 없다.

### 11-2. 구현 범위

- `backend/app/srs/migration.py`: `_authorized(connection, key, *, lock=False)`, `inspect_card`가 `for_update`를 `lock`으로 전달. 구독 카드 + PostgreSQL + `lock=True`일 때만 10-1의 문장과 11-1의 대기 상한·오류 코드를 쓴다. 개인 카드, SQLite, dry-run, 롤백 판정(`judge_rollback_card`), 리뷰 경로는 그대로다. 새 커밋 경계나 재시도는 없다.
- `backend/scripts/srs_migrate.py`: `WRITE_PRIVILEGES`에 두 열 `UPDATE` 튜플만 추가한다. 읽기 프로필, 객체 목록, 승인 형식, 프로필 알고리즘은 바꾸지 않는다.
- 판정 직전 읽기: `SELECT current_setting('lock_timeout') AS previous, (SELECT setting FROM pg_catalog.pg_settings WHERE name = 'lock_timeout') AS setting_ms`. `pg_settings.setting`의 `lock_timeout` 단위는 밀리초다.
- 실제 PG의 구문·권한·잠금·대기 동작은 이번에 확인하지 않는다. 가짜 연결의 SQL 문자열·오류 주입과 SQLite 결과는 그 증거가 아니다.

### 11-4. 독립 구현 검토와 합성 마감 (2026-10-29)
