# E-5a 계정 쓰기 경계 결과

2026-10-19 · `codex/fsrs-srs-replacement` · HEAD `e2c07f8` · 검토 대기.
보완안 승인과 `E5A_CONTRACT.md`를 먼저 기록하고 구현했다.

## 변경

- 새 `app/account_write.py`: 같은 연결에서 계정 존재 확인과 쓰기 직렬화.
  SQLite BEGIN IMMEDIATE 후 SELECT, PG users 행 FOR UPDATE. 없는 계정은
  404 `account_not_found`. DB/잠금/커밋 오류를 계정 없음으로 바꾸지 않는다.
- SRS `storage.begin_card_write`는 공용 경계를 쓰되 기존 SrsWriteError 타입과
  코드/상태를 유지한다. SQLite도 이제 계정 존재를 확인한다.
- 단어·덱·용어·패키지·공유 발행/가져오기·구독·진도·피드백의 저장소 쓰기에
  경계를 연결했다. 기존 계정 생성과 전역 seed는 구분한다. HTTP 쓰기 23개
  handler를 기존 계정 쓰기 20개와 provisioning/login/읽기 분석 3개로 명시 분류한다.
- 공유 발행의 lexeme·공유 단어는 발행 transaction에 포함한다. 구독 생성과
  import_count 갱신도 한 transaction이다. 하위 helper는 선택 연결을 받아
  자체 커밋/종료 없이 사용하며, 기존 단독 호출 방식도 유지한다.
- 발행은 정규화된 공용 단어 키 순서로 쓰고, 기존 덱 내 순서는 sort_order로
  유지한다. 두 계정이 반대 덱 순서로 발행할 때 공용 행 잠금 순서가 뒤집히지 않는다.
- SQLite 다중 계정 식별 표시도 모든 계정 존재를 확인한 뒤에만 쓴다.
- HTTP에 공통 오류 처리를 추가했다. deck 수정의 넓은 catch와 진도 수정의
  ValueError catch가 account_not_found를 400으로 바꾸지 않게 했다.

제품 변경 파일: `app/account_write.py`, `app/main.py`, 저장소 7개
(`vocab`, `deck`, `custom_term`, `deck_package`, `feedback`, `lexeme`, `shared_deck`),
`app/srs/storage.py`, `app/srs/identity.py`. 이 밖의 기존 제품 변경은 이번 작업이 아니다.
스키마·API URL/요청 모델·응답 정상 형식·프론트·SRS 알고리즘/보존 정책은 바꾸지 않았다.

## 수정 전과 후

수정 전에 계정 행만 지운 합성 SQLite에서 지연된 저장·수정이 실행되거나,
SRS 표의 FK 오류로 끝났다. 깨끗한 계정 없음 거부가 아니었다. 같은 검사를 먼저 고정했다.
수정 후 직접 저장소 쓰기 23종은 모두 404이고 모든 표와 SQLite 파일 바이트가 같았다.

PG에서 users 삭제는 카드까지 CASCADE하므로 기존 단어/덱/용어 수정 helper 3개는
쓰기 연결을 열기 전에 기존 missing-card 값(None)으로 끝날 수 있다. 이 기존
404 연결 의미를 바꾸지 않았으며, 다른 20종은 account_not_found, 모두 쓰기 0이다.
이 차이를 기대값 완화로 숨기지 않고 검사에 명시했다.

## 검증

- **새 SQLite/API 검사 68개 통과.** 정상 23종, 삭제 뒤 거부 23종(한 검사 내
  하위 사례), HTTP 실제 인증 후 계정 삭제 주입 20개 URL, 원자성 실패 주입,
  다중 계정 표시, 표시 순서, 잘못된 id와 DB 오류, 라우트 목록을 포함한다.
  HTTP는 ASGI 인프로세스 요청이며 실제 브라우저/uvicorn 검사는 아니다.
- SQLite 경합 8종 × 두 순서. 실제 별도 연결/스레드와 BEGIN 진입을 관측했다.
  먼저 잡은 writer가 풀리기 전에 다른 작업은 끝나지 않으며 종료 후 계정 자료 0이다.
- **실제 PG 새 검사 4개 통과.** 한 검사에서 경합 8종 × 두 순서의 대기 상대를
  pg_locks/pg_blocking_pids로 확인한다. 다른 계정 행 불변, 계정 잔존 0,
  예상 밖 예외/교착/잠금 초과를 성공으로 인정하지 않는다. 별도 검사에서 두 계정의
  반대 순서 발행을 겹쳐 실행해 둘 다 정상 커밋하고 표시 순서도 유지됨을 확인했다.
- PG 원자성 실패 주입: 발행 단어 기록·구독 생성 후 실패 모두 카드·공유 자료·
  구독·카운터가 전체 롤백됐다. 시퀀스 값은 PG의 비트랜잭션 특성이므로 행 불변과 구분한다.
- **기존 실제 PG 검사 4개 통과.** SQLite/PG 다섯 단계 비교, 단어/덱 삭제와
  평가 경합 양방향, 최신 스키마 반복 시작, 작업자 동시 시작.
- 메모리 변형 4종을 새 검사가 모두 잡았다: 계정 확인 제거, 발행/구독의 중첩
  연결 복원, 공용 단어 정렬 제거. 파일을 변형하지 않았다. PG에서도 정렬을
  제거한 음성 대조는 실제 DeadlockDetected로 실패했다. 통과로 세지 않았고,
  정상 순서 재검사 1회가 통과했다.
- **최종 전체 백엔드 948개: 882 통과, 실제 PG 전용 66 건너뜀.**
  위 실제 PG 8개는 별도 실행 결과이며 전체 회귀 숫자에 합산하지 않는다.
- 기존 회귀 스크립트 9종 rc=0, 프론트 159/159, 타입 검사, diff 검사 통과.
  프론트 제품 변경이 없어 빌드와 화면 검사는 하지 않았다.

초기 제한 환경에서 인프로세스 HTTP가 끝나지 않아 해당 실행을 중단했다.
같은 검사는 권한이 허용된 환경에서 정상 종료했고 전체 회귀도 그 환경에서 돌렸다.
초기 구독 원자성 검사가 모드 판별용 읽기 연결까지 금지하던 테스트 문제도 고쳤다.
두 미완료/실패 실행은 통과로 계산하지 않는다. 최초 실패 fixture의 DB만 정리했다.

## 범위와 남은 일

- 삭제 작업은 테스트 fixture뿐이다. 실제 계정 삭제 도구나 API/화면은 없다.
  **E-5a 완료가 P-ACC 전체, E-5 전체 또는 운영 전환 준비 완료를 뜻하지 않는다.**
- 다음은 E-5b 삭제 도구: 법정 보존 검토, 공유 덱 수동 처리, 요청/본인 확인/
  결과 통지, 외부 사본과 백업 절차를 구분한다. 승인 보완안이 위법성 없음의
  인증이나 실제 계정 삭제 허가는 아니다. 운영 사실 확인은 계속 필요하다.
- 공유 발행의 전역 lexeme 신규 생성과 외부 seed가 동시에 같은 키를 만들 때의
  unique-key 경합 가능성은 코드상 관찰이며 이번에 재현/해결하지 않았다.
  실제 변경이 있는 init_db의 기존 교착도 해결 범위 밖이다. 계정당 잠금 시간이
  늘어나는 경로의 성능 측정은 E-6에 남는다.
- 내부 low-level helper/원시 SQL은 호출자가 transaction을 소유한다. 새 저장소
  경로가 생기면 라우트 분류와 쓰기 경계 검사에 추가해야 한다.
- 보호된 PG 장치의 정상 teardown 뒤 빈 DB 검사로 사용자 객체 0 확인.
  이번에 켠 PID/실행 파일/자료 경로를 대조한 뒤 서버를 종료했다.
- 운영·Neon·기존 vocab.db는 열지 않았다. 기존 c1 임시 폴더 19개·사용자 변경과
  미추적 자료는 보존했다. 스테이징·커밋·푸시·병합 없음.
