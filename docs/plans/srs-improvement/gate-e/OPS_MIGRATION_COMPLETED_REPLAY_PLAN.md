## 1. 코드 확인 사실

### 1-1. 제품 `apply_plan`의 완료 재호출 [코드]

`backend/app/srs/migration.py` `apply_plan`(882행부터), `_run_id`(797행)를 기준으로 한다.

- `approved=True`인 적용 호출에서 새 실행·기존 실행 전용 인자만 생략하면(`new_run_only=False`, `existing_run_only=False`), 완료된 실행의 같은 키를 첫 연결 하나에서 다음 순서로 처리한다. `approved`까지 생략하면 `explicit_apply_required`로 연결 전에 거부된다.
  1. `begin_card_write` → `begin_account_write`: 계정 `users` 행 `FOR UPDATE`, 활성 쓰기 차단 조회. 차단이 있으면 `account_writes_blocked`
  2. `_run_id`: 같은 키 행 조회. 범위·`mode`·설정이 다르면 `migration_run_conflict`, `aborted`면 `migration_run_closed`. 그 외(`completed` 포함)에는 기존 id를 쓴다. 새 행은 만들지 않는다.
  3. 실행 행의 `summary_json`·`started_at`을 읽는다. 커서 < 카드 수일 때만 30일 창을 판정한다.
  4. 저장된 결과의 `applied`를 메모리에서 `already_applied`로 바꾸고, 커서 ≥ 카드 수이면 그대로 반환한다(카드 반복·마무리 연결 없음).
- 연결 수는 1이다. 표 행 변경은 없지만, 연결 종료 시 커밋되고 그때까지 `users` 행 잠금을 잡는다. 시퀀스는 부르지 않는다(INSERT 없음).
- **같은 기본 호출이 `started`·커서 < 카드 수이면 남은 카드를 처리한다**(P2의 `expected_progress` 사전 값 대조는 없지만 기존 범위·차단·30일 창·카드별 커서·재판정 검사는 유지된다). 커서 = 카드 수이고 `started`이면(`cursor_end_not_completed`) 완료 표시 없이 저장 결과만 돌려준다. 즉 기본 호출의 반환값만으로는 완료를 구별할 수 없다(CLI 계획 0절·4-2와 같은 사실).
- `existing_run_only=True`면 `completed`는 `migration_run_not_resumable`, `new_run_only=True`면 기존 행이 있다는 이유만으로 `migration_run_exists`로 거부한다. 둘 다 완료 재조회 경로가 아니다.

### 1-2. 현재 CLI가 보장하는 것 [코드]

`backend/scripts/srs_migrate.py` 기준이다.

| 명령 | 승인·입력 | 제품 호출 | 보장하는 것 |
| --- | --- | --- | --- |
| `apply`(최초, `run_apply`) | 적용 승인 A₀(근거 조회 승인 I₀), 계획 파일, 백업 근거 | 새 `dry_run`과 계획 비교 뒤 `apply_plan(..., new_run_only=True)` 한 번 | 실행 행이 없을 때만 새 실행. 기존 키가 있으면 잠금 아래 `migration_run_exists`(4, 쓰기 0). 완료 실행도 이 거부에 해당한다 |
| `resume`(미완료, `run_resume`) | 적용 승인 Aₙ(이전 사슬, I₀ 근거), 계획 파일, 최초·새 백업 근거 | 사전 `read_status` → `judge_status`. `completed`면 **제품 호출 전에** `migration_run_completed`(4). 재개 가능 상태일 때만 `existing_run_only=True`와 9개 값으로 한 번 | 완료·닫힘·커서 끝·충돌·불일치는 쓰기 연결 없이 거부·보고. `cursor_end_not_completed`는 보고만(6, D7-A) |
| `status`(`run_status`) | 새 조회 승인(`kind = inquiry`, 현재 단계 `status`·읽기, `_admit`). 계획 파일·A₀·근거 없음 | 제품 쓰기 함수 호출 없음. 읽기 연결 1개에서 `read_status`: PostgreSQL이면 `SET TRANSACTION ISOLATION LEVEL REPEATABLE READ`, 실행 행·snapshot 읽기만(잠금 절 없음) | 4-3 상태 판정과 종료 코드: `completed` 0(결과에 `conflict`·`blocked`가 있으면 5), `cursor_end_not_completed` 6, `inconsistent`·`conflict` 6, `incomplete`·`failed_at_cursor` 3, `closed` 0, `not_started` 0 |

- `status`의 정보 비노출 [코드]: 키가 없거나, 다른 계정의 실행이거나, 범위를 해석할 수 없어 소유를 확정할 수 없으면 모두 `None` → `state: not_started`로 같은 답을 낸다(`read_status`). 따라서 `not_started`는 실행 부재의 증거가 아니다(CLI 계획 4-3).
- `status` 출력 [코드]: `state`, `reason`(해당 시), `card_count`, `cursor`, 결과 종류별 건수(`results`, 저장된 요약에서), `finished`, `window`. 카드별 결과 목록·실행 id·시각 원문·snapshot 내용은 내지 않는다.
- 판정 시각 [코드]: `run_status`는 입력의 같은 `now`를 최초 사전 검사와 연결의 공급자 경로에 재사용한다(`apply`·`resume`의 `_timed_connector`는 쓰지 않는다). 호출이 연결마다 있다는 사실과 판정 시각의 신선도는 별개다. 최초 검사 뒤 연결 전 만료되면 과거 시각으로 통과할 수 있으므로, 연결 1개라는 이유로 현재 시각 재확인을 충족한다고 보지 않는다(C5, 3-7).
- 명령줄 [코드]: `main`은 `status`를 받지만 실제 드라이버가 없다. 현재는 합성 경로뿐이다.

### 1-3. 완료와 `cursor_end_not_completed`의 구별 [코드]

`judge_status`(275행):

- `completed`: 실행 행 `status = completed`, `finished_at` 있음, 커서 = 카드 수, 요약 결과와 snapshot 키 일치(`applied`·`already_applied`인 카드만 snapshot 있음).
- `cursor_end_not_completed`: `status = started`, 커서 = 카드 수(마무리 연결이 완료 표시를 남기지 못한 경우). 보고만 한다(D7-A).
- 상태와 `finished_at`이 어긋나거나, 커서가 짧은데 `completed`이거나, snapshot이 요약과 다르거나, 저장 JSON에 중복 키가 있으면 `inconsistent`다. 범위·설정·모드가 다르면 `conflict`다.
- 제품의 기본 재호출(1-1)은 이 둘을 구별하지 못한다. `status`만 구별한다.

### 1-4. `status`만으로 요구를 충족하는가 [코드 + 판단]

| 요구 | `status`가 주는 것 | 판정 |
| --- | --- | --- |
| 저장 결과 반환 | 결과 종류별 건수, 커서, 카드 수, 완료 여부 | 건수 수준에서는 충족. 카드별 결과 목록은 내지 않는다(결정 C1) |
| 쓰기 없음 | 읽기 전용 트랜잭션, 제품 쓰기 함수 호출 없음, 잠금 절 없음 | 충족. 제품 기본 재호출보다 엄격하다(계정 행 잠금도 잡지 않음) |
| 완료와 커서 끝 미완료의 구별 | `completed`(0·5)와 `cursor_end_not_completed`(6) | 충족(제품 재호출은 못 함) |
| 손상 판정 | `inconsistent`·`conflict` 6, 아무것도 고치지 않음 | 충족 |
| 다른 계정·소유 불명 비노출 | `not_started`로 같은 답 | 충족(대가: `not_started`가 부재 증거가 아님) |
| 새 실행·남은 카드 처리 없음 | 제품 쓰기 경로를 부르지 않음 | 구조적으로 충족 |
| 활성 쓰기 차단 반영 | 읽지 않는다 | 제품 재호출과 다르다. 재조회는 쓰기가 아니므로 차단과 무관하다고 볼지 결정한다(C3) |

결론 [제안]: C1~C4를 권장안으로 채택하면 기존 `status`의 반환 의미로 요구를 충족할 수 있다. 별도 재조회 명령이나 제품의 완료 전용 모드는 필요하지 않다. 다만 시각 신선도 결함(C5)은 별개이며, C5-(나) 채택 시 CR-S1의 작은 CLI 보정·합성 검사를 먼저 마쳐야 한다. 문서 정리만으로 전체 경로를 검증 완료로 선언하지 않는다.

## 3. 계약안 (안 1 기준) [제안]

### 3-1. 세 경로의 목적과 반환 의미

| 경로 | 목적 | 반환 의미 |
| --- | --- | --- |
| 최초 적용 `apply` | 실행 행이 없는 작업에 새 실행을 만들고 배치만큼 처리 | 이번 호출에서 처리한 결과. 완료면 0(충돌·차단 있으면 5), 부분이면 3 |
| 미완료 재개 `resume` | 기존 `started`·`failed` 실행의 남은 카드 처리 | 저장된 앞 결과(`already_applied`)와 이번 호출의 처리 결과를 함께 반환 |
| 완료 결과 재조회 `status` | 이미 끝난 실행의 저장 결과 확인 | 저장된 과거 결과의 건수와 상태. 이번 호출에서 새로 처리한 건수는 정의상 0이다 |

- 건수 구분: `status`의 `results`는 **저장된 과거 처리 건수**다. 재조회는 이번 호출에서 카드를 처리하지 않는다(새 처리 0). `resume` 출력의 `results`에는 저장된 앞 결과와 새 결과가 섞여 있다. 새로 처리한 건수는 `cursor_before` 대비 결과로 해석한다고 문서에 적는다. 출력 필드 추가는 이번 범위가 아니다(결정 C4).

### 3-2. 필요한 승인·입력과 근거

| 항목 | 재조회에 필요한가 | 근거 |
| --- | --- | --- |
| 조회 승인(새 `inquiry`, 현재 단계 `status`·읽기) | 필요 | `_admit`이 서명 검증된 조회 승인과 단계를 요구한다(4-3). 쓰기 권한은 없다 |
| 계획 파일 | 불필요 | 쓰기·후보 비교가 없다. 저장된 범위(`scope_json`)와 요청 카드의 일치만 `judge_status`가 본다 |
| 최초 적용 승인 A₀·이전 사슬 | 불필요 | 재조회는 권한을 이어받지 않는다. 사슬을 받지 않으므로 기존 사슬 정합성을 최신 사슬 증명으로 쓰는 일도 생기지 않는다 |
| 현재 manifest | 필요(조회 승인의 manifest와 같아야 함) | 사전 검사의 기존 규칙이다. 재개의 "현재 manifest = I₀" 규칙과 달리, 재조회 승인은 현재 배포로 새로 서명한다 |
| 백업 근거 | 불필요 | 쓰기가 없다 |

### 3-3. 출력과 종료 코드

- `completed`: 0. 저장 결과에 `conflict`·`blocked`가 있으면 5(기존 `run_status` 규칙). 출력은 건수만이다. 충돌·차단 카드는 이미 처리 종료된 결과이며 재조회는 재처리하지 않는다.
- `cursor_end_not_completed`: 6, 보고만(D7-A). 완료 표시·커서·요약·snapshot 수정, 자동 재시도, 새 작업 키 우회는 없다. 필요하면 상태 보정을 별도 후속 결정으로 둔다.
- `inconsistent`·`conflict`: 6. 원인 코드만 낸다.
- `not_started`: 0이지만 **재조회 성공이 아니다**. "키 없음·다른 계정·소유 불명"과 구별하지 않는 비노출 답이므로, 완료 결과 재조회의 성공 조건은 `state = completed`뿐이라고 정한다.
- `incomplete`·`failed_at_cursor`: 3, `closed`: 0. 재조회 대상이 아니다(재개·종료 상태).

### 3-4. 예비 조회 뒤 변경·손상

- 안 1에는 "예비 조회 뒤 제품 호출"이라는 두 번째 단계가 없다. 결과는 한 읽기 트랜잭션(PostgreSQL REPEATABLE READ)의 시점 값이다. 출력 뒤의 변경(예: 정리·롤백 도구)은 다음 조회에서만 보인다. 이를 "그 시점의 기록"이라고 문서에 적는다.
- 손상(중복 키·요약과 snapshot 불일치 등)은 `inconsistent`로 보고만 하고 고치지 않는다.
- 계정 잠금 아래 원자 확인이 필요하다면 안 3이다(결정 C2).

### 3-5. 무변경의 범위

- 표 행: 실행 행·snapshot·카드·설정·소개·로그 행 모두 변경 0. 커서·요약·상태·`finished_at`도 그대로다.
- 잠금: 읽기 트랜잭션의 일시적 relation 잠금(AccessShare)은 있다. 행 잠금(`FOR UPDATE`·`FOR SHARE`)은 없다. 제품 기본 재호출과 달리 계정 `users` 행 잠금도 없다.
- 시퀀스: 호출 없음(INSERT 없음).
- 연결: 읽기 역할 연결 1개. 쓰기 역할 연결 0.

### 3-6. 기존 `apply`·`resume`로 결과를 얻지 않는 이유

- `apply`는 기존 키를 잠금 아래 거부하고(`new_run_only`), `resume`은 `completed`를 제품 호출 전에 거부한다. 따라서 두 명령은 완료 재조회 경로가 아니며, 그대로 둔다.
- 제품 기본 호출을 재조회에 쓰면, 사전 조회와 호출 사이에 상태가 바뀔 때 남은 카드 처리가 일어날 수 있다(1-1). 이를 막으려면 안 3의 별도 모드가 필요하다. 안 1은 제품 쓰기 경로를 부르지 않으므로 이 경합이 없다.

### 3-7. 연결마다의 재확인

- 안 1의 연결은 하나이며, 공급자의 사전 검사(서명·승인·manifest·대상)·관측·판정·연결 후 재판정을 그 연결에서 한 번 거친다(기존 경로).
- 현행 입력 `now` 재사용은 현재 시각의 유효성 보장이 아니다. C5-(나) 권장안은 `run_status(..., clock=None)`을 추가하고, 생략 시 실제 UTC 시계, 합성 검사에서는 명시적 시험 시계를 쓰는 것이다. 승인·서명·manifest·업무 입력 바이트는 고정하고, 최초 `_admit` 직전과 실제 읽기 연결 요청 직전에 각각 새 `now`를 얻는다. 읽기 연결은 기존 `_timed_connector`를 거쳐 기존 공급자 검사 전체를 다시 실행한다.
- 최초 검사 때 유효했어도 연결 요청 시각이 만료 정각이면 거부한다. 드라이버 연결 생성 0·업무 SELECT 0이 기대값이다. 최초 검사를 통과한 뒤라 app이 이미 import됐을 수 있으며, 이 사례에 app 미import를 요구하지 않는다. 같은 과거 `inputs.now`를 주거나 최초 검사 결과를 재사용해 이 거부를 피할 수 없어야 한다. 여기서 신선도 경계는 기존 apply·resume과 같은 **연결 요청 시점**이며, 연결·관측·조회가 끝날 때까지 승인이 계속 유효함을 보장하는 새 계약은 아니다.
- 잘못된 시계·시각·일반 호출 오류는 원문 없이 `clock_invalid`·종료 4로 보고하고 연결하지 않는다. `KeyboardInterrupt`·`SystemExit`은 일반 오류로 바꾸지 않는다. 기존 `_admit`의 입력·도구·종류·단계 거부를 유지한다. 30일 창 출력은 기존 `migration.now_utc()` 판정이며 이 승인 시계 보정과 혼동하지 않는다.

완료 기준 [제안]:

- 완료 재조회 무변경: 표 행·snapshot·커서·요약·상태·`finished_at`의 전후 해시가 같다. 쓰기 역할 연결이 0이다.
- 잘못된 상태·소유·결속 거부: `cursor_end_not_completed`·`inconsistent`·`conflict`는 6, 다른 계정·없는 키·소유 불명은 같은 `not_started`, 적용 승인·잘못된 단계·manifest 불일치는 연결 전 4.
- 다른 계정 불변: 같은 키·같은 lexeme을 가진 다른 계정의 행 전체가 같다.
- 조회와 제품 호출 사이의 경합: 안 1에는 제품 호출이 없다. 조회 대상과 무관한 다른 작업의 커밋만으로는 스냅숏 분리를 증명할 수 없으므로, 아래처럼 **같은 실행의 읽히는 자료**를 바꾼다. 행 잠금 부재와 격리 수준을 서로 다른 판정으로 기록한다.

### 5-1. 대상 행 비차단 검사 [설계, 실제 PG 승인 전]

- 읽기 연결이 첫 실행 행 SELECT를 마친 뒤, snapshot SELECT 전에 정지점을 보유한다. 별도 관리자 트랜잭션이 계정 users 행·해당 실행 행·해당 실행의 기존 snapshot 행을 정확한 키로 UPDATE한다. 각 UPDATE는 기존 값을 자신에게 대입하는 닫힌 문장으로 논리 내용을 유지하고 영향 행 1을 확인한다. 이는 잠금 검증을 위한 시험 DB 관리자 쓰기이며 제품 기능이 아니다.
- 읽기 정지점이 **아직 보유 중일 때** 관리자 COMMIT이 성공해야 한다. 두 PID, 행 키, 영향 행, 커밋 완료, 정지점 보유·해제 순서를 저장한다. 시간 지연이나 `pg_locks`의 빈 결과만으로 성공을 추정하지 않는다. 읽기 역할은 계속 읽기 전용이며 관리자 쓰기와 계수를 분리한다.
- 실제 실행 SQL에 잠금 절이 없음을 함께 확인한다. `pg_locks`·`pg_blocking_pids`는 보조 관측으로만 쓴다. 행 잠금 정보는 보통 `pg_locks`에 직접 보이지 않는다([PostgreSQL 18 pg_locks](https://www.postgresql.org/docs/18/view-pg-locks.html)). 이 사례의 대상 행 비차단을 모든 relation 잠금·DDL의 비차단으로 확대하지 않는다.

### 5-2. 같은 실행의 스냅숏 분리 검사 [설계, 실제 PG 승인 전]

- 두 카드가 applied로 완료된 실행을 고정한다. 읽기 R이 실행 행·기존 요약을 읽은 뒤 snapshot SELECT 전에 정지한다. 독립 관리자 W가 **동일 실행**의 둘째 결과를 conflict로 바꾸고 해당 카드의 snapshot을 지우는 변경을 한 트랜잭션으로 커밋한다. 커서·카드 범위·완료 시각은 유지한다. 새 상태 자체도 요약과 snapshot이 맞는 완료 상태다.
- W의 커밋이 확인된 뒤 R을 재개한다. 정상 REPEATABLE READ에서는 이전 요약과 이전 snapshot이 함께 보여 기존 completed·종료 0이어야 한다. 별도 새 조회에서는 새 요약과 새 snapshot이 보여 completed·종료 5여야 한다. R의 반환 행과 snapshot은 저장 시 고정 사본으로 남겨 단순 문자열 표시와 구분한다.
- 검사 장치에서만 격리 수준을 READ COMMITTED로 낮춘 변형은 이전 요약과 새 snapshot을 섞어 위 정상 기대값을 충족하지 못해야 한다. 해당 변형을 검출하지 못하면 단일 스냅숏 검증으로 인정하지 않는다. [PostgreSQL 18 격리 설명](https://www.postgresql.org/docs/18/transaction-iso.html)의 최초 일반 문장 시점 스냅숏 규칙에 따른다.
- 이 변경·복원은 별도 실제 PG 계획에서 행 키·원문 값·허용 SQL·원복·실패 시 정지점 해제·스레드 종료 규칙을 먼저 고정하고 승인받는다. 경합 중 전체 DB 불변을 요구하지 않고 W에 귀속된 변경만 허용한다. 읽기 경로에 귀속되는 쓰기는 0이어야 한다. 검사가 끝나면 시험 원본을 명시적으로 복원·대조한다. 이 시험용 원복을 D7 상태 보정 기능이나 운영 절차로 취급하지 않는다.

## 7. 독립 검토 지적 3건의 설계 보완 (2026-10-30)

- C5: 입력 시각 재사용의 결함을 현재 코드 사실과 분리해 명시했다. 연결이 하나라는 이유로 시각 신선도가 보장된다는 근거를 철회하고, 최초 검사·연결 요청 시각 갱신을 권장안으로 바꿨다. 최초 검사 뒤 만료되는 사례와 시계 오류를 CR-S1 완료 기준에 넣었다.

## 8. CR-S1 구현 인계 계약 [9절 승인 범위]

- Codex가 이 계약과 완료 기준을 작성·검토한다. Claude Sonnet은 구현·검사만 하고, 설계·정책을 바꾸거나 Git 스테이징·커밋·푸시를 하지 않는다. 같은 작업 보정은 최대 3회이며 작업 범위를 새로 이름 붙여 횟수를 초기화하지 않는다.
- 허용 변경: `backend/scripts/srs_migrate.py`, 직접 호출자를 담은 `backend/tests/test_srs_migrate_status.py`, 필요한 새 status 시계·완료 재조회 합성 검사 파일. 실제 호출자 목록은 착수 직전 다시 검색한다. 다른 호출자가 발견되면 근거를 보고하고 범위를 확인한다. `app/`, 공통 승인·공급자·어댑터·연결 도우미, 기존 실제 PG 실행기·권한·스키마·manifest 구성은 바꾸지 않는다.
- 새 서명은 `run_status(request, *, inputs, expected, driver, clock=None)`다. 생략된 시계는 실제 UTC 현재 시각이며 `inputs.now`로 대체하지 않는다. 서명·대상·명령·입력 거부와 app import 순서를 유지하고, 새 시계의 일반 오류는 고정 코드로만 거부한다. 승인·서명 바이트와 기대 프로필은 고정하며 갱신되는 것은 해당 판정의 `now`뿐이다.
- 초기 검사와 읽기 연결 요청의 두 채취 시점을 시험 시계로 구분한다. 기존 고정 시각 fixture에는 명시적 시계를 주입하되 기대 상태·출력·거부 코드는 유지한다. app 최초 import 전 안전 환경 세 값 고정, 외부 PYTHONPATH·PG 환경 변수 차단, 합성 SQLite·가짜 서버만 허용한다. 비UTC 정상 시각·naive·범위 초과·일반 오류·중단·현재 시각 기본값도 다룬다.
- 집중 회귀는 새 검사와 status·dry-run CLI·합성 SQLite·resume SQLite·공급자 경로의 직접 영향 묶음으로 고정한다. 단독 실행·루트 discovery와 새 프로세스의 초기 거부 시 app 미import를 확인하고 ResourceWarning을 숨기지 않는다. 최초 검사 뒤 연결 직전 만료는 app import가 이미 일어났을 수 있으므로 연결 생성·업무 SQL 0으로 판정한다. 실제 PG·사용자 키·운영 신뢰 루트·실제 권한 변경은 하지 않는다. 임시 시험 키가 꼭 필요하면 기존 합성 fixture만 사용·정리하고 실제/가짜 서명 경계를 보고한다.
- 고정 시각으로 되돌린 변형에서 새 만료 회귀가 실패해야 한다. 구현 보고에는 변경 파일, 보정 전 재현, 검사 수·결과, 실제/가짜 경계, 잔존물과 한계를 남긴다. Codex가 실제 diff·검사 증거를 검토한 뒤에만 관련 파일을 커밋·푸시한다. 다음 실제 PG 계획·실행은 별도 승인이다.

## 10. CR-S1 합성 구현·독립 검토 마감 (2026-10-30)

- 구현 기준 `55974e0`. Claude Code의 명시적 Sonnet 작업 세션에서 구현·검사를 수행했고, Codex가 실제 변경과 실행 로그를 검토했다. 최초 인계 뒤 같은 범위 보정은 1회(상한 3회)였다. worker 변경은 9절 네 파일뿐이며 Git 작업은 하지 않았다. 전달 기록·결과·검사 로그는 저장소 밖에 두었다.
- `run_status(..., clock=None)`는 생략 시 실제 UTC 시계를 쓴다. 최초 사전 검사와 실제 읽기 연결 요청마다 새 시각을 얻고 기존 `_timed_connector`·공급자 경로를 사용한다. 과거 `inputs.now`는 승인 만료를 피하는 데 쓰이지 않는다. dry-run의 시각 의미와 apply·resume의 공통 시계 함수는 바꾸지 않았다.
- 명시적인 잘못된 시계(`False`, 0, 빈 문자열·목록·dict 등)는 기본 시계로 바꾸지 않고 `clock_invalid`·4로 거부한다. 시계 호출의 일반 `Exception`만 고정 오류로 바꾸고 `KeyboardInterrupt`, `SystemExit(9)`, 취소 등 `Exception`이 아닌 `BaseException`은 같은 객체로 전파한다. UTC 변환 범위 초과도 거부한다.
- 첫 구현 검토에서 위의 명시적 falsy 시계 대체와 과도한 `BaseException` 포착을 발견했다. 보정 전 시계 12개 검사에서 하위 사례 실패 10건을 재현했고, 보정 뒤 통과했다. 초기 새 API를 구 코드에 실행해 생긴 `TypeError`와 이 동작 결함의 재현을 구별한다.
- 완료 재조회는 실제 제품 `dry_run`·`apply_plan`이 만든 합성 SQLite 기록으로 검사했다. 완료 0, 실제 제품 conflict와 blocked 5, 마무리 실패로 만든 커서 끝·완료 미기록 6, 중복 요약·snapshot 불일치 6, 다른 계정·없는 키의 같은 응답, 전체 논리 DB 불변과 읽기 연결만 사용함을 확인했다. 재조회 중 제품 적용 호출은 금지했다.
