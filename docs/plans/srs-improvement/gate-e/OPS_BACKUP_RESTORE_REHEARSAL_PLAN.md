## 2. 호출 흐름

1. 준비(관리 연결): 클러스터·TLS·역할·원본 DB → 앱 import 전 환경 고정 → 소유 역할로 `ensure_schema` → 합성 자료(감사 계획과 같은 정상 자료 + 시퀀스를 앞당기는 삽입·삭제 몇 건) → 원본 식별 행(실행별 nonce) → 감사·백업 권한 → 생성 기록(PID·OID·경로 즉시 기록).
2. 원본 기준선(관리 연결, 읽기만): 표별 행 수·내용 해시, 스키마 지문(열·형식·기본값·NOT NULL, `pg_get_constraintdef`, `pg_get_indexdef`, 소유자, `relacl`), 시퀀스 `last_value`·`is_called`·증가값.
3. 덤프(`pg_dump`, 백업 역할): 시험 실행기가 대상 보호 확인(서버 PID·실행 파일·리스너, 프리셋 DB·역할) 뒤 자식 프로세스로 실행. 출력은 `dumps/<실행 ID>/src.dump` 하나.
4. 덤프 확인: 종료 코드 0, 파일 크기 > 0, `pg_restore --list` 목차가 기대 객체를 포함, SHA-256 기록. 실패면 복원하지 않는다.
5. 원본 불변 확인: 2단계 기준선과 같아야 한다(덤프는 읽기만).
6. 복원 준비(관리 연결): `jp_vocab_test_br_dst`를 `jpvb_owner` 소유로 새로 만들고 비어 있음을 확인(사용자 관계 0), DB 수준 권한(`PUBLIC` 회수, 감사 역할 `CONNECT`)을 원본과 같게 설정.
7. 복원(`pg_restore`, 관리 역할): `--single-transaction --exit-on-error`로 전부 아니면 무. 원본과 같은 클러스터·같은 역할이므로 소유자·권한을 덤프대로 재현한다.
8. 복원 대상 독립 식별: 식별 표 자료는 덤프에서 제외되므로(3절) 복원 직후 관리 연결이 복원본 전용 nonce 식별 행을 넣고 생성 기록에 남긴다. 원본 식별값과 달라야 한다.
9. 비교: 2단계 항목을 복원본에서 다시 계산해 대조(식별 행 제외), 시퀀스 다음 id 충돌 검사, 두 DB에 대해 공급자 경로 감사(`run_synthetic_audit`)를 각각 실행해 결과 전체 비교.
10. 정리(6-2의 R2 방식): 기록 대조 뒤 서버 정지, `pg64`(덤프 포함)·시험 키 삭제.

## 3. 덤프 형식과 옵션

- 형식: 사용자 지정 형식 `-Fc`(압축, `pg_restore`로 목차 확인·단일 트랜잭션 복원 가능). 평문 SQL은 쓰지 않는다.
- 범위: `--dbname`으로 원본 DB 하나. `--no-password`(비밀번호 프롬프트 금지), `--exclude-table-data=jp_vocab_ops_synthetic.db_identity`(식별 행 복제 방지, 표 정의는 포함), 그 밖 기본값(소유자·권한·시퀀스 `setval` 포함). 역할·테이블스페이스·DB 수준 설정은 덤프에 없으므로 6단계에서 관리 연결이 명시적으로 만든다(기록).
- 복원: `pg_restore --single-transaction --exit-on-error --no-password --dbname=<복원 DB>`. `--clean`·`--create`는 쓰지 않는다(빈 새 DB에만 복원).
- 소유·권한·역할: 같은 클러스터의 같은 역할로 소유자와 `GRANT`가 그대로 재현되는지 비교한다. 다르면 실패이며 권한을 손으로 맞추지 않는다.
- 시퀀스: 덤프의 `setval`로 `last_value`·`is_called`가 같아야 하고, 표마다 시퀀스 다음 값이 `max(id)`보다 커야 한다(충돌 위험 0).

## 4. 권한 분리와 접속

- 백업 역할 `jpvb_backup`: 원본 DB `CONNECT`, 스키마 `USAGE`, 원본의 모든 표·시퀀스 `SELECT`만. 쓰기·소유·생성 없음. 복원 DB에는 접속 권한 없음. 공급자 경로가 아니라 시험 실행기의 `pg_dump` 자식 프로세스 전용이다.
- 관리 역할 `jpvb_admin`: 클러스터 준비, 복원 DB 생성, `pg_restore` 실행, 식별 행 삽입, 비교용 읽기, 정리. 공급자에 넘기지 않는다.
- 감사 역할 `jpvb_audit`: 감사 계획의 확정 읽기 권한만(두 DB), 공급자 경로(verify-full·SCRAM, 비밀번호는 메모리)만.
- 비밀번호를 남기지 않는 접속: 백업·관리 역할은 SSPI(현재 Windows 사용자 명시 매핑)로 비밀번호 자체가 없다. 자식 프로세스에는 연결 문자열 `host=localhost port=55482 dbname=… user=… sslmode=verify-full sslrootcert=<이번 실행 CA> gssencmode=disable`만 넘기고(비밀값 없음), 자식 환경에서 `PG*` 변수를 모두 지운다. 이번 실행 CA로 verify-full이므로 이 클러스터 서버에만 연결된다. 덤프·복원 로그는 고정 분류만 남기고 원문은 남기지 않는다.

## 5. 덤프 보관·접근 제한·파기

- 위치 `C:/JV_Tools/pg64/dumps/<실행 ID>/src.dump`, 폴더는 현재 Windows 사용자만 접근(상속 해제 ACL). 저장소·세션 임시 폴더·네트워크 경로에는 두지 않는다.
- 내용은 합성 자료뿐이다. 크기·SHA-256만 생성 기록에 남긴다.
- 파기: R2에서 기록의 경로·해시를 대조한 뒤 `pg64` 전체와 함께 삭제하고, 삭제를 확인한다. 불일치면 삭제하지 않고 멈춘다.

## 9-2. 준비 관문 구현 (2026-10-25, 시험 코드·PG 없는 검사만)

- `check`는 b1보다 먼저 `baseline_gate`를 실행한다. 원본은 `snapshot`(행·열·제약·인덱스·소유자·권한·시퀀스·최대 id)·식별 행(엄격 읽기, 실패를 대체값으로 바꾸지 않음)·관계·스키마, 복원·실패 주입 DB는 `failure_db_state`(스키마·관계·식별 열 없는 `snapshot`)를 실제 수집 함수로 읽는다.
- 대상별 정상 초기 상태 계약(코드 주석에 먼저 기재): 원본은 스키마가 정확히 `public`+합성 스키마, 관계에 식별 표와 앱 표 전체, 식별 행은 기록된 원본 값 하나. 복원·실패 주입 DB는 스키마가 `public`뿐이고 관계가 없으며 수집 항목이 모두 비어 있다. 이 두 DB에는 식별 표가 아직 없는 것이 정상이므로 식별 행을 읽지 않는다.
- 수집 질의가 예외를 내면 시험 장치 결함(`error`·`harness_defect`), 수집 결과가 계약과 다르면 준비 실패(`fail`·`preparation_failure`)로 기록한다. 어느 쪽이든 자식 프로세스와 b1~b8을 시작하지 않고 종료 코드는 1이다.
