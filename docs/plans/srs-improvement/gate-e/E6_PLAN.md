## 1. 합성 자료 (계정당 1천·1만 카드, 크기별로 따로 실행)

- 측정 계정 T 1개(FSRS 모드, 테스트 DB 안의 합성 계정만)와 비교용 다른 계정 O 1개(소량)를 둔다. 공유 덱 2개는 O가 소유하고, T가 둘 다 구독한다.
- 개인·구독 비율 **초안 50:50**: 개인 카드는 T의 덱 2개에 나누고, 구독 카드는 공유 덱 2개에 나눈다. 비율은 미정(4절).
- 상태 구성 초안(카드 수 대비): 신규 30%(구독 신규 중 절반은 progress 행 없음), 학습·재학습 예정 10%, 오늘 복습 예정 15%, 연체 15%, 나중 예정 25%, 일시중지·legacy 미전환 5%.
- 평가 로그: 카드당 0~20건, 평균 약 5건. 1만 카드면 약 5만 건이다. 오늘(서울) 처음 평가한 카드도 일부 넣어 오늘 새 단어 수가 0이 아니게 한다.
- 생성 방법:
  - 소수 카드는 앱의 실제 경로(카드 생성, FSRS 평가)로 만든다.
  - 대량은 같은 열 값을 직접 INSERT한다.
  - 생성 뒤 `srs_invariant_audit`로 불변식을 확인한다.
- 난수 시드, 상태별 기대 건수, 생성 규칙을 기록에 남긴다. 단어 내용은 `w00001` 같은 합성 문자열만 쓴다.

## 3. 측정 방법

- **준비 시간과 요청 시간 분리.**
  - 준비 시간: 자료 생성, 통계 갱신(PG `ANALYZE`, SQLite `ANALYZE`), 정확성 확인. 단계별 소요를 따로 적는다.
  - 요청 시간: ASGI 인프로세스 요청(httpx `ASGITransport`) 시간과 함수 직접 호출 시간을 구분해 적는다.
- 측정 횟수 **초안**: 대상마다 예열 5회를 버리고 30회를 측정한다. 기록에는 실제 사용한 횟수를 남긴다.
- 기록 항목:
  - 중앙값·95번째 값·최소·최대(ms)
  - 요청당 SQL 질의 수와 반환 행 수: 테스트 전용 실행 래퍼로 세고, 제품 코드에는 훅을 두지 않는다.
  - 응답 항목 수
- 시계: 큐의 기준 시각을 측정 동안 테스트에서 고정해, 회차마다 같은 분류가 나오게 한다.
- PG에서는 주요 질의마다 `EXPLAIN (ANALYZE, BUFFERS)`를 측정 회차 밖에서 한 번 실행하고, 인덱스 사용 요약만 적는다.
- SQLite도 같은 시나리오를 재서 한 표에 둔다.
- 보고 형식: 기기 사양, DB 종류·버전, 카드 수, 횟수, 수치, 실행 계획 요약. "빠름" 같은 판정은 쓰지 않는다.

## 4. 정확성과 정리

- **측정 전 확인:**
  - 대상별 결과를 생성 규칙의 기대 건수와 대조한다: 큐 범주별 수, 지금 복습 id 집합, 오늘 새 단어 수, 통계 합계.
  - SQLite와 PG 결과가 같은지 확인한다.
  - 불변식 감사가 통과해야 한다.
- **측정 후 확인:** 모든 표의 행 수와 내용 해시가 측정 전과 같아야 한다(측정은 읽기만 한다). 대상 결과도 측정 전과 같아야 한다.
- **PG 소유 증명과 정리:** 기존 E-1 장치를 그대로 쓴다.
  1. 빈 DB 검사
  2. 실행 표식과 OID 기록
  3. 매 쓰기 전 대상 재확인
  4. 실행이 만든 객체만 reset/teardown
  5. 빈 DB 재검사
  6. 시작한 서버만 PID·실행 파일·자료 경로를 확인한 뒤 정지, 55432 리스너 부재 확인
- 중단 시 잔여 객체는 실행 자신의 소유 기록으로만 정리한다. 그 외는 보고하고 승인을 받는다. CASCADE, DB 재생성, 세션 강제 종료는 하지 않는다.
- **SQLite:** `APP_ENV=test`와 세션 전용 임시 파일을 쓰고, 끝나면 제거한다. `vocab.db`, `.env`, 기존 임시 폴더 19개는 건드리지 않는다.

  - 운영 PG 주 버전과 같은지는 확인되지 않았다.

| 기존 `jp_vocab_test_e` 재사용 | 관리 작업이 없고, 검증된 역할·HBA·보호 장치를 그대로 쓴다 | 측정 중에는 E 테스트를 돌릴 수 없다. 대량 실행이 중단되면 정리 전까지 E 테스트가 막힌다 |
