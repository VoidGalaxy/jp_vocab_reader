## 3. 카드 삭제와 로그 보존 (D-P1)

### 3-1. 왜 바꿔야 하나
PG에서는 카드를 지우면 그 카드의 개인 로그가 사라진다. 그런데 아래 기능들은 **삭제된 카드의 로그가 남아 있다는 전제**로 SQLite에서 승인·검증됐다.
- 오늘 새 단어 집계 `goals.first_review_dates`/`count_introduced`(`goals.py:93`). 독스트링에 "deleted cards included"라고 적혀 있다. 로그가 사라지면 오늘 이미 시작한 단어가 0으로 돌아가 **하루 목표를 다시 소비**한다.
- 기록 달력·과거 집계: 지운 단어의 날짜 기록이 사라진다.
- 식별 검사 `identity.scan_identity`의 `log_before_created`·`deleted_then_reused` 입력.
- 정수로만 로그를 가리키는 것들: 영수증 `review_log_id`, snapshot `last_log_id`, 증거 재시작 경계. 로그가 사라지면 가리킬 대상이 없어진다.

### 3-2. 선택지

| 안 | 내용 | 무결성 | 기존 집계·식별 | 판단 |
| --- | --- | --- | --- | --- |
| **A(권장)** | `review_logs.vocab_item_id`의 카드 FK만 제거. NOT NULL 정수 식별자, 로그 id, user FK(CASCADE)는 유지 | 카드 없는 로그가 생긴다(의도). 대신 3-3의 불변식으로 감시 | SQLite와 같은 자료 모양. 승인·검증된 집계 그대로 | 권장 |
| B | FK를 `ON DELETE SET NULL`로 변경 | `vocab_item_id NOT NULL`을 먼저 풀어야 한다. 삭제된 카드끼리 구별이 안 된다 | **깨짐**: `readability.py:64`의 `int(row["ref"])`가 NULL에서 TypeError가 난다. `first_review_dates`는 (종류, id)로 묶어 지운 카드가 한 키로 합쳐진다. 원장·식별 검사가 로그와 id로 맞출 수 없다. SQLite(정수 유지)와 결과가 갈린다 | 비권장 |
| C | 지금처럼 CASCADE | FK 유지 | 하루 목표 재소비, 기록 달력 손실, 두 DB 결과 불일치. 영수증·snapshot·증거 경계가 없는 로그를 가리킨다 | 비권장 |

**FK만 떼어도 되는 이유와 한계 (안 A 검토)**
- 카드 없는 로그는 이미 SQLite에서 정상 상태다. 관련 코드는 모두 카드가 없을 때를 처리하도록 검증됐다(U3·U4·U9·U10·U12 테스트).
- FK가 하던 일 중 "없는 카드에 로그를 쓰지 못하게 막기"는 사라진다. 지금 쓰기 경로는 계정 잠금 안에서 카드를 읽은 뒤 로그를 쓴다(`storage.begin_card_write` → `load_card`). PG는 카드 행도 `FOR UPDATE`로 잡는다(`storage.py:62`). 그래서 실제 위험은 경로 밖의 직접 쓰기다. 3-3의 I1·I2로 감시한다.
- PG 카드 id는 IDENTITY라 자동으로는 재사용되지 않는다. 하지만 `GENERATED BY DEFAULT`라 명시 id 삽입은 막지 않는다. 예를 들어 `scripts/migrate_sqlite_to_postgres.py`는 id를 그대로 복사한 뒤 시퀀스를 맞춘다. 그래서 운영 PG에도 SQLite 시절 재사용 혼합이 들어와 있을 수 있다. 식별 검사(U3)를 PG에서도 돌려야 한다(I4).

### 3-3. 안 A의 감시 불변식 (전환 전·후, 정기 점검)

| ID | 불변식 | 위반 시 |
| --- | --- | --- |
| I1 | 카드 없는 개인 로그의 (계정, id)는 삭제 원장에 같은 (계정, `personal`, id)가 있다. 예외는 D-P1 적용 이전에 이미 있던 로그다. PG는 지금까지 CASCADE였으므로 적용 시점의 고아 로그는 0이어야 한다 | 중단. 원장을 추정으로 채우지 않는다 |
| I2 | 살아 있는 카드의 로그는 `log.user_id = card.user_id` | 중단, 식별 검사로 넘김 |
| I3 | 카드 id 시퀀스 ≥ 카드·두 로그·영수증·snapshot·원장·식별 표시에서 본 최대 개인 id(U2의 SQLite 규칙과 같음) | 쓰기 전 중단 |
| I4 | `identity.scan_identity` 결과가 0이거나, 발견분은 표시(`flag_identity_unknown`)된 상태 | 해당 계정 전환 제외 |
| I5 | 영수증 `review_log_id`, snapshot `last_log_id`, 증거 경계, 카드 `evidence_from_log_id`가 가리키는 로그가 존재(계정 삭제 이외에는 로그를 지우지 않으므로) | 중단 |
| I6 | 로그 행 수는 카드 삭제 전후에 줄지 않는다 | 중단 |

**E-3 사전 검토 대조 (2026-10-18, `E3_PREP.md` 3절)**
- 실제 PG 재현에서 I5·I6이 현재 동작과 충돌했다(사라진 로그를 가리키는 영수증·snapshot, 로그 7→2).
- I1은 CASCADE 아래에서는 고아 자체가 없어 로그 손실을 잡지 못한다.
- **I7 (2026-10-18 보정)**: 시점과 평가 이력을 고정했을 때, 카드 삭제 때문에 다음이 달라지지 않는다.
  - 계정의 날짜별 신규 실적(exact 값, 확인 불가 상태와 하한 포함)
  - 하루 목표 잔여
  - 기록 달력의 평가 수
  - 불변 대상이 아닌 것: 지금 남은 단어 수, 덱·계획 범위 집계, 달력의 담은 단어 수. 이들은 남아 있는 카드에서 세므로 삭제와 함께 달라지는 것이 맞다.
- E-D1 A안은 2026-10-18 승인됐다(APPROVAL_REQUEST 1절).

### 3-4. 제약 변경 방식 (승인 뒤 구현할 모양)
- 새 DB: `create_postgres_tables`의 `review_logs` 정의에서 `vocab_item_id`의 REFERENCES를 뺀다. 열은 `INTEGER NOT NULL` 그대로다.
- 기존 DB: 이름을 가정하지 않는다. 카탈로그(`pg_constraint`)에서 `review_logs(vocab_item_id) → vocab_items(id)` FK를 찾는다.
  - 정확히 1개면 제거한다. 0개면 아무것도 안 한다(멱등). 2개 이상이거나 모양이 다르면 중단한다.
  - 한 트랜잭션에서 하고, 자료는 바꾸지 않는다.
- 되돌리기 (2026-10-18 보정):
  - **DB 제약 복구**: 카드 없는 로그(고아 로그)가 한 건이라도 생긴 뒤에는 기존 FK를 그대로 다시 붙일 수 없다. 그 복구를 위해 로그를 지우거나, 카드를 복원하거나, 참조를 다른 카드로 다시 잇지 않는다. 그래서 FK를 다시 만들지 않는다.
  - **앱 코드 복구**: 앱을 이전 버전으로 되돌리는 것은 가능하다. 이전 코드도 FK가 없는 DB에서 동작해야 하며, SQLite에서는 이미 그렇다. PG에서는 확인해야 한다(검사표 P-UP3). 이전 코드의 `CREATE TABLE IF NOT EXISTS`는 기존 표에 FK를 다시 붙이지 않는다.
- 범위 밖으로 둔다: `lexeme_review_logs.lexeme_id → lexemes` CASCADE. lexeme 삭제 경로가 없어서다. 대신 전환 절차에서 lexeme 삭제를 금지 항목으로 둔다(승인 항목 E-D7).

### 3-5. 지키는 것
- 삭제한 카드는 어떤 경로로도 복구하지 않는다. 롤백·재전환·영수증 재시도 모두 카드가 없으면 미적용이나 404로 끝난다.
- 남은 로그로 일정·완료 증거·삭제 원장·학습 이력 표시를 추정하거나 합성하지 않는다.
- U9·U10 예외는 그대로다. 삭제 시 영수증과 snapshot에서 카드 내용만 지우고, 결과·해시·로그 id·최소 snapshot은 남긴다. 기간 만료 정리 규칙도 그대로다.

## 4. 계정 삭제 (D-P5)

### 4-1. 현재: 경로 없음
API·화면·운영 스크립트 모두 없다. 이 문서는 **새 API·화면을 만들지 않는다.** 아래는 운영자가 실행하는 정리 절차의 계약안이며, 실행 형식과 대상 선정은 승인 항목이다(E-D6).

### 4-2. 카드 삭제와 구분
| | 카드 삭제(D-P1) | 계정 삭제(D-P5) |
| --- | --- | --- |
| 원로그 | 남김 | 그 계정 것은 전부 삭제 |
| 삭제 원장·학습 이력 증거 | 남김 | 전부 삭제 |
| 영수증·snapshot | 내용만 제거, 결과·최소 기록 남김 | 전부 삭제 |
| 목적 | 계정 안의 집계·감사 유지 | 그 사람의 학습 자료를 남기지 않음 |

"원로그 삭제 금지"(K6)는 이전 작업 규칙이다. 계정 삭제는 별도 절차로, 그 계정의 로그를 지우는 유일한 경로다.

### 4-3. 대상 계정 자료 (권장: 전부 삭제, 익명 보존 없음)

| 표 | 선택 조건 | 지금 PG에서 users 행 삭제 시 | 지금 SQLite에서 |
| --- | --- | --- | --- |
| `vocab_items`, `decks`, `custom_terms` | `user_id = 대상` | CASCADE | **남음**(FK 없음) |
| `review_logs`, `lexeme_review_logs` | `user_id = 대상` | CASCADE | **남음** |
| `user_word_progress`, `user_deck_subscriptions` | `user_id = 대상` | CASCADE | **남음** |
| `shared_deck_imports`(가져온 사람으로서) | `user_id = 대상` | CASCADE | 남음 |
| `srs_user_settings`, `srs_review_receipts`, `srs_card_deletions`, `srs_card_identity_flags`, `srs_evidence_restarts` | `user_id = 대상` | CASCADE | CASCADE |
| `srs_migration_snapshots` | `user_id = 대상` | **남음**(FK 없음) | **남음** |
| `srs_migration_runs` | `scope_json` 최상위 `user_id = 대상` | **남음**(계정 열 없음) | **남음** |
| `meaning_feedback` | `user_id = 대상` | CASCADE | 남음 (E-D5) |
| `app_feedback` | `user_id = 대상` | user만 NULL, 내용 남음 | 남음 (E-D5) |
| `users` 행 | `id = 대상` | - | - |

순서(한 트랜잭션, 두 DB 같은 절차):
1. 계정 쓰기 잠금(`begin_card_write`). 이 잠금을 잡는 경로(평가·이전 적용·카드·덱 삭제·식별 표시)와만 직렬화된다. PG는 잠금 뒤 그 경로들이 `account_not_found`(404)로 끝난다(`storage.py:47~49`). **나머지 쓰기 경로는 이 잠금을 잡지 않는다. 4-7 참고.**
2. 사전 검사: 4-4의 공유 덱 조건, 진행 중(`started`) 실행이 없는지, 모든 `scope_json`을 읽을 수 있는지. 하나라도 못 읽으면 중단한다(건너뛰지 않음).
3. snapshot → 실행 → 나머지 SRS 표 → 로그 → 진도·구독·가져오기 → 카드·용어·덱 → (E-D5 결정분) → users.
   snapshot이 runs를 FK로 가리키므로 snapshot을 먼저 지운다.
4. 4-6의 잔존 검사가 0이 아니면 롤백하고 중단한다.

### 4-4. 다른 계정에 미치는 영향

| 상황 | 지금 PG CASCADE의 결과 | 지금 SQLite |
| --- | --- | --- |
| 대상이 **공유 덱 소유자**이고 구독자가 있음 | `shared_decks` → 구독자의 `user_deck_subscriptions`·`shared_deck_words`·`shared_deck_imports` 행 삭제. 구독자 진도·로그는 남지만 단어 접근 권한이 사라진다. 구독자 로그의 `shared_deck_id`는 NULL로 바뀐다(**다른 사람의 로그 수정**) | 공유 덱이 소유자 없이 남음 |
| 대상이 구독자 | 자기 행만 삭제. 공유 덱·다른 구독자 영향 없음 | 자기 행이 남음 |
| 대상의 공유 덱을 다른 사람이 개인 덱으로 가져감 | 가져간 사람의 개인 덱·카드는 그 사람 소유라 영향 없음. 가져오기 기록 행만 삭제 | 영향 없음 |

**현재 공개 상태와 과거 공개 이력은 다르다** (E-0 보정, 코드 확인):
- `shared_decks.visibility`는 지금 상태만 담는다. 값은 `public`·`unpublished` 두 가지다(`shared_deck_repository.py:406`, `:446`).
- 공개 이력을 기록하는 열·표는 없다. `updated_at`은 다른 변경에도 바뀌므로 이력이 아니다.
- 코드의 모든 생성 경로는 `visibility='public'`으로 넣는다(`shared_deck_repository.publish_deck` `:144`, `scripts/seed_jlpt_shared_decks.py:188`). 그래서 앱으로 만든 공유 덱은 **모두 한 번은 공개됐다**고 봐야 한다.
- 직접 DB 수정·이전 스크립트로 들어온 행은 이 추론이 맞는지 증명할 수 없다. **어떤 행도 "공개된 적 없음"으로 추정하지 않는다.**
- 구독·가져오기 행이 0이어도 "아무도 받아 가지 않았다"는 증명이 아니다. `import_count`는 계수이고, 공개 중에는 구독 없이 누구나 단어에 접근하고 평가할 수 있다(`shared_deck_word_access_allowed`).

공유 덱 소유자 처리 선택지(승인 항목 E-D3, **미승인**):
- **안 1(권장): 차단.** 공유 덱을 하나라도 가진 계정은 삭제 절차를 시작하지 않는다. 지금 상태가 `unpublished`이거나, 구독·가져오기 행이 0이거나, 이력을 확인할 수 없는 경우도 모두 포함한다. 다른 사람의 자료를 바꾸지 않는다. 대가는 그런 계정은 별도 결정 전까지 지울 수 없다는 것이다.
- 안 1-b: 다른 계정의 구독·진도·로그·가져오기 행이 하나도 없을 때만 공유 덱을 함께 지운다. 이 경우에도 "공개된 적 없음"은 가정하지 않는다. 공개 중 접근한 흔적이 없다는 것만 확인한다. 공개 중 누군가 내용을 보았을 가능성은 남는다.
- 안 2: 공유 덱도 지움(지금 PG CASCADE 그대로). 구독자가 그 덱 단어에 접근하지 못하고, 구독자 로그의 덱 표시가 사라진다.
- 안 3: 공유 덱을 소유자와 분리해 유지(소유권 이전·무소유 덱). 스키마·정책 변경이며 **이번에 구현하거나 승인된 것으로 기록하지 않는다.**
- 확인이 실패하면(행을 읽을 수 없음 등) 어느 안에서든 차단한다.

### 4-5. 서버 밖 잔존
- 읽기 세션, 기기별 학습 계획 선택값은 브라우저 저장소에 있다(`frontend/components/readingSessionStorage.ts` 등). 서버 절차로 지울 수 없다. 계정별로 분리돼 있어 다른 계정에 섞이지는 않는다(e2c07f8). 이 사실을 안내 문구 대상으로만 적는다.
- 백업: 삭제 전 백업에는 자료가 남는다. 백업 보존 기간은 운영 정책이며 이번 범위 밖이다(승인 항목에 메모).

### 4-6. 잔존 검사 (삭제 후, 같은 트랜잭션 안에서 커밋 전)
- 4-3 표의 각 표에서 `user_id = 대상` 행 0.
- `srs_migration_runs` 중 `scope_json` 최상위 `user_id = 대상` 0. 파싱 불가 행이 하나라도 있으면 "확인 불가"로 중단한다.
- `srs_migration_snapshots` 중 `user_id = 대상` 0. 다른 계정 실행에 붙은 대상 계정 snapshot도 0이어야 한다.
- 다른 계정 행 수: 삭제 전후 같음(표별 계정 제외 합계 비교). 안 1에서는 `lexeme_review_logs.shared_deck_id`의 NULL 수도 같아야 한다.
- 고아 검사: 대상 id를 가리키는 영수증·원장·표시·재시작 0.
- 결과 보고에는 표별 건수만 쓴다. 단어·뜻·예문·이메일은 쓰지 않는다.

### 4-7. 삭제 뒤 지연된 쓰기 (E-0 보정)

**재현** (세션 전용 합성 SQLite, TestClient. 제품 코드 무변경. 스크래치 스크립트는 실행 뒤 지웠다)
- 계정 삭제 절차가 없어서 4-3 순서를 합성 SQL로 흉내 냈다.
- 각 요청은 인증을 통과한 직후, 라우트의 쓰기 전에 계정이 지워지도록 했다. 이는 "이미 인증된 지연 요청"이다.
- 인증(`auth.get_current_user_*`)은 **별도 연결**에서 users 행 존재만 본다. 그 뒤 쓰기는 새 연결·새 트랜잭션에서 한다. 그 사이에 삭제가 커밋되면 쓰기가 그대로 진행된다.

| 쓰기 경로 | 계정 잠금 | 같은 트랜잭션의 계정 확인 | 삭제 뒤 결과(SQLite 실행) | 다시 생긴 행 |
| --- | --- | --- | --- | --- |
| `POST /vocab-items` | 없음 | 없음 | 200 | 카드 1, 기본 덱 1 |
| `POST /decks` | 없음 | 없음 | 200 | 덱 1 |
| `POST /custom-terms` | 없음 | 없음 | 200 | 용어 1 |
| `POST /shared-decks/{id}/import` | 없음 | 없음 | 200 | 구독 1 |
| `PATCH /shared-decks/{id}/words/{lexeme}/progress` | 없음 | 없음 | 200 | 진도 1 |
| `POST /shared-decks/{id}/words/{lexeme}/review`(legacy 형식) | 있음(SQLite는 BEGIN IMMEDIATE만, 계정 확인 없음) | 없음 | 200 | 진도 1, 구독 로그 1 |
| `POST /feedback/meaning` | 없음 | 없음 | 200 | 1 |

실행하지 않은 경로(코드로만 판단):
- 다시 만들 수 있음: `POST /decks/import-package`(덱·카드·용어 생성, 계정 확인 없음).
- 소유 확인으로 404일 것: 용어·덱 수정·삭제, 단어 삭제, `explain`.
- `POST /auth/register`는 새 id를 받는다. users id는 두 DB 모두 재사용되지 않는다(AUTOINCREMENT / IDENTITY). 그래서 지운 계정의 토큰이 새 계정에 붙지 않는다.

PG(코드상 추론, 미검증):
- 대부분의 표는 users FK가 있다. 지연 쓰기는 FK 위반 오류로 실패할 것으로 보인다(깨끗한 404가 아니라 서버 오류).
- 계정 잠금 경로는 `account_not_found` 404다.
- FK 검사는 users 행에 키 공유 잠금을 잡는다. 그래서 쓰기 트랜잭션이 먼저 행을 쓰면 삭제가 기다렸다가 CASCADE로 함께 지울 것으로 보인다.
- users FK가 없는 표(snapshot·실행)는 잠금을 잡는 이전 경로만 쓴다.
- **이 내용은 모두 E-2에서 실행으로 확인해야 한다.**

**불변식 D1**: 계정 삭제가 커밋된 뒤에는 어떤 경로도 그 계정 id로 행을 만들거나 고치지 못한다. 대상은 4-3의 모든 표와 실행 `scope_json`이고, 시간 제한이 없다.
- 지연 요청은 401·404·409 중 하나로 끝나고 쓰기 0이다. 응답에 내용을 담지 않는다.
- 삭제 직전에 커밋된 쓰기는 삭제가 함께 지운다(잔존 0).

**경계 방식 비교 (승인 항목 E-D11, 미승인)**

| | A. 유지보수 상태에서만 삭제 | B. 모든 쓰기가 같은 트랜잭션에서 계정 확인 |
| --- | --- | --- |
| 방법 | 그 계정(또는 전체)의 관련 쓰기를 막는 표시를 먼저 켠다. 진행 중 요청이 모두 끝난 것을 확인한 뒤 삭제한다. 삭제 뒤에는 인증이 401로 막는다 | 모든 쓰기가 계정 쓰기 잠금 안에서 users 행 존재를 확인한다. PG는 `FOR UPDATE`, SQLite는 `BEGIN IMMEDIATE` 뒤 SELECT. 삭제도 같은 잠금을 잡는다 |
| 적용 범위 | 차단 장치가 놓인 곳만. 여러 서버·워커가 있으면 표시는 DB에 있어야 한다 | 잠금·확인을 넣은 경로만. 위 표의 8개 이상이 바뀐다. 여러 연결로 나뉜 쓰기(`publish_deck`, `upsert_lexeme`·`add_word_to_shared_deck`는 자기 연결을 엶)는 구조를 바꿔야 한다 |
| 한계 | "진행 중 요청이 끝났다"를 증명해야 한다. 요청 시간 상한을 넘긴 요청, 표시를 읽기 전에 들어온 요청, 재시도가 남는다. 운영 절차 의존 | 새 쓰기 경로가 생길 때 빠뜨릴 수 있다(경로 목록 대조 테스트 필요). SQLite는 이미 전역 직렬, PG는 계정 단위 직렬 |
| 결정성 | 시간·절차에 기댄다 | 경합 순서와 관계없이 결정적 |
| 제품 코드 변경 | 차단 표시와 검사(작음) | 쓰기 경로 전반(큼) |

- 어느 쪽이든 삭제 직후와 진행 중 요청이 끝난 뒤에 4-6 잔존 검사를 **두 번** 한다.
- 권장 의견: 최종 상태는 B가 결정적이다. B가 없는 동안 운영자 삭제를 해야 한다면 A를 임시로 쓴다. **선택은 승인 대상이다.** 이번에 제품 코드는 고치지 않았다.

검사표 추가:
- 위 표의 모든 쓰기 경로에 대해 "인증 통과 → 삭제 커밋 → 쓰기"와 "쓰기 커밋 → 삭제" 두 순서를 실행한다.
- 결과는 상태 코드와 표별 잔존 건수로 기록한다. 두 DB 모두 한다(EXECUTION_PLAN P-ACC3).
- 경로 목록은 라우트 표에서 자동으로 뽑아 대조한다. 새 쓰기 라우트가 목록에 없으면 실패로 둔다.
