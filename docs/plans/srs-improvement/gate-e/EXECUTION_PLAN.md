#### 1-2-1. E-1 보정 설계 (2026-10-18, 구현 전 기록)

**결함 1. 외부 표를 소유로 넣음.**
- 1차 E-1은 단계 전후 카탈로그 차이와 표 이름만으로 소유를 정했다. 그래서 단계 중 다른 세션이 만든 표도 소유 목록과 TRUNCATE 대상에 들어갔다.
- 같은 이름으로 다시 만든 표도 구별하지 못했다.

**소유 증명 방식 (관리된 DDL + 생성 트랜잭션 + 객체 식별)**
1. 생성 단계는 harness가 연 **연결 하나, 트랜잭션 하나** 안에서만 실행한다. 단계 함수는 그 연결을 인자로 받는다. app의 `init_db`를 이 연결로 돌리는 연결 어댑터는 E-2에서 만든다.
2. 호출자는 단계 전에 **예상 생성 목록**(표 이름)을 낸다.
3. 같은 트랜잭션 안에서 다음을 차례로 한다.
   - 대상 확인, 표식 잠금, 표식 확인
   - 이 트랜잭션의 xid 조회
   - 사전 카탈로그(관계 oid 전체) 조회
   - 단계 실행
   - 사후 카탈로그(oid, 이름, 종류, 소속 표, `pg_class.xmin`) 조회
4. 새로 보인 관계는 아래를 **모두** 만족해야 소유로 인정한다.
   - 사전에 없던 oid다.
   - `pg_class` 행의 `xmin`이 이 트랜잭션의 xid다. 즉 PG 카탈로그가 "이 트랜잭션이 그 행을 넣었다"고 증언한다.
   - public 스키마의 표이고, 이름이 예상 목록에 있다.
   - 인덱스·시퀀스는 같은 조건을 만족하고, 소속 표가 소유 표다.
5. 위 조건을 하나라도 어기는 새 객체가 있으면 중단하고 **트랜잭션을 롤백**한다. 소유 목록은 바뀌지 않는다. 예를 들면 다른 세션이 커밋한 표(xmin이 다름), 예상 밖 이름, 예상했지만 생성되지 않은 표다.
   - READ COMMITTED에서는 다른 세션의 커밋이 다음 문장에 보이므로 사후 조회에서 잡힌다.
   - 롤백으로 이 실행의 DDL도 함께 사라진다(PG 트랜잭션 DDL). 외부 객체는 건드리지 않는다.
6. 커밋한 뒤에만 소유 목록에 **(이름, oid)** 를 기록한다. 표식 표의 oid도 시작할 때 기록한다.
7. reset·teardown·verify 전에 소유 표마다 같은 이름의 oid가 기록과 같은지 확인한다. 다르면(삭제 뒤 재생성) 중단하고 정리하지 않는다.
8. 단계가 실패하면 롤백만 한다. 실패 단계에서 무엇도 회수(소유 편입)하지 않는다.
9. 정리는 계속 소유 표 이름 목록과 RESTRICT만 쓴다. CASCADE·스키마 삭제는 쓰지 않는다.

**한계 (미검증)**
- 판정은 xmin 비교와 PG 트랜잭션 DDL이라는 PG 동작에 기대며, 가짜 연결로는 이 동작을 흉내 낸 것뿐이다. 실제 PG에서는 E-2에서 확인한다.
- 단계 안에서 저장점(하위 트랜잭션)을 쓰면 xid가 달라져 중단된다. 안전한 쪽으로 실패한다.
- 얼린(frozen) xmin은 일치하지 않으니 역시 중단된다.

**결함 2. 접속 전 안전 검사 우회.**

#### 1-2-2. 정리(reset·teardown)의 잠금·검증 순서 (2026-10-18, 구현 전 고정)

**결함**: 2차 E-1의 `_cleanup()`은 oid·소유 범위를 검사한 뒤 이름으로 TRUNCATE·DROP을 실행했다. 대상 표를 잠그지 않았다. 그래서 다음 순서가 가능했다.
1. 검사 통과
2. 다른 세션이 같은 이름의 새 표로 교체
3. 새 표를 정리하고 성공을 보고

검사를 더 해도 검사와 실행 사이의 틈은 남는다. 그래서 **잠금으로 막는다.**

**순서** (연결 하나, 트랜잭션 하나. 단계마다 실패하면 전체 롤백, 정리 SQL 0)
1. 연결 전 검사(1-2-1), 연결.
2. `SET LOCAL lock_timeout`. 모든 잠금 대기에 시간 제한을 둔다(기본 5초). 시간이 넘으면 오류가 나고 롤백한다.
3. 대상 확인: DB 이름·루프백 주소·포트.
4. 잠금 1: 표식 표 `ACCESS EXCLUSIVE`.
5. 잠금 2: **소유 목록에 있는 표만**, 이름 정렬 순서로, 한 문장 `LOCK TABLE ... IN ACCESS EXCLUSIVE MODE`로 잠근다. 순서를 고정하면 같은 장치끼리 교착이 생기지 않는다.
   - 소유 목록 밖 객체는 잠그지 않는다.
   - 이름이 없으면(삭제됨) 잠금이 실패해 롤백한다.
6. **잠금 뒤 새 카탈로그 조회**로 다시 확인한다.
   - 소유 표 이름마다 oid가 기록과 같은지
   - 표식 값·표식 oid
   - 소유 경계(외부 표·뷰·스키마·함수·타입·확장, 외부 인덱스, 경계를 넘는 FK)
   - 잠금 전에 교체된 표는 이 단계에서 oid가 달라 걸린다. 그 표를 잠깐 잠갔더라도 정리 SQL은 실행하지 않고 롤백한다.
7. 정리 SQL을 실행한다. 소유 표 이름 목록 + RESTRICT, CASCADE 없음. 같은 트랜잭션이다.
8. 커밋. 잠금은 커밋이나 롤백까지 유지된다(PG 표 잠금은 트랜잭션 끝에 풀림).

**보장하려는 것**
- 잠금을 얻은 뒤에는 다른 세션이 대상 표를 DROP·교체할 수 없다(PG의 DROP은 `ACCESS EXCLUSIVE`가 필요해 기다림). 그래서 6의 확인과 7의 실행 사이에 대상이 바뀌지 않는다.
- 정리를 마친 뒤 외부에서 만든 새 객체는 이번 정리 대상이 아니다. 다음 정리는 경계 검사에서 멈춘다.

**미검증**: 이름으로 잠금 대상을 정하는 동작, DROP이 잠금을 기다리는 동작, `lock_timeout`은 모두 PG 동작이다. 가짜 연결은 이를 흉내 낼 뿐이다. 실제 잠금 검증은 E-2 항목이다.

## 2. SQLite·PG 비교 검사표

같은 합성 시나리오를 두 DB에서 실행한다. 비교는 정규화한 전체 표(행 수, id 순서 관계, 상태 JSON, 날짜)와 HTTP 응답으로 한다.
- 결과는 **통과 / 불일치 / 검증 불가** 셋 중 하나다. 건너뜀은 검증 불가로 적는다.
- **불일치는 출시 차단**이다. SQLite 통과로 대신하지 않는다.

**정규화 규칙** (이것만 바꾸고 나머지는 그대로 비교한다)
- DB id는 시나리오가 붙인 논리 이름으로 바꾼다(사용자·덱·카드·로그 `<카드>#<n>`·실행 키). 참조도 이름으로 비교한다.
  - **(E-2a 보정) 이름은 시나리오가 실제로 만든 객체에만, DB 조회로 확인한 관계와 함께 등록한다.**
    - 사용자: 이메일로 한 행 확인.
    - 카드: 그 계정의 카드이고, 그 계정의 덱에 있는지 확인.
    - 덱: 소유 계정 확인.
    - 로그: 그 카드 id 아래 로그를 계정과 함께 읽어 카드·계정을 기록한다. 다른 계정의 로그가 섞여 있으면 오류다.
    - 실행: 계정 기록.
  - 등록되지 않은 id, 다른 종류, 다른 계정의 카드, 다른 카드나 다른 계정의 로그는 **비교 불가(`NotComparable`)로 실패**한다.
    - 종류가 없는 카드 id는 추측하지 않는다.
    - 한 객체에 두 이름, 한 이름에 두 객체도 비교 불가다.
    - 등장 순서로 이름을 붙이던 처리는 없앴다.
  - API 경로 안의 id도 같은 등록 규칙으로 바꾼다.
- **(E-2a 2차 보정) 참조 필드 타입 계약**: 라벨로 바꾸기 전에 필드마다 확인한다.
  | 필드 | 허용 | NULL |
  | --- | --- | --- |
  | `user_id`, `owner_user_id`, `vocab_item_id`, `lexeme_id`, `run_id`, `source_run_id`, `previous_boundary`, `new_boundary` | 등록된 정수 id | 불가 |
  | `card_id`, `card_ref`, `ref_id`, `item_id`, `id`(카드 종류가 있는 행만) | 그 종류로 등록된 정수 id | 불가 |
  | `deck_id`, `shared_deck_id`, `review_log_id`, `evidence_from_log_id` | 등록된 정수 id | 허용 |
  | `last_log_id` | 등록된 정수 id, 또는 0("로그 없음", `MigrationCandidate` 계약) | 불가 |
  - 문자열(숫자 문자열, 라벨과 같은 문자열 포함)·불리언·실수·객체·배열은 id가 아니라서 비교 불가다. JSON 문자열과 중첩 관측에도 같은 규칙을 적용한다.
  - 등록도 정수 id만 받는다.
  - 라벨은 전용 타입(`Ref`)이다. 그래서 같은 글자의 원시 문자열과 비교하면 다르게 나온다.
  - `request_id`·실행 키·일반 문자열은 참조가 아니며 그대로 비교한다.
- **(E-2a 보정) `sort_key`**: 큐 계약 `[버킷, 시각, 종류 순위, 덱 내 순서, 카드 id]`(`queue._key_json`)을 확인한다.
  - 길이 5, 각 자리 타입, 종류 순위 = 카드 종류의 `KIND_RANK`, 마지막 자리 = 그 항목의 카드 id.
  - 마지막 자리만 이름으로 바꾸고, 나머지는 그대로 비교한다.
  - 형식이 다르면 비교 불가다.
- 요청 id는 카드별 순번으로 만든다. 그래서 단계 일부만 실행해도 입력이 같다.
- 시각 문자열은 UTC ISO(마이크로초)로 쓴다. 시간대 없는 시각은 그대로 둔다(추정하지 않음).
- JSON 문자열은 파싱해 같은 규칙을 적용한다. 불리언은 0/1로 쓴다.
- id를 해시하는 값(카드·로그 지문, 요청 해시, 큐 커서)은 **있는지 여부만** 비교한다.
- 목록 순서, 버전, 개수, 상태 코드, 오류 코드, 권한, 완료 증거는 그대로 비교한다. 비교는 허용 오차 없이 모든 차이를 경로와 함께 보고한다.

## 3. 성능 측정 계획 (1천·1만 카드)

- **목적은 측정과 보고다.** 통과 기준 수치는 정하지 않는다. 결과를 본 뒤 사용자가 정한다.
- 자료: 합성 계정 1개에 개인 카드와 구독 카드를 1천·1만으로 만든다. 상태는 신규·학습·복습·연체를 섞고, 카드당 로그 0~20, 공유 덱 2개로 한다. 생성 규칙과 난수 시드를 기록에 남긴다. 실제 단어 내용은 쓰지 않는다.
- 측정 대상:
  - 학습 큐(개인·구독·혼합, 한도 기본값)
  - 오늘 새 단어·하루 목표 집계(`introduction_count`)
  - 예정 집계·통계 탭 조회
  - 학습 계획 진도
  - 평가 1건 쓰기(잠금 포함)
- 방법: 데이터를 덥힌 뒤 측정한다. 같은 요청을 N회(기록에 N 명시) 보내 중앙값과 95번째 값을 적는다. PG는 `EXPLAIN (ANALYZE, BUFFERS)`로 인덱스 사용을 기록한다. SQLite도 같은 시나리오를 측정해 함께 표로 둔다.
- 장소: 1-3의 성능용 빈 DB. 기존 `scripts/benchmark_lexeme_study_queue.py`(SQLite, 수치만)를 참고하되 운영 DB 경로는 쓰지 않는다.
- 보고 형식: 기기 사양, PG 버전, 카드 수, N, 중앙값, 95번째 값, 실행 계획 요약. "빠름·충분" 같은 판정은 쓰지 않는다.

## 4. 운영 전환 절차 초안 (실행은 별도 승인)

이 절차는 문서일 뿐이다. 운영 DB 접속·백업·적용은 각각 사용자의 명시 승인이 있어야 한다.

### 4-1. 준비
1. E 검사표 2절이 PG에서 전부 통과 또는 사용자가 명시적으로 받아들인 항목만 남음.
2. 배포할 코드와 커밋이 정해짐. 기본 모드는 legacy 그대로다(기본 FSRS 활성화 아님).
3. 운영 백업: Neon 분기·시점 복구 또는 `pg_dump` 중 하나로 한다. 방법은 사용자가 고른다. 백업이 실제로 복원되는지 별도 빈 DB에서 확인한다.

### 4-2. 사전 검사 (읽기 전용, 결과는 건수만)
- 실제 FK 목록이 예상과 같음(CONTRACT 1절).
- 시작 상태(`started`)인 이전 실행 0. 파싱 불가 `scope_json` 0.
- I3(시퀀스), I4(식별 검사), I5(로그 참조) 통과.
- 손상 시각·큰 수 사전 점검(U10-b·U11 도구의 dry run).
- 하나라도 실패하면 시작하지 않는다.

### 4-3. 적용 (명시 범위)
1. 스키마 업그레이드(`init_db`)와 D-P1 제약 변경. 자료 변경 없음. 실행 후 FK 목록을 다시 확인한다.
2. 앱 배포. 모든 계정이 legacy 모드인 상태에서 평가·삭제가 이전과 같은지 표본을 확인한다.
3. FSRS 이전은 **승인된 계정 id 목록만** 대상으로 한다. 계정마다 dry run → 결과 확인 → 적용 → 사후 검사 순서다. 한 번에 한 계정씩 한다.
4. 모드 전환(계정별 `srs_user_settings`)은 이전 적용과 분리해 승인된 계정에만 한다. 지금 이 값을 쓰는 제품 경로는 없다(운영 SQL만 가능). 되돌릴 때는 4-5 순서를 따른다.

### 4-4. 중단 조건 (하나라도 보이면 멈추고 보고)
- 계정 자료 혼입, 평가 중복·유실, 카드와 로그 불일치.
- 대량 due 앞당김, 신규 집계 불일치, 불변식 I1~I6 위반.
- PG와 SQLite 리허설 결과 불일치.
- 예상 밖 오류율 증가. 기준 수치는 3절 측정 뒤 사용자가 정한다.

### 4-5. 복구 (이후 평가 보존) — E-0 보정

**"모드만 legacy로 변경"은 학습 복구 방법이 아니다.** 합성 SQLite로 확인했다.
- FSRS 카드(개인 1, 구독 1)를 남긴 채 계정 모드만 legacy로 바꿨다.
- legacy 형식 평가(`rating`만)는 개인·구독 모두 **422 `review_upgrade_required`** 였다. 쓰기는 0이다.
  - 평가 분기는 계정 모드가 아니라 카드 엔진으로 정해진다(`vocab_repository.record_review`의 `srs_engine == "fsrs"` 분기 → `reviews.validate_request`).
- 버전을 붙인 FSRS 형식 요청은 200으로 FSRS 기록이 남았다.
- 통합 큐(`GET /study-queue`)는 legacy 계정에 409다(설계대로).
- 결론: 모드만 바꾸면 legacy 화면에서 그 카드들을 공부할 수 없다. 롤백 완료를 확인하기 전에는 legacy 학습이 된다고 보장하지 않는다.

복구 순서(설계, 실행은 별도 승인):
1. **중간 요청 차단**: 그 계정의 평가 쓰기를 막는다. 대상은 CONTRACT 4-7의 A 또는 B 방식과 같은 장치다(E-D12, 미승인). 막는 동안 들어온 요청은 409이고 쓰기 0이다. 화면은 다시 불러오기 안내를 보인다.
2. **dry run**: `rollback_plan` 대상과 결과를 미리 본다. 카드별로 아래 셋을 분류한다.
   - 되돌림: snapshot 있음, 기간 안.
   - 만료: 30일 기간 밖, `rollback_window_closed`/`unverifiable`.
   - 차단: 식별 불가 표시, 삭제됨, 권한 없음, 확인 불가.
3. **롤백 적용**(계정 쓰기 잠금 안에서 실행 단위). 전환 이후의 평가 로그는 남기고 legacy 상태를 복원한다. 삭제된 카드는 복구하지 않는다.
4. **완료 확인**: 계정의 모든 카드가 legacy 엔진인지 본다. 큐·통계가 롤백 전 로그 수를 유지하는지도 본다. 하나라도 FSRS 엔진이 남으면 5로 가지 않는다.
5. **계정 모드 legacy로 변경**. 4가 확인된 뒤에만 한다.
6. 차단 해제, 사후 검사(로그 수 불변, I1~I6, 잔존 FSRS 카드 0).

부분 실패·만료·차단 카드:
- 롤백이 중간에 실패하면 실행은 `failed`로 남는다. 이미 처리한 카드는 커밋된 상태 그대로다. 같은 실행을 재개하거나(U10-d의 재개 규칙과 기간 검사) 중단한다. 이 상태에서는 모드를 바꾸지 않는다.
- 만료·차단 카드가 하나라도 있으면 그 계정은 "legacy 복구 불가"다.
  - 모드를 FSRS로 유지하고 FSRS 형식으로 계속 학습하게 할지, 그 카드들을 어떻게 다룰지는 사용자 결정이다(E-D12).
  - 이후 평가를 지우거나 상태를 추정해 legacy로 만들지 않는다.
- 차단을 푼 뒤 늦게 도착한 요청: 카드 버전 CAS로 409 처리된다. 기록 추가 0.

그 밖의 복구 규칙:
- D-P1 제약은 되돌리지 않는다(CONTRACT 3-4). 이전 앱 버전도 FK 없이 동작하는지는 P-UP3에서 확인한다.
- 백업 복원은 기본 수단이 아니다. 복원 시점 이후의 실제 평가가 사라지기 때문이다. 쓴다면 별도 승인을 받는다. 그 전에 이후 평가 목록(로그 id 범위·건수)을 먼저 확보한다.
