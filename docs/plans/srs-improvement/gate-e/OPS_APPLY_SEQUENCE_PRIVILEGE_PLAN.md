# 최초 `apply` 쓰기 프로필의 시퀀스 USAGE 제거 계획·실행 기록 (2026-10-27 작성, 2026-10-27 마감)

**현재 상태(2026-10-27 마감)**: "PostgreSQL 18.6의 최초 `apply` 경로에서 두 시퀀스 USAGE 제거 검증" 범위를 마감했다. S1(제거 정책)·S2(최소 코드 변경·합성 회귀, 6절)·S3(실제 로컬 PG 재확인·R2, 7절)은 모두 승인·완료됐다. S3 집계는 a1·a2·s1 **3/3**이며 G0·사후 확인은 통과했지만 통과 수에 넣지 않았다. C12 2차 21/21·보완 2/2와 합산하지 않는다. 현재 계약(`srs_migrate.WRITE_PRIVILEGES`)에는 두 시퀀스 USAGE가 **없다**. 증거 목록은 `OPS_APPLY_REAL_PG_EVIDENCE.md`(실행 ID 20261027T195331).

작성 당시 상태: 계획만 있었고 S1~S3 모두 승인 전, 계약에는 두 USAGE가 있었다. 아래 0~5절은 작성 당시의 계획 문서이며, 그 안의 "승인 전" 표기는 작성 당시 상태다.

## 0. 대상 (이것뿐)

최초 `apply` 쓰기 프로필의 다음 두 권한:

- `("sequence", "public", "srs_migration_runs_id_seq", "", "USAGE")`
- `("sequence", "public", "srs_migration_snapshots_id_seq", "", "USAGE")`

`READ_PRIVILEGES`, 다른 쓰기 권한, 시퀀스 객체 목록, 소유·역할·스키마, 제품 동작은 바꾸지 않는다.

## 2. 변경 영향 (최소안)

### 2-1. 최소안
- `backend/scripts/srs_migrate.py`의 `WRITE_PRIVILEGES`에서 위 두 튜플만 뺀다. `READ_PRIVILEGES`와 그 밖 쓰기 권한(`users` 열 권한, 실행·snapshot 표 INSERT, 실행 표 열 UPDATE, 카드 열 UPDATE, 설정 표 SELECT·INSERT, 근거 표 SELECT 등)은 그대로다.
- 계약 문서 `OPS_MIGRATION_CLI_PLAN.md` 4-4-4 표의 "+ 시퀀스 USAGE" 두 곳을 같은 단위에서 고친다(정책 승인 뒤).

### 2-2. 지문·승인·manifest
- **기대 프로필 지문**: `_ops_provider.profile_fingerprint`(형식 `PROFILE_VERSION = jp-vocab-ops/profile/v2`)는 역할·객체·권한·search_path·기본 읽기 전용·격리·TLS를 정규화해 SHA-256을 낸다. 권한 집합이 줄면 **쓰기 프로필 지문 값만 바뀌고** 알고리즘은 그대로 쓸 수 있다. 값이 바뀐다는 이유로 형식 버전을 올리지 않는다. 읽기 프로필 지문은 읽기 권한이 그대로이므로 바뀌지 않는다. 객체 목록은 그대로다.
- **단계별 승인 프로필**: 적용 승인의 `apply` 단계(`access: write`)에 서명된 `profile`은 새 쓰기 지문이어야 한다. `dry_run` 단계·조회 승인의 읽기 프로필은 그대로다. 따라서 적용 승인은 새 지문으로 **다시 만들고 다시 서명**해야 한다.
- **manifest**: `srs_migrate.py` 바이트가 바뀌므로, 배포 manifest가 이 파일을 목록에 두는 경우 그 항목 해시와 manifest 지문이 바뀐다. 그러면 manifest를 다시 만들고 서명해야 하고, manifest 지문을 담은 **조회 승인과 적용 승인 모두** 다시 서명해야 한다. 운영 배포 manifest의 파일 구성은 아직 정해지지 않았으므로(운영 미구현), 이 계획은 "목록에 있으면 재생성·재서명"을 규칙으로 둔다. 합성 검사의 manifest(시험 파일 목록)는 영향이 없다.
- **작업 계획 지문**(2026-10-27 검토 정정): `_ops_approval.job_plan_fingerprint`(449행)의 입력은 DB 식별, **manifest 지문**, 도구, 계정, 작업 키, 작업 입력, 제품 지문, 계획 파일 해시다. 권한 제거 **자체**는 제품 지문·계획 파일 해시를 바꾸지 않는다. 그러나 작업 계획 지문은 manifest 지문까지 같을 때만 같다.
  - **합성 검사**: 시험 manifest(`test_ops_preflight.FILES` 등 시험 파일 목록)에는 `srs_migrate.py`가 없으므로 manifest 지문·작업 계획 지문은 바뀌지 않는다. 검사 편의를 위해 manifest 구성을 바꾸지 않는다.
  - **실제 배포**: 배포 manifest가 `srs_migrate.py`를 목록에 두면 그 바이트 변경으로 manifest 지문이 바뀌고, 따라서 작업 계획 지문을 **다시 계산**해야 한다. 순서: 새 manifest 생성·서명 → 새 manifest 지문으로 조회 승인 재생성·재서명(조회 승인의 `manifest`가 바뀜) → 새 조회 승인 바이트의 해시로 적용 승인의 `based_on` 결합을 다시 맞추고, 새 manifest 지문으로 계산한 작업 계획 지문을 적용 승인의 `plan`에 넣음 → 사전 검사의 `based_on`·`plan` 검증 경로로 결합을 확인한 뒤 적용 승인 재서명. 옛 조회 승인·옛 `plan`을 이어 쓰지 않는다.
- **옛 승인·옛 프로필**: 변환하지 않는다. 옛 쓰기 지문이 서명된 적용 승인은 새 기대 프로필과 맞지 않아 사전 검사(단계 프로필 = 연결 관측 프로필) 또는 공급자 판정에서 거부된다. 옛 권한(USAGE 있음) 그대로인 역할로 연결하면 새 기대 프로필보다 권한이 많으므로 `observed_privileges_excess`로 거부된다. 초과 권한을 허용하거나 옛 지문을 받아 주는 호환 경로는 만들지 않는다.

### 3-1. 실행기 `c1_sequences` 전환 범위 (S2에 포함, 2026-10-27 검토 보정)

현재 코드(`tests/_ops_apply_real.py`): `VARIANTS["c1_sequences"]`(142행대)는 적용 = 두 USAGE **회수**, 원복 = 재부여다. `c1_sequences()`(1190행대)는 회수 상태에서 CLI 실행의 기대 코드를 `observed_privileges_missing`(관측 후 거부)로 두고, 같은 회수 상태에서 `direct_apply()`로 제품 `apply_plan`을 원시 쓰기 연결(공급자 미경유)로 실행해 `direct_apply_without_usage`로 기록한다(판정 없음). 새 계약에서는 다음을 모두 바꾼다.

- 권한 문장: 적용 = 두 USAGE **부여**, 원복 = 두 USAGE 회수(계약 상태로 복귀).
- 기대 코드: 부여 상태 CLI 실행은 정확히 `observed_privileges_excess`(관측 후 거부, 쓰기 인계 0·업무 쓰기 0, 전체 DB 불변).
- 원복 확인: 원복 뒤 쓰기 역할 관측이 새 계약 프로필과 같음을 기록·판정한다.
- 기록 필드: `attidentity`(카탈로그 사실), 부여 상태 결과(코드·종료·역할별 계수), 원복 확인. 기존 `direct_apply_without_usage`는 기록하지 않는다(아래 탐침 처리).
- 적용 범위: 새 `check-seq`의 s1과 **기존 전체 `check`의 c1이 같은 함수**를 써서 새 계약과 일관되게 판정한다. 전체 21항목 목록과 의미는 유지하되 c1의 판정 내용만 새 계약으로 바뀐다.
- 과거 C12 기록(1·2차·보완)과 원시 증거는 수정하지 않는다. 2차 c1의 `observed_privileges_missing`·`direct_apply_without_usage: ok`는 옛 계약의 결과로 남는다.

**`direct_apply_without_usage` 탐침 처리 제안: 제거.** 근거:
- 이 탐침은 계약에 USAGE가 있던 시절에 "회수 상태에서도 제품 INSERT가 되는가"를 공급자 밖에서 확인하려고 만든 것이다(`direct_apply`는 `business_check`·`require_ours`·연결 후 확인만 거치고 공급자 관측·판정은 거치지 않음).
- 새 계약에서는 USAGE가 없는 상태가 **정상 상태**이므로, a2(그리고 `check-seq`의 a2)가 실제 CLI·공급자 경로로 같은 `INSERT ... RETURNING id`·snapshot `INSERT`를 이미 실행한다. 별도 원시 연결 탐침은 정보가 늘지 않고 공급자 우회 경로만 남긴다.
- 유지하면 c1의 새 실행 조건(부여 상태)에서 돌게 되어 이름("without usage")과 실제 조건이 어긋난다. 분리 유지(예: 계약 상태 직접 실행)도 a2와 중복이다.
- 따라서 S2에서 `direct_apply()` 호출과 기록 키를 c1에서 없앤다. 함수 자체를 지울지는 다른 사용처가 없음을 코드로 확인한 뒤 같은 단위에서 정한다. 프리셋의 `c1p` 검사 DB는 프리셋을 바꾸지 않으므로 남지만 쓰지 않게 되며, 그 사실을 실행기 주석과 계획에 적는다.

- 기존 `test_srs_migrate_apply_flow.py`의 가짜 카탈로그는 계약 상수로 권한을 만들므로 자동으로 따라온다. 객체 목록(`contract_objects`)의 두 시퀀스는 그대로 둔다.
- C12 2차 c1의 "회수 시 부족 권한 거부" 결과는 옛 계약의 기록으로 남기며, 새 계약의 검사는 위 표로 따로 둔다.

## 4. 실제 로컬 PG 재확인 계획(S3) — 작성 당시 계획, 2026-10-27 승인·실행 완료(7절)

### 4-1. 최소 실행 범위와 근거
- 변경은 쓰기 프로필의 시퀀스 USAGE 두 항목뿐이다. 영향받는 것은 (1) 쓰기 역할 관측·판정(모든 쓰기 연결), (2) 실행 행·snapshot INSERT(identity 기본값). 잠금(`users` 열 권한), 경합, 만료, 부분 커밋, d1 거부 경로는 이 두 권한에 의존하지 않으므로 **전체 21항목은 반복하지 않는다**.
- s1은 3-1절의 전환된 c1 함수를 그대로 쓴다(전체 `check`의 c1과 같은 판정).
- 고정 진입점 제안 `check-seq`(코드에 고정, 명령줄·환경 변수 선택 없음): G0 → a1(두 역할 관측이 새 계약 프로필과 정확히 같음, 쓰기 관측에 두 USAGE 없음) → a2(개인 3 + 구독 2 최초 적용: 실행 행 INSERT·`RETURNING id`·snapshot 5·커서·`completed`) → s1(관리자가 두 USAGE를 승인된 문장으로 일시 **부여** → CLI가 정확히 `observed_privileges_excess`·쓰기 인계 0·업무 쓰기 0 → 원복(회수) → 원복 뒤 관측이 새 계약과 같음) → 사후 확인(다른 계정·범위 밖 행 불변, 업무 세션·`idle in transaction` 0). 통과 수는 a1·a2·s1 세 개, G0와 사후 확인은 기록하되 제외. 이전 21/21·2/2와 합산하지 않는다.
- 관측값을 기대값으로 채택하지 않는다. 실패하면 권한을 넓혀 통과시키지 않고 중단·보고한다.
