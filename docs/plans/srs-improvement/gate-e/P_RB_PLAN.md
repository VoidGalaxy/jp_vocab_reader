## 0. 현재 구현 사실

- **롤백 경로.** `migration.rollback_plan(run_key, rollback_key, user_id, approved=True)`는 apply 실행 하나를 되돌린다. [사실]
  - 계정 쓰기 잠금(`begin_card_write`) 안의 **한 트랜잭션**이다.
  - 30일 기간(`ROLLBACK_WINDOW`, 시작 시각 기준)을 확인한다. 만료·확인 불가면 아무것도 쓰지 않고 거부한다(`rollback_window_closed`/`_unverifiable`).
  - 그 실행의 snapshot 카드만 다룬다. 카드별 결과는 `rolled_back` · `conflict` · `blocked:snapshot_incomplete` · `skipped:identity_unknown` · `missing_or_access_lost`다.
  - 이후 평가 로그 중 읽을 수 없는 것이 하나라도 있으면 전체를 거부한다. `rollback_history_mismatch`도 전체 거부다.
  - **예외가 나면 실행 트랜잭션 전체가 롤백된다.** 카드 변경, snapshot 기록, 그 트랜잭션에서 만든 실행 행이 모두 사라진다. 그래서 `failed` 행이 남지 않는다. EXECUTION_PLAN 4-5의 "failed로 남는다"는 코드와 다르므로 정정 대상이다.
  - **정상 반환에도 결과가 섞일 수 있다.** 한 실행 안에 `rolled_back`과 `blocked`·`conflict`·`skipped`·`missing_or_access_lost`가 함께 있을 수 있다. 그래도 롤백 실행은 `completed`, 원래 apply 실행은 `aborted`가 된다.
    - 따라서 `completed`는 "모든 카드가 되돌아갔다"는 뜻이 아니다.
    - 같은 `rollback_key`로 다시 부르면 저장된 요약만 돌려준다. 되돌리지 못한 카드는 다시 시도하지 않는다.
- **롤백이 지키는 것.** 이후 평가 로그를 지우지 않는다. 그 평가는 legacy 규칙(`compute_review_schedule`)으로 순서대로 반영한다. 카드 버전은 올라가고, 완료 이력(`first_completed_at` 등)과 과거 학습 표시는 보존한다. [사실]
- **운영 도구 없음.** `rollback_plan`을 부르는 곳은 테스트뿐이다. 운영자 CLI가 없다. [사실]
- **모드 변경 경로 없음.** 계정 모드(`srs_user_settings.srs_mode`)를 바꾸는 제품 경로는 없다. 운영 SQL로만 바꿀 수 있다. [사실]
- **평가 분기는 카드 엔진이 정한다.** 계정 모드가 아니다. [사실]
  - FSRS 카드가 남은 채 모드만 legacy로 바꾸면, legacy 형식 평가가 422 `review_upgrade_required`다(E-0 재현).
  - 통합 큐는 legacy 계정에 409다.
- **계정 쓰기 잠금.** E-5a 이후 모든 쓰기 경로가 같은 트랜잭션에서 계정 잠금을 잡고 계정 존재를 확인한다. [사실]
  - 이 잠금은 **트랜잭션 하나 동안만** 직렬화한다.
  - 그래서 여러 apply 실행의 롤백, 엔진 확인, 모드 변경처럼 여러 트랜잭션에 걸친 복구 전체를 막아 주지 않는다.
- **차단 장치 없음.** 계정별 쓰기 차단 표시도, 앱의 유지보수 상태도 없다. [사실]
- **오래된 요청.** [사실]
  - 롤백은 카드 버전을 올린다. 그래서 이전 버전을 든 FSRS 요청은 `card_version_conflict`(409)다.
  - 같은 `request_id` 재시도는 저장된 영수증을 그대로 돌려주고 쓰기가 없다.
- **전환 뒤 새 카드.** FSRS 모드에서 만든 개인 카드와 첫 구독 평가로 생긴 진도 행은 처음부터 FSRS다. snapshot이 없으므로 어떤 롤백도 이 카드를 legacy로 돌리지 않는다. [사실]

## 1. 권장 복구 순서 [제안]

1. **요청 차단·배출**: 그 계정의 쓰기를 막는다(2절). 차단 기록이 커밋된 뒤 진행 중이던 쓰기가 모두 끝났음을 확인한다.
2. **복구 가능성 사전 확인(읽기만, 차단 안에서 다시 실행)**: 차단 전에 한 번, 차단 뒤에 다시 한 번 한다. 다음 중 하나라도 있으면 **롤백을 시작하지 않는다**(승인된 방향).
   - 만료·확인 불가 실행
   - 읽을 수 없는 이후 로그
   - snapshot 없는 FSRS 카드(①: 강제 legacy 변환 없음)
   - 식별 불가 표시, snapshot 불완전, 엔진·버전 불일치(롤백 시 `conflict`가 될 카드)
   - 구독 해제로 접근을 잃은 진도 행

   사전 확인 통과는 롤백 결과를 보장하지 않는다. 확인과 실행 사이 상태가 바뀌지 않게 하는 것은 차단이다.

   함께 건수로만 기록할 것:
   - 계정의 apply 실행 목록과 각 실행의 기간 상태
   - snapshot 카드
   - snapshot 없는 FSRS 카드(개인·구독)
   - 식별 불가 표시, 읽을 수 없는 이후 로그
   - 전 표 행 수와 로그 수
3. **롤백**: apply 실행마다 `rollback_plan`을 부른다(최신 실행부터, 고정 `rollback_key`). 결과를 실행별로 기록한다. 정상 반환이라도 `rolled_back`이 아닌 카드가 하나라도 있으면 거기서 멈춘다.
4. **실행 후 전수 확인(읽기만)**:
   - 계정의 모든 개인 카드와 진도 행이 legacy인지 확인한다.
   - 실행별 요약에 `rolled_back` 외 결과가 없는지 확인한다.
   - 하나라도 어긋나면 5로 가지 않는다. 이 상태는 **복구되지 않은 상태**다. FSRS 모드를 유지해도 복구로 보지 않는다(3절).
5. **모드 변경**: 계정 잠금 안의 한 트랜잭션에서 FSRS 카드 0을 다시 확인하고, 그 트랜잭션에서 모드를 legacy로 바꾼다.
6. **차단 해제·사후 확인(운영은 읽기 전용)**: 다음을 확인한 뒤 차단을 푼다.
   - 로그 수가 2단계와 같다.
   - 완료 이력이 보존됐다.
   - I1~I6을 통과한다.
   - 남은 FSRS 카드가 0이다.
   - 큐·통계 읽기가 정상이다.
   - **운영 계정에는 시험 평가를 기록하지 않는다.** legacy 평가 성공 확인은 합성 검증(5절)에서만 한다.

각 단계가 실패하면 그 자리에서 멈춘다. 차단은 유지한다. 자동으로 다음 단계로 가거나 차단을 풀지 않는다.

## 2. 요청 차단 방식

| 방식 | 지금 가능 | 새 구현 | 장점 | 단점 |
| --- | --- | --- | --- | --- |
| **A. 운영 중단**(전체 서비스 정지 또는 배포 플랫폼의 유지보수 전환 후 복구) | 서버 정지는 앱 밖에서 가능. 앱 안의 유지보수 상태는 없음 | 진행 요청 배출 확인 절차. 앱 유지보수 응답이 필요하면 제품 변경 | 코드 변경 없이 모든 계정의 쓰기를 확실히 막음 | 모든 사용자가 멈춤. 배출 완료를 앱이 증명하지 못함(플랫폼 기록 의존) |
| **B. 계정별 차단 표시**(예: 차단 행. 모든 쓰기가 `begin_account_write` 직후 같은 트랜잭션에서 확인하고 409) | 없음 | 스키마(표 또는 값) + 잠금 함수 확인 + 운영 도구 | 다른 계정은 그대로 쓴다. 표시를 커밋하면 이후 모든 쓰기가 잠금 아래 거부되므로, 배출은 진행 중인 잠금 보유 트랜잭션이 끝나는 것으로 충분 | 제품 쓰기 경로 변경. 읽기는 계속되므로 화면이 잠시 이전 상태를 보일 수 있음 |

- 권장: **B(계정별 차단)를 구현해 쓴다.** 구현 전까지 운영 복구가 꼭 필요하면 A를 임시로 쓴다. [제안]
- 어느 쪽이든 계정 잠금만으로 복구 전체가 보호된다고 보지 않는다.

| 경우 | 지금 동작 [사실] | 처리 [제안] |
| --- | --- | --- |
| 30일 만료 | 그 실행 롤백 전체 거부 | 그 계정은 legacy 복구 불가. FSRS 모드를 유지하고 차단을 해제할지 사용자 결정 |

| 식별 불가 표시 | 그 카드 `skipped` | 그 카드가 FSRS로 남으면 4단계에서 멈춤 |
| snapshot 불완전 / 충돌 | `blocked` / `conflict` | 4단계에서 멈춤. 카드별로 보고 |
| 카드 삭제 | `missing`. 카드는 복구하지 않고 로그는 남음 | 남은 카드가 아니므로 모드 변경을 막지 않음 |
| 구독 해제 | `missing_or_access_lost`. 진도 행은 FSRS로 남음 | 남은 FSRS 행으로 보고 4단계에서 멈춤(다시 구독하면 422). 별도 결정 |
| 부분 실패(예외) | 그 실행 트랜잭션 전체가 롤백된다. 여러 실행에서는 앞 실행만 끝난 상태가 가능하다 | 차단을 유지한다. 원인을 보고하고 사람이 재개를 결정한다 |
| 부분 복구(정상 반환, 결과 섞임) | 실행은 `completed`, 원래 실행은 `aborted`. 남은 카드는 같은 키로 재시도되지 않음 | 차단을 유지한다. "복구됨"으로 판단하지 않는다. 처리 방법은 남은 결정이다 |

**snapshot 없는 전환 뒤 FSRS 카드** — **①이 승인됐다(2026-10-20)**:
- ① **강제로 legacy로 바꾸지 않는다.** 사전 확인에서 발견되면 롤백을 시작하지 않는다.
- 아래 ②·③은 기록용 대안이다(채택하지 않음).
- ② 평가 0건인 새 카드(버전 0, 로그 없음)만 legacy 기본값으로 초기화한다. 추정은 없지만 새 도구가 필요하다. 평가가 있는 카드가 하나라도 있으면 ①로 간다.
- ③ 평가가 있는 카드도 legacy 기본값에서 시작해, 자기 FSRS 로그를 롤백과 같은 legacy 규칙으로 순서대로 반영한다. 로그는 보존한다. 롤백과 같은 계산이지만 snapshot이 없어 시작 상태가 기록이 아닌 규칙값이다. 그래서 따로 승인이 필요하다.
- 제외: 백업 복원, 로그 삭제, 예약 추정, 무조건 legacy 변환.

## 4. 모드 변경 조건 [제안]

- 계정 잠금 안의 한 트랜잭션에서, 개인 카드와 진도 행 중 FSRS 엔진이 0일 때만 바꾼다.
- 3절에서 멈춘 계정은 모드를 바꾸지 않는다. 만료, 확인 불가, 남은 FSRS 행, 미완료 실행이 해당한다.
- 완료를 증명하지 못하면 모드 변경도, 차단 해제도 자동으로 하지 않는다. 사람이 결과를 보고 승인한다.

## 6. 승인 상태 (2026-10-20 갱신)

승인된 방향:
- B 계정별 쓰기 차단 구현 방향(계약은 `P_RB_BLOCK_CONTRACT.md`, 검토 대기)
- ① snapshot 없는 FSRS 카드는 강제로 legacy로 바꾸지 않음
- 사전 확인에서 복구 불가면 롤백을 시작하지 않음
- 부분 복구 상태를 "FSRS 유지"만으로 복구 완료로 보지 않음
- 운영 계정에 시험 평가 기록 금지

남은 결정:
1. 차단 장치 상세 계약
2. 복구 도구 구현
3. 실제 복구 실행
4. 부분 복구 상태(정상 반환에 결과가 섞인 경우)의 처리
5. 임시 A 사용 조건
6. EXECUTION_PLAN 4-5 "failed로 남음" 문구 정정
