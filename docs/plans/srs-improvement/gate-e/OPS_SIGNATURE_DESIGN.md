# 서명 도구·신뢰 루트 설계안 (4-0단위, 2026-10-21, 승인 대기)

상태: **설계안. 승인되지 않았다.** 읽기 전용 조사와 문서만 했다. 설치·다운로드·키 생성·서명·DB 접속은 없고, 사용자 `.ssh`·개인 키·비밀 보관소·인증 정보는 열지 않았다. 서명 방식의 최종 승인, 운영 키 관리, 운영 실행 승인이 아니다.
관련: `OPS_TOOL_SAFETY_CONTRACT.md` 4-2(신뢰 근거 후보 D), 4-5(합성·운영 경계), 5절(manifest), 1단위 `scripts/_ops_approval.py`의 `SignatureVerifier` 인터페이스.

## 1. 이 기기에서 확인한 것 (2026-10-21)

| 도구 | 위치·버전 | 확인한 근거 | 판단 |
| --- | --- | --- | --- |
| Windows OpenSSH `ssh-keygen` | `C:\WINDOWS\System32\OpenSSH\ssh-keygen.exe`, `OpenSSH_for_Windows_9.5p2, LibreSSL 3.8.2` | 사용법 출력에 `-Y sign`·`-Y verify -f allowed_signers -I identity -n namespace -s signature [-r krl] [-O option]`·`-Y find-principals`·`-Y check-novalidate`가 있다. 파일 소유자 `NT SERVICE\TrustedInstaller`, Authenticode `Valid`(서명자 Microsoft Windows) | **권장안** |
| Git for Windows `gpgv` | `C:\Program Files\Git\usr\bin\gpgv.exe`, GnuPG 2.4.9 | `--version`만 확인. Authenticode `NotSigned` | 대안 |
| Git for Windows `ssh-keygen` | `C:\Program Files\Git\usr\bin\ssh-keygen.exe` | 존재만 확인 | 쓰지 않음(같은 기능의 서명된 OS 사본이 있음) |
| `gpg`(PATH)·`openssl`·`signtool`·`minisign`·`signify`·`cosign` | 없음 | `Get-Command` | - |
| 파이썬 `cryptography`·`PyNaCl` 등 | backend 가상환경에 없음 | 설치 메타데이터 목록(import 없음) | 새 의존성이라 제외 |

공식 문서 근거: OpenBSD `ssh-keygen(1)` 매뉴얼(https://man.openbsd.org/ssh-keygen.1). `-Y verify`는 메시지를 표준 입력으로, 서명은 `-s` 파일로 받고, `-n` 이름 공간은 "다른 용도 사이의 서명 혼동을 막는" 용도다. 허용 서명자 파일은 키별 `namespaces=`·`valid-after=`·`valid-before=`를 지원하고, `-r`는 KRL 또는 공개 키 목록으로 폐기 키를 받으며, `-O verify-time=`으로 검증 시각을 지정한다. 성공은 종료 코드 0이라고만 적혀 있다(실패 코드 값은 문서화돼 있지 않음). 이 기기의 9.5p2 사용법 출력은 같은 옵션을 보인다. 실제 서명·검증은 실행하지 않았다.

## 2. 권장 방식과 대안

| | 권장: OS 기본 OpenSSH `ssh-keygen -Y` | 대안: Git의 `gpgv` |
| --- | --- | --- |
| 새 의존성 | 없음(Windows 구성 요소) | 없음(Git 설치에 포함) |
| 용도 분리 | 서명 자체에 이름 공간이 들어가고, 검증 때 `-n`이 다르면 실패. 허용 서명자 파일의 `namespaces=`로 키별 허용 용도도 제한 | 이름 공간 개념이 없다. 용도는 서명된 내용(`purpose`·`kind` 필드)으로만 구별 |
| 키 유효 기간·폐기 | `valid-after`/`valid-before`, `-r` 폐기 목록 | 키 만료·폐기 인증서(OpenPGP 방식) |
| 실행 파일 신뢰 | 고정 경로, TrustedInstaller 소유, Microsoft 서명 | 서명 없음, Git 업데이트에 따라 바뀜 |
| 사용자 서명 방법 | `ssh-keygen -Y sign`(사용자 기기에서, 보안 키 `ed25519-sk` 가능) | GnuPG 키 관리 필요 |

권장 이유: 새 의존성이 없고, 서명 용도 분리를 도구가 직접 강제하며, 검증 실행 파일이 OS 서명·소유로 고정돼 있다.

## 3. 서명 대상과 용도

- 승인 기록과 manifest는 각각 **시작 때 읽어 고정한 원본 바이트**에 분리 서명한다. 서명 파일은 대상마다 따로 둔다.
- 이름 공간 네 개(검증 때 정확히 일치해야 함):

| 대상 | 운영 | 합성 |
| --- | --- | --- |
| 승인 기록 | `jp-vocab-ops/v1/ops/approval` | `jp-vocab-ops/v1/synthetic/approval` |
| manifest | `jp-vocab-ops/v1/ops/manifest` | `jp-vocab-ops/v1/synthetic/manifest` |

- 다른 용도의 정상 서명을 가져와도 이름 공간이 달라 검증이 실패한다(승인 기록 서명을 manifest에, 합성 서명을 운영에). 허용 서명자 파일에서도 운영 키는 `namespaces="jp-vocab-ops/v1/ops/*"`, 합성 키는 합성 이름 공간만 허용한다.
- 1단위의 `signature_namespace(purpose)`(`jp-vocab-ops-approval:<용도>`)는 승인 기록만 다룬다. 구현 단위에서 이 표의 네 값으로 바꾸고 manifest용을 더한다(1단위 판정 규칙은 그대로).

## 4. 신뢰 루트 (제안만, 실제 설정 없음)

- 운영 검증 키는 사용자 소유다. 개인 키는 사용자 기기 밖으로 나오지 않고, 에이전트(Claude·Codex)·운영 도구·저장소·실행 계정은 접근하지 않는다.
- 위치 제안: 저장소 밖 고정 경로 `C:\ProgramData\jp-vocab-ops\trust\`
  - `allowed_signers.ops`(운영 서명자·허용 이름 공간·유효 기간), `revoked_keys.ops`(폐기 목록)
  - ACL: 관리자만 변경, 운영 도구 실행 계정은 읽기만. 경로는 코드 상수이고 명령줄·환경 변수·설정 파일로 바꿀 수 없다. 임의 공개 키를 인자로 주어 운영 신뢰를 바꾸는 경로는 두지 않는다.
- 등록·교체·폐기 절차(제안): 등록은 사용자가 관리자 권한으로 공개 키 한 줄을 추가하고 그 파일 지문을 기록. 교체는 새 키를 `valid-after`로 추가하고 옛 키에 `valid-before`를 걸어 겹치는 기간을 둔다. 폐기는 `revoked_keys.ops`에 추가. 모두 사용자가 직접 하며 도구는 쓰지 않는다.
- 합성 키는 시험이 만든 임시 폴더 안의 허용 서명자 파일로만 신뢰하고, 합성 이름 공간만 받는다. 운영 신뢰 목록에는 넣지 않는다. 운영 모드는 운영 경로 상수만 읽는다.
- **보류(현재 정책을 코드로 충족할 수 없음):**
  - 에이전트 비접근: 에이전트가 사용자와 같은 OS 계정에서 돌면, 사용자 계정 안의 개인 키 파일은 코드로 막을 수 없다. 하드웨어 보안 키(`ed25519-sk`)나 다른 기기에 개인 키를 두는 것은 사용자 결정이다.
  - ACL의 효과: 운영 도구 실행 계정이 그 폴더를 바꿀 수 있는 관리자이거나 사용자 본인 계정이면 ACL은 보호하지 못한다. 별도 비관리자 실행 계정 여부는 사용자 결정이다.

## 5. 검증 실행과 오류 (구현 단위에서 지킬 규칙)

- 시작 때 승인 기록·서명·manifest·manifest 서명·신뢰 루트 파일을 한 번 읽어 바이트로 고정한다(기존 계약 4-4). 검증은 고정한 바이트로 한다.
  - `ssh-keygen`은 메시지를 표준 입력으로 받으므로 고정한 원본 바이트를 그대로 넘긴다.
  - 서명·허용 서명자·폐기 목록은 파일 경로로만 받으므로, 고정한 바이트를 실행마다 새로 만든 전용 임시 폴더에 써서 넘기고 끝나면 지운다.
  - 한계: 같은 OS 계정의 다른 프로세스는 그 임시 파일을 바꿀 수 있다.
- 호출: 셸을 거치지 않고 인자 배열로 고정 경로 실행 파일을 부른다(`shell=False`, PATH 검색 없음). 인자는 `-Y verify -f <allowed_signers 사본> -I <서명자 이름> -n <이름 공간> -s <서명 사본> -r <폐기 목록 사본> -O verify-time=<주입된 UTC 시각>`이다. 환경은 최소 변수만 넘기고, 표준 출력·오류는 버린다(내용을 거부 사유로 쓰지 않음).
- 판정: 종료 코드 0만 성공이다. 0이 아닌 코드, 시간 초과(제한 시간은 구현 단위 결정), 실행 실패, 실행 파일 확인 실패, 이름 공간·키·서명자 불일치는 모두 고정 거부 코드로 끝내고 도구 원문을 담지 않는다.
- 실행 파일 신뢰 근거: 고정 경로, TrustedInstaller 소유와 실행 계정의 쓰기 권한 없음 확인, 버전 문자열 기록. Authenticode 확인을 실행 때마다 할지는 결정 항목이다(파이썬 표준 라이브러리로 하려면 Windows API 호출 코드가 필요).
- 최초 진입점: 운영 도구의 첫 파이썬 파일과 인터프리터는 manifest가 검사하기 **전에** 이미 실행된다. 이 부분의 신뢰는 배포 폴더의 쓰기 권한과 실행 계정 분리에 기대며, 서명으로 증명되지 않는다.
- 보호 범위: 같은 OS 계정이나 관리자는 실행 파일·임시 파일·신뢰 루트·파이썬 자체를 바꿀 수 있다. 이 설계는 실수와 다른 경로의 변조를 줄일 뿐 그런 공격자로부터 실행 환경 전체를 보호하지 않는다.

## 6. 다음 합성 구현 범위 (승인 뒤 별도 단위)

포함: 고정 경로 `ssh-keygen` 검증기(1단위 `SignatureVerifier` 구현), 네 이름 공간, 임시 시험 키. 제외: 운영 키·신뢰 루트 설치, 기존 CLI 연결, 운영 접속, 1~3단위 재설계.

| # | 사례 | 기대 | 종류 |
| --- | --- | --- | --- |
| 1 | 임시 시험 키로 서명한 합성 승인 기록·manifest | 통과 | 실제 서명(`-Y sign`·`-Y verify`, 시험 키만) |
| 2 | 서명 뒤 원본 1바이트 변조, 서명 파일 변조 | 거부 | 실제 서명 |
| 3 | 허용 목록에 없는 다른 시험 키의 서명 | 거부 | 실제 서명 |
| 4 | 승인 기록 서명을 manifest에, manifest 서명을 승인 기록에 | 거부 | 실제 서명 |
| 5 | 합성 서명을 운영 이름 공간으로 검증, 운영 모드가 합성 허용 목록을 읽으려 함 | 거부 | 실제 서명 / 판정 |
| 6 | 허용 서명자의 `namespaces=`·`valid-before`·폐기 목록에 걸린 키 | 거부 | 실제 서명 |
| 7 | 도구 0이 아닌 종료, 시간 초과, 실행 실패 | 고정 거부, 원문 없음 | 모킹 |
| 8 | 실행 파일 경로가 고정값이 아님, 명령줄·환경 변수로 신뢰 루트 지정 | 거부 | 판정 |
| 9 | 실행 파일·신뢰 루트에 실행 계정 쓰기 권한 | 거부 | OS 권한(실제 ACL 조작이 필요하면 별도 승인 전 미검증) |
| 10 | 시작 뒤 서명·신뢰 루트 파일 변경 | 고정한 바이트로만 판정 | 실제 파일 |

시험 키는 시험마다 임시 폴더에 만들고 지운다. 사용자 `.ssh`·에이전트·운영 경로는 건드리지 않는다.

## 7. 남은 사용자 결정 (승인 아님)
1. 서명 도구: 권장안(OS OpenSSH) 또는 대안(gpgv)
2. 사용자 서명 키의 보관 방식(하드웨어 보안 키 권장 여부)과 서명자 이름
3. 신뢰 루트 위치·ACL, 별도 비관리자 실행 계정 여부
4. 키 교체 겹침 기간과 폐기 절차
5. 검증 제한 시간, Authenticode 매번 확인 여부
