# E-4 읽기 전용 무결성 점검

2026-10-19. 사용자 지시 "다음 작업 실행"에 따라 E-4만 구현한다.
운영 접근, 실제 사용자 이전, 자동 복구, 계정 삭제, 기본 FSRS 활성화,
스테이징/커밋/푸시/병합 승인은 포함하지 않는다.

## 범위와 실행

- 모듈: `backend/app/srs/invariant_audit.py`. 앱에서는 호출하지 않는다.
- 도구: `backend/scripts/srs_invariant_audit.py`.
- SQLite: `python scripts/srs_invariant_audit.py --sqlite-db <명시한 합성.db>`.
  존재하는 `.db`만 URI `mode=ro`로 연다. 기본 경로, `.env`, 주변의
  `DATABASE_URL`을 사용하지 않는다. 파일/스키마를 생성하지 않는다.
- PostgreSQL: `--local-test-postgres`. 기존 E-1의 전용 URL 환경 변수와
  opt-in=1을 모두 요구한다. 기존 로컬 URL 보호 검사를 재사용하며,
  명시 포트와 테스트 DB 이름을 요구한다. 연결 자체의 DB 이름, 포트,
  루프백 주소를 읽기 전용 트랜잭션 안에서 다시 확인한다.
- PG 접속은 시작부터 기본 읽기 전용이다. search_path와 질의/잠금 제한을
  명시한다. 원격/운영 접속은 지원하지 않는다. 이 도구의 실제 자료 실행은
  이번 작업에 포함하지 않는다.
- 출력은 고정 상태/사유 코드와 건수만이다. 카드/계정 id, 단어, 뜻, 예문,
  로그 본문, 경로, 토큰, 연결 문자열, 원시 드라이버 오류는 출력하지 않는다.

## 검사 의미

| 항목 | 검사 |
| --- | --- |
| I1 | 카드 없는 개인 로그에 같은 계정·개인 카드 id의 삭제 원장이 있는지. 과거 예외를 자동 승인하지 않는다 |
| I2 | 살아 있는 개인 카드와 로그의 계정 일치. 구독 로그는 계정+lexeme 단위이며 개인 id와 섞지 않는다 |
| I3 | 개인 카드 시퀀스가 카드, 개인 로그, 영수증, snapshot, 실행 scope/summary, 원장, 식별 표시, 재시작 기록, 의미 피드백의 모든 개인 id 이상인지 |
| I4 | 기존 `identity.scan_identity` 발견분이 표시되어 있는지. 판정 불능과 손상 기록은 확인 불가이며 표시를 쓰지 않는다 |
| I5 | 영수증, snapshot의 last_log/baseline/restart, 카드 증거 경계, 재시작 기록의 로그가 같은 종류·계정·카드의 로그인지. 재시작의 근거 snapshot 연결도 확인한다 |
| I6 | 삭제 리허설 전후 원로그가 줄거나 바뀌지 않았는지 |
| I7 | 이력이 고정된 삭제 리허설에서 날짜별 계정 신규 수·확인 상태·하한·목표 잔여·달력 평가 수가 같은지 |

- I3는 SQLite AUTOINCREMENT도 확인한다. PG는 시퀀스 값을 읽을 뿐
  nextval/setval을 호출하지 않는다. 미사용 PG 시퀀스의 다음 id 충돌과
  증가량 이상도 판정한다. JSON 참조를 읽지 못하면 조용히 제외하지 않는다.
- snapshot 구조와 apply scope는 기존 U10의 값 계약 판정기를 재사용한다.
  손상 원값은 수정하거나 지우지 않는다.
- I4의 기존 탐지 한계는 그대로다. 미표시 혼합 id가 없음을 완전히
  증명하지 못하며 브라우저에만 남은 id도 조사하지 못한다.
- 구독 로그에 현재 progress가 없는 건수는 참고 건수다. 현재 공유 권한이나
  카드 생존만으로 과거 로그의 오류를 추정하지 않는다.

## 삭제 전후 증거와 상태

단독 CLI 실행은 한 시점만 보므로 I6/I7은 항상 `not_evaluated`다.
현재 로그가 적어 보이지 않는다는 이유로 과거 보존을 통과시키지 않는다.

합성 삭제 리허설에서는 같은 연결에서 새 읽기 전용 snapshot을 열어
`capture_deletion_baseline(at=고정_시각, days=명시한_서울_날짜들)`로 기준을
메모리에 둔다. snapshot을 끝낸 뒤 외부 리허설이 삭제를 실행하고, 같은
연결의 새 snapshot에서 `audit(baseline=기준)`로 비교한다. 도구는 삭제하지
않으며 기준의 디스크 저장/불러오기 기능도 제공하지 않는다.

- 계정 전체를 비교한다. 특정 덱/계획 범위, 남은 단어 수, 달력의 담은
  단어 수는 I7 불변 대상으로 넣지 않는다.
- 달력은 실제 통계 API가 쓰는 읽기 함수를 재사용한다.
- 원로그 전체 값의 해시와 참조를 메모리에서 비교한다. 새 평가, 로그 변경,
  계정 구성 변경이 있으면 I7은 삭제만의 비교로 볼 수 없어 미검증이다.
- 손상 시각 때문에 달력을 검산할 수 없으면 I7은 확인 불가다. I6의 실제
  로그 보존 검사는 별도로 유지한다.
- 이 비교가 날짜 범위 밖의 모든 과거 날짜나 삭제 이외 원인까지 증명하지는
  않는다. 평가/설정 변경을 통제한 삭제 전용 리허설이 전제다.

| 최종 상태 | 종료 코드 | 뜻 |
| --- | --- | --- |
| pass | 0 | 요청한 검사 전부 확인/통과 |
| fail | 1 | 위반 발견; 다른 확인 불가도 결과에 남음 |
| unknown / error | 2 | 근거·형식·연결·스키마 확인 불가, 또는 실행 거부 |
| partial | 3 | 정적 검사는 통과했지만 삭제 전후 증거 없음 |

## 읽기와 한계

- 모듈은 새 트랜잭션만 받는다. SQLite는 query_only+BEGIN, PG는 READ ONLY+
  REPEATABLE READ이며 성공해도 rollback한다. 외부의 진행 중 트랜잭션은
  인수하지 않는다. 임의 쓰기 SQL은 DB가 거부한다.
- PG 시퀀스는 MVCC 대상이 아니다. I3는 관측값이며 시퀀스 변경을 잠그지
  않는다. 출시 전 점검에는 쓰기·DDL이 중단된 운영 창이 필요하다.
- 최신 E-D13이 실제 스키마 변경 때의 기존 교착까지 해결한 것은 아니다.
  E-4는 그 잠금 정책을 바꾸지 않는다.
- 대규모 계정 성능 측정, 운영 사용 장치, 외부 기준 파일 형식은 범위 밖이다.
  현재 도구는 로컬 합성 DB 검증용이며 운영 전환 준비 완료를 뜻하지 않는다.
