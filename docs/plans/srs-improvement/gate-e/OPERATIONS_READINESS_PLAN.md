## 4. 다음 한 단위 제안: 운영 도구 안전 계약 (설계만)

산출물: `gate-e/OPS_TOOL_SAFETY_CONTRACT.md`(2026-10-21 설계안, 보정 3차 재검토 대기). 구현·DB 연결·권한 부여·백업·배포·이전 실행은 포함하지 않는다. 아래 4-1·4-2는 요약이고, 상세와 다음 구현 단위(공통 승인·대상 확인·연결 모듈, 합성 환경)는 그 문서에 있다. 보정 1차: 지문을 DB 식별·연결·권한·계획 셋으로 분리, A 결과 미확정 시 토큰 보존, 승인은 사용자 키 서명·실행 코드는 서명된 파일 manifest로 고정. 보정 2차: 하위 명령을 뺀 작업 계획 지문과 명령·역할 허용 목록 분리, manifest 공통 루트(배포 루트) 기준 허용 경로, 실제 PG 검증을 개별 질의·거부 [P]와 정상 종단 [P*]로 구분. 보정 3차: 승인을 조회 승인(계획 지문 없이 읽기 명령만, 지문 출력)과 적용 승인(조회 결과의 작업 계획 지문 고정, `based_on`으로 연결, 쓰기 명령 허용)으로 분리, 결과 미확정·만료 뒤 `status`는 기존 작업 키에 묶인 조회 승인.
로컬 안전 장치(`_local_test_postgres`, E-1 장치, `assert_safe_database_url`)를 제거하거나 완화해 운영 접속을 허용하는 안은 다루지 않는다. 운영 대상은 별도의 명시 경로로 설계한다.

### 4-1. 계약에 넣을 항목

| 항목 | 설계할 내용 |
| --- | --- |
| 대상 DB 확인 | 명시 대상 인자만(환경 기본값·`.env` 없음). 연결 전: 주소·DB 이름을 승인의 DB 식별값과, 역할을 그 단계에 승인된 역할과 대조. 연결마다: DB 식별 지문(역할 제외)과 단계별 연결·권한 지문을 따로 대조. 계약 3절 |
| 계정·카드 범위 | 승인된 계정 id 목록(파일 또는 인자), 계정 id 재입력, 카드 범위는 도구가 DB에서 계산하고 건수만 출력 |
| dry-run | 기본값. 읽기 전용 세션. 결과는 건수·코드·계획 지문만 |
| 계획 지문·재확인 | 작업 계획 지문(DB 식별·manifest·계정·작업 키·업무 입력·제품 지문, 하위 명령 제외)을 승인에 고정하고 단계마다 대조. 실행 명령·역할은 승인 허용 목록으로 따로 검사. 제품은 기존처럼 잠금 아래 자기 계획을 다시 계산해 다르면 쓰기 0으로 거부(제품 지문·API 변경 없음). 계약 3-3·3-5 |
| 잠금·실패 처리 | 계정 잠금 순서, 도구별 트랜잭션 단위(카드별·배치별·전체 한 트랜잭션), 실패 시 커밋 범위와 커서 보고. 재개 방법은 도구 계약을 따른다(아래 재실행·재개 행) |
| 로그 최소화 | 출력에 연결 문자열·이메일·단어·토큰 없음(기존 규칙). 실행 기록에는 실행자·시각·도구·대상 지문·결과 코드만 |
| 재실행·재개 | 도구마다 다르므로 일반화하지 않는다. 완료된 같은 요청의 결과 반환(전환 `already_applied`, P-RB B·completed 해제는 쓰기 0), 미완료 재개(전환은 같은 `run_key`·30일 창 안, 정리 3종은 `--after-id`·재실행), 실패 뒤 재시도(P-RB B는 같은 키·토큰, 삭제는 preview부터), 만료·확인 불가(창 판정 코드로 거부)를 구분한다. 결과 반환이 없는 경우도 있다(삭제 뒤 `account_not_found`, 무변경 해제 뒤 `recovery_grant_invalid`, verify는 증명 갱신 쓰기 가능). 표는 `OPS_TOOL_SAFETY_CONTRACT.md` 10절 |
| 권한 | 읽기 역할과 도구군별 쓰기 역할(사용자 방향), 단계별 역할은 승인 기록에 고정, 운영 역할은 슈퍼유저·생성 권한·표 소유 없음. 계약 8절 |
| 실행 전 금지 | 계약 정렬 전 도구(현재 `prb_recover.py` 포함)의 운영 실행 금지 명시 |

### 4-2. 필요한 정책 결정 (승인 아님)

| 결정 | 권장안 | 대안 | 영향 |
| --- | --- | --- | --- |
| 운영 대상 지정 방식 | 별도 운영 변수 + 명시 인자 + 승인 기록 지문 대조, 직접 엔드포인트·`verify-full`(사용자 방향) | 앱 `DATABASE_URL` 재사용 | 권장안은 실수 접속을 줄이나 설정이 늘어난다 |
| 읽기·쓰기 역할 분리 | 감사·dry-run은 읽기 전용 역할, 적용은 도구군별 쓰기 역할(사용자 방향) | 단일 역할 | 분리 시 운영 계정 관리가 늘어난다 |
| 승인 기록 형식·신뢰 | 작업마다 조회 승인과 적용 승인(각각 최대 24시간, 사용자 방향)을 사용자 보유 키로 분리 서명, 실행 코드는 서명된 파일 manifest로 고정(HEAD 비교 안 함). 도구의 자기 승인 경로 금지. 서명 도구·신뢰 루트 위치는 결정 항목 | 보호 경로 + 외부 저장소 기록 | 서명은 키 관리 필요. 임의 JSON의 `approved_by`·자체 해시는 승인을 증명하지 못한다. 계약 4·5절 |
| 실행 기록 보관 | 저장소 밖 운영 기록(비밀값 없음). 위치·보존 기간은 미정 | 저장소 안 문서 | 저장소 안은 공개·커밋 위험 |
| 백업 방법 | 결정은 4단위에서(Neon 분기·시점 복구 / `pg_dump`) | - | 복원 리허설 방식이 달라진다 |
| P-RB 토큰 | 복구 작업 1개(같은 키·차단)에 토큰 1개. `prepare` 직전 난수로 생성해 승인된 비밀 보관소에 저장·확인, 매 단계 숨김 입력으로 재입력, 해제와 그 재호출 결과를 기록한 뒤 폐기. 원문은 코드·DB·저장소·실행 기록·명령줄에 남기지 않음. 결과 미확정(응답 유실·연결 끊김·종료 코드만)이면 폐기하지 않고 같은 대상·키의 읽기 전용 `status`로 확인. 미커밋 확인 때만 폐기·새 작업. 승인 만료는 토큰 폐기·차단 해제가 아님. 분실·유출 처리는 결정 항목(우회·자동 재발급·강제 해제 없음) | 여러 작업에 같은 토큰 | 같은 토큰 재사용은 유출 시 피해 범위가 커진다. 명령마다 새 토큰은 현재 계약에서 A 뒤 단계를 모두 막아 쓸 수 없다. 상세는 `OPS_TOOL_SAFETY_CONTRACT.md` 9절 |
