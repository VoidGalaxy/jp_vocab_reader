# E-3 Codex 검토 (2026-10-18)

대상: codex/fsrs-srs-replacement 작업 트리, REPORT 11절.
제품 코드·정책·스키마 수정 없이 읽기와 합성 재현으로 검토했다.

## P1. 구독 평가와 전체 init_db의 교착 잔존 (기존 위험)

- 실제 로컬 PG 18.6, SSPI·제한 역할·기존 E-1/2 보호 장치를 사용했다.
- 옛 CASCADE 스키마에 합성 구독 카드와 첫 평가를 만들었다.
- 앱 init_db를 FK 제거 함수의 두 번째 카탈로그 조회 직후에 잠시 멈췄다. 이는 E-3 기존 개인 카드 경합 검사의 upgrade-first 위치와 같다.
- 별도 연결에서 구독 카드의 다음 평가를 시작했다. 실제 pg_locks에서 shared_deck_words의 미획득 RowShareLock을 관측한 뒤 업그레이드를 풀었다.
- 결과: 업그레이드 성공, **구독 평가는 DeadlockDetected**. 구독 로그는 첫 평가 1건 그대로였고, 두 번째 평가가 성공한 것으로 처리하지 않았다.
- 서버의 교착 기록:
  - 구독 평가는 user_word_progress 잠금을 가진 상태에서 구독 권한 확인의 shared_deck_words FOR SHARE를 기다린다.
  - 업그레이드는 앞선 create_postgres_tables의 shared_deck_words ALTER 잠금을 가진 상태에서 ensure_srs_schema의 user_word_progress ALTER를 기다린다.
- 위치: backend/app/database.py:1057, backend/app/srs/schema.py:237, backend/app/srs/storage.py:130.
- **대조군:** FK 제거 함수만 비활성화하고 create_postgres_tables 뒤 같은 위치에서 멈춘 경우에도 같은 교착이 재현됐다. 따라서 E-3의 새 FK 제거 함수가 처음 만든 회귀라고 보고하지 않는다. 이전 전체 소스 체크아웃을 실행한 비교는 아니다.
- E-3의 개인 카드 잠금 순서 보정은 이 경로까지 보호하지 않는다. REPORT의 단순한 "다른 ALTER의 잠금 시간 제한 없음"과 구분해, 기존 출시 차단 위험과 구독 경합 회귀로 추적해야 한다. 범위를 넓힌 제품 보정은 이번 검토에서 하지 않았다.

## P2. 경합 검사의 거짓 통과 가능성

### 삭제 먼저일 때 임의 예외 허용
- backend/tests/test_srs_e3_fk_real.py:361은 평가 결과가 error이면 예외 종류와 관계없이 통과한다.
- check_outcome에 다른 최종 관측은 정상으로 두고 RuntimeError를 넣자 검사가 통과했다. PG 접속 없는 검사 함수 재현이다.
- 실제 저장소의 카드 없음 계약은 record_review의 정상 None 반환이다. 따라서 이 시나리오는 정상 반환과 None을 명시적으로 검사하고, RuntimeError·드라이버 오류·교착 등은 실패시켜야 한다. HTTP 계층 검사는 별도로 404를 확인한다.

### 잠금 관측 대상 미지정
- 같은 파일 275행은 클러스터 전체의 NOT granted 개수만 센다.
- 이 값만으로는 두 번째 작업이 첫 번째 작업을 기다린다고 증명하지 못한다. 다른 연결·DB의 잠금 대기도 합격 근거가 될 수 있다.
- 작업별 backend PID, 대상 DB·관계, pg_blocking_pids 관계를 기록해 두 번째 작업이 첫 번째 작업 때문에 대기하는지 확인해야 한다.
- 관련 없는 대기만 존재하거나 예상 밖 작업 예외가 생겼을 때 검사가 실패하는 부정 대조도 필요하다.
