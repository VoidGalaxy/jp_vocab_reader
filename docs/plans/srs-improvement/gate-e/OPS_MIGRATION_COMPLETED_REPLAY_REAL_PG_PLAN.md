# 완료 결과 재조회 실제 로컬 PG 검증 계획 (2026-10-30, 제안·실행 승인 전)

**상태**: CR-S1 합성 구현 마감 뒤 Codex가 작성한 준비 설계다. 이 문서는 대상 등록·시험 코드·PG 준비·접속·키 생성·권한 변경·관리자 자료 변경·증거 작업을 승인하지 않는다. C1~C5는 `OPS_MIGRATION_COMPLETED_REPLAY_PLAN.md` 9절 확정 정책을 그대로 참조한다. 새로운 제품 정책이나 상태 보정 기능은 만들지 않는다.

## 1. 목적과 증거 구분

- 실제 CLI `run_status` → ProductConnector → 어댑터·공급자 → `read_status`·`judge_status`로 완료 결과를 재조회한다. 제품 `apply_plan`을 재조회에 쓰지 않는다.
- 합성 SQLite 9개와 시계·공급자 검사 12개는 PG 격리·행 잠금 증거가 아니다. 과거 C12·RS4·PG67·PG68 결과와 새 집계를 합산하지 않는다.
- 서버에서 확인할 것: 실제 읽기 문장 수용, 읽기 전용·REPEATABLE READ 설정, 대상 행 비차단, 같은 실행의 단일 스냅숏, 업무 쓰기·논리 행·시퀀스 무변경.
- 서명·시계·대상 거부는 CLI/공급자 판정이며 서버 오류라고 부르지 않는다. 시각 경계는 주입한 시험 시계로 구분하고 OS 시각은 바꾸지 않는다.

## 3. 관문과 자료 준비

- G0: 대상·OID·nonce·TLS·역할·객체·권한·합성 자료와 DB 목록을 대조한다. 기대 프로필은 계약 상수에서 고정하며 관측값으로 기대값을 만들지 않는다.
- G1: `check-completed` 실행 안에서 만든 시험 전용 키로 실제 dry-run·최초 apply를 수행해 완료 실행을 만든다. 키·서명·근거는 그 실행에만 묶는다. 정상 두 카드 실행, blocked/conflict 실행을 카드 키로 구별한다. 다른 계정과 범위 밖 자료를 포함한다.
- 손상·커서 끝·쓰기 차단 자료는 승인된 관리 변경으로만 만든다. `failed`나 장애를 실제로 겪은 것처럼 서술하지 않는다. 변경 전후 원문·행 키·영향 행 수를 시험 메모리에 고정하고, 증거에는 허용된 필드·해시만 남긴다.
- G1 직후 DB 전체 논리 행·필요 시퀀스 값과 대상 실행 필드를 독립 관리 조회로 고정한다. 각 사례의 정상 기대값은 계약·G1 계획으로 계산한다. 관리자 변경이 있는 검사는 그 변경의 귀속을 분리한다.

- 공통: 조회 업무 문장에 INSERT·UPDATE·DELETE·시퀀스 호출 없음, 카드·실행·snapshot·다른 계정·설정·로그의 논리 내용 동일. 읽기 트랜잭션의 정상 COMMIT은 쓰기 커밋 증거로 세지 않는다. 계수의 생성·인계·업무 문장·업무 쓰기·커밋을 각각 기록한다.
- 상태 SELECT는 실제 본문을 실행한다. 설정 탐침은 두 SET TRANSACTION 사이 또는 첫 조회 전에 넣지 않는다. 실제 조회가 정상 종료한 뒤 원래 종료 전, 기존 RS4에서 확인한 저장점 탐침 규칙으로 `transaction_isolation`·`transaction_read_only`를 읽는다. 탐침 오류는 장치 결함이며 제품 예외보다 우선하지 않는다.
- G0·G1·사후 확인은 통과 수에서 뺀다. 필수 하위 사례가 모두 저장·재읽기돼야 상위 1개를 통과로 센다. 예상한 음성 거부는 통과이고, 목표 단계 이전의 다른 거부는 실패다.

## 5. P8·P9 중첩과 원복

- `read_status`가 실행 행 SELECT를 정상 완료한 뒤 snapshot SELECT를 보내기 전에만 정지한다. 래퍼는 원래 반환 객체를 그대로 넘기며 기록은 고정 사본으로 남긴다. 정지점 시간 초과·미도달은 장치 결함이다.
- P8은 논리 동일값 UPDATE를 고정 키로 한 행씩 수행한다. 읽기 정지점이 명시적으로 보유 중일 때 관리자 COMMIT 완료를 요구한다. 시간 지연·pg_locks 빈 결과만으로 비차단을 추정하지 않는다. 모든 relation 잠금·DDL에 대한 비차단으로 확대하지 않는다.
- P9는 같은 완료 실행의 둘째 결과 applied를 conflict로 바꾸고 그 카드 snapshot을 제거하는 하나의 관리자 트랜잭션이다. 원래·변경 후 상태가 모두 judge_status의 정상 completed 조건을 충족함을 관리 자료로 먼저 확인한다. 제품 카드 자체의 내용을 변경하지 않는다.
- 정상 RR 읽기, 새 읽기, READ COMMITTED 변형은 각각 같은 원본에서 시작하도록 명시적 원복한다. 지워진 snapshot은 원래 id와 모든 열을 그대로 복원하고, 요약 원문·대상 행 수·시퀀스 값까지 기준선과 대조한다. 이 시험 원복은 제품 상태 보정 기능이 아니다.
- 본 검사 전체에서 첫 실패 시 후속 중첩은 실행하지 않는다. 다만 소유한 정지점 해제·스레드 종료·연결 정리는 항상 시도한다. 해제 → 제한 join → 이번 소유 연결만 닫기 → 제한 재join·is_alive 확인이다. 종료 미확인·짝 없는 조정/최종 정리 시작 기록이면 check와 별도 cleanup 모두 파괴적 R2를 거부한다.
- 최초 업무 예외·중단의 객체·SystemExit 값을 보존하고 정리 오류가 덮지 않게 한다. 비밀 원문·예외 클래스 이름 대신 고정 단계 코드만 기록한다. 다른 프로세스 종료·스레드 강제 종료·무한 재시도는 없다.

## 6. 사후 확인·증거·정리

- 관리자 변경 원복, 조회에 귀속되는 쓰기 0, 다른 계정·범위 밖 자료 불변, 업무 세션·idle in transaction 0, 정지점 해제·스레드 종료를 대조한다. 실제 연결·서버 PID와 대상 기록이 일치할 때만 R2 대상에 포함한다.
- 첫 실패·준비 실패·장치 결함·기록 실패는 모두 종료 1, 나머지는 미실행이다. 10개·관문·사후 확인 모두 성공하고 저장·재읽기됐을 때만 종료 0이다. 원하는 결과를 얻기 위한 현장 수정·재실행은 없다.
- `record.json`, `target.json`, `server.log`, 준비·검사·정리 출력의 목록·크기·전체 SHA-256을 남긴다. 정리 전 record 사본에는 정리 결과가 없으므로 cleanup 출력의 역할과 한계를 분리한다.
- 승인된 경우에만 기존 로컬 보관 정책에 따라 새 위치로 덮어쓰기 없이 복사·대조하고 custody를 작성한다. 기존 증거·ACL·임시 원본은 삭제하지 않는다. 독립 사본 보류·단일 C 드라이브 위험·진본성 한계는 유지한다.
