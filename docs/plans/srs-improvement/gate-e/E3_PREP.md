# E-3 사전 검토: 개인 카드 삭제와 평가 로그 (E-D1)

작성 2026-10-18 · HEAD `e2c07f8`(커밋 없음) · 상태: 작성 당시 E-D1 미승인. **2026-10-18 A안 승인(APPROVAL_REQUEST 1절), 구현 결과는 REPORT 11절.**
제품 코드·스키마는 바꾸지 않았다. 추가한 것은 재현 테스트(`backend/tests/test_srs_e3_delete.py`)와 이 문서뿐이다.

## 1. FK가 생기는 경로 (코드·이력)
- 새 PG DB: `app/database.py:1021`, `create_postgres_tables()`의 `review_logs` 정의.
  `vocab_item_id INTEGER NOT NULL REFERENCES vocab_items(id) ON DELETE CASCADE`
- 호출 경로:
  - `init_db → initialize_database → ensure_schema` PG 분기(`app/database.py:288~295`)
  - `scripts/migrate_sqlite_to_postgres.py:301`(SQLite→PG 이전 스크립트). 같은 함수를 쓴다.
- 이전 PG 스키마: PG `review_logs` 표는 커밋 `d7ef5dc`(2026-07-09)에서 **이 FK와 함께 처음** 생겼다(`git log -S`). 그 뒤 이 줄은 바뀌지 않았고, FK를 더하거나 빼는 ALTER는 어디에도 없다.
  - `CREATE TABLE IF NOT EXISTS`는 기존 표를 바꾸지 않는다. 따라서 그 이후 만들어진 모든 PG DB(운영 포함)는 같은 FK를 가진 것으로 **추정한다**. 운영 카탈로그는 보지 않았다.
- SQLite: `review_logs`에 FOREIGN KEY가 없다(`PRAGMA foreign_key_list` 0행, 재현에서 확인).
- `app/srs/schema.py`는 로그 표에 열만 더한다(`LOG_COLUMNS`). FK와는 무관하다.

## 2. 실제 PG 재현 (로컬 18.6, `jp_vocab_test_e`, 제한 역할, E-1 장치·E-2 어댑터 보호 경유)

**카탈로그** (`pg_constraint`를 열·참조·삭제 동작으로 읽음, 이름으로 판단하지 않음)
| 열 | 참조 | ON DELETE | 검증됨 | 지연 가능 |
| --- | --- | --- | --- | --- |
| `review_logs.user_id` | `users(id)` | CASCADE | 예 | 아니요 |
| `review_logs.vocab_item_id` | `vocab_items(id)` | **CASCADE** | 예 | 아니요 |

카드 FK는 정확히 1개였다(로컬 이름 `review_logs_vocab_item_id_fkey`, 판정에는 쓰지 않음).

**합성 시나리오**
- 계정 A(FSRS)의 카드:
  - 일반 새 카드 n1·n2·b1·b2. b1·b2는 별도 덱 `e3-bulk`에 있다.
  - 과거 학습 표시 카드 h1. 로그는 없고 legacy 정답 수만 있다. 이전 결과는 `blocked`였고, 표시는 `before_tracking`·`2026-05-27`이다.
  - legacy 로그를 이전한 카드 m1. snapshot이 1개 있다.
- 평가는 이틀 전(05-30)과 오늘(06-01)에 했다. 영수증과 구독 단어 평가 1건도 있다.
- 계정 B: 카드 x1에 평가 1건.
- 삭제 순서: n1 → h1 → m1 단어 삭제, 그다음 덱 `e3-bulk` 일괄 삭제.

| 관측(계정 A) | 삭제 전 | n1 삭제 | h1 삭제 | m1 삭제 | 덱 삭제 | SQLite(모든 단계) |
| --- | --- | --- | --- | --- | --- | --- |
| 개인 로그 수 | 7 | **6** | 6 | **4** | **2** | 7 |
| 오늘 새 단어(서울 06-01) | 3 exact | **2** | 2 | 2 | **1** | 3 |
| 이틀 전 새 단어(05-30) | 2 exact | 2 | 2 | 2 | **1** | 2 |
| 하루 목표 잔여(목표 20) | 17 | **18** | 18 | 18 | **19** | 17 |
| 기록 달력 평가 수(05-24 / 05-30 / 06-01) | 1 / 3 / 4 | 1 / 3 / **3** | 같음 | **0** / **2** / 3 | 0 / **1** / **2** | 1 / 3 / 4 |
| 삭제 원장(학습 이력 증거) | 0 | n1 | +h1 `before_tracking` 05-27 | +m1 `logged` | +b1·b2 | PG와 같음 |
| 개인 영수증 6건 중 사라진 로그를 가리키는 수 | 0 | 1 | 1 | 2 | **4** | 0 |
| snapshot `last_log_id`가 사라진 로그 | 0 | 0 | 0 | **m1** | m1 | 0 |
| 계정 B 로그 / A의 구독 로그 | 1 / 1 | 같음 | 같음 | 같음 | 같음 | 같음 |
| 식별 검사 발견(A) | 0 | 0 | 0 | 0 | 0 | 0 |

- 기록 달력의 "저장한 단어 수"는 남아 있는 카드에서 세므로 **두 DB 모두** 카드 삭제와 함께 준다. 지금 설계이며 로그 보존과는 별개다.
- 과거 학습 표시 카드 h1은 로그가 없어서 CASCADE로 잃는 것이 없다. 표시는 두 DB 모두 원장 증거로 남았다(U4).
- 일반 새 카드는 로그를 잃는다. 그래서 그 카드가 오늘 새 단어로 셌던 몫이 빠지고, 하루 목표가 다시 열린다(재소비).
- 다른 계정 로그와 구독 로그는 바뀌지 않았다.
- 판정: PG와 SQLite의 관측 비교는 **불일치**다. 테스트에는 `expectedFailure`로 남겼다. E-D1이 미승인이라 기대값을 바꾸지 않았다.

## 4. A안 구현 준비 (적용하지 않음)

**변경 지점**
1. `backend/app/database.py:1021`: 새 DB 정의에서 `REFERENCES vocab_items(id) ON DELETE CASCADE`만 뺀다. `vocab_item_id INTEGER NOT NULL`, `user_id` FK CASCADE, 로그 id, 인덱스 `idx_review_logs_item`은 그대로 둔다.
2. 기존 DB 업그레이드: 새 함수 하나(예: `app/srs/schema.py`의 `drop_personal_log_card_fk(connection)`).
   - PG 분기에서 `create_postgres_tables` 뒤, 같은 `ensure_schema` 트랜잭션 안에서 부른다.
   - 카탈로그에서 `public.review_logs`의 FK 중 **열 집합에 `vocab_item_id`를 포함하는 것**을 모두 찾는다.
     - 0개: 아무것도 안 한다(멱등, 새 DB·재실행).
     - 정확히 1개이고 모양이 `(vocab_item_id) → public.vocab_items(id)` 단일 열이며 지연 불가: 카탈로그에서 읽은 이름을 식별자로 인용해 `ALTER TABLE public.review_logs DROP CONSTRAINT ...`.
     - 2개 이상이거나 다른 모양(다중 열, 다른 참조 표·열, 지연 가능 등): **쓰기 전에** 오류로 중단한다. 트랜잭션 전체가 롤백된다.
   - 삭제 동작(CASCADE·NO ACTION 등)은 판정에 쓰지 않고 기록만 한다. 위 모양이면 모두 같은 처리다.
   - FK를 다시 만들지 않는다. 되돌리기 경로도 두지 않는다(고아 로그가 생긴 뒤에는 다시 붙일 수 없다).
3. SQLite 분기: 변경 없음(FK 없음).
4. 하지 않는 것:
   - SET NULL, 로그 삭제·합성·재연결, 삭제 카드 복원
   - 계정 삭제(D-P5), 구독 lexeme FK(E-D7)
   - `meaning_feedback`

**위험**
- FK가 막던 "없는 카드에 로그 쓰기"를 더는 DB가 막지 않는다. 쓰기 경로는 계정 잠금 안에서 카드를 읽고 쓰므로 실제 위험은 경로 밖 쓰기다. I1·I2 점검으로 감시한다.
- `DROP CONSTRAINT`는 `review_logs`와 `vocab_items`에 강한 잠금을 잠깐 잡는다. 앱 시작 시 `init_db`가 실행되므로 운영 적용 때 잠금 대기가 생길 수 있다. 실행 창과 `lock_timeout`이 필요하다.
- 고아 로그가 생긴 뒤에는 기존 FK를 그대로 복구할 수 없다. 그 복구를 위해 로그를 지우거나 카드 복원·참조 재연결을 하지 않는다. 앱 코드는 이전 버전으로 되돌릴 수 있으며, FK 없는 DB에서 도는지 확인해야 한다(P-UP3, CONTRACT 3-4).
- 운영 DB의 실제 카탈로그는 보지 않았다. 적용 전 읽기 전용 점검이 필요하다(운영 접속은 별도 승인).
