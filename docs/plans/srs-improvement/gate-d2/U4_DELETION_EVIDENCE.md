## 1. 재현 (세션 전용 SQLite, 기존 코드 그대로)

조건:

- 과거 학습 카드: 로그 0건, `last_reviewed_at` = 2026-10-05 서울 정오(K), 정답 수 2.

| A. `before_tracking` + 오늘 첫 FSRS 로그 | 단어 삭제 | 오늘 | 신규 exact 0, 잔여 목표 20 | **exact 1, 잔여 목표 19** |

부수 발견: 학습 이력 표시로 생긴 확인 불가도 큐의 `new_blocked_reason`은 `review_time_unreadable`로 나온다(이유 값이 정확하지 않음). 화면은 이 값으로 "신규 확인 불가" 안내를 보이므로 사용자 문구는 맞다. 이유 값을 나누려면 API 계약 변경이라 이번에는 바꾸지 않았다(승인 항목 E7).

## 2. 최소 보존 계약 (승인 전 초안)

- **카드 삭제 ≠ 학습 기록 삭제.**
  - 카드(내용·예약·분류)는 지운다.
  - 계정 전체 신규 집계에 쓰인 학습 사실은 남긴다. 원로그가 이미 남는 것과 같은 원칙이다.
- **남기는 것은 다섯 가지뿐**: 계정, 카드 종류, 카드 식별자, 학습 이력 상태, 기준일. 삭제 시각은 U3 원장에 이미 있다.
- **남기지 않는 것**: 단어·읽기·뜻·예문·원문·토큰·카드 내용 사본, 분류·예약·카운터.
- **원로그**: 수정·삭제·합성하지 않는다. 남은 로그로 사라진 기준일을 추정하지 않는다.
- **집계 유지**: 카드가 사라져도 계정 전체 신규 집계의 기존 증거와 불확실성은 그대로다. 삭제만으로 exact가 되거나 신규가 다시 소비되지 않는다.
- **계정 삭제**: 이 증거도 함께 지운다(D-P5 절차에 포함).
- **보존 기간**: 영수증 7일·snapshot 30일 기준을 이 증거에 재사용하지 않는다. 계정이 있는 동안 유지하고, 다른 기간은 별도 승인 대상이다.
- **사용자 영향(명시)**:
  - `unknown` 표시 카드를 지워도 그 계정의 신규 집계는 계속 확인 불가다. **신규 출제가 계속 멈출 수 있다.**
  - 기준일이 오늘인 `before_tracking` 카드를 지운 날에도 오늘은 확인 불가로 남는다.
  - 삭제만으로 불확실성을 해제할지(예: 사용자가 확인하고 해제)는 **별도 정책**이며 이 초안에서 정하지 않는다(승인 항목 E5).

## 4. 데이터 수명·집계 규칙 (초안)

### 4-1. 살아 있는 카드 표시와 삭제 후 증거가 함께 있을 때
- U2 재구성 뒤에는 개인 카드 id가 재사용되지 않으므로, 같은 (계정, 종류, id)에 살아 있는 카드와 삭제 증거가 함께 있을 수 없다.
- 함께 있다면 재구성 전 재사용(혼합)이다. U3 탐지 신호 `deleted_then_reused`로 그 id는 식별 불가가 되고, 식별 불가 규칙이 먼저 적용된다.
- 탐지 표시가 아직 없어도 **더 불확실한 쪽을 쓴다**: `unknown` > `before_tracking`(더 늦은 기준일) > `logged` > 없음. 두 증거를 합치거나 기준일을 좁히지 않는다.
- 같은 id의 삭제 증거가 여러 행이면(재구성 전 여러 번 재사용) 위와 같은 순서로 가장 불확실한 값을 쓴다.

### 4-2. 덮어쓰기 금지
- 삭제 증거는 삭제 순간 카드의 표시를 그대로 복사하고, 이후 갱신하지 않는다.
- 살아 있는 카드의 표시는 지금처럼 NULL일 때만 기록한다(U4).
- 어느 쪽도 나중의 로그·`last_reviewed_at` 변경·재실행으로 좁혀지지 않는다.

### 4-3. 원자성과 경합 순서
- 증거 복사는 삭제와 같은 트랜잭션에서 DELETE 직전에 한다(U3 원장과 같은 문장). 증거 기록이 실패하면 삭제도 일어나지 않고, 삭제가 실패하면 증거 행도 남지 않는다.
- 권장: 삭제 경로도 평가·이전 적용처럼 계정 쓰기 잠금(`begin_card_write`)을 먼저 잡는다.
  - SQLite는 쓰기가 이미 직렬화되지만, PostgreSQL에서는 이전 적용의 표시 기록과 삭제 사이에 순서가 보장되지 않는다.
  - 순서: 표시 기록이 먼저 확정되면 삭제가 그 표시를 복사하고, 삭제가 먼저면 표시 기록은 0행으로 끝난다.

### 4-4. 단어·덱·계정 삭제
| 삭제 | 카드 | 원로그 | 삭제 증거 |
| --- | --- | --- | --- |
| 단어 삭제 | 삭제 | 보존 | 그 카드 1행 |
| 덱 삭제(카드 일괄) | 덱의 카드 전부 삭제 | 보존 | 카드마다 1행(같은 문장) |
| 계정 삭제(D-P5, API 없음) | 전부 삭제 | 전부 삭제 | **전부 삭제**(잔존 0) |

### 4-5. 구독 해제·진도 행 삭제의 실제 동작
- 코드 확인 결과:
  - 구독을 비활성화하는 경로가 없다(`is_active = FALSE` 쓰기 없음).
  - `user_word_progress` 행을 지우는 경로가 없다.
  - 공유 덱 "삭제"는 공개 해제(`visibility = 'unpublished'`)만 한다(`shared_deck_repository.delete_shared_deck`).
- 그래서 구독 카드의 표시는 지금 사라지지 않고, 이번 계약을 구독 카드에 적용할 필요는 현재 없다.
- 해제·진도 삭제 경로를 새로 만들 때는 같은 계약(`card_kind = 'lexeme'`)을 함께 승인받아야 한다.

### 4-6. 계정 전체 집계와 덱 범위 집계
- **계정 전체 집계**(큐 `new_goal` 계정 값, 평가 응답, `/stats` `today_seoul`)는 삭제 증거를 포함한다. 삭제된 카드의 로그를 이미 포함하는 것과 같다.
- **덱·계획 범위 집계**는 지금처럼 현재 카드만 범위로 본다. 삭제된 카드의 증거·로그는 범위 밖이다.
- 따라서 삭제 뒤 계정 값은 그대로 확인 불가인데 덱 범위 값은 exact일 수 있다. 계획 범위 신규 출제는 계정 값도 함께 확인하므로(계정 확인 불가면 신규 멈춤) 재소비는 생기지 않는다.

### 4-7. 롤백·재전환·snapshot 만료와 독립
- 삭제 증거는 이전 도구가 읽거나 쓰지 않는다. 롤백(카드가 없으면 `missing_or_access_lost`로 건너뜀)·재전환·snapshot 만료·영수증 만료가 이 증거를 바꾸지 않는다.

### 4-8. 이미 사라진 증거의 복구 한계
- 이 계약 전에 지워진 카드의 표시는 남아 있지 않다. U3 원장 행은 있지만 새 두 열은 NULL이다.
- NULL은 "삭제 때 표시가 없었음 또는 계약 이전 삭제"를 뜻하며, **"학습한 적 없음"으로 해석하지 않는다.** 그 id의 집계는 남은 로그 규칙을 따른다.
- 남은 로그·`last_reviewed_at` 흔적으로 사라진 기준일을 추정하지 않고, 삭제된 카드를 복원하지 않는다.
- 보고서·화면에서 "복구됨"으로 표현하지 않는다.
- 계약 이전 삭제와 계약 이후 "표시 없음" 삭제를 구분해야 하면 원장에 기록 버전 열이 하나 더 필요하다(승인 항목 E6, 권장하지 않음: 집계 결과가 같다).
