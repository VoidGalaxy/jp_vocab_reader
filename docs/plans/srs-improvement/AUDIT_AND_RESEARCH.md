## 1. 결론

권장 방향은 **학습 대상/평가/완료 기준을 정리한 뒤, 검증된 FSRS 라이브러리를 서버에 도입**하는 것이다.
현재 구조의 가장 큰 문제는 간격표만이 아니라, 읽기 분류가 복습 참여를 결정하고 여러 화면에서 신규/접함의 정의가 다른 점이다.
FSRS는 이 정책을 자동으로 해결하지 않는다. 알고리즘, 세션 큐, 학습 목표, 완료 지표는 별도 설계해야 한다.

FSRS는 유력한 실용 후보이지, 모든 학습자/일본어 과제에서 가장 효과적이라고 증명된 유일한 방법은 아니다.
이번 조사로 확인한 강한 학습 근거는 간격 반복과 반복 인출이다. 알고리즘 벤치마크의 기억 예측 정확도는 장기 학습 효과의 직접 비교와 구분한다.

- Again: 어느 레벨이든 0으로 돌아가 5분 후.

## 3. 우선 보정/결정할 문제

### A. 읽기 자기분류와 예약 복습이 결합되어 있다 [DB 재현]

known으로 바뀌면 next_review_at이 이미 지나도 예정 큐에서 제외된다.
특히 구독 덱 미분류 단어의 첫 Easy는 known이 되므로 예약은 생겨도 통상 예정 큐에 돌아오지 않는다.
개인은 첫 평가로 분류를 자동 변경하지 않는다. 같은 Easy의 큐 참여 결과도 분류 이력/카드 종류에 따라 달라진다.

제안: 읽기 분류는 자기평가/필터, SRS는 실제 평가와 스케줄, 복습 제외는 별도 명시적 제외/보류로 분리한다.
이는 현재 제품 계약 변경이다. 기존 known을 전부 즉시 복습에 넣지 말고, 미평가 known의 참여 정책과 기존 예약의 이전 방식을 승인받아야 한다.

### B. 신규/첫 학습/예정의 정의가 다르다 [DB 재현 + 코드 확인]

- 개인 미평가 unknown은 next_review_at NULL이라 오늘 큐에도 들어간다.
- 구독 미평가 미분류는 신규이고, 예정 큐에는 들어가지 않는다.
- 구독 첫 Again은 last_reviewed_at이 생겨 계획의 seen에는 포함되지만, 구독 통계 new_count는 review_level=0 조건으로 계속 신규로 센다.
- 복습 탭의 구독 신규와 학습 계획의 신규 실행은 서로 다른 조건이다. 복습 탭은 LIMIT 뒤 분류로 거르므로 앞쪽 분류 단어 때문에 빈 큐/축소 큐가 가능하다.

제안: 신규=미평가, 학습 중=첫 평가 후 단기 단계, 복습=장기 단계, 재학습=장기 단계에서 실패로 통일한다.
새 단어 수(개), 전체 평가 횟수(회), 예약 복습 수(개)를 구분한다. 서버 공통 큐 계약을 사용하고 필터를 LIMIT보다 먼저 적용한다.

### C. 짧은 간격을 예약하지만 세션은 고정 배열이다 [코드 확인]

Again의 5분 예약이 세션 중 지나도 자동으로 카드가 돌아오지 않는다. 세션 끝나거나 재시작해야 다시 조회한다.
한 번 더 복습은 기존 모드 전체를 다시 조회하므로 신규/자유 학습에서 너무 이른 반복 평가가 생길 수도 있다.

제안: 다음 학습 시각을 고려하는 단기 큐와 장기 예정 큐를 분리한다. 대기 카드가 있으면 정확한 다음 시각/다시 확인을 표시하고, 타이머 도래/앱 복귀 때 갱신한다.
즉시 연속 같은 카드, 무한 세션, 세션 완료를 숙련 완료로 해석하는 동작은 피한다.

### D. 반복 인출에서 무엇을 평가하는지가 불명확하다 [코드 확인]

문제 쪽에는 일본어 표제어와 읽기가 함께 보이고, 한국어 뜻은 정답 공개 뒤 보인다.
현재 과제는 일본어→한국어 뜻 인출에 가깝다. 한자 읽기 인출, 한국어→일본어 생성, 문맥 사용 능력까지 측정했다고 볼 수 없다.
여러 뜻은 저장 문자열 하나이며 `getMeaningSenses()`는 실제로 한 항목만 반환한다.

제안: 초기 목표는 원문 읽기를 돕는 핵심 의미 인출로 좁힌다. 읽기 인출/역방향/뜻별 카드는 추후 별도 카드 유형으로 다룬다.
어떤 뜻까지 맞히면 성공인지 정해야 한다. 문맥과 다른 의미 전부를 한 번에 외웠다는 완료 지표는 만들지 않는다.
Hard는 기억났지만 어려웠음, Again은 기억하지 못했음으로 안내한다. 현재 버튼 힌트는 결과 간격 설명이라 이 차이를 직접 알려주지 않는다.

### E. 데이터/안전 후속 점검 [정적 관찰, 실제 브라우저 미재현]

- `submitStudyReview()`는 POST 뒤 account epoch/session ID 검사 없이 상태와 인덱스를 갱신한다. 로그인 전환/세션 교체 중 지연 평가 응답이 새 세션에 적용되는지 반드시 지연 브라우저 검사로 확인해야 한다. 조회 쪽의 epoch 보호만으로 평가 보호를 입증할 수 없다.
- 평가 POST의 idempotency 키/평가 취소 이력은 이번 감사 범위 코드에서 확인되지 않았다. 응답 유실 후 재시도와 이중 평가의 계약이 필요하다.
- response_time_ms는 개인만 보내며, 정답 공개 후 평가 버튼을 누르기까지 시간이다. 답을 떠올린 시간으로 해석하거나 이를 근거로 자동 등급을 매기면 안 된다.
- 구독 이력에는 response_time_ms가 없다. FSRS 기본 평가/시각 사용에는 치명적이지 않지만 두 경로의 시간 통계는 비교 불가다.
- 기존 `/stats`의 reviewed_today_count 시작은 UTC 00시이고 학습 기록/계획은 서울 날짜다. 일일 신규 상한/실적 설계에서는 서울 날짜 계약을 명시하고 기존 수치와 혼동하지 않아야 한다.
- 개인 같은 단어는 덱별 별도 카드, 구독은 계정 전체 lexeme 공유 카드다. 개인+구독을 하나로 합치면 중복 제거 이상의 이력 변경이므로 별도 승인해야 한다.

## 4. 외부 근거: 효과와 예측 성능을 분리

### 반복 인출과 간격

외국어 단어 실험에서 한 번 맞힌 뒤에도 다시 떠올리는 연습을 계속한 조건이 지연 회상에 유리했다. 단순히 다시 읽는 것과 구분된다.
따라서 아는 단어/첫 성공을 영구 복습 종료로 취급하는 정책은 재검토할 근거가 있다.
[Karpicke & Roediger, Science 2008](https://doi.org/10.1126/science.1152408)

간격 연구에서는 기억을 유지하려는 기간에 따라 유리한 간격도 달라졌다. 모든 단어/사용자에 고정된 단일 간격표가 최적이라는 근거는 아니다.
[Cepeda et al., Psychological Science 2008](https://digitalcommons.usf.edu/psy_facpub/1766/)

### 후보 비교

| 후보 | 강점 | 한계 / 이 프로젝트 판단 |
| --- | --- | --- |
| 현재 고정 단계 | 단순하고 설명/회귀가 쉽다 | 개인차/연체/기억 확률을 반영하지 않음. 현재 비교 기준으로 유지 |
| SM-2 | 평가별 easiness factor와 간격 배수, 구현 단순 | 오래된 휴리스틱. 유지 확률 목표를 직접 제공하지 않음. 전환 비용을 들여 새로 채택할 1순위는 아님 |
| FSRS | 난이도/안정도/인출 확률 추정, 실제 평가 이력으로 적응, 목표 유지율 설정 | 로그 품질과 평가 일관성이 필요. 가장 실용적인 우선 검토 후보 |
| HLR / 신경망 연구 모델 | 언어 특성과 큰 데이터로 기억을 예측할 수 있음 | 자체 학습/운영/검증 부담. 예측 성적만으로 제품 도입 가치가 결정되지 않음 |

SM-2의 실제 원문은 1일/6일 이후 카드별 easiness factor로 간격을 늘리고 0~5 평가를 사용한다. 현재 4종 고정 레벨과 동일한 알고리즘이 아니다.
[SuperMemo 원문](https://super-memory.com/english/ol/sm2.htm)

FSRS는 난이도(D), 안정도(S), 인출 확률(R)을 구분한다. 안정도는 모델에서 회상 확률이 90%가 되는 경과 기간이고, 현재 기억 확률과 같은 값이 아니다.
[FSRS 알고리즘 문서](https://github.com/open-spaced-repetition/awesome-fsrs/wiki/The-Algorithm)

Anki는 FSRS를 제공하고 목표 유지율 기본값을 90%로 둔다. 유지율을 올리면 복습 부담이 늘며, 잊었을 때 Hard 대신 Again을 사용하는 것이 중요하다.
이는 우리 서비스에서 90% 효과를 보장한다는 뜻이 아니다. 0.90은 초기 검증 설정 후보이며 사용자/과제의 관측 데이터로 확인해야 한다.
[Anki 공식 설정 문서](https://docs.ankiweb.net/manual/deck-options)

FSRS 개발 커뮤니티의 공개 벤치마크는 Anki 기록을 대상으로 Log Loss, RMSE, AUC를 비교한다.
열람 시 FSRS-7 계열뿐 아니라 일부 신경망이 더 낮은 예측 오차를 보였다. FSRS가 모든 지표의 최상위라고 요약하면 틀리다.
이 데이터는 일본어 학습자가 무작위 배정된 알고리즘 비교 실험이 아니며, 예측 성적/학습 효과/총 시간 절약을 서로 같은 수치로 다루지 않는다.
[공개 벤치마크](https://github.com/open-spaced-repetition/srs-benchmark)

Duolingo HLR 논문은 기억 예측 오차 개선과 사용자 참여 개선을 보고한다. 참여 증가를 곧 장기 기억 성적 증가라고 바꾸어 말하지 않는다.
큰 데이터에서 언어 특성을 반영할 여지는 있지만 현재 프로젝트에는 FSRS보다 운영 부담이 큰 후보로 판단한다.
[Settles & Meeder, ACL 2016](https://aclanthology.org/P16-1174/)

## 5. 권장 설계 (아직 승인/구현 전)

1. 자기분류/학습 단계/복습 참여를 분리한다. known을 숙련이나 자동 제외와 동일시하지 않는다.
2. 네 등급을 유지하되 Again=실패, Hard/Good/Easy=성공의 난이도 차이로 일관되게 사용한다.
3. 미학습/학습 중/장기 복습/재학습 큐를 통일한다. 개인/구독 권한과 카드 정체성은 보존한다.
4. 서버에서 검증된 Python FSRS 구현을 사용한다. 수식을 새로 손으로 작성하지 않는다. 버전/파라미터/스케줄러 버전을 고정해 추후 재현 가능하게 남긴다.
5. 초기에는 라이브러리 기본 파라미터와 목표 유지율 0.90을 검증한다. 이력이 부족한 사용자에게 불안정한 개인 최적화를 강제하지 않는다.
6. 단기 학습/재학습 단계는 별도 정책이다. 라이브러리의 학습 단계 예시를 그대로 정답으로 확정하지 말고, 예상 부담과 세션 동작을 함께 확인한다.
7. 하루 신규 목표는 신규 도입 수에만 적용한다. 기한이 지난 복습을 숨기거나 제외해 목표를 맞췄다고 표시하지 않는다. 복습 과부하 때 신규를 줄이는 선택을 제공한다.
8. 화면에는 다음 간격, 실제 학습 단계, 신규/복습 부담을 간결하게 표시한다. 고급 D/S/R 수치를 기본 화면에 전부 나열하지 않는다.

Python 백엔드에 맞는 후보는 `py-fsrs`다. UTC 시각, 카드 상태, 등급, review log와 선택적 optimizer를 제공한다.
열람한 README는 21개 파라미터 예시를 사용하며, 벤치마크의 FSRS-7 표와 동일 버전이라고 가정하지 않는다.
도입 때 릴리스/호환성/라이선스/기본 파라미터/당일 평가 동작을 고정한 버전에서 재확인해야 한다. 이번에는 설치하지 않았다.
[py-fsrs 공식 저장소](https://github.com/open-spaced-repetition/py-fsrs)

## 6. 학습 완료와 계획 예측

- 첫 학습 완료: 모든 현재 덱 카드에 실제 첫 평가가 있음. 현재 지표를 별도 유지한다.
- 기억 안정: 장기 안정도, 서로 다른 날짜의 성공, 최근 실패와 현재 인출 확률을 함께 고려하는 제품 기준 후보.
- 영구 완료: 보장하지 않는다. 안정 상태여도 나중에 복습/재학습 대상이 될 수 있다.
- 목표 유지율 90%를 곧 완료 90%로 표시하지 않는다. 신규 카드도 초기 R이 높을 수 있고, 오래 배운 카드의 R은 시간에 따라 줄어든다.
- 30일 안정도나 성공 3회 같은 문턱은 아직 확정하지 않는다. 그런 숫자는 보편적 과학 기준이 아니라 검증해야 할 제품 정책이다.
- 일정은 첫 학습 예상일과 기억 안정 예상 범위를 분리한다. 잊음/부재/실제 난이도가 바뀌므로 완벽 학습 완료일을 단일 확정 날짜로 약속하지 않는다.

## 7. 이력 이전과 검증 게이트

### Gate A: 계약 확정

학습 목표(뜻 인출 우선), known 정책, 네 평가 의미, 신규/복습/재학습 정의, 일일량, 안정 지표를 먼저 승인한다.
평가 지연 중 계정/세션 교체 및 응답 유실 재시도 위험도 실제 브라우저로 재현한다.

### Gate B: 로그/스키마/이전 설계

개인 review_logs와 구독 lexeme_review_logs를 카드별 시각 순서로 어댑트한다. rating/시각은 있지만 알고리즘 버전/당시 D/S/state는 없다.
로그 누락, 중복, 이력이 없는 기존 카드, 같은 시각 평가, 과거 자유 복습, 삭제 카드, 기존 known의 처리 기준을 정한다.
기존 review_level을 임의로 안정도 일수로 바꾸지 않는다. 재생 가능한 이력은 검증된 라이브러리로 재생하고, 불완전 이력은 보수적 초기화 정책을 별도 정한다.
기존 due를 한 번에 전부 당기지 않는 전환 방식, 비활성 비교 모드, 백업/되돌리기, 알고리즘 버전 필드를 설계한다.

### Gate C: 엔진/큐 구현 및 DB 비교

기존 고정 알고리즘과 신규 엔진을 같은 합성 시나리오로 비교한다. 미평가 4종, Again 반복, 오래된 카드 실패, 조기/지연 평가, 날짜 경계, 중복 카드, 권한 분리와 idempotency를 다룬다.
운영 DB에 접근하지 않고 세션 SQLite 및 보호된 빈 로컬 PostgreSQL에서 비교한다. 실제 PG 검증은 현재 미완료다.

### Gate D: 제품 흐름

복습의 동적 단기 큐, 신규 도입 목표, 학습 계획/통계의 정의 통일, 세션 보호와 접근성을 검증한다. 기존 디자인을 재구축하는 범위와 섞지 않는다.

### Gate E: 실제 효과 확인

시간 순서로 나눈 로그 검증으로 회상 예측 오차/보정을 확인한다. 합성 로그만으로 학습 효과를 증명하지 않는다.
장기적으로 서로 다른 날의 회상 성공률, 완료한 평가 수, 실제 학습 시간, 신규 도입, 연체량을 함께 관찰한다.
즉시 반복의 높은 정답률을 장기 기억 개선으로 간주하지 않는다. 가능한 범위에서 기존/신규를 비교하되 이력/사용자 조건 차이를 통제한다.

## 8. 이번 검증과 한계

- `audit_current_srs.py`: 고정 간격/실제 저장소/큐/통계를 합성 SQLite로 15항목 확인했다.
- PASS는 현재 동작을 재현했다는 의미이며, 학습 효과 또는 정책의 타당성을 통과했다는 뜻이 아니다.
- 개인 overdue known 제외, 구독 첫 Easy 제외, 첫 Again 신규/접함 불일치를 DB 함수로 직접 확인했다.
- 원격 DB, 운영 계정, 기존 로컬 DB는 접근하지 않았다. 임시 SQLite는 실행 후 삭제했다.
- 제품 코드 수정, 의존성 설치, 브랜치 생성, 빌드, 커밋/푸시는 하지 않았다.
- 실제 앱 브라우저 재현, PostgreSQL, 실제 사용자 학습 성과 비교는 이번에 하지 않았다.
- 앞서 언급한 평가 응답 경합은 정적 발견으로 남겼고 실제 결함 재현으로 과장하지 않았다.
