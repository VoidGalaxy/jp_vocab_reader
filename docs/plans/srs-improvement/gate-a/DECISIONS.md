### 1-1. 학습 단계별 첫 평가 결과 [소스 계산, 실행 검증 아님]

유지율 0.90에서 초기 S: Again 0.212, Hard 1.2931, Good 2.3065, Easy 8.2956일.

| 신규 카드 첫 평가 | 권장 `(1분, 10분)` | 비교: `(10분,)` 1단계 |
| --- | --- | --- |
| Again | 1분 뒤 (Learning step 0) | 10분 뒤 |
| Hard | 5.5분 뒤 ((1+10)/2, step 유지) | 15분 뒤 (1.5배) |
| Good | 10분 뒤 (step 1), 그 뒤 Good이면 Review | 바로 Review, 2일 뒤 |
| Easy | 단계를 건너뛰고 Review, 8일 뒤 | 바로 Review, 8일 뒤 |

권장 `(1분, 10분)`: 첫 Good도 같은 세션에서 10분 뒤 한 번 더 확인한다. 1분 단계 때문에 Again 직후 곧바로 같은 카드가 다시 나올 수 있으므로, 큐는 "다음 카드 경계에서 due 재확인" 규칙(동적 세션)으로 처리하고 타이머로 현재 카드를 바꾸지 않는다.
두 번째 평가 이후의 간격·S, 그리고 완료 기준 도달 시점은 실제 엔진 실행 시뮬레이션(Gate B-1)으로 확인해야 한다. 이 표는 손으로 따라간 첫 단계뿐이다.

S2를 다시 다룰 때 함께 정해야 하는 항목(이번 단계 미결, 모두 별도 승인):

- 예약 TTL 길이, 새로고침·취소·창 닫힘 때 예약 처리.
- 서울 자정을 넘긴 예약의 처리.
- 사용자가 답을 떠올리는 중 예약이 만료된 뒤 들어온 평가의 처리. 이 평가를 받아들이면 상한을 넘을 수 있고, 거부하면 이미 한 학습을 버리게 되므로 "엄격한 상한"과 "만료 후 평가 수용"은 함께 보장할 수 없다. 어느 쪽을 택할지와 유예 시간이 승인 대상이다.
- 같은 카드 두 창 예약, 분실 응답 재시도.

S2를 구현·검증하기 전에는 엄격한 상한을 구현했다고 보고하지 않는다.

### 5-3. 자정(Asia/Seoul), S1 기준

- 신규 실적의 날짜 = 서버가 평가를 **받은** 시각의 서울 날짜. 화면 표시 시각으로 소급하지 않는다.
- 23:59에 본 카드를 00:01에 평가하면 다음 날 신규 1개. 전날 목표 계산은 바꾸지 않는다.
- 클라이언트는 다음 카드 경계와 앱 복귀 때 `server_now`로 날짜 변화를 확인하고 큐를 다시 읽는다.
- 예약 만료·유예와 관련된 자정 규칙은 S2 항목으로 남긴다.

### 6-1. 짧은 간격 연속 평가의 처리

정상적인 반복 연습(예: 학습 단계 1분 뒤 재평가, 같은 세션 재출제)도 같은 카드·같은 등급·짧은 간격 로그를 만든다. 그래서 간격은 판정 근거가 아니라 `short_interval_repeat` 같은 **의심 표시**로만 남긴다.

| 증거 | 판정 | 처리 |
| --- | --- | --- |
| 짧은 간격이지만 로그 연결(M1)이 이어지고 마지막 로그=카드 현재값 | complete + 의심 표시 | 로그 순서대로 모두 재생. 표시는 감사·통계용이며 결과를 바꾸지 않음 |
| 짧은 간격이고 로그 연결이 끊김(앞 로그의 next ≠ 뒤 로그의 previous) | incomplete (연결 근거) | M4 |
| 동시각 로그, 연결 정보로 순서를 정할 수 있음 | complete + 의심 표시 | 연결이 가리키는 순서로 재생 |
| 동시각 로그, 연결 정보로도 순서를 정할 수 없음 | incomplete (순서 불명) | M4 |
| 마지막 로그 ≠ 카드 현재값 | incomplete (카드 상태 근거) | M4, 카드 현재값 보존 |
| 미래 시각·잘못된 등급 등 값 오류 | incomplete | M4 |

알려진 한계: 현재 서버에는 요청 ID가 없어서, 응답 유실 후 재시도로 생긴 이중 기록(REPORT 2절)은 로그 연결이 정상인 연속 평가와 과거 자료만으로 구별할 수 없다. 이런 기록은 위 첫 줄처럼 그대로 재생된다. 이를 받아들일지, 사용자가 카드별로 직접 검토하는 별도 도구를 둘지는 승인 대상이다. 자동 중복 제거는 하지 않는다.
전환 이후 평가는 요청 ID 영수증(R1)으로 이중 기록 자체를 막는다.

## 7. 평가 저장 계약 (재현 결과 반영)

| # | 항목 | 권장 초안 |
| --- | --- | --- |
| R1 | 요청 ID | 클라이언트 생성 `request_id`, `(user_id, request_id)` 유일 영수증. 같은 내용 재전송 → 같은 응답, 다른 내용 → 409 |
| R2 | 카드 버전 | `expected_card_version` CAS. 다른 창 stale 평가 → 409, 쓰기 없음 |
| R3 | 클라이언트 가드 | 평가 시작 snapshot(accountEpoch, sessionId, cardKey, requestId)이 다르면 응답을 화면에 적용하지 않음. `isReviewing`도 세션별로 |
| R4 | 응답 유실 | 같은 request_id로만 재시도. 오류 문구는 "저장 여부 확인 중"으로, 실패 단정 금지 |
| R5 | 옛 클라이언트 | FSRS 카드에 request_id 없는 평가 → 업그레이드 필요 오류. legacy 카드는 기존 요청 유지 |

## 8. API·스키마 변경 초안

`IMPLEMENTATION_CONTRACT.md` 2~4절 방향을 따른다. 실제 컬럼 기준 차이만 적는다.

```text
vocab_items / user_word_progress (추가, 기존 열 유지)
  + srs_engine TEXT NOT NULL DEFAULT 'legacy'      -- legacy|fsrs
  + srs_config_version TEXT NULL
  + srs_state SMALLINT NULL                        -- 1 Learning, 2 Review, 3 Relearning (6.3.2 IntEnum)
  + srs_step SMALLINT NULL
  + srs_stability REAL NULL, srs_difficulty REAL NULL
  + srs_due_at TEXT NULL                           -- FSRS 계산 due(UTC)
  + srs_effective_due_at TEXT NULL                 -- 전환 유예 포함 실제 출제 기준
  + srs_last_review_at TEXT NULL
  + srs_card_version INTEGER NOT NULL DEFAULT 0
  + srs_participation TEXT NOT NULL DEFAULT 'active', srs_pause_reason TEXT NULL
  + srs_history_quality TEXT NULL                  -- complete|incomplete|fresh
  + srs_history_flags TEXT NULL                    -- 예: short_interval_repeat (판정에 쓰지 않는 의심 표시)
  + completion_metric_version TEXT NULL, first_completed_at TEXT NULL
  (vocab_items는 현재 PK 외 인덱스가 없음 → (user_id, srs_participation, srs_effective_due_at) 등 추가 검토)

review_logs / lexeme_review_logs (추가)
  + request_id TEXT NULL, srs_engine TEXT NULL, srs_config_version TEXT NULL
  + card_version_before INTEGER NULL
  + srs_before_json TEXT NULL, srs_after_json TEXT NULL   -- 감사·롤백용 snapshot, 권위 상태 아님
  + seoul_date TEXT NULL, is_first_review INTEGER NULL

새 테이블: srs_user_settings(하루 신규 목표 포함), srs_review_receipts, srs_migration_runs(+snapshot)
         srs_intake_reservations는 S2를 별도 승인할 때만 (이번 초안 범위 밖)

POST /study-items/{id}/review, POST /shared-decks/{sid}/words/{lid}/review
  req  + request_id, expected_card_version
  resp + srs{state, step, due_at, effective_due_at}, card_version, completed,
         completion_metric_version, request_id, accepted_at, server_now
GET  /study-queue (신규, 읽기 전용)  -- counts(new_introduced_today, new_goal_remaining 등), next_due_at, server_now, scheduler_version
GET  /learning-plan/progress        -- 기존 필드 유지 + completion_* / paused / introduced_today
```

승인된 방향: 기존 `/stats` UTC 응답 필드는 호환용으로 보존하고, 서울 기준 일일 실적 필드를 별도로 추가해 화면의 '오늘' 실적은 서울 기준으로 통일한다. 연결은 Gate D에서 수행하며 Gate B-1에서는 기존 집계/화면을 변경하지 않는다.

## 9. 사용자 승인 묶음 (2026-10-09)

1. **엔진**: `fsrs==6.3.2` 고정, 유지율 0.90, 최대 간격 365일, fuzz 끔, 기본 파라미터.
2. **단계**: 초기 학습 `(1분, 10분)`(첫 Good 10분 뒤 재확인, Easy는 단계 건너뜀 가능), 재학습 `(10분,)`.
3. **학습 완료 v1**: 네 조건은 시뮬레이션용으로 채택, 실제 엔진 실행 결과 후 재승인 전제. 최종 제품 기준 확정은 아님.
4. **참여**: 분류-참여 분리, 기존 known 제외 의도·예약·평가 이력 보존, 명시 선택으로만 재참여.
5. **신규량**: 계획 Q를 하루 신규 목표로 전환, 계정 초기 목표 20개, 추가 학습은 명시 선택. 1단계는 S1이며 여러 기기 엄격한 상한을 보장하지 않음.
6. **엄격한 상한(S2)**: 후속 작업으로 분리. TTL·자정·평가 중 만료·유예는 그때 별도 승인.
7. **자유 복습**: SRS 예약에 반영하지 않는 연습(A).
8. **이전**: 기존 예약 유지, 불완전 이력은 다음 평가부터 새 추정, 짧은 간격은 의심 표시로만, 과거 이중 기록은 자동 제거하지 않음. 이전 검토 보고서에 표시하고 사용자용 검토 도구는 후속으로 미룸.
9. **통계 날짜**: 기존 `/stats` UTC 응답 필드는 호환용으로 보존. 서울 일일 실적 필드를 별도로 추가해 화면의 '오늘'은 서울 기준으로 통일. Gate D 연결.
10. **브랜치/진행**: Gate B-1 시작 시 `codex/fsrs-srs-replacement` 생성 또는 해당 작업의 기존 브랜치 재사용. 엔진/추가형 스키마/테스트 후 보고하고 멈춤.

현재 사용자 원문 승인: 'ㅇㅇ 숭인하고 작업지시 프롬프트 ㄱㄱ'. 직전 권장 승인안의 1~7번, 수정된 8~9번, 브랜치 및 Gate B-1 범위에 대한 승인으로 기록한다. 커밋/푸시/병합/운영 자료 이전 승인이 아니다.
