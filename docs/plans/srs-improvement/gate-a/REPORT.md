## 2. 실제 앱 재현 (개인 덱 경로)

방법: 격리 백엔드 + `next dev`(같은 저장소 코드, 수정 없음), 합성 계정 A·B와 각 6단어 덱. 브라우저 페이지에서 `window.fetch`를 감싸 **평가 POST는 서버에 즉시 보내되 응답만 붙잡거나(지연) 버리게(유실)** 했다. 계정 전환은 두 번째 탭에서 토큰을 바꿔 실제 storage 이벤트로 일으켰다. 결과는 화면과 DB 로그로 확인했다.

원인(코드 확인): `frontend/app/page.tsx:3955` `submitStudyReview()`는 await 뒤 account epoch·`studySessionIdRef`를 확인하지 않고 `setCurrentStudyIndex(i => i + 1)`, 안내, 통계를 갱신한다. 서버 평가 API에는 요청 ID·카드 버전이 없다.

정적 위험으로만 남긴 것(실제 재현 안 함):
- 구독(lexeme) 평가 경로: 같은 `submitStudyReview()`를 쓰므로 같은 화면 문제가 예상되지만 브라우저로 돌리지 않았다. 구독 경로는 첫 평가 자동 분류까지 두 번 적용될 수 있다.
- 서버 동시 요청 lost update(두 요청이 같은 행을 같은 순간 읽음): 이번 두 창 사례는 순차 도착이었다.
- 계정 전환 뒤 이전 계정 응답이 B 화면의 `sessionCounts`·통계 재조회에 섞이는지 수치로는 확인하지 않았다(화면 진행/안내만 확인).
- 계획 실행기(`planStudyLauncher`)를 거친 세션 교체는 실행하지 않았다. 같은 `studySessionIdRef`를 올리므로 같은 결과로 추정.
