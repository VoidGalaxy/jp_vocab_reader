# 손상된 평가 시각 처리 제안 (승인 대기, 미구현)

작성: 2026-10-09. 대상: `GET /study-queue`(Gate C-1)와 B-2 FSRS 평가 경로.
상태: **6절 다섯 항목 승인(2026-10-09), 구현·검증 완료.** 확정 계약은 `CONTRACT.md` 7절(4-5), 결과는 `REPORT.md` 7절. 1절의 재현 표는 보정 전 기록이다.

## 1. 재현 [실행 확인, 합성 SQLite]

로그 시각 하나를 잘못된 값으로 바꾼 뒤, 정상 카드만 있는 상태와 비교했다. 재현 스크립트는 세션 스크래치에서만 실행했고 저장소에는 넣지 않았다.

| 손상 위치 | 값 | `GET /study-queue` | 다른 정상 카드의 FSRS 평가 | 평가 쪽 쓰기 |
| --- | --- | --- | --- | --- |
| 개인 `review_logs.reviewed_at` | `garbage` | 500 | 500 | 0 (로그·영수증·카드 버전·DB 바이트 동일) |
| 개인 `review_logs.reviewed_at` | `''` | 500 | 500 | 0 |
| 구독 `lexeme_review_logs.created_at` | `garbage` | 500 | 500 | 0 |
| 구독 `lexeme_review_logs.created_at` | `''` | 500 | 500 | 0 |
| 삭제된 개인 카드의 로그 | `''` | 500 | 500 | 0 |

- 기준 상태(손상 없음)의 큐는 200이었다.
- 큐 원인: `goals.first_review_times`가 카드별 `MIN(시각)`을 고른 뒤 `goals.introduced_on`에서 `datetime.fromisoformat`이 실패하고, 예외가 그대로 올라간다.
- 평가 원인: B-2 `record_fsrs_review`가 카드·로그를 갱신한 뒤 응답용 `introduced_on`을 호출할 때 같은 예외가 난다. 트랜잭션 전체가 롤백되어 **일부 쓰기는 남지 않았다.** 다만 사용자는 원인을 알 수 없는 일반 500을 받는다. 계정에 손상 로그가 하나라도 있으면 그 계정의 모든 FSRS 평가가 막힌다.
- legacy 평가 경로는 신규 집계를 부르지 않으므로 영향이 없다.

코드 검토로 확인한 관련 위험(실행 재현은 하지 않음):

- **평가하는 카드 자신의 로그가 손상된 경우**: `record_fsrs_review`가 완료 판정용 이벤트를 만들 때 `fromisoformat`에서 실패한다. 카드 갱신 전이라 쓰기는 없지만 500이다.
- **시간대 없는 값**(`2026-10-09 00:00:00`): `fromisoformat`은 통과하지만 `seoul_date → to_utc`가 시간대 없음으로 거부해 500이 된다.
- **텍스트 MIN이 손상을 가리는 경우**: 신규 집계는 문자열 `MIN`으로 카드별 첫 평가를 고른다. 손상 값이 정상 값보다 문자열 순서가 뒤라면(`garbage` 대 `2026-…`) 손상 값은 조용히 무시된다. 앞이라면(`''`, `0…`) 그 값이 "첫 평가"로 뽑힌다. 그래서 예외가 안 나는 경우에도 손상이 드러나지 않을 수 있다.
- **`Z` 표기**(`…Z`): Python 3.11+ `fromisoformat`이 받아들여 올바른 시각으로 센다. 정규 형식은 아니지만 값은 정확하다.
- **B-2 롤백 도구**(`migration.rollback_plan`)도 로그 시각을 해석한다. 손상 로그가 있는 카드는 롤백 중 예외로 중단된다(트랜잭션 롤백). 이번 범위 밖이며 후속 확인 대상이다.

## 2. 지켜야 할 것

- 원로그를 삭제하거나 고치지 않는다.
- 손상된 기록을 조용히 빼고 신규 실적을 0이나 다른 정확한 값처럼 계산하지 않는다.
- 불확실한 신규 수를 영수증·로그·응답에 정확한 값처럼 기록하지 않는다.
- 정상 예정 복습은 계속 받을 수 있어야 한다.

## 3. 판정 규칙 제안

1. 계정의 신규 집계는 모든 로그의 시각을 카드별로 읽는다. 문자열 MIN에 기대지 않고, 정규 UTC 형식(또는 `Z` 등 해석 가능한 시간대 포함 값)인지 하나씩 확인한다.
2. 어느 카드든 해석할 수 없는 시각이 하나라도 있으면, 그 카드의 첫 평가 날짜를 **알 수 없음**으로 둔다. 손상 로그가 실제로는 더 이른 평가였을 수 있으므로, 같은 카드의 다른 정상 로그로 대신하지 않는다.
3. 오늘 날짜를 알 수 없는 카드가 하나라도 있으면 계정의 `introduced_today`는 **확인 불가**다. 정상 시각으로 확인된 오늘 신규 수는 "적어도 이만큼"(하한)으로만 보여 준다.
4. 계획 덱 scope의 `introduced_today_in_scope`는 그 scope 안 카드에 손상이 있을 때만 확인 불가다. 계정 목표는 계정 전체 기준이므로, 계정 어디에든 손상이 있으면 계정 잔여량은 확인 불가다.

## 4. `GET /study-queue` 응답 보완 제안

HTTP 200을 유지한다. 신규만 멈추고 due는 그대로 낸다.

```jsonc
"new_goal": {
  "introduced_today_status": "unknown",        // "exact" | "unknown"
  "introduced_today": null,                    // exact일 때만 정수
  "introduced_today_at_least": 4,              // 확인된 정상 시각 기준 하한
  "unreadable_review_time_cards": 1,           // 시각을 해석할 수 없는 카드 수(계정 전체)
  "introduced_today_in_scope_status": "exact", // 덱 scope일 때. 위와 같은 규칙
  "introduced_today_in_scope": 2,
  "account_remaining": null,                   // 확인 불가면 null
  "plan_remaining": null,
  "new_blocked_reason": "review_time_unreadable",
  "is_strict_limit": false,
  "…": "기존 필드 유지"
},
"counts": { "new_allowed_now": 0, "…": "다른 범주는 그대로" }
```

- 확인 불가 상태에서는 `new_allowed_now = 0`, 신규 항목 0개, 첫 페이지 `chain_new_allowed = 0`이다.
- due 항목, `pending_later`, `next_due_at`는 그대로다.
- 손상 로그가 있는 카드 자신은 3절 2번에 따라 첫 평가 날짜를 알 수 없다. 그 카드를 출제할지가 별도 결정이다. **권장: `invalid_state`로 세고 출제하지 않는다.** 평가 경로가 그 카드를 거부해야 하므로(5절) 출제해도 평가할 수 없기 때문이다.
- 응답에 카드 id나 원래 손상 값은 넣지 않는다. 검토 도구는 승인 8번에 따라 후속이다.
- 커서: 확인 상태가 바뀌면(손상 → 정상, 또는 반대) 목표 계산 조건이 바뀐 것이므로 이전 커서는 409다. 커서의 `goal_basis`에 `introduced_status`를 추가한다.

## 5. B-2 평가 경로 영향 제안

| 경우 | 현재 | 제안 |
| --- | --- | --- |
| 다른 카드의 로그 시각 손상 | 500, 쓰기 0 | **평가는 진행한다.** 평가 시각은 서버가 만드는 정상 값이다. 응답·영수증의 `srs.introduced_today`는 `null`, `srs.introduced_today_status = "unknown"`, 하한 `introduced_today_at_least`를 함께 기록한다. 정확한 값처럼 저장하지 않는다 |
| 평가하는 카드 자신의 로그 시각 손상 | 500, 쓰기 0 | **엔진 실행·카드 갱신·로그·영수증 전에 409 `review_history_unreadable`로 거부.** 완료 판정과 첫 평가 여부를 믿을 수 없기 때문이다 |
| 같은 request_id 재시도 | 처음 저장된 응답 반환 | 그대로. 처음 응답에 기록된 상태(`exact` 또는 `unknown`)를 그대로 돌려준다 |
| legacy 카드 평가 | 영향 없음 | 그대로 |

- 응답 모델(`SrsReviewMetadata.srs`)은 dict라 필드 추가에 스키마 변경은 없다. 클라이언트는 아직 이 필드를 쓰지 않는다(C-2 이전).
- 평가 뒤 신규 집계가 확인 불가여도 평가 자체를 실패시키지 않는 이유: 목표는 엄격한 상한이 아니고(승인 5), 이미 받은 카드의 평가를 거부하지 않는다는 계약과 맞추기 위해서다.

## 6. 승인이 필요한 항목

1. 판정 규칙(3절): 카드에 해석할 수 없는 로그 시각이 하나라도 있으면 그 카드의 첫 평가 날짜를 알 수 없음으로 두는 것, 그리고 문자열 MIN을 쓰지 않는 것.
2. 큐 응답 필드(4절): `introduced_today_status`, null 값, `introduced_today_at_least`, `unreadable_review_time_cards`, `new_blocked_reason`과 신규 출제 중단.
3. 손상 로그가 있는 카드 자신을 `invalid_state`로 세고 출제하지 않는 것.
4. 평가 경로(5절): 다른 카드 손상 시 평가는 진행하고 신규 수는 확인 불가로 기록, 자기 카드 손상 시 409 `review_history_unreadable`.
5. `Z`처럼 정규 형식은 아니지만 시간대가 있는 값은 정상으로 셀지, 정규 형식만 인정할지. **권장: 시간대가 있고 해석 가능하면 정상**(값이 정확하므로). 큐 정렬용 카드 시각은 기존대로 정규 형식만 인정한다.
