### 1-3. 규칙

- **서울 자정** [승인 9]: 화면의 "오늘"은 서울 날짜. 저장·엔진 시각은 UTC. M1·M2는 요청 시각의 서울 날짜로 서버가 계산하고, 화면은 응답의 `seoul_date`가 바뀌면 다시 조회한다(대기·앱 복귀 경계). 자정을 넘긴 회차의 이번 회차 평가 수는 초기화하지 않는다 [승인 C-2 D6].
- **기존 UTC 계약 보존** [승인 9]: `/stats`의 기존 필드(`reviewed_today_count`, `today_*_count`, `streak_days`, `due_today_count`)는 이름·의미를 바꾸지 않는다. 서울 값은 새 필드로 더한다(예: `today_seoul: { date, reviews: {total, by_rating}, introduced: {status, count, at_least} }`). 같은 라벨에 두 기준을 섞지 않는다.
- **계정 전환**: 모든 집계 조회는 account epoch를 묶어 시작하고 늦은 응답은 버린다(기존 통계 로더 규칙). 판별 결과·큐 집계는 epoch별이다. 이전 계정 숫자를 한 프레임도 보이지 않는다.
- **조회 실패·확인 불가**: 실패는 "확인할 수 없음", 판별·조회 중은 "확인 중", 확인 불가 신규 수는 "확인할 수 없음 (적어도 N개)". 어느 것도 0으로 표시하지 않는다.
- **범위와 중복** [승인 C-1]: 카드 정체성은 개인 `(user, vocab_item)`, 구독 `(user, lexeme)`. 같은 lexeme가 여러 구독 덱에 있어도 1장. 개인과 구독의 같은 표제어는 2장. 전체 범위 수는 카드 키로 한 번씩 센다. 구독 덱 범위의 진도는 다른 덱에서 본 것도 포함(`account_shared`). M2는 로그 행 수라 카드 중복과 무관하다.
- **삭제 카드**: M1·M2는 삭제된 카드의 로그도 센다(이미 쓴 하루 목표는 되돌아가지 않음). M3·M4·M6은 현재 카드만. PostgreSQL은 지금 로그가 CASCADE로 지워져 결과가 다르다(4절, 출시 차단).
- **보존 키**: `first-review-v1`, 학습 계획 `learning-plan-v1`, 읽기 `reading-session-v3` 키와 내용은 바꾸지 않는다. 계획의 첫 학습 예상일은 지금 규칙 그대로이며, 완료 예상일은 시뮬레이터·실데이터 근거가 생기기 전까지 만들지 않는다.

### 1-4. 홈 legacy 숫자의 FSRS 대체안 [미정 D-M1]

- 권장: FSRS 계정의 홈 복습 카드는 `/study-queue?limit=1` 한 번으로 M3과 M1을 함께 받는다(모드 판별 요청과 같은 응답을 재사용할 수 있다). 값은 "지금 복습 N개", 보조 줄 "오늘 새 단어 a / 목표 b".

해석의 한계:
- 가정 학습자는 엔진과 **같은 망각 곡선 모양**을 쓴다. 완료 뒤 실패율이 기준 사이에서 비슷하게(약 10%, 약한 가정에서 16~17%) 나오는 것은 "모든 due를 유지율 0.90에 맞춘다"는 엔진 가정의 결과일 뿐이다. **실제 기억률이나 기준 간 효과가 같다는 증거가 아니다.**
- 고정 패턴(위 표)에서 확실히 말할 수 있는 것은 각 기준이 **완료라고 부르기까지 요구하는 평가 수·날짜·경과일**뿐이다. V1의 쉬움 2회·8일, 30일 연체 2회·30일이 짧은 것은 두 번째 평가 하나로 S가 30일을 넘기 때문이다.
- 불완전 이력은 세 기준 모두 같은 처리(확인 불가)다. 기준 선택과 무관하게 3-2절의 "증거 구간" 결정이 필요하다.

### 2-3. 권장안 [미정 D-C1]

- 권장: **V3(S≥30, 서로 다른 날짜 3개, 7일 간격 성공 2회)**. 근거는 고정 패턴의 요구 조건뿐이다: 짧은 연속 쉬움·연체 한 번으로 완료되는 경우(V1의 2회·8일)를 막으면서, 어려움을 섞어 꾸준히 맞히는 패턴(29일)은 V1과 같게 둔다. V2는 모든 패턴을 2개월 이상으로 미룬다. 합성 결과로는 어느 기준이 기억에 더 낫다고 말할 수 없다.
- 대안: V1 유지(가장 빠른 동기 부여, 문구로 "학습 완료"가 확정적 숙달이 아님을 설명), V2(가장 보수적).
- 적용 규칙(어느 안이든): 새 기준은 새 `completion_metric_version`(예: `meaning-completion-v1`)으로 시작한다. 기존 `-v1-draft` 판정·`first_completed_at`은 지우거나 다시 계산하지 않고 출처 버전과 함께 보존한다. 화면 집계는 승인 버전 결과만 센다. 이번 문서는 함수·버전·이력을 바꾸지 않는다.
- 파일럿: 실제 사용자 자료가 생기면 완료 뒤 다음 평가 성공률을 관찰해 다시 보정한다. 자료가 없으면 "미검증"으로 표시한다.

### 3-2. 권장 방식: 다음 실제 평가부터 추정 [승인 8: 방향 / 미정: 세부]

### 3-3. 기존 학습 여부와 최초 날짜 확인 상태의 분리 [미정 D-H7]

지금 오늘 새 단어 집계는 "카드별 가장 이른 로그 시각의 서울 날짜"만 본다(F15·F16). 그래서 로그가 있는 불완전 카드는 첫 FSRS 평가 뒤에도 과거 날짜가 유지되지만(재소비 없음), **로그 0건 과거 학습 카드는 첫 FSRS 평가 로그가 곧 첫 평가 날짜가 되어 오늘 새 단어를 다시 소비한다.** `is_first_review=0`으로 기록해도 집계는 달라지지 않는다.

두 값을 나눈다:

| 값 | 뜻 | 가능한 값 |
| --- | --- | --- |
| 기존 학습 여부 | 이 카드를 이미 학습한 적이 있는가 | 있음 / 없음 / 확인 불가 |
| 최초 날짜 확인 상태 | 첫 평가의 서울 날짜를 증명할 수 있는가 | 로그로 확인(날짜 있음) / 기록 이전(날짜 미상. 기준일 **당일이나 그 이전**이라는 것만 앎) / 확인 불가(기준 시각 손상 등) |

`last_reviewed_at`의 뜻: 첫 학습일이 아니라 **"늦어도 이때는 이미 학습했다"는 상한**이다. 첫 학습은 그 시각 당일이거나 그 이전 어느 날이다. 로그가 없으면 그 범위 안 어느 날인지 알 수 없다.

권장안(D-H7-a, 스키마 추가 필요): 카드에 학습 이력 상태 필드를 둔다(예: `intro_status` = `logged` / `before_tracking` / `unknown`, `intro_known_by` = 판정 근거가 된 `last_reviewed_at`의 서울 날짜, 곧 기준일). 전환 때 "로그 0건 + 읽을 수 있는 `last_reviewed_at`·정답 수 있음"이면 `before_tracking`으로, `last_reviewed_at`을 읽을 수 없으면 `unknown`으로 한 번 기록하고, **롤백·재전환·이후 평가 어느 것도 지우지 않는다.**
- 집계 규칙(날짜 D의 오늘 새 단어를 셀 때):
  - `before_tracking`, D > 기준일: 그 카드는 D에 새로 학습된 것이 아니다(기준일까지 이미 학습). **신규에서 제외**하고 exact를 유지한다.
  - `before_tracking`, D = 기준일 또는 D < 기준일: 그날이 첫 학습일일 수도 있다. 별도 증거가 없으면 **확인 불가**(검증된 하한은 유지, 0으로 바꾸지 않음).
  - `unknown`(기준 시각 손상): 상한이 없으므로 범위를 임의로 좁히지 않는다. **모든 날짜에서 확인 불가**(지금 손상 시각 정책과 같은 영향: 그 계정의 신규 수가 확인 불가가 된다).
  - 어느 경우든 이 카드에 나중에 생긴 로그를 첫 평가로 보지 않는다. 날짜를 추정하거나 로그를 만들지 않는다.
- "별도 증거"의 후보: 카드 행의 생성 시각은 하한(그 전에는 학습할 수 없음)이 될 수 있다. 다만 SQLite id 재사용(4-7)과 가져오기 경로의 생성 시각 의미를 확인한 뒤에만 쓸 수 있으므로 D-2 승인 항목으로 남긴다. 이번 권장안은 생성 시각을 쓰지 않는다.
- 일상 영향: 오늘(D)은 보통 기준일보다 뒤라서 제외(exact)가 되어 오늘 신규 목표가 다시 소비되지 않는다. 기준일이 오늘이면 오늘 신규 수는 확인 불가가 된다. 과거 날짜를 보는 기록 달력에서는 기준일 이전 날짜의 신규 수가 확인 불가가 될 수 있다.
- seen(`first-review-v1`)은 `last_reviewed_at`이 있어 이미 1이다. 바뀌지 않는다.

대안(D-H7-b, 스키마 무변경): 기존 `srs_history_flags`의 `missing_history`를 표시로 쓴다. 단 지금 롤백은 `srs_*` 필드를 전환 전 값으로 되돌리므로(`migration.py:302`) **롤백하면 표시가 사라지고**, 그 뒤 남은 FSRS 로그가 첫 평가로 집계된다. 롤백이 이 표시를 보존하도록 바꾸는 것까지 포함해야 한다. 권장하지 않음.

대안(D-H7-c): 로그 0건 과거 학습 카드는 전환하지 않고 legacy로 남긴다(차단 유지). 재소비는 없지만 그 카드는 FSRS로 학습할 수 없다.

## 4. PostgreSQL 로그·삭제·보존 정책

### 4-1. 지금 상태 [확인: 소스 정의. 실제 PG 카탈로그는 미검증]

| 자료 | SQLite | PostgreSQL |
| --- | --- | --- |
| 개인 평가 로그 → 카드 | FK 없음(카드 삭제 뒤 남음) | `vocab_item_id` FK CASCADE(함께 삭제) |
| 구독 평가 로그 → lexeme | FK 없음 | `lexeme_id` FK CASCADE |
| 로그 → 계정 | FK 없음(계정 삭제 뒤 남음) | user FK CASCADE |
| 로그 → 공유 덱 | FK 없음 | `shared_deck_id` SET NULL |
| 영수증 | user FK CASCADE, 카드 FK 없음, 개인은 카드 내용 사본 포함(F10) | 같음 |
| 이전 snapshot | 계정·카드 FK 없음, 카드 행 전체 사본(F11) | 같음 |
| 이전 실행 기록 | `scope_json`에 계정·카드 id | 같음 |
| 개인 카드 id | `INTEGER PRIMARY KEY`, 삭제된 최대 id 재사용(F12) | identity, 재사용 없음 |

### 4-2. 카드 삭제 [미정 D-P1]

- 권장(B-2 제안 유지): 로그의 카드 식별자를 살아 있는 카드 FK에서 떼고, NOT NULL 정수 식별자·로그 id·계정 FK는 유지한다. PG도 SQLite처럼 카드 삭제 뒤 평가 기록·첫 평가 날짜가 남는다.
- 식별자를 NULL로 바꾸지 않는다. 카드 소프트 삭제·내용을 담은 묘비는 만들지 않는다.
- 삭제된 카드는 어떤 경로로도 복구하지 않는다: 롤백·재전환·영수증 재시도 모두 카드가 없으면 미적용/404.
- 이 권장은 **카드 id가 재사용되지 않는다는 전제**가 있어야 성립한다. SQLite는 4-7절을 함께 정해야 한다.

### 4-3. 계정 삭제 [미정 D-P5]

계정 삭제 API는 없다(F13). 운영에서 계정을 지울 때:
- 권장: 계정의 모든 학습 자료를 지운다 — 카드, 진도, 두 로그, 영수증, 설정, 그 계정이 들어간 이전 snapshot·실행 범위, 4-7절의 삭제 카드 원장. 익명 보존 없음.
- PG는 user FK CASCADE로 로그·영수증·설정이 지워지지만 snapshot에는 user FK가 없어 남는다(F11). SQLite는 로그에도 user FK가 없다. 두 DB에 같은 정리 절차를 둔다.
- 공유 덱 작성자 계정 삭제 시 구독자의 평가 로그는 구독자 소유라 남는다.

### 4-4. 영수증: 최초 응답 재현과 내용 최소화 [미정 D-P3]

충돌 지점: B-2 계약은 "같은 요청 재시도에 처음 응답을 그대로" 돌려준다. 그 처음 응답에 카드 내용(표제어·뜻·예문·문맥 설명)이 들어 있으면(F10), 재현하려면 내용 사본을 보관해야 하고, 내용을 지우면 처음 응답과 달라진다. 또 지금 카드 내용으로 다시 조립하면 "처음 응답"이 아니게 되고, 그사이 뜻이 바뀌었거나 id가 재사용됐다면 **다른 내용**이 나간다(F14).

권장 응답 계약:
- FSRS 평가 응답(처음·재시도 공통)은 **평가 결과만** 담는다: 카드 종류·id, 요청 id, 수락 시각, 등급, `srs`(상태·카드 버전·예약·완료 상태), 정답·오답 수, 신규 집계. 표제어·뜻·예문·문맥 설명은 넣지 않는다. 화면은 이미 카드 내용을 큐에서 받아 갖고 있고, C-2c 컨트롤러는 응답에서 `srs.state.phase`만 쓴다.
- 영수증은 이 응답을 그대로 저장하고, 재시도는 저장본을 그대로 돌려준다. **현재 카드 내용으로 재조립하지 않는다.** 처음 응답과 재시도 응답이 바이트 단위로 같다.
- legacy 계정의 평가 응답(영수증 없음)은 지금 모양 그대로다.

기존 영수증(내용 사본이 든 것) 처리 안:
- 권장(D-P3-a): 승인 뒤 일회성 정리 작업으로 내용 필드만 지운다(평가 결과 필드·해시·로그 id는 유지). 그 뒤 재시도 응답은 처음 응답에서 내용 필드가 빠진 모양이 되며, 이것은 "처음 응답의 결과 부분 재현"으로 계약에 명시한다. 원본을 다시 만들지 않는다. [D-2 준비 보정 K4] 이것은 "재시도 = 처음 응답" 계약의 **명시적 예외**이며 정리 시점 이전 영수증에만 적용된다. 정리 뒤 생긴 영수증에는 예외가 없다.
- 대안(D-P3-b): 보존 기간이 끝날 때까지 그대로 두고 자연 만료.
- 대안(D-P3-c): 바로 전부 삭제(그 요청의 재시도는 아래 "만료 뒤" 규칙을 따름).

보존 기간:
- **예시**(값의 범위를 보이기 위한 것, 결정 아님): 1일, 7일, 30일.
- **권장**: 7일. 근거: C-2c의 재시도는 메모리의 시도 객체로만 일어나 새로고침하면 사라진다(새 저장 키 없음). 실제 재시도 창은 한 화면이 열려 있는 동안이다. 7일은 탭을 오래 열어 둔 경우와 서버 쪽 지연 재처리를 덮는 여유분이다.
- 만료 뒤 같은 요청 재시도: 영수증이 없으므로 새 요청처럼 처리되지만, 카드 버전 비교(CAS) 때문에 처음 평가 뒤 버전이 올라간 카드는 **409 `card_version_conflict`**, 첫 구독 평가(null)는 진도 행이 이미 있어 409, 카드가 지워졌으면 404, 권한을 잃었으면 404다. 두 번 기록되지 않는다. 화면은 409를 받으면 재평가하지 않고 다시 조회한다(C-2c 규칙). 이 동작을 계약에 명시하고 테스트한다.

삭제·권한·롤백:
- 카드 삭제: 그 카드의 영수증에 내용 사본이 있으면 함께 지운다(새 계약 이후에는 원래 없음). 영수증 행은 만료까지 남아도 되지만, 재시도는 카드가 없으므로 404이고 영수증을 돌려주지 않는다(지금도 개인은 카드 조회가 먼저다).
- 계정 삭제: user FK CASCADE(두 DB 모두 영수증에는 user FK가 있음).
- 권한 상실(구독 해제): 지금처럼 현재 권한을 먼저 확인하고 404. 영수증이 권한을 대신하지 않는다 [확인: B-2].
- 롤백: 영수증을 지우거나 바꾸지 않는다. 롤백 뒤 재시도는 처음 결과를 돌려주되 평가를 추가하지 않는다 [확인: B-2].
- id 재사용(F14): 4-7절의 재사용 방지 없이는 위 규칙이 삭제 카드의 응답을 새 카드에 돌려줄 수 있다.

### 4-5. 이전 snapshot [미정 D-P4]

- 롤백이 실제로 읽는 값은 전환 전 카드의 `srs_*` 필드, `review_level`, `next_review_at`, `completion_metric_version`, `first_completed_at`과 `last_log_id`뿐이다(`migration.py:291~305`). 뜻·예문·표제어는 쓰지 않는다.
- 권장: 새 snapshot은 위 필드와 카드 지문(해시)만 저장한다. 기존 snapshot은 승인 뒤 같은 필드만 남기고 내용 필드를 지운다(롤백 결과 불변을 테스트로 확인).
- 보존 기간 예시: 실행 종료 뒤 30일·90일. 권장: 해당 실행의 롤백 가능 기간(승인으로 정함) + 계정이 있는 동안 최소 필드만. 기간이 지나면 그 실행은 롤백 불가로 닫는다(다른 실행의 재전환에는 영향 없음).
- 카드 삭제: 그 카드의 snapshot 내용 필드를 지운다. 롤백은 카드가 없으면 `missing_or_access_lost`로 건너뛰므로 복구되지 않는다 [확인: `migration.py:286`].
- 계정 삭제: snapshot·실행 기록을 계정 id로 찾아 지운다(FK가 없으므로 절차로).
- 권한 상실: 롤백이 현재 권한을 확인해 건너뛴다 [확인].

### 4-6. 권한 상실 뒤 재시도·잔존 자료

- 구독 해제 뒤 재시도: 현재 권한 확인 → 404. 영수증이 권한을 대신하지 않는다.
- 개인 카드 삭제 뒤 재시도: 404. 영수증 내용을 다시 보여 주지 않는다.
- 롤백·재전환은 삭제 카드를 다시 만들지 않는다.

### 4-7. 카드 ID 재사용과 카드 식별자 [미정 D-P2]

생성 시각 비교만으로 해결된다는 이전 권장안은 **철회한다**. 이유:
- 같은 초에 삭제·생성되거나 시각 형식이 다른 경우 순서를 증명하지 못한다.
- 영수증 조회는 시각을 보지 않고 `(user, request_id)`와 카드 키로 맞춘다(F14). snapshot·실행 범위도 `card_ref` 정수만 가진다.
- 읽기 쪽 규칙일 뿐 재사용 자체를 막지 못해, 새로 생기는 혼합을 계속 걸러야 한다.

방안 비교:

| 안 | 내용 | 막는 것 | 한계 |
| --- | --- | --- | --- |
| P2-a 재사용 방지 id 할당 | SQLite 개인 카드 테이블을 AUTOINCREMENT로 재구성(PG는 이미 identity) | 앞으로의 재사용 | **AUTOINCREMENT의 시작점은 테이블에 지금 남은 최대 id 기준이다.** 이미 지워진 최대 id(로그·영수증·snapshot·실행 범위에만 남은 id)보다 작은 값부터 다시 줄 수 있으므로, 재구성 때 시퀀스를 "카드 테이블·두 로그·영수증·snapshot·실행 범위에서 본 최대 id" 이상으로 맞춰야 한다. 그래도 이미 혼합된 과거 자료는 그대로 |
| P2-b 불변 카드 식별자 | 카드마다 바뀌지 않는 별도 식별자(예: 무작위 UID)를 두고, 로그·영수증·snapshot이 그것을 함께 기록 | 앞으로의 혼합(정수 id가 겹쳐도 UID로 구분) | 모든 참조 테이블 스키마 추가, 기존 행에는 UID가 없어 과거 자료 구분은 못 함 |
| P2-c 삭제 카드 원장 | 카드를 지울 때 `(종류, 계정, id, 삭제 시각)`만 기록(내용 없음) | 과거 혼합의 탐지 근거 | 원장 이전에 일어난 재사용은 탐지 못 함. 단독으로는 재사용을 막지 못함 |
| (철회) 생성 시각 비교 | 카드 생성 시각보다 이른 로그를 제외 | - | 위 이유로 해결책이 아님. 탐지 신호로만 쓴다 |

권장: **P2-a(시퀀스를 남은 참조의 최대 id 이상으로 맞춘 재구성) + P2-c(이후 삭제 원장)**. P2-b는 정수 id가 계속 유일해지면 필요성이 낮고 변경 범위가 크므로 보류한다. PG는 identity라 P2-a가 불필요하지만, 재구성 없이도 원장(P2-c)은 두 DB에 같게 둔다.

현재 카드 이력과 삭제된 카드의 과거 실적을 함께 보존하는 계약:
- 재사용 방지 이후, 카드 정체성은 `(종류, 계정, id)`로 유일하다. 로그·영수증·snapshot은 그 정체성에만 묶인다.
- 삭제된 카드의 로그는 그 정체성으로 계속 남아 오늘 평가 횟수·오늘 새 단어(이미 쓴 하루 목표)·기록 달력에 들어간다. 새 카드는 그 로그를 이력으로 보지 않는다(정체성이 다름).
- 현재 카드의 이력·완료·첫 평가 날짜는 자기 정체성의 로그로만 계산한다.

이미 혼합된 자료(재사용 방지 이전): 추정 재연결·삭제를 하지 않는다.
- 탐지 신호: 같은 `(개인, 계정, id)`에 대해 카드 생성 시각보다 이른 로그·영수증·snapshot, 원장 기록, 카드 행과 맞지 않는 로그 사슬. 신호는 "혼합 의심"으로만 쓴다.
- 의심 카드는 **식별 불가**로 표시한다: 그 id의 로그 전체를 그대로 두고, 어느 쪽 카드의 것인지 정하지 않는다.
  - FSRS 전환: 하지 않는다(차단, 보고서에 표시).
  - 완료 판정: 확인 불가.
  - 첫 평가 날짜: 확인 불가. 단 지금처럼 계정 전체 신규 수를 확인 불가로 만들면 신규 학습이 멈추므로, "확인 불가가 영향을 줄 수 있는 날짜(그 id의 로그가 있는 서울 날짜들)"를 셀 때만 확인 불가로 하는 날짜 한정 규칙을 함께 승인받는다 [미정 D-P6].
  - 오늘 평가 횟수·기록 달력: 로그 행 수라 그대로 센다(실제 평가였던 것은 맞다).
  - 영수증: 그 id의 옛 영수증은 재시도에 쓰지 않는다(새 카드 URL에서 404 또는 409로 끝나게). 내용 사본은 4-4 정리에 포함.
  - snapshot·실행 범위: 그 id를 가리키는 옛 실행의 롤백은 해당 카드에 대해 건너뛴다.
- 사용자에게는 이전 검토 보고서에 표시만 하고, 카드별 수동 정리 도구는 후속(승인 8과 같은 방식).
- [D-2 준비 보정, `../gate-d2/APPROVAL_REQUEST.md` K2·K3] 날짜 한정 규칙은 그 id 로그의 시각을 **모두 읽을 수 있을 때만** 쓴다. 하나라도 읽을 수 없으면 손상 시각 규칙(계정 전체 확인 불가)을 따른다. 탐지 신호는 의심일 뿐이며, 원장 이전·같은 초·형식이 다른 시각의 재사용은 탐지하지 못할 수 있다(이미 섞인 자료를 전부 찾는다고 보장하지 않음).

### 4-8. 검증과 출시 차단

- 제약 변경·삭제 정책 변경·재구성은 이번에 구현하지 않았다.
- 로컬 PostgreSQL이 없다. 설치·원격 DB로 우회하지 않는다. **보호 검사를 통과한 빈 로컬 PG에서 4절과 B-2·C-1·C-2 동시성·롤백을 실행하기 전까지 운영 전환은 차단**이다(E 단계). PostgreSQL은 미검증이다.
