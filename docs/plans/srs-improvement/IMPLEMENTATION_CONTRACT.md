# SRS 교체 데이터/실행 계약 초안

작성: 2026-10-08. 상태: 권장 설계, Gate A 승인 전. 실행 가능한 마이그레이션/제품 코드를 만든 문서가 아니다.
제품 원리는 `PRODUCT_SRS_DESIGN.md`, 순서는 `REPLACEMENT_PLAN.md`를 따른다.

## 1. 식별자와 상태

- 개인 카드: `(user_id, vocab_item_id)`.
- 구독 카드: `(user_id, lexeme_id)`; shared_deck_id는 출제 문맥/접근 권한이지 카드 정체성이 아니다.
- 같은 lexeme가 여러 구독 덱에 있어도 같은 카드다. 개인 카드와 구독 카드를 표제어로 합치지 않는다.
- 원문 전체는 서버에 새로 보내지 않는다. 기존 예문/뜻 저장의 허용 범위도 확장하지 않는다.
- `status`는 기존 자기분류 그대로다. `participation`과 FSRS 상태는 분리한다.
- 신규 미평가 카드는 FSRS Card의 '즉시 due'와 달리 제품에서 별도 신규 후보로 취급한다. 생성만으로 예정 복습 수가 늘지 않는다.
- '학습 완료'는 완료 판정 함수의 결과다. 새로운 FSRS 종결 state를 만들지 않는다.

## 2. 스키마 방향

기존 `vocab_items`/`user_word_progress`와 두 로그 테이블을 유지하고 추가형 확장을 우선한다. 통합 generic-card 테이블로 기존 FK/권한을 전면 교체하지 않는다.

카드별 후보 필드:

| 필드 | 의미 |
| --- | --- |
| `srs_engine` | legacy / fsrs, 기본 legacy |
| `srs_version` | 실제 어댑터/라이브러리 버전 |
| `srs_config_version` | 정확한 파라미터/단계/유지율/상한 설정 참조 |
| `srs_state` | 미평가 null 또는 Learning/Review/Relearning의 검증된 표현 |
| `srs_stability`, `srs_difficulty`, `srs_step` | 엔진이 유지해야 하는 상태. 누락/NaN/범위 위반 검증 |
| `srs_due_at`, `srs_last_review_at` | UTC의 실제 FSRS 예약/평가 시각 |
| `srs_card_version` | 서버의 단조 증가 버전, CAS 및 응답 검증 |
| `srs_participation`, `srs_pause_reason` | active / paused, 명시 보류 또는 legacy 제외 의도 구분 |
| `srs_history_quality` | complete / incomplete / fresh, 완료 검증 증거 구분 |
| `completion_metric_version`, `first_completed_at` | 최초 완료 이력/판정 버전. 현재 완료를 이 시각 유무만으로 판단하지 않음 |

정확한 컬럼 타입/상태 번호/NOT NULL/인덱스는 고정 라이브러리 직렬화와 두 DB를 확인해 Gate A에서 확정한다.
JSON과 정규 컬럼을 둘 다 권위 상태로 쓰지 않는다. 이 안은 정규 컬럼을 권위로 하고, 완전한 before/after 직렬화는 로그/이전 snapshot에 저장하는 방향이다.
`next_review_at`/`last_reviewed_at`는 기존 조회 호환용으로 같은 트랜잭션에서 동기화한다. FSRS 코드가 옛 `review_level`로 기억 상태를 판단하지 않는다.
기존 `review_level`/간격 함수는 전환 비교/롤백을 위한 legacy projection으로만 사용하고, 일반 화면에 FSRS 단계인 것처럼 표시하지 않는다.
설정 변경은 버전을 생성하며 모든 due를 자동 재계산하지 않는다. 현재 S에 일괄 배수를 곱하지 않는다.
보류/재개 등 큐 참여를 바꾸는 동작도 카드 version을 증가시켜 이미 열린 옛 질문의 평가를 막는다. 단어 뜻 수정은 별도 내용 버전/질문 재확인으로 처리할지 Gate A에서 확정한다.

두 기존 로그에 요청/엔진/설정/카드 버전 및 상태 전후 snapshot을 추가한다. 기존 로그 한 행은 여전히 평가 한 회다.
새 테이블 후보:

- `srs_user_settings`: 모드, 설정 참조, 계정 하루 신규 목표, 버전. 계획 자체를 서버 저장하는 테이블이 아니다.
- `srs_review_receipts`: `(user_id, request_id)` 유일, 정규 요청 hash/응답 snapshot/이벤트 참조. 원문/토큰/비밀번호 없음.
- `srs_migration_runs` 및 snapshot: 카드 범위/기준 버전/이력 품질/단계/검산값/되돌리기 자료. 운영 원자료는 문서에 넣지 않음.
- `srs_intake_reservations`: 엄격한 신규 상한(S2)을 후속으로 별도 승인할 때만 추가한다. 1단계 범위 밖이며 TTL/자정/만료 후 평가/유예는 그때 정한다(Gate A 보정).

큐 인덱스는 user+participation+state+due, 카드 유일키, 로그 user+card+time+id를 중심으로 검토한다.
PostgreSQL 전용 SQL을 문자열 치환으로 SQLite에 억지 적용하지 않는다. 기존 어댑터의 트랜잭션/rowcount/RETURNING 특성을 확인한다.
스키마 생성은 추가형으로 멱등 처리하되, 자료 재생/운영 전환은 앱 시작의 `init_db()`에서 자동 실행하지 않는다.

## 3. 평가 API

기존 개인/구독 평가 URL을 유지하고 FSRS 필드를 확장하는 방향이다.

```text
POST /study-items/{item_id}/review
POST /shared-decks/{shared_deck_id}/words/{lexeme_id}/review

request: rating, request_id, expected_card_version,
         session_id (문맥). introduction_claim은 S2 별도 승인 시에만 추가
response: 기존 허용 필드 + srs, completed, completion_metric_version,
          request_id, accepted_at, server_now
```

사용자가 전달한 client 시간/유지율/S/D/owner를 그대로 신뢰하지 않는다. 유효 시각/계정은 서버 기준이다.
개인 response_time_ms는 계속 참고용일 뿐 의미 인출 속도나 등급 입력으로 쓰지 않는다.

처리 순서:

1. 인증/카드 접근 확인. 구독 URL이 current subscription을 통과하는지 확인한다.
2. 같은 계정 request_id의 영수증이 있으면 같은 내용에 같은 결과를 반환한다. 다른 카드/등급 내용이면 409, 쓰기 없음.
3. 카드 현재 version과 expected version을 비교하고, 첫 평가이면 계정의 오늘 신규 수를 정확히 다시 센다(목표 초과로 거부하지 않음).
4. UTC 시각에 고정 엔진을 실행한다.
5. 카드 CAS, 기존 한 평가 로그, 신규/성공/완료 증거, 영수증을 한 트랜잭션으로 기록한다.
6. 전체 성공 뒤 응답한다. 어느 단계든 실패하면 평가 일부만 남기지 않는다.

두 요청이 같은 옛 version을 쓰면 서로 다른 request_id라도 하나만 성공한다. 같은 request_id 동시 요청도 유일 제약과 트랜잭션으로 한 평가만 남는다.
클라이언트는 응답 유실 때 request_id를 바꾸지 않는다. 409는 조용히 새 버전으로 재평가하지 않고 카드/결과를 다시 확인한다.
FSRS 카드에 새 필드 없는 옛 클라이언트는 명확한 업그레이드 필요 오류로 멈추게 한다. 안전성 없는 legacy 요청을 FSRS로 자동 처리하지 않는다.
legacy 계정/카드는 전환 중 기존 요청을 계속 지원한다. 배포 순서에서 서버 먼저/프론트 다음/명시 활성화를 지킨다.

미래 예정 카드를 자동 큐가 먼저 평가하지 않는다. 자유 복습은 별도 명시 연습으로 유지하는 안을 권장한다.
단순 '미리 보기'는 SRS/로그를 바꾸지 않는다. 조기 평가를 SRS에 반영할 기능은 별도 확인과 엔진의 실제 경과 시간 처리로 제공할지 Gate A에서 정한다.

## 4. 조회와 동적 큐

신규 읽기 전용 `GET /study-queue` 후보를 사용하고 기존 두 study-items URL은 전환 중 호환 경로로 유지한다.
필터 예: scope(전체/개인 덱/구독 덱), mode, limit, cursor. 허용 mode 목록과 필터 조합을 검증한다.

응답 후보:

```text
items: 카드 종류/식별자/출제 덱/현재 version/학습 단계/내용/예약
counts: new_available, learning_due, review_due, relearning_due,
        pending_later, paused, new_introduced_today
next_due_at, server_now, scheduler_version, next_cursor
```

- 조회 GET은 카드 평가/claim/실적 생성 없이 읽기 전용이다.
- 재학습/학습 due -> 장기 due -> 신규, 같은 단계에서는 시각 우선. 동률은 안정적인 tie-break로 pagination 누락/중복을 막는다.
- 구독 교집합을 dedup하고 개인+구독은 별개로 합친 뒤 전역 우선순위를 적용한다. 종류별 LIMIT 후 단순 이어붙이기 금지.
- 페이지 cursor/설정 버전이 변경된 경우 재조회한다. 업데이트되는 큐를 고정 완결 snapshot이라고 보장하지 않는다.
- 타이머는 다음 도래 시점/앱 복귀에서 읽기 요청만 한다. 빈 큐를 바쁜 polling으로 계속 호출하지 않는다.
- 다음 간격은 서버가 같은 카드 version/설정에서 미리 계산한다. 버튼 표시는 추정이고 확정 due는 실제 평가 시각 결과다. 표시를 맞추려고 엔진 결과를 수정하지 않는다.
- 최초 파일럿에서 fuzz를 끄는 안은 테스트 재현 목적이다. 후속 분산을 켜면 실제 선택 결과를 저장하고 재시도에 재사용해야 한다.

## 5. 신규량과 두 기기

계획 Q는 로컬 목표다. 계정 전체 하루 신규 목표는 서버 설정이다(초기 후보 20개, 상한이 아닌 목표). 서로 다른 기기의 Q를 자동 동기화하거나 몰래 상한 변경 요청으로 바꾸지 않는다.
카드의 유효 첫 평가를 서울 날짜별 신규 1개로 센다. 첫 Again도 1개, 같은 카드 재평가는 0개다.
구독은 계정+lexeme 최초 평가 기준이며 개인은 vocab_item 기준이다. 과거 자료 이전은 '오늘 신규' 이벤트를 생성하지 않는다.

큐가 내는 신규량은 Q 잔여, 계정 목표 잔여, 대상 미평가 잔량의 최소를 따른다. 날짜가 바뀌면 서버 값으로 다시 확인한다.
1단계(S1)는 정확한 첫 평가 집계와 큐 재조회에 기반한 하루 신규 목표다. 서버는 어떤 카드가 실제로 화면에 표시됐는지 증명할 수 없으므로, 여러 기기·창이 각각 받아 둔 신규 카드를 평가하면 목표를 넘을 수 있고 초과량의 상한도 약속하지 않는다. 이미 받은 카드의 첫 평가는 거부하지 않는다.
새 단어 더 학습은 명시 선택한 양의 버전 있는 추가 목표량으로 처리한다. 재시작/다른 모드로 조용히 목표를 우회하지 않는다.

엄격한 상한(S2, 후속·별도 승인)을 다룰 때의 검토 항목 (이번 계약 범위 밖, 구현·검증 안 함):

- 카드 질문 표시 전에 읽기 조회와 별도로 claim한다. 계정 일일량을 잠그고 이미 평가/예약된 카드와 잔여량을 재확인한다.
- 평가되지 않은 예약은 실적이 아니다. 한 번에 과도한 카드 수를 예약하지 않고, 활성 신규 질문의 소량 예약을 우선한다.
- claim은 계정/카드/서울 날짜/요청 ID에 묶고 TTL/새로고침/취소/자정 만료 규칙을 확정한다.
- 동일 카드 두 창 claim은 서로 다른 신규 자리 두 개를 차지하지 않는다. 예약 연장/분실 응답 재시도는 같은 ID로 처리한다.
- 평가에서 예약을 소비하고 최초 이벤트를 기록한다. 대기 중 상한/날짜/예약이 바뀌었으면 질문 표시 전에 다시 확인한다.
- 자정 경계에서 표시한 카드의 평가를 어느 날로 셀지, TTL 도래 뒤 아직 답하는 카드의 유예를 S2 승인 때 정한다. 만료 후 평가를 받아들이면 엄격한 상한이 깨지고 거부하면 한 학습을 버리므로, 둘 중 무엇을 택할지가 승인 대상이다. 임의로 전날 시각을 만들어 기록하지 않는다.

Gate A 보정 권장: 서버 엄격한 상한은 별도 후속 단계로 분리한다. S2를 구현·검증하기 전에는 '상한 보장', '두 기기 실제 상한'이라고 표시·보고하지 않는다.
클라이언트 slice만으로 다중 기기 한도를 구현했다고 주장하는 우회는 허용하지 않는다.

## 6. 완료와 진도

표시 용어: 학습 완료. 내부 버전 후보: `meaning-completion-v1`.
기준: Review, S>=30일, 마지막 Again 이후 2개 서울 날짜에서 성공, 그중 직전 유효 평가와 7일 이상 간격 성공.
정확한 경계는 UTC 경과 7*24시간과 서울 distinct date로 테스트한다. Hard는 성공에 포함하며 무효/취소 이벤트는 제외한다.
보류/실패는 현재 완료 분자에서 빠질 수 있다. 실패 후 '재학습 필요', 과거 first_completed_at은 유지한다.
단지 시간이 지나 R이 낮아졌다는 이유로 완료 상태를 매일 해제하지 않는다. 완료 뒤 due 카드도 유지 복습 큐에 남는다.
증거가 불완전하거나 엔진 상태를 아직 계산하지 못했으면 완료를 0으로 단정하지 않는다.

`GET /learning-plan/progress`의 기존 `metric_version=first-review-v1`, total/seen/progress_scope를 보존하고 다음을 추가하는 안이다.

```text
completion_metric_version, completion_status(ready|unavailable),
completed (미확인 null), paused, needs_relearning,
introduced_today, new_goal_remaining (해당 요청의 Q가 있는 경우)
```

첫 학습=seen, 학습 완료=completed. 기존 로컬 계획 payload가 first-review-v1을 담고 있어도 손상으로 삭제하거나 완료 지표로 바꾸지 않는다.
추가 완료 응답 검증은 별도 함수로 하고 옛 저장본/다른 창 충돌 보호를 유지한다.
빈 덱은 '덱에 단어가 없어요', 0/0 학습 완료 100%로 처리하지 않는다.
완료 예상 기간은 후속 시뮬레이터가 있는 경우만 범위로 표시한다. 첫 학습 예상일을 완료일로 이름만 바꾸지 않는다.
계획 Q 변경/새 단어 수/오늘 평가 수의 서로 다른 단위를 유지한다.

통계 기존 known_count/learned_rate는 자기분류 수치로 유지한다. 완료 지표는 별도다.
UTC 기준인 기존 오늘 집계를 서울 기준으로 통일할지 Gate A에서 API 영향표로 확정한다. 임시로 둘을 같은 라벨로 섞지 않는다.
옛 레벨 그래프는 유지 복습 단계/재학습 분포로 교체할 수 있지만 기록장 실루엣을 바꾸는 디자인 작업과 섞지 않는다.

## 7. 이력 이전과 되돌리기

자료 분류:

| 종류 | 권장 처리 |
| --- | --- |
| 미평가 | FSRS 신규 후보, 기존 분류/서버 ID/자료 유지 |
| 완전하고 일관된 로그 | UTC 시각 + 등급 + log ID 순으로 결정적 재생, 원로그 보존 |
| 연결 끊김/순서 불명 동시각/누락/잘못된 등급/카드값 불일치 | 의심 내용을 조용히 제거하지 않음. incomplete로 분류해 승인한 재초기화 정책 사용 |
| 짧은 간격 같은 등급 연속 평가 | 시간 간격만으로 incomplete로 보지 않음. 의심 표시로만 기록하고 로그 연결·카드 상태로 판정(`gate-a/DECISIONS.md` 6-1). 원로그 삭제·추정 중복 제거 없음 |
| legacy known | 기존 제외를 보류 이유로 보존. 사용자 동의로 재참여, 완료 자동 부여 없음 |
| 삭제된 카드의 로그 | 기록으로 보존, 카드를 임의 복구/신규 생성하지 않음 |

불완전 이력 권장 초안: 기존 last_reviewed_at/seen/로그/예약은 보존하고, 다음 실제 평가에서 새 FSRS 추정을 시작한다. 완료 증거는 신뢰 가능한 이후 평가로 쌓는다.
이력이 불완전하다고 신규 목표를 다시 소비하거나 first-review를 오늘로 바꾸지 않는다.
실제 초기화 시 어떤 카드 상태로 시작할지는 이전 시각/현재 평가를 포함한 검산 후 승인한다. 레벨을 S로 근사하지 않는다.

완전 이력도 기존 due를 전환 시 일괄 앞당기지 않는 안을 우선한다. '전환 첫 예약만 legacy due 유지 -> 다음 실제 평가부터 FSRS 예약'을 검증한다.
FSRS 계산 due와 전환 유예 effective due를 구분해 남긴다. 해당 due/파라미터 변경을 모델이 계산한 결과로 위장하지 않는다.
로그 재생으로 학습 완료를 판정할 수 있는지 또한 신뢰도/증거를 검사하고, 불완전 카드를 임의 완료하지 않는다.

이전 도구는 dry-run 기본, 명시 user/card 범위, 실행 ID, batch/cursor, snapshot+카드 version 확인, 재시작 가능성을 가진다.
경합한 카드/실패 batch는 미적용으로 남긴다. 앱 startup에 모든 계정 재생을 넣지 않는다.
백업/이전 원자료/DB URL을 일반 reports/references/커밋에 넣지 않는다. 로컬에서는 합성 SQLite/빈 테스트 PG만 사용한다.

롤백은 snapshot 이후 이벤트를 전부 유지한 채 legacy로 재생하는 별도 검증 경로다. 전환 이전 백업만 덮어쓰면 새 평가가 유실되므로 금지한다.
재생은 간격/기억 상태의 projection이며 기존 record_review 함수를 다시 호출해 평가 로그/정답 수를 중복 생성하지 않는다. 옛 구독 자동 분류도 재적용하지 않고 사용자 분류를 보존한다.
계정 단위 모드 복귀, 기존 예약 보호, 로그/실적 건수, 재전환 멱등성을 실제 DB에서 확인한다.
기존 함수/컬럼 제거는 모든 전환/롤백 필요가 끝난 별도 단계다.

## 8. 프론트 저장/세션 경계

평가 시작 snapshot = accountEpoch, sessionId, currentCardKey, expectedVersion, requestId, requestGeneration.
await 뒤 map/count/index/안내/통계 갱신 및 catch/finally 앞에서 snapshot이 여전히 유효한지 확인한다.
계정 전환 즉시 기존 질문/응답/대기/claim/재시도를 비운다. 취소로 서버 승인 평가가 자동 취소됐다고 가정하지 않는다.
응답 유실은 같은 계정/요청의 결과를 재확인한다. 새 계정에 이전 요청을 재전송하지 않는다.
서버에 이미 A로 기록된 평가는 B 화면에 적용하지 않되, A 이력에는 정상 평가로 남는다.
이어하기/교체/취소는 기존 planStudyLauncher 보호를 유지한다. 큐 fetch는 평가 진행 중 세션을 바꾸지 않는다.
동적 큐 추가로 세션 position/version이 바뀌는 규칙을 명시해 confirm snapshot이 잘못 유효해지지 않게 한다.
서버 읽기/평가 실패 시 현재 단어와 입력은 보존한다. 확인 전 카드 넘김/낙관적 실적 증가는 하지 않는다.
읽기 원문 v3 owner/instanceId/revision/Web Locks, 복구 UI, 원문 서버 전송 금지는 변경하지 않는다.

## 9. 범위 밖

개인 optimizer, 완전한 암기/언어 활용 자동 판정, 역방향/뜻별 카드 분해, 오프라인 평가 동기화, 계획 서버 동기화, 최근 평가 되돌리기는 첫 교체의 필수 범위가 아니다.
되돌리기를 후속 도입하면 취소 이벤트/상태 재생/실적 정합성을 별도 계약으로 구현한다.
실제 학습 효과 검증은 합성 테스트나 빌드 성공과 별개로 보고한다.
