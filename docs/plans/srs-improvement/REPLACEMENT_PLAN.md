# FSRS 기반 SRS 교체 작업 계획

작성: 2026-10-08. 코드 기준: main `e2c07f8bcc534713587f628cf3f8f9f798bb2e5a`.
상태: 설계/준비 완료, 제품 구현 및 운영 전환 전. 실제 체크아웃은 작업 시작 시 재확인한다.

## 1. 확정과 제안의 경계

확정: 표시 용어는 '학습 완료'. 기존 고정 단계 SRS를 FSRS 기반 시스템으로 대체하는 작업을 준비한다.
학습 완료 뒤에도 유지 복습이 이어진다. 실패 시 '재학습 필요'가 되며 과거 완료 이력은 보존한다.

아래 수치와 변경 정책은 권장 초안이지 승인 완료가 아니다. Gate A에서 묶어서 승인받는다.

| 항목 | 권장 초안 |
| --- | --- |
| 엔진 | Python `fsrs==6.3.2` 검증 후보, 구현 전 실제 배포물 재확인 |
| 목표 유지율 | 0.90, 고정한 라이브러리 기본 파라미터 |

학습 단계/365일/20개/완료 문턱은 과학적으로 확정된 최적값이 아니라 제품 검증용 초안이다.

## 3. 구현 단계와 중단 지점

### Gate A: 계약 확정과 기준선

- 기존 감사 15항목을 합성 SQLite에서 다시 측정한다. 기존 정책의 재현을 새 정책 통과로 보고하지 않는다.
- 평가 응답 지연 중 계정 전환/세션 교체/초기화, 응답 유실 재시도, 두 창 중복 평가를 실제 앱에서 재현한다.
- 최신 버전이라는 이유로 다른 알고리즘 세대를 선택하지 않는다. 6.3.2 배포물의 API/당일 전이/파라미터/라이선스/서버 Python 호환성을 확인한다.
- 위 권장 수치, known 이전, 하루 상한/예약, 자유 복습, 완료 실패 후 표시를 승인표로 정리한다.
- 합성 이력 분류표, API/스키마 diff 초안, 롤백 검산표를 작성한다. 운영 DB 접근/변경 없음.
- 보고: `gate-a/REPORT.md`, `DECISIONS.md`. 미정 계약이 있으면 코드 교체 전에 멈춘다.

### Gate B-1: 엔진 어댑터와 추가형 스키마

- 승인 버전을 requirements에 정확히 고정한다. optimizer/외부 업로드는 도입하지 않는다.
- 주어진 UTC 시각과 4종 평가로 카드 전이/간격/직렬화를 계산하는 순수 어댑터와 완료 판정 함수를 만든다.
- 카드/로그 확장, 계정 설정, 평가 영수증을 추가한다. 신규 예약(엄격한 상한)은 별도 승인 전 추가하지 않는다. 기존 자료/로그를 덮거나 삭제하지 않는다.
- SQLite와 PostgreSQL DDL 둘 다 작성하고 보호된 새 로컬 PG에서 실행한다. PG가 없으면 보류로 보고하고 설치/운영 DB로 우회하지 않는다.
- 기본 동작은 legacy다. schema를 배포했다고 자동으로 새 엔진을 켜지 않는다.

### Gate B-2: 평가 원자성 및 이력 이전

- 개인/구독 평가를 권한 검사 -> 요청 영수증 -> 카드 버전 비교 -> 엔진 -> 카드/로그/실적/영수증 한 트랜잭션으로 연결한다.
- 무효 등급/시각/권한, 동일 요청 ID의 다른 내용, 다른 창 stale version, 저장 중 오류를 처리한다.
- 이력 재생 dry-run, 결과 diff, 재실행, 중간 실패, 새 평가와 이전의 경합을 검증한다.
- 불완전 로그는 승인한 보수적 초기화 정책으로만 처리한다. old review_level -> S 임의 환산 금지.
- 새 FSRS 이력과 기존 레벨 경로의 비교 상태를 분리해 보존한다. 실제 큐는 아직 legacy로 유지한다.

### Gate C-1: 통합 큐 및 신규량

- 읽기 전용 통합 큐에서 개인/구독 권한, 참여, 신규/due를 먼저 거른 후 전역 우선순위/중복 제거/LIMIT을 적용한다.
- 하루 신규 목표는 첫 평가 트랜잭션의 정확한 신규 집계와 큐 재조회로 적용한다. 조회만으로 평가 실적을 올리지 않는다. 서버는 어떤 카드가 실제로 표시됐는지 알 수 없으므로 여러 기기·창의 엄격한 상한은 보장하지 않으며, 그렇게 표현하지 않는다.
- 엄격한 상한(예약/claim)은 후속 작업으로 분리한다. 예약 TTL·자정·평가 중 만료·유예는 서로 맞물리는 결정이므로(만료 후 평가를 받으면 엄격한 상한이 깨진다) 그때 별도 승인한다. 1단계는 이미 받은 카드의 첫 평가를 목표 초과로 거부하지 않는다.
- 기존 모드 today/new/unknown/uncertain/all을 누락 없이 매핑한다. 상태 필터가 곧 완료/예약 조건이 되지 않도록 한다.
- due/신규/대기/보류 개수, 다음 도래 시각, server_now를 같은 카드 식별자 기준으로 반환한다.

### Gate C-2: 실제 복습 세션

- 평가 중 같은 카드 중복 클릭 차단, 요청 ID 유지 재시도, account epoch/session ID/card version 확인을 연결한다.
- 오래된 catch/finally도 새 세션의 진행 표시/안내/인덱스를 바꾸지 못하게 한다.
- 현재 카드를 타이머가 바꾸지 않도록 하고, 다음 카드 경계/앱 복귀에서 큐를 재확인한다.
- Again 뒤 미래 대기 카드가 있으면 재등장 시각을 보여 주고 종료를 허용한다. 카드를 즉시 무조건 반복시키지 않는다.
- 이 단계부터 합성 계정에만 FSRS를 명시적으로 켜 실제 흐름을 검증한다. 자유 복습의 조기 평가 정책은 Gate A 승인안을 따른다.

### Gate D: 계획/통계 및 이전 리허설

- 첫 학습은 seen, 학습 완료는 별도 completed로 연결한다. 첫 Again은 seen에만 포함될 수 있다.
- 오늘 신규 개수/평가 횟수/예정 카드 수를 분리한다. 서울 자정과 계정 전환/늦은 응답을 다시 검사한다.
- 목표 기간과 첫 학습 예상일을 유지하되, 데이터/시뮬레이터 없는 완료 예상일은 제공하지 않는다.
- 기존 로컬 계획과 원문 저장 키는 변경하지 않는다. 기존 metric_version을 완료 지표라고 재해석하지 않는다.
- 합성 이력으로 전환 -> 평가 -> 실패 -> 롤백 -> 재전환을 리허설한다. 단어/분류/모든 평가 건수와 권한을 검산한다.
- 1280/390부터 실제 화면 판정, 최종 후보는 1920/1024/800/375/320도 확인한다. 기존 지면 재디자인은 하지 않는다.

### Gate E: 출시 후보 검증

- SQLite + 실제 보호된 로컬 PG의 일치, 권한/두 창/재시도/자정/이전 검증을 완료한다.
- 전체 프론트 테스트/타입, 백엔드 테스트/회귀/구독 smoke, 최종 build, diff check를 실행한다.
- 부하 검사는 1천/1만 카드에서 큐/예정 집계/진도 조회를 측정한다. 수치를 근거 없이 통과 기준으로 만들지 않는다.
- 토큰/비밀번호/QA 훅/임시 DB/원문/스크래치가 제품 코드/커밋 후보에 없는지 검사한다.
- 운영 전환 runbook과 중단/복구 조건을 보고하고 멈춘다. 커밋/푸시/병합/운영 마이그레이션은 별도 승인이다.

출시 후보 통과는 알고리즘이 실제 학습 효과를 개선했다는 증명이 아니다.
출시 후 파일럿은 실제 지연 회상 성공률/예측 보정/연체/학습 부담을 관찰하고 완료 기준을 보정한다.
실제 사용자 로그가 없으면 예측 우수성 검증을 '미검증'으로 표시한다. 합성 데이터로 대신 통과시키지 않는다.

## 5. 롤아웃과 중단

모드 제안: legacy(기존) -> shadow(비활성 비교) -> fsrs(명시 활성화).
shadow는 기존 카드 결과/통계에 영향을 주지 않는 비교다. 한 평가를 두 로그로 세거나 실적을 두 번 늘리지 않는다.
계정 설정/스케줄러/파라미터/완료 기준 버전과 카드의 계산 버전을 저장한다. 버전이 불명확하면 자동 fallback하지 않고 쓰기를 멈춘다.

중단: 계정 자료 혼입, 평가 중복/유실, 카드-로그 불일치, 대량 due 앞당김, 신규 집계 불일치, PG 불일치.
롤백은 오래된 DB 백업으로 운영 평가를 지우는 방식이 아니다. 전환 snapshot + 전환 이후 유효 평가 이벤트를 재생해 legacy 상태를 복구하고 모든 새 평가를 보존해야 한다.
파일럿 뒤 비교 상태를 제거할 때도 실제 사용자 이력은 삭제하지 않는다. 옛 간격 함수/컬럼 삭제는 별도 후속 단계다.

## 6. 준비 상태

- 이번에 한 것: 코드 경로 재확인, 공식 라이브러리 메타데이터 확인, 제품 용어 보정, 계획/계약/첫 지시 문서 작성.
- 하지 않은 것: 제품 코드 수정, FSRS 설치, 테스트 DB 연결, 운영 접근, 브랜치 생성, 스테이징/커밋/푸시/병합.
- 예정 브랜치 이름: `codex/fsrs-srs-replacement`. 생성은 별도 요청/작업 시작 시 진행한다.
- 기존 `docs/roadmap.md`, tsbuildinfo, 미추적 이미지/목업/QA 파일은 그대로 둔다.
- 첫 실행 단계는 Gate A다. 이후 단계는 해당 결과를 검토하고 승인한 뒤 진행한다.
- 문서 준비만 한 이번 단계에는 제품 테스트/빌드를 새로 실행하지 않는다. 감사/계약을 구현 통과로 보고하지 않는다.

## 7. 확인한 외부 원본

- [fsrs 6.3.2 배포 정보](https://pypi.org/project/fsrs/6.3.2/): Python >=3.10, MIT. Python 3.14/배포 환경의 실제 동작은 아직 실행하지 않았다.
- [py-fsrs 구현/설정](https://github.com/open-spaced-repetition/py-fsrs): UTC, 상태 직렬화, 학습 단계/유지율/최대 간격 설정. 우리 임시 수치는 원본 기본값과 구분한다.
- [알고리즘](https://github.com/open-spaced-repetition/awesome-fsrs/wiki/The-Algorithm): 기억 계산과 제품의 완료 판정은 별도다.

main 브랜치 문서/소스와 고정 배포 버전을 동일하다고 가정하지 않는다. Gate A 결과에 실제 고정 배포물과 확인 날짜를 기록한다.
