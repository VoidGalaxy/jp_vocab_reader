## 1. 세션과 평가 보호

### 1-1. 식별자 [확정 방향: IMPLEMENTATION_CONTRACT 8절 + B-2] / 세부 [제안]

| 값 | 생성 시점 | 용도 |
| --- | --- | --- |
| `accountEpoch` | 기존 `statsAccountEpochRef` | 계정 경계 |
| `sessionId` | 회차 시작·교체·초기화 때 새 무작위 문자열(`crypto.randomUUID`, 서버 허용 문자, 128자 이하) | 서버 `session_id`, 화면 갱신 소유권, 회차 미루기 범위 |
| `sessionSeq` | 기존 `studySessionIdRef` 정수 | 같은 탭 안 빠른 비교 |
| `attempt` | 평가 버튼을 누른 순간 한 번 고정 | 1-2 |

### 1-2. 평가 시도 고정 [제안]

버튼을 누른 순간 다음을 묶어 **불변 객체**로 고정한다. 재시도는 이 객체를 그대로 다시 보낸다.

```text
attempt = {
  accountEpoch, sessionId, sessionSeq,
  card: { kind, id, versionField, sharedDeckId },
  payload: { rating, request_id, session_id, response_time_ms (개인만),
             expected_card_version: <정수> 또는 명시적 null(구독 최초 평가, 3-2) },
  token
}
```

- `response_time_ms`와 `expected_card_version`은 서버 요청 해시에 들어가므로 처음 값 그대로 보낸다. 명시적 null은 null로, 정수는 같은 정수로 보낸다.
- 화면의 "현재 카드"는 `(sessionId, kind, id)`로 식별한다. 위치 index만으로 판단하지 않는다.

### 1-3. 결과 적용 규칙 [제안]

응답(성공·실패·네트워크 오류)과 `finally`는 **다음이 모두 맞을 때만** 화면에 적용한다.

1. `attempt.accountEpoch === 현재 epoch`
2. `attempt.sessionId === 현재 sessionId`
3. 현재 카드가 `attempt.card`와 같은 카드
4. 이 시도가 그 회차의 현재 진행 중 시도

하나라도 다르면 응답을 버린다. 서버에 이미 기록된 평가는 그 계정 이력에 정상으로 남는다. 화면 진행 수, 카드, 안내, 통계, 회차 미루기 집계, 버튼 상태를 바꾸지 않는다. `isReviewing`은 전역 값이 아니라 "현재 회차의 진행 중 시도 유무"에서 계산한다.

### 1-4. 응답별 처리 [제안]

| 결과 | 처리 |
| --- | --- |
| 200 | 시도 완료. 진행 수 +1, 회차 미루기 집계(2-3), 다음 카드 경계(2-1) |
| 네트워크 오류·시간 초과·5xx | **결과 미확정**. 카드 그대로, 버튼 잠금, "저장 여부를 확인하지 못했어요 · 다시 시도". 다시 시도는 같은 시도 객체. 자동 재시도는 짧은 지연 뒤 1회만 |
| 409 `card_version_conflict` | 다른 창·기기에서 먼저 평가·생성됐다. **자동 재평가하지 않는다.** 안내 뒤 큐 재조회 |
| 409 `request_id_conflict` | 클라이언트 결함. 회차를 멈추고 오류 표시 |
| 409 `card_paused`·`invalid_engine_state`·`review_history_unreadable`·`history_initialization_requires_approval`·`unsupported_config_version` | 지금 평가할 수 없는 카드. 안내 뒤 큐 재조회, 재시도 없음 |
| 409 `srs_mode_not_fsrs`(평가 중) | 계정 모드가 바뀌었다. 회차를 멈추고 모드 판별(4-1)부터 다시 |
| 404 | 카드·구독·권한이 사라졌다. 안내 뒤 큐 재조회 |
| 422 `review_upgrade_required` | 오래된 클라이언트. 회차를 멈추고 새로고침 안내 |
| 401 | 기존 인증 만료 경계 처리. 재시도 없음 |

### 1-5. 계정 전환·회차 교체·탭 이동·새로고침 [제안]

| 상황 | 처리 |
| --- | --- |
| 계정 전환 | 기존처럼 회차를 즉시 비운다. 시도는 버리고, **새 계정 토큰으로 재시도하지 않는다** |
| 같은 계정에서 모드·덱 변경, 계획 "바꾸기" | 활성 회차(1-6)면 기존 이어하기/바꾸기/취소 확인을 거친다. 시도가 **전송 중**이면 교체 버튼을 응답이나 시간 초과까지 막는다. **결과 미확정**이면 "저장 여부를 확인하지 못한 평가가 있어요"를 함께 알린다. 교체 뒤 늦은 응답은 1-3에 따라 무시한다 |
| 앱 안 탭 이동 | 회차는 메모리에 남는다(기존 동작). 시도도 그대로 진행한다 |
| 새로고침·창 닫기 | 회차와 시도는 메모리에만 있어 사라진다. **새 저장 키를 만들지 않는다.** 다시 열면 큐 첫 페이지를 서버에서 받는다 |

`beforeunload` [제안]: **전송 중이거나 결과 미확정인 시도가 있을 때만** 브라우저 기본 확인창을 요청한다. 그 밖에는 등록하지 않는다. 이 확인창은 사용자가 떠나기 전에 한 번 더 묻는 것일 뿐이다. 요청 전달이나 저장을 보장하지 않으며, 브라우저가 표시하지 않을 수도 있다. 문서와 화면에서 저장 보장 수단으로 설명하지 않는다.

시도를 저장소에 남겨 새로고침 뒤 자동 확인하는 방식은 저장 키 계약을 바꿔야 하므로 뺐다 [미정].

### 1-6. 활성 회차와 계획 실행기 [확정 유지 + 제안]

- 이어하기/바꾸기/취소, busy, 늦은 조회 무시, 계정 변경 stale 규칙은 그대로다 [확정].
- **활성 회차** [제안]: 회차를 시작한 뒤 "이번 회차 마치기"나 회차 요약에 이르기 전까지의 상태. 카드 표시 중, 시도 진행 중·결과 미확정, **대기 화면(2-4의 곧 돌아옴·미룬 카드만 남음)** 을 모두 포함한다.
- 활성 회차는 계획 실행기의 `inProgress=true`로 보고되며, 이어하기/바꾸기 확인 보호 대상이다. 회차 요약 화면과 회차 시작 전 화면만 비활성이다.
- FSRS 계정에서 `fetchQueue`는 `GET /study-queue`(덱 scope, `mode=new|today`, `plan_daily_new=Q`)를 부른다 [제안].

## 2. 동적 큐와 회차 미루기

### 2-1. 큐 흐름 [제안]

- 회차는 `GET /study-queue` **첫 페이지**(커서 없음, `limit` 10)로 시작한다.
- **다음 카드 경계**에서 첫 페이지를 다시 조회한다. 경계는 평가 성공, 409·404로 카드를 넘김, 대기 화면의 시각 도래, 대기 화면에서 앱 복귀다.
- 조회에는 이번 회차에서 미룬 카드 목록을 `exclude_card`로 함께 보낸다(2-3).
- 다음 카드는 응답의 첫 항목이다. 방금 평가한 카드가 다시 첫 항목이면(단계 시각이 이미 지남) 그대로 출제한다.
- 커서는 회차 진행에 쓰지 않는다. prefetch는 하지 않는다.
- 조회 실패 시 현재 상태를 유지하고 "다시 불러오기"를 제공한다. 실패를 "할 카드 없음"으로 바꾸지 않는다.

### 2-2. 타이머와 앱 복귀 [제안]

- 타이머는 사용자가 보고 있는 카드를 바꾸지 않는다. 질문·정답 화면에서는 타이머로 조회하지 않는다.
- 타이머는 대기 화면에서만 `next_due_at`에 맞춰 한 번 다시 조회한다. 바쁜 폴링은 없다. 시각 차이는 `server_now`로 보정한다.
- 앱 복귀(visible)는 대기·빈 화면일 때만 즉시 재조회한다.

### 2-3. 회차 미루기: 서버 예약을 바꾸지 않는 제외 [제안]

목적: 학습 단계에서 Again·Hard가 반복되는 카드(B-1 관찰)가 한 회차를 끝없이 붙잡지 않게 한다. 서버 예약·단계·로그는 바꾸지 않는다.

비교:

| 안 | 내용 | 문제 |
| --- | --- | --- |
| D1 클라이언트만 제외 | 첫 페이지 10개 중 미룬 카드를 화면에서 건너뜀 | 앞 10개가 모두 미뤄지면 뒤 카드를 받을 수 없다(LIMIT 뒤 제외) |
| D2 limit 키우기 | 페이지를 크게 받아 클라이언트에서 거름 | 상한이 없으면 같은 문제. 응답이 커짐 |
| D3 서버 회차 상태 저장 | 미룬 카드를 서버 테이블에 기록 | 조회 쓰기 0 계약 위반, 스키마 변경 |
| **D4 요청 제외 매개변수 (권장)** | 클라이언트가 이번 회차에 미룬 카드 키를 `exclude_card=personal:123&exclude_card=lexeme:45`로 보내면, 서버가 **출제 후보에서 LIMIT 전에** 뺀다 | 요청이 길어질 수 있음 → 최대 100개 |

D4 세부:
- 형식: `kind:id`(kind는 `personal`·`lexeme`, id는 양의 정수). 최대 100개, 중복은 하나로, 형식 오류나 초과는 400. 다른 계정·범위 밖 키는 조용히 무시한다(정보 노출 없음).
- 서버는 제외 키를 범주 분류 뒤, 정렬·LIMIT 전에 출제 후보(단기·장기 due, 신규)에서 뺀다. **범주 집계와 `total_in_scope`는 바꾸지 않는다.** 범주는 서버 상태이지 회차 상태가 아니기 때문이다. 제외로 빠진 출제 후보 수는 `counts.excluded_by_request`로 따로 준다.
- `next_due_at`은 제외되지 않은 카드만으로 계산하고, 제외된 카드의 가장 이른 시각은 `next_due_at_excluded`로 따로 준다.
- 신규 허용량 계산은 바꾸지 않는다. 제외는 신규 실적을 만들거나 줄이지 않는다.
- 커서를 쓰는 요청이면 정규화한 제외 목록이 커서 바인딩에 들어간다(바뀌면 409). 회차 진행은 커서를 쓰지 않으므로 보통은 해당하지 않는다.
- 조회 쓰기 0은 그대로다.

**미루기 기준**:
- 셈하는 사건: 이번 회차(같은 `sessionId`)에서 그 카드에 대해 **서버가 200으로 받은 평가** 가운데, 응답의 결과 단계가 Learning·Relearning인 것.
- 세지 않는 것: 재시도(같은 시도의 재전송), 409·404·네트워크 오류, 재렌더, 반복 조회, 대기 화면 체류, 다른 회차의 평가.
- 미룸: 그런 평가가 **3회**가 되면 그 카드를 이번 회차 제외 목록에 넣는다. 4번째 등장을 막는다 [제안 수치].
- 초기화: 새 `sessionId`가 생길 때(회차 시작·교체·초기화·계정 전환·새로고침)마다 집계와 제외 목록을 비운다. 서울 자정은 초기화 사유가 아니다.

### 2-4. 회차 화면 상태와 우선순위 [제안]

큐 응답(제외 매개변수 포함)과 회차 로컬 상태로 **주 상태 하나**를 고른다. 위에서부터 판정한다.

| 순위 | 주 상태 | 조건 | 문구(초안) | 조작 |
| --- | --- | --- | --- | --- |
| 1 | 오류 | 큐 조회 실패, 회차 정지 오류 | 오류 안내 | 다시 불러오기 |
| 2 | 카드 있음 | `items` ≥ 1 | 질문 화면 | 평가 |
| 3 | 곧 돌아옴 | 항목 0, `next_due_at`이 15분 이내 [제안 수치] | "다음 카드는 HH:MM에 돌아와요" | 기다리기 · 이번 회차 마치기 |
| 4 | 미룬 카드만 남음 | 항목 0, 3이 아님, `excluded_by_request` > 0 | "이번 회차에서 미룬 단어만 남았어요" | 이번 회차 마치기 · 새 회차로 다시 보기(새 sessionId) |
| 5 | 신규량 확인 불가 | 항목 0, `new_blocked_reason = review_time_unreadable` | "오늘 새 단어 수를 확인할 수 없어 새 단어는 멈췄어요" | 이번 회차 마치기 |
| 6 | 신규 목표 달성 | 항목 0, 신규 후보 > 0(`new_available` + C-2 이후 `new_unmaterialized`), `account_remaining == 0` 또는 `plan_remaining == 0` | "오늘 새 단어 목표 N개를 채웠어요" | 이번 회차 마치기(추가 학습 없음) |
| 7 | 지금 할 복습 끝 | 항목 0, 위 어느 것도 아님 | "지금 할 복습을 마쳤어요" + 다음 복습 시각(있으면) | 이번 회차 마치기 |

- 5·6이 7보다 먼저라서 "오늘 복습 끝"이 신규 목표 달성이나 확인 불가를 삼키지 않는다.
- 3이 4보다 먼저라서, 미룬 카드 말고도 곧 돌아올 카드가 있으면 기다릴 수 있다. 미룬 카드만 남았으면 무한 대기하지 않는다.
- 보조 줄: 주 상태와 별개로 신규 목표 줄(4-4)과 "일부 단어는 아직 새 복습 방식으로 옮겨지지 않았어요"(`not_converted`·`blocked_history`·`invalid_state`·`unsupported_config` > 0)를 붙인다.
- **"학습 완료"라는 말은 회차 화면 어디에도 쓰지 않는다.** 학습 완료는 진도 API의 지표이고 기준은 아직 재승인 전이다.
- 회차 요약: 이번 회차 평가 수(등급별), 이번 회차에서 처음 평가한 카드 수(로컬 집계, 서버 신규 수와 구분), 미룬 카드 수, 다음 복습 시각.

### 2-5. Again·Hard [제안]

- 엔진 규칙을 바꾸지 않는다. 단계를 임의로 올리지 않고, 카드를 즉시 다시 내지 않는다. Again·Hard 뒤 카드는 단계 시각까지 미래 대기다.
- 회차 미루기(2-3)가 반복 상한 역할을 한다.

## 3. 신규 카드 생성

### 3-1. FSRS 계정의 새 개인 카드 [제안]

대상: `srs_user_settings.srs_mode = 'fsrs'` 계정에서 **새로 만들어지는** 개인 카드.

| 경로 | 처리 |
| --- | --- |
| 단어 담기(`create_or_update_vocab_item`, 새 행 INSERT) | 아래 초기값 |
| 덱 패키지 가져오기(`import_deck_package`) | 아래 초기값 |
| 공유 덱 복사(`import_shared_deck`의 개인 카드 복사) | 아래 초기값 |
| 기존 카드 갱신(같은 단어 다시 담기 → UPDATE) | **SRS 열 무변경** |

초기값(같은 INSERT 트랜잭션에서 설정 행을 읽어 결정):

```text
srs_engine='fsrs', srs_config_version=<현재 설정>, srs_participation='active',
엔진 상태 열 전부 NULL, srs_effective_due_at=NULL,
srs_card_version=0, srs_history_quality='fresh', srs_history_flags=NULL,
completion_metric_version=NULL, first_completed_at=NULL
```

- 자기분류가 known이어도 참여는 active다(PRODUCT_SRS_DESIGN 2절) [제안].
- legacy·shadow 계정, 설정 행이 없는 계정은 지금처럼 legacy다 [확정 방향].
- 기존 legacy 카드와 불완전 이력 카드는 자동 전환하지 않는다. B-2 이전 도구로만 옮긴다 [확정].
- 개인 카드는 행이 있으므로 첫 평가는 일반 FSRS 평가(`expected_card_version: 0`)다.

### 3-2. progress가 없는 구독 단어: 요청 정체성과 원자적 생성 [제안]

**외부 요청 버전과 내부 CAS 버전을 분리한다.**

| 구분 | 값 | 의미 |
| --- | --- | --- |
| 외부 `expected_card_version` | **명시적 JSON `null`** | "이 계정에 이 단어의 progress 행이 없다고 보고 처음 평가한다" |
| 내부 CAS 버전 | `0` | 서버가 같은 트랜잭션에서 방금 만든 행에 대해서만 쓰는 값. 요청·영수증에 나타나지 않음 |
| 응답 `srs.card_version` | `1` | 평가 뒤 카드 버전 |

**누락과 명시적 null 구별**:
- 요청 JSON에 `expected_card_version` 키가 **있고 값이 null**일 때만 최초 평가 요청이다. 서버는 Pydantic `model_fields_set`으로 판별해 저장소 함수에 별도 표시(예: `FIRST_REVIEW`)로 넘긴다.
- 키가 **없으면** 지금과 같다. `request_id`도 없는 legacy 요청은 legacy 경로이고, `request_id`가 있으면 B-2 규칙대로 422 `review_upgrade_required`다(FSRS 카드인 경우). 누락을 null로 해석하지 않는다.
- 명시적 null은 **구독 URL에서만** 허용한다. 개인 URL에서 null이면 422.
- null + `request_id`·`session_id` 필수. 하나라도 없으면 422.

**서버 처리 순서**(한 트랜잭션, B-2 계정 잠금 그대로):

1. 계정 잠금(`begin_card_write`).
2. lexeme 존재 확인. 없으면 404.
3. **(순서 변경)** 최초 평가 요청이면 `get_or_create_progress`를 **부르지 않는다.** 지금 순서(progress를 먼저 legacy로 생성)는 최초 평가 요청에 쓰지 않는다. legacy 요청의 순서와 동작은 그대로다.
4. 활성 구독 + 덱 멤버십 확인(`require_subscription`). 실패하면 404, 쓰기 0.
5. 같은 계정 `request_id` 영수증 확인. 요청 해시는 **원래 외부 payload**(`expected_card_version: null` 포함)로 계산한다.
   - 같은 payload: 처음 저장한 응답을 그대로 반환. 그 사이 행이 생기고 버전이 바뀌었어도 마찬가지다.
   - 같은 request_id에 다른 payload(예: null 대신 0, 등급 변경): 409 `request_id_conflict`, 쓰기 0.
6. 계정 모드 확인. FSRS가 아니면 409 `srs_mode_not_fsrs`, 쓰기 0.
7. progress 행 확인.
   - 없음: 3-1 초기값으로 INSERT(`status='unclassified'`, 자동 분류 없음, `srs_card_version=0`). 이어서 B-2 FSRS 평가를 내부 CAS 0으로 수행한다.
   - 있음(다른 창이 먼저 만들었거나 legacy 행이 있음): 409 `card_version_conflict`, 쓰기 0. 자동 재평가하지 않는다.
8. progress 생성, 카드 갱신, 로그 1행(첫 평가 표시), 완료 증거, 영수증(원래 payload 해시와 응답)을 한 번에 커밋한다. 어느 단계든 실패하면 생성한 행까지 모두 롤백한다.

**재시도·동시성**:
- 같은 요청 재시도는 5단계에서 처음 응답이다. 행·로그·영수증·신규 수가 늘지 않는다.
- 두 창의 동시 최초 평가(다른 request_id)는 계정 잠금으로 직렬화된다. 먼저 온 쪽이 생성·평가하고, 나중 쪽은 7단계에서 409다.
- `UNIQUE(user_id, lexeme_id)`가 마지막 방어선이다.
- PostgreSQL 실행은 미검증으로 남는다.

**큐 표현과 출제 시점**:
- 생성 경로(3-2 서버)가 구현·검증되기 전에는 progress 없는 단어를 출제하지 않는다(C-1 동작 유지) [확정].
- 준비된 뒤: `card_version: null`, `materialized: false`, `bucket: "new"`, `review.path`는 같은 구독 URL. 클라이언트는 이 항목을 평가할 때 `expected_card_version: null`을 보낸다.
- `new_available`(생성된 카드)과 `new_unmaterialized`(progress 없음)는 계속 서로 겹치지 않는 별도 범주로 센다. 준비 뒤 두 범주가 모두 신규 버킷 후보이며, 신규 허용량은 두 수의 합 기준이다.

## 4. 모드와 화면 연결

### 4-1. 모드 판별 [제안]

- 계정 epoch마다 한 번 `GET /study-queue?limit=1`을 호출한다.
- **409 `srs_mode_not_fsrs`일 때만** legacy 화면 경로로 간다.
- 200이면 FSRS 경로다.
- 그 밖의 응답(401, 404, 400, 5xx, 네트워크 오류)은 **오류**로 표시하고 legacy로 전환하지 않는다. 다시 시도를 제공한다.
- 판별 전에는 복습 시작 버튼을 "확인 중"으로 둔다.

### 4-2. 연습 모드 [확정 방향: 승인 7] / 화면 [제안]

- FSRS 계정의 `unknown`·`uncertain`·`all`은 `mode=practice`. 평가 POST를 보내지 않는다. SRS 예약·로그·영수증·신규 실적이 바뀌지 않는다.
- 화면: 같은 책 지면에서 정답 뒤 버튼을 "다시 볼게요 / 알겠어요"로 바꾸고, "연습 · 예약에 반영되지 않아요"를 표시한다.
- legacy 계정의 세 모드는 지금 그대로다.

### 4-3. recent [제안: 승인 전, v0.1의 R3 권장 철회]

recent의 의도는 "방금 담은 특정 개인 단어 id 묶음"이다(읽기 저장 v3에 보관, 그대로 유지).

| 안 | 내용 | 판단 |
| --- | --- | --- |
| R1 연습만 | 묶음 전체를 연습 | 미평가 카드의 첫 인출이 기록되지 않음 |
| **R2 실제 학습, 목표 적용 (권장, 승인 전)** | 묶음 안에서 아래 규칙 | 목표 계약과 일치 |
| R3 목표 미적용 | 묶음의 미평가를 목표와 무관하게 출제 | 목표 우회. **승인된 계약 아님.** 필요하면 별도 정책 승인 |

R2 세부:
- 서버 큐에 `mode=selected&card_id=…`(개인 카드 id만, 최대 200개)를 추가한다. 묶음 밖 카드는 나오지 않는다. 범위·권한·범주 판정은 C-1과 같다.
- 묶음 안 **due 카드**(단기·장기): 실제 복습으로 출제한다. 신규 목표와 무관하다.
- 묶음 안 **미평가 카드**: 실제 첫 학습. **하루 신규 목표 잔여량 안에서만** 출제한다. 목표에 닿았거나 신규 수가 확인 불가면 신규 출제를 멈추고 2-4 상태 5·6을 보여 준다.
- 묶음 안 **미래 예약 카드**(아직 due 아님): 출제하지 않는다. 사용자가 고르면 같은 묶음을 연습(`mode=practice`와 같은 규칙)으로 볼 수 있다 [제안: "남은 단어 연습하기" 보조 조작]. 연습은 평가 POST를 보내지 않는다.
- **이미 받은 카드의 평가**: 화면에 출제된 신규 카드는, 평가하기 전에 목표가 채워졌어도(다른 창 등) 평가를 허용한다(C-1 계약: 이미 받은 카드는 거부하지 않음).
- 묶음의 legacy·불완전·보류 카드는 출제하지 않고 C-1 범주로 센다. 보조 줄로 안내한다.
- 목표 우회(방금 담은 단어는 목표와 무관하게 학습)는 별도 정책 승인 항목이다 [미정].

### 4-4. 신규 수 표시 [확정: C-1 7절]

- `introduced_today: null` + `status: "unknown"`이면 "오늘 새 단어: 확인할 수 없음 (적어도 N개)". **0으로 표시하지 않는다.**
- `account_remaining`·`plan_remaining`이 null이면 남은 수를 숨기고 확인 불가 문구를 쓴다.
- 신규 목표는 "목표"로 표기하고 "상한"이라 하지 않는다.

### 4-5. 화면 변경 범위 [제안]

- 기존 복습 책 지면·에셋·레이아웃을 유지한다. 새 목업·에셋을 만들지 않는다.
- 추가: 결과 미확정 표시와 다시 시도, 충돌 안내, 대기·미룸 화면 상태, 신규 목표 줄, 연습 표시. 기존 메시지 영역과 완료 영역을 재사용한다.
- 읽기 저장 v3 키, 학습 계획 로컬 저장 키는 바꾸지 않는다.

## 5. 구현 단계 [제안]

| 단계 | 내용 | 검증 | 다음 단계 조건 |
| --- | --- | --- | --- |
| C-2a 서버 | 3-1 새 개인 카드 초기값, 3-2 구독 최초 평가(요청 정체성·원자적 생성), 큐 `exclude_card`(2-3), 생성 경로 준비 뒤 큐의 미생성 카드 출제, (R2 승인 시) `mode=selected` | 서버 단위·트랜잭션·동시성·API(SQLite) | 서버 검사 통과와 사용자 검토 |
| C-2b 클라이언트 순수 | 시도 고정·결과 적용·응답별 전이, 회차 미루기 집계, 화면 상태 우선순위 모듈 | node 단위 검사 | 통과 |
| C-2c 클라이언트 연결 | 모드 판별, 동적 큐 회차, 평가 시도, 대기·미룸, 연습, 계획 실행기, (승인 시) recent R2 | 실제 브라우저(세션 전용 SQLite, 합성 계정), 지연·유실 주입 | 통과와 사용자 검토 |

C-2a는 클라이언트 없이 단독으로 검증하고 보고한다. 클라이언트는 서버 계약이 확인된 뒤에 연결한다.

## 6. C-2에서 구현하지 않는 것

- 불완전 이력 초기화, PostgreSQL 로그 보존·실행 검증, 학습 완료 기준, 추가 신규량·목표 우회, 설정·목표 변경 API, 보류·재참여 API, 기본 FSRS 활성화, 실제 사용자 이전.
- 시도를 저장소에 남겨 새로고침 뒤 자동 확인하는 기능.

## 7. 승인이 필요한 결정

1. 평가 시도 고정·결과 적용 4조건·응답별 처리, 자동 재시도 1회(1-2~1-4).
2. 새로고침 정책(새 저장 키 없음)과 `beforeunload`를 전송 중·결과 미확정일 때만 쓰는 것(1-5).
3. 활성 회차 정의(대기 화면 포함)와 계획 실행기 보호(1-6).
4. 동적 큐: 경계마다 첫 페이지 재조회, 커서·prefetch 미사용, 타이머는 대기 화면 전용(2-1·2-2).
5. 회차 미루기 D4: `exclude_card`(최대 100, LIMIT 전 적용, 범주 집계 불변, `excluded_by_request`·`next_due_at_excluded` 추가), 셈 기준(200 응답 중 결과 단계가 Learning·Relearning인 평가) 3회, 새 sessionId마다 초기화(2-3).
6. 회차 화면 주 상태 우선순위와 "곧 돌아옴" 15분 기준(2-4).
7. FSRS 계정의 새 개인 카드 초기값, known도 active(3-1).
8. 구독 최초 평가: 명시적 null만 최초 평가로 인정, 내부 CAS 0과 분리, 원래 payload로 영수증 해시, progress 생성 전 구독·영수증 확인, 같은 트랜잭션 생성(3-2).
9. 모드 판별: 409 `srs_mode_not_fsrs`만 legacy 전환, 그 밖은 오류(4-1). 연습 화면 버튼(4-2).
10. recent R2(지정 묶음, 목표 적용, due 복습, 미래 예약은 연습 선택, 이미 받은 카드 평가 허용)와 `mode=selected` 추가(4-3).
11. 구현 단계 C-2a → C-2b → C-2c와 단계별 검토(5).

## 9. C-2a 구현에서 확정한 세부 (2026-10-10, 승인 11개 채택 뒤)

7절 11개 항목이 채택됐다(recent R2, 회차 미루기 D4). 아래는 C-2a 서버 구현 중 계약 안에서 정한 세부와, 요청받은 보충이다.

### 9-1. `exclude_card` 100개 한도와 중단 계약 (2-3 보충)

- 서버: 서로 다른 키가 100개를 넘으면 **400 `too_many_excluded_cards`**다. 중복 키는 하나로 센다. 원문 값이 200개를 넘어도 같은 오류다. 서버는 목록을 자르거나 일부만 적용하지 않는다.
- 클라이언트(C-2b·C-2c에서 구현):
  - 회차 제외 목록이 이미 100개인데 101번째 카드를 미뤄야 하면, **기존 항목을 버리지 않는다.** 오래된 항목을 빼고 새 항목을 넣는 방식도 금지다.
  - 대신 회차를 정지하고 주 상태 **"이번 회차에서 미룬 단어가 많아 여기서 회차를 마칠게요"**를 보여 준다. 우선순위는 2-4의 4번(미룬 카드만 남음)과 같은 자리다.
  - 조작은 [이번 회차 마치기] [새 회차로 다시 보기]다. 새 회차는 새 `sessionId`이므로 제외 목록이 비고 처음부터 시작한다.
  - 정지 중에는 큐를 다시 조회하지 않는다. 400을 받는 상황 자체를 만들지 않는다.
  - 서버에서 400 `too_many_excluded_cards`를 받으면 같은 정지 상태로 간다(방어용).
- 회차당 미루기 3회 기준이라 보통은 닿지 않는 한도다.

### 9-2. `exclude_card` 구현 세부

- 적용 위치: 범위·권한·멤버십 → 범주 분류 뒤, 정렬·LIMIT·신규 분량 적용 전. 연습 모드 목록에도 같은 제외를 적용한다.
- `excluded_by_request`: 범위 안이면서 제외 키와 맞는 카드 중, 범주가 단기 due·장기 due·미래 대기·신규(생성·미생성)인 카드 수. 보류·미전환·손상 카드는 원래 출제 대상이 아니므로 세지 않는다.
- `next_due_at`은 제외되지 않은 미래 대기 카드 기준이다. `next_due_at_excluded`는 제외된 미래 대기 카드 중 가장 이른 시각이다.
- 범주 집계, `total_in_scope`, `new_allowed_now`, `new_goal`은 제외 여부와 무관하다.
- 커서 바인딩: 정규화한 제외 목록과 selected 목록의 해시(`filters_hash`)를 넣는다. 바뀌면 409다.

### 9-3. `mode=selected` 구현 세부 (4-3 R2)

- `card_id`(반복, 서로 다른 값 최대 200, 1 이상 정수). `scope=all`만 허용한다. `status`·`plan_daily_new`와는 함께 쓸 수 없다. `card_id`를 다른 모드에서 쓰면 400이다.
- 대상은 이 계정의 개인 카드 중 지정한 id뿐이다. 구독 카드, 다른 계정 id, 없는 id는 조용히 무시한다. 범주 집계와 `total_in_scope`도 이 묶음 기준이다.
- 출제 규칙:
  - 단기·장기 due는 정상 출제한다.
  - 미평가 카드는 계정 신규 목표 잔여 안에서만 낸다.
  - 신규 수가 확인 불가면 신규 0이다.
  - 미래 대기는 출제하지 않는다(`pending_later`로만 셈).
- 미래 예약 카드를 연습으로 보는 화면·요청은 C-2c 범위다.
- 이미 받은 카드의 평가는 B-2 평가 경로가 목표를 보지 않으므로 그대로 허용된다(검사로 확인).

### 9-4. 구독 최초 평가 구현 세부 (3-2)

- 판별: 구독 평가 라우트에서 `"expected_card_version" in body.model_fields_set and value is None`일 때만 최초 평가다. 개인 라우트의 명시적 null은 422 `null_card_version_not_allowed`다.
- 저장소 `record_lexeme_review(first_review=True)`는 계정 잠금과 lexeme 확인 뒤, **legacy 지연 생성(`get_or_create_progress`)을 거치지 않고** `reviews.record_first_lexeme_review`로 간다.
- 그 뒤 순서는 평가 등급 → 현재 구독·멤버십(404) → id 형식(422) → 영수증(원래 null payload 해시) → 계정 모드(409 `srs_mode_not_fsrs`) → 행 존재(409 `card_version_conflict`) → 새 FSRS progress INSERT → B-2 FSRS 평가(내부 CAS 0, 영수증 해시는 null)다.
- 이 lexeme에 progress 없이 로그만 남아 있으면 B-2 규칙대로 409 `history_initialization_requires_approval`이고, 생성한 행도 롤백된다.
- 큐는 이 경로가 있는 상태에서만 미생성 단어를 신규로 낸다(`queue.SERVE_UNMATERIALIZED`). 이력(로그)이 있거나 정렬 시각이 정규 형식이 아닌 미생성 단어는 출제하지 않고 `new_unmaterialized`로만 센다.
